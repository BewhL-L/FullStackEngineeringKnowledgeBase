# 微服务核心组件知识点系统梳理（优化版）

> **文档说明**：系统梳理微服务架构核心组件，涵盖注册中心、配置中心、网关、负载均衡、熔断限流、链路追踪等内容。

---

## 1. 概述

微服务架构将单体应用拆分为多个独立部署的小服务，每个服务围绕特定业务能力构建。微服务核心组件解决服务间的注册发现、配置管理、路由转发、容错保护等问题。

**微服务核心组件全景**：

| 组件 | 作用 | 主流实现 |
|------|------|----------|
| 注册中心 | 服务注册与发现 | Nacos、Eureka、Consul、Zookeeper |
| 配置中心 | 集中管理配置 | Nacos、Apollo、Spring Cloud Config |
| 网关 | 统一入口、路由、鉴权 | Spring Cloud Gateway、Zuul |
| 负载均衡 | 客户端负载 | Spring Cloud LoadBalancer、Ribbon |
| 熔断降级 | 容错保护 | Sentinel、Resilience4j、Hystrix |
| 链路追踪 | 分布式追踪 | SkyWalking、Zipkin、Jaeger |
| 远程调用 | 服务间通信 | OpenFeign、Dubbo、gRPC |

## 2. 注册中心

### 2.1 Nacos（推荐）

**核心功能**：服务注册发现 + 动态配置管理

```yaml
# 服务端配置
spring:
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        namespace: dev
        group: DEFAULT_GROUP
```

**核心概念**：
- **Namespace**：命名空间，隔离环境（dev/test/prod）
- **Group**：分组，隔离不同业务
- **Service**：服务名
- **Cluster**：集群，同一服务的不同集群

### 2.2 服务注册发现原理

1. 服务启动时向注册中心注册自己的地址
2. 注册中心维护服务注册表（服务名 → 实例列表）
3. 消费者从注册中心获取服务实例列表
4. 消费者本地缓存实例列表，定期拉取更新
5. 服务实例通过心跳续约，宕机则被剔除

> 🔍 **知识点深度解析**
>
> **作用**：注册中心是微服务的通讯录，解决服务间地址动态变化的问题。
>
> **原理**：服务提供者启动时向注册中心注册（IP、端口、服务名），并定期发送心跳（默认 5s）续约。注册中心检测到心跳超时（默认 15s 未收到）将实例标记为不健康，超过 30s 剔除。消费者启动时订阅服务，获取实例列表并缓存到本地，注册中心变更时通过推送（Nacos 长轮询）或拉取更新消费者缓存。Nacos 支持 AP（可用性优先）和 CP（一致性优先）模式切换，默认 AP。
>
> **用法要点**：① Nacos 同时支持注册中心和配置中心，减少组件数量；② 用 namespace 隔离环境，group 隔离业务；③ 服务下线要优雅停机（发送注销请求），避免消费者调用已下线实例；④ 面试常考：注册中心原理、Nacos vs Eureka、AP vs CP、心跳机制。

### 2.3 主流注册中心对比

| 特性 | Nacos | Eureka | Consul | Zookeeper |
|------|-------|--------|--------|-----------|
| CAP | AP/CP | AP | CP | CP |
| 健康检查 | 心跳/TCP/HTTP | 心跳 | TCP/HTTP/脚本 | Session |
| 配置管理 | 支持 | 不支持 | 支持（KV） | 支持 |
| 多数据中心 | 支持 | 不支持 | 支持 | 不支持 |
| 社区活跃度 | 高（阿里） | 低（停更） | 中 | 中 |

## 3. 配置中心

### 3.1 Nacos Config

```yaml
# bootstrap.yml（优先级高于 application.yml）
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        file-extension: yaml
        namespace: dev
        group: DEFAULT_GROUP
        shared-configs: # 共享配置
          - data-id: common.yaml
            refresh: true
```

**配置加载顺序**：`${spring.application.name}-${profile}.${file-extension}` → `${spring.application.name}.${file-extension}` → 共享配置

### 3.2 动态刷新

- `@RefreshScope`：标注的 Bean 在配置变更时自动刷新
- Nacos 通过长轮询推送配置变更，客户端收到后刷新上下文

> 🔍 **知识点深度解析**
>
> **作用**：配置中心集中管理各环境配置，支持动态刷新，不需要重启服务。
>
> **原理**：配置存储在 Nacos 服务端，客户端启动时根据 dataId（服务名+环境+后缀）拉取配置。动态刷新通过长轮询实现：客户端发起请求，服务端如果配置没变则 hold 住请求（默认 30s），有变更则立即返回变更内容；客户端收到后刷新 Spring 环境，@RefreshScope 标注的 Bean 会被销毁重建，使用新配置。
>
> **用法要点**：① 配置放 bootstrap.yml（比 application.yml 先加载）；② 需要动态刷新的 Bean 加 @RefreshScope；③ 敏感配置（密码）用加密或环境变量；④ 配置版本管理，支持回滚；⑤ 面试常考：配置中心原理、动态刷新实现、bootstrap 与 application 区别。

## 4. 网关

### 4.1 Spring Cloud Gateway

**核心概念**：
- **Route**：路由，由 ID、目标 URI、断言、过滤器组成
- **Predicate**：断言，匹配请求条件（路径、方法、Header 等）
- **Filter**：过滤器，修改请求/响应（鉴权、限流、日志）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service  # lb:// 表示负载均衡
          predicates:
            - Path=/api/order/**
          filters:
            - StripPrefix=1  # 去掉 /api 前缀
            - name: RequestRateLimiter  # 限流
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20
```

### 4.2 全局过滤器（鉴权示例）

```java
@Component
public class AuthFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (token == null) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        return chain.filter(exchange);
    }
    @Override
    public int getOrder() { return -100; } // 优先级，越小越先执行
}
```

> 🔍 **知识点深度解析**
>
> **作用**：网关是微服务统一入口，负责路由转发、鉴权、限流、日志、跨域等。
>
> **原理**：Gateway 基于 WebFlux（响应式编程），请求进入后通过断言链匹配路由，匹配成功后经过过滤器链处理，再转发到目标服务。过滤器分为 Pre（请求前）和 Post（响应后），GlobalFilter 全局生效，GatewayFilter 只对特定路由生效。`lb://service-name` 结合 LoadBalancer 实现客户端负载均衡。Gateway 是 Netty 异步非阻塞模型，性能比 Zuul 1.x（同步阻塞）好很多。
>
> **用法要点**：① 网关做统一鉴权，服务间调用可内网免鉴权；② 限流用 Redis + Lua 脚本实现（令牌桶/漏桶）；③ 跨域在网关层统一配置；④ 面试常考：Gateway 工作原理、断言/过滤器、与 Zuul 区别、鉴权实现。

## 5. 负载均衡

### 5.1 Spring Cloud LoadBalancer

```java
@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// 调用时用服务名代替 IP:Port
restTemplate.getForObject("http://order-service/api/orders", List.class);
```

### 5.2 负载均衡策略

- **轮询（RoundRobin）**：默认，依次分配
- **随机（Random）**：随机选择
- **权重（Weighted）**：按权重分配
- **一致性哈希**：相同参数路由到同一实例

## 6. 熔断限流

### 6.1 Sentinel

**核心功能**：流量控制、熔断降级、系统负载保护

```java
// 定义资源
@SentinelResource(value = "getOrder", fallback = "getOrderFallback")
public Order getOrder(Long id) {
    return orderMapper.selectById(id);
}

public Order getOrderFallback(Long id, Throwable e) {
    return new Order(); // 降级返回
}
```

**熔断策略**：
- **慢调用比例**：响应时间超过阈值的比例达到阈值则熔断
- **异常比例**：异常比例达到阈值则熔断
- **异常数**：异常数达到阈值则熔断

### 6.2 限流算法

| 算法 | 原理 | 优缺点 |
|------|------|--------|
| 计数器 | 固定时间窗口计数 | 简单，但有临界突发问题 |
| 滑动窗口 | 细分窗口滑动统计 | 平滑，实现稍复杂 |
| 漏桶 | 固定速率流出 | 平滑，无法应对突发 |
| 令牌桶 | 固定速率生成令牌 | 允许突发，最常用 |

> 🔍 **知识点深度解析**
>
> **作用**：熔断限流保护系统不被流量冲垮，是微服务高可用的关键。
>
> **原理**：熔断器模式（Circuit Breaker）有三种状态：Closed（关闭，正常调用）→ Open（打开，直接降级，不调用下游）→ Half-Open（半开，放行少量请求探测）。当下游错误率/慢调用比例达到阈值，熔断器从 Closed 变为 Open，经过冷却时间后进入 Half-Open，探测成功则 Closed，失败则继续 Open。限流通过限制单位时间请求数保护系统，令牌桶算法最常用（固定速率生成令牌，请求取令牌，取不到则拒绝，桶容量允许突发）。
>
> **用法要点**：① 熔断在调用方配置（保护自己不被下游拖垮）；② 降级返回要合理（默认值、缓存、友好提示）；③ 限流在网关或服务层配置；④ Sentinel 支持控制台动态配置规则；⑤ 面试常考：熔断器状态机、限流算法、Sentinel vs Hystrix、降级策略。

## 7. 链路追踪

### 7.1 核心概念

- **Trace**：一次请求的完整链路，唯一 TraceID
- **Span**：链路中的一个操作（一次 RPC 调用），有 SpanID 和 ParentSpanID
- **Annotation**：事件标注（cs/cr/ss/sr）

### 7.2 SkyWalking

- Java Agent 无侵入埋点
- 支持分布式追踪、服务拓扑、性能分析
- 自动上报 Trace 数据到 OAP 服务端

### 7.3 TraceID 传递

- HTTP：通过 Header 传递（`traceparent`、`sw8`）
- MQ：通过消息属性传递
- 线程池：需手动传递（TransmittableThreadLocal）

> 🔍 **知识点深度解析**
>
> **作用**：链路追踪定位微服务中的性能瓶颈和错误，是排查分布式问题的必备工具。
>
> **原理**：请求进入网关时生成唯一 TraceID，每次服务间调用生成新的 SpanID，通过 Header（HTTP）或消息属性（MQ）传递 TraceID 和 ParentSpanID。各服务将 Span 数据上报到追踪系统，追踪系统根据 TraceID 聚合成完整调用链。SkyWalking 用 Java Agent（字节码增强）在类加载时插入追踪代码，对业务无侵入。OpenTelemetry 是 CNCF 的统一标准，正在成为行业规范。
>
> **用法要点**：① TraceID 要打印到日志中，便于关联；② 异步调用（线程池）需手动传递上下文（TTL）；③ 采样率配置（全量采样影响性能，生产用比例采样）；④ 面试常考：Trace/Span 概念、链路追踪原理、SkyWalking 实现、TraceID 传递。

## 8. 远程调用

### 8.1 OpenFeign

```java
@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {
    @GetMapping("/api/users/{id}")
    User getUser(@PathVariable("id") Long id);
    
    @PostMapping("/api/users")
    void createUser(@RequestBody UserCreateRequest request);
}
```

**特点**：
- 声明式 HTTP 客户端，像调用本地方法一样调用远程服务
- 集成 Ribbon/LoadBalancer 负载均衡
- 支持 Sentinel 熔断降级

### 8.2 Dubbo

- 高性能 RPC 框架，基于 TCP 协议（Hessian2 序列化）
- 面向接口代理，服务治理能力强
- 适合内部服务间高性能调用

## 📝 精简总结

- 注册中心：Nacos 推荐，服务注册发现，心跳续约
- 配置中心：Nacos Config，集中管理，动态刷新（@RefreshScope）
- 网关：Spring Cloud Gateway，统一入口，路由+鉴权+限流
- 负载均衡：LoadBalancer，客户端负载，轮询/随机
- 熔断限流：Sentinel，熔断器三状态，令牌桶限流
- 链路追踪：SkyWalking，TraceID 串联全链路，无侵入埋点
- 远程调用：OpenFeign 声明式，Dubbo 高性能 RPC
