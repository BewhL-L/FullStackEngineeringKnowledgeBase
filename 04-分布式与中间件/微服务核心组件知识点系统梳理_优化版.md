# 微服务核心组件知识点系统梳理（优化版）

> **文档说明**：系统梳理微服务架构核心组件，涵盖注册中心、配置中心、网关、负载均衡、熔断限流、链路追踪等内容。

---

## 1. 概述

微服务架构将单体应用拆分为多个独立部署的小服务，每个服务围绕特定业务能力构建。微服务核心组件解决服务间的注册发现、配置管理、路由转发、容错保护等问题。

**微服务核心组件全景**：

| 组件 | 作用 | 主流实现 |
|------|------|----------|
| 注册中心 | 服务注册与发现 | Nacos、Eureka、Consul、Zookeeper |
| 配置中心 | 集中管理配置 | Nacos、Apollo、Spring Cloud Config |
| 网关 | 统一入口、路由、鉴权 | Spring Cloud Gateway、Zuul |
| 负载均衡 | 客户端负载 | Spring Cloud LoadBalancer、Ribbon |
| 熔断降级 | 容错保护 | Sentinel、Resilience4j、Hystrix |
| 链路追踪 | 分布式追踪 | SkyWalking、Zipkin、Jaeger |
| 远程调用 | 服务间通信 | OpenFeign、Dubbo、gRPC |

## 2. 注册中心

### 2.1 Nacos（推荐）

**核心功能**：服务注册发现 + 动态配置管理

```yaml

> 🔍 **知识点深度解析**
>
> **作用**：Nacos 是 Spring Cloud Alibaba 首选注册中心，同时支持服务发现和配置管理，兼容 AP/CP。
>
> **原理**：服务注册：微服务启动时 Nacos Client 注册实例（IP/端口/元数据），心跳 5s 续约，15s 不健康 30s 摘除。临时实例用 Distro（AP），持久实例用 Raft（CP）。消费者本地缓存服务列表，10s 轮询更新。Spring Cloud LoadBalancer 做客户端负载均衡。相比 Eureka，Nacos 支持配置中心、更活跃的社区和 K8s 集成。
>
> **用法要点**：① spring-cloud-starter-alibaba-nacos-discovery 引入  ② 临时实例 AP（Distro），持久实例 CP（Raft）  ③ 心跳续约+本地缓存，Nacos 宕机仍可消费  ④ Nacos 同时是配置中心，一组件两用  ⑤ 面试常考：Nacos vs Eureka、AP/CP、心跳机制

# 服务端配置
spring:
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        namespace: dev
        group: DEFAULT_GROUP
```

**核心概念**：
- **Namespace**：命名空间，隔离环境（dev/test/prod）
- **Group**：分组，隔离不同业务
- **Service**：服务名
- **Cluster**：集群，同一服务的不同集群

> 🔍 **知识点深度解析**
>
> **作用**：Nacos 是集注册中心 + 配置中心于一体的中间件，降低微服务组件数量，是 Spring Cloud Alibaba 生态的默认选型。
>
> **原理**：Nacos Server 同时提供注册发现（服务实例注册到注册表）和配置管理（配置存于服务端内部存储，支持 MySQL 持久化）。逻辑隔离用三层模型：Namespace（环境隔离，如 dev / test / prod）→ Group（业务分组）→ Service / DataId（具体服务或配置）。客户端通过 SDK 注册、订阅、拉取配置。
>
> **用法要点**：① 用 namespace 隔离环境、group 隔离业务线；② 注册发现 server-addr 指向 Nacos 集群（逗号分隔多节点）；③ 配置优先级：指定 profile 的 > 默认 service 的 > 共享配置；④ Nacos 支持 AP / CP 切换（默认 AP，注册中心常用）；⑤ 生产用 Nacos 集群部署 + MySQL 持久化；⑥ 相比 Eureka（已停更）和 Apollo（仅配置），Nacos 一体化更省心。

### 2.2 服务注册发现原理

1. 服务启动时向注册中心注册自己的地址
2. 注册中心维护服务注册表（服务名 → 实例列表）
3. 消费者从注册中心获取服务实例列表
4. 消费者本地缓存实例列表，定期拉取更新
5. 服务实例通过心跳续约，宕机则被剔除

> 🔍 **知识点深度解析**
>
> **作用**：注册中心是微服务的通讯录，解决服务间地址动态变化的问题。
>
> **原理**：服务提供者启动时向注册中心注册（IP、端口、服务名），并定期发送心跳（默认 5s）续约。注册中心检测到心跳超时（默认 15s 未收到）将实例标记为不健康，超过 30s 剔除。消费者启动时订阅服务，获取实例列表并缓存到本地，注册中心变更时通过推送（Nacos 长轮询）或拉取更新消费者缓存。Nacos 支持 AP（可用性优先）和 CP（一致性优先）模式切换，默认 AP。
>
> **用法要点**：① Nacos 同时支持注册中心和配置中心，减少组件数量；② 用 namespace 隔离环境，group 隔离业务；③ 服务下线要优雅停机（发送注销请求），避免消费者调用已下线实例；④ 面试常考：注册中心原理、Nacos vs Eureka、AP vs CP、心跳机制。

### 2.3 主流注册中心对比

| 特性 | Nacos | Eureka | Consul | Zookeeper |
|------|-------|--------|--------|-----------|
| CAP | AP/CP | AP | CP | CP |
| 健康检查 | 心跳/TCP/HTTP | 心跳 | TCP/HTTP/脚本 | Session |
| 配置管理 | 支持 | 不支持 | 支持（KV） | 支持 |
| 多数据中心 | 支持 | 不支持 | 支持 | 不支持 |
| 社区活跃度 | 高（阿里） | 低（停更） | 中 | 中 |

> 🔍 **知识点深度解析**
>
> **作用**：对比主流注册中心差异，帮助按一致性要求、功能需求做技术选型，避免"拍脑袋"选组件。
>
> **原理**：注册中心差异主要在 CAP 取向与功能边界：Nacos 支持 AP / CP 双模式且自带配置中心；Eureka 纯 AP、心跳续约、已停更；Consul 基于 Raft 的 CP、KV 可做配置；ZooKeeper 基于 ZAB 的 CP、用临时节点做注册。AP 模型可用性高、最终一致；CP 模型强一致但分区时可能不可用。
>
> **用法要点**：① 一致性要求高（CP）选 Consul / ZK；② 可用性优先（AP）选 Nacos / Eureka；③ 需要配置中心选 Nacos / Apollo / Consul；④ 多数据中心选 Nacos / Consul；⑤ Eureka 已停更，新项目不推荐；⑥ 面试常考：CAP 取舍、Nacos vs Eureka、AP vs CP 的场景含义。

## 3. 配置中心

### 3.1 Nacos Config

```yaml

> 🔍 **知识点深度解析**
>
> **作用**：Nacos Config 提供分布式配置管理，支持配置热更新、环境隔离和灰度发布。
>
> **原理**：bootstrap.yml 配置 Nacos 地址和 namespace/group/dataId。应用启动时从 Nacos 拉取配置，长轮询监听变更（默认 30s），配置变更后推送通知。@RefreshScope 标注的 Bean 在配置变更时自动刷新。多环境用 namespace 隔离（dev/prod），group 区分项目，dataId 对应应用名+profile+扩展名。
>
> **用法要点**：① spring-cloud-starter-alibaba-nacos-config 引入  ② bootstrap.yml 配置 server-addr/namespace/group/file-extension  ③ @RefreshScope + @Value 实现配置热更新  ④ 长轮询（Long Polling）30s 监听变更，近实时推送  ⑤ 面试常考：配置热更新原理、namespace/group/dataId、长轮询

# bootstrap.yml（优先级高于 application.yml）
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: localhost:8848
        file-extension: yaml
        namespace: dev
        group: DEFAULT_GROUP
        shared-configs: # 共享配置
          - data-id: common.yaml
            refresh: true
```

**配置加载顺序**：`${spring.application.name}-${profile}.${file-extension}` → `${spring.application.name}.${file-extension}` → 共享配置

> 🔍 **知识点深度解析**
>
> **作用**：Nacos Config 集中管理各环境配置，支持动态变更，避免配置散落各服务、改配置必须重启的问题。
>
> **原理**：客户端启动时读 bootstrap.yml（优先级高于 application.yml），根据 `${spring.application.name}-${profile}.${file-extension}` 拼接 dataId 向 Nacos 服务端拉取配置。shared-configs 配置共享配置（如 common.yaml，多服务共用）。配置变更通过长轮询推送到客户端并刷新。
>
> **用法要点**：① 连接信息放 bootstrap.yml（最先加载，先于 application.yml）；② file-extension 决定格式（yaml / properties），dataId 必须匹配；③ 共享配置 refresh=true 才能动态刷新；④ 配置热更新依赖 @RefreshScope（见 3.2）；⑤ 敏感配置用 Nacos 加密插件或环境变量；⑥ 配置要纳入版本管理、支持回滚。

### 3.2 动态刷新

- `@RefreshScope`：标注的 Bean 在配置变更时自动刷新
- Nacos 通过长轮询推送配置变更，客户端收到后刷新上下文

> 🔍 **知识点深度解析**
>
> **作用**：配置中心集中管理各环境配置，支持动态刷新，不需要重启服务。
>
> **原理**：配置存储在 Nacos 服务端，客户端启动时根据 dataId（服务名+环境+后缀）拉取配置。动态刷新通过长轮询实现：客户端发起请求，服务端如果配置没变则 hold 住请求（默认 30s），有变更则立即返回变更内容；客户端收到后刷新 Spring 环境，@RefreshScope 标注的 Bean 会被销毁重建，使用新配置。
>
> **用法要点**：① 配置放 bootstrap.yml（比 application.yml 先加载）；② 需要动态刷新的 Bean 加 @RefreshScope；③ 敏感配置（密码）用加密或环境变量；④ 配置版本管理，支持回滚；⑤ 面试常考：配置中心原理、动态刷新实现、bootstrap 与 application 区别。

## 4. 网关

### 4.1 Spring Cloud Gateway

**核心概念**：
- **Route**：路由，由 ID、目标 URI、断言、过滤器组成
- **Predicate**：断言，匹配请求条件（路径、方法、Header 等）
- **Filter**：过滤器，修改请求/响应（鉴权、限流、日志）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service  # lb:// 表示负载均衡
          predicates:
            - Path=/api/order/**
          filters:
            - StripPrefix=1  # 去掉 /api 前缀
            - name: RequestRateLimiter  # 限流
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20
```

> 🔍 **知识点深度解析**
>
> **作用**：网关是系统统一入口，承担路由转发、鉴权、限流、跨域、日志等横切关注点，是微服务的"门面"。
>
> **原理**：Gateway 基于 Spring WebFlux（Netty 响应式、异步非阻塞）。请求进来先经 RoutePredicate（断言）匹配路由，再经 GatewayFilter / GlobalFilter 链处理（Pre 改请求、Post 改响应），最后用 `lb://` 经 LoadBalancer 转发到目标服务。核心是 Route（id + uri + predicates + filters）三元组。
>
> **用法要点**：① 路由用 lb://service-name 做客户端负载均衡；② 过滤器 StripPrefix 去掉前缀、RewritePath 改写路径；③ 全局鉴权用 GlobalFilter（实现 Ordered 控制执行顺序）；④ 限流用 RequestRateLimiter + Redis（令牌桶）；⑤ 跨域在网关统一配置（CorsConfigurationSource）；⑥ 网关只做轻量逻辑，重业务逻辑下沉到服务；⑦ 相比 Zuul 1.x（同步阻塞）性能更好。

### 4.2 全局过滤器（鉴权示例）

```java
@Component
public class AuthFilter implements GlobalFilter, Ordered {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (token == null) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
        return chain.filter(exchange);
    }
    @Override
    public int getOrder() { return -100; } // 优先级，越小越先执行
}
```

> 🔍 **知识点深度解析**
>
> **作用**：网关是微服务统一入口，负责路由转发、鉴权、限流、日志、跨域等。
>
> **原理**：Gateway 基于 WebFlux（响应式编程），请求进入后通过断言链匹配路由，匹配成功后经过过滤器链处理，再转发到目标服务。过滤器分为 Pre（请求前）和 Post（响应后），GlobalFilter 全局生效，GatewayFilter 只对特定路由生效。`lb://service-name` 结合 LoadBalancer 实现客户端负载均衡。Gateway 是 Netty 异步非阻塞模型，性能比 Zuul 1.x（同步阻塞）好很多。
>
> **用法要点**：① 网关做统一鉴权，服务间调用可内网免鉴权；② 限流用 Redis + Lua 脚本实现（令牌桶/漏桶）；③ 跨域在网关层统一配置；④ 面试常考：Gateway 工作原理、断言/过滤器、与 Zuul 区别、鉴权实现。

## 5. 负载均衡

### 5.1 Spring Cloud LoadBalancer

```java
@Bean
@LoadBalanced
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// 调用时用服务名代替 IP:Port
restTemplate.getForObject("http://order-service/api/orders", List.class);
```

> 🔍 **知识点深度解析**
>
> **作用**：客户端负载均衡让调用方在本地决定请求发往哪个服务实例，避免对中心负载均衡器的依赖，是微服务内部调用的基础。
>
> **原理**：@LoadBalanced 标注的 RestTemplate / WebClient 会被拦截器增强，把 URI 中的服务名解析为具体实例 IP:Port。LoadBalancer 从本地缓存的服务实例列表（来自注册中心）按策略挑一个实例。它替代了已停更的 Ribbon，基于 Reactive 实现。
>
> **用法要点**：① 给 RestTemplate 加 @LoadBalanced 即可用服务名调用；② 实例列表来自注册中心本地缓存，需注册中心健康探活剔除下线实例；③ 默认轮询策略，可自定义 LoadBalancerClient 实现权重 / 一致性哈希；④ OpenFeign 内部也集成 LoadBalancer；⑤ 实例列表有短暂延迟（缓存刷新周期），已下线实例可能被短暂命中（需容错重试）。

### 5.2 负载均衡策略

- **轮询（RoundRobin）**：默认，依次分配
- **随机（Random）**：随机选择
- **权重（Weighted）**：按权重分配
- **一致性哈希**：相同参数路由到同一实例

> 🔍 **知识点深度解析**
>
> **作用**：不同负载均衡策略适应不同流量特征，合理选择能提升吞吐、降低热点、保证会话 / 缓存亲和性。
>
> **原理**：轮询（RoundRobin）依次分配，均衡但无视实例负载；随机（Random）实现简单；权重（Weighted）按实例配置权重分配，让强机器多担；一致性哈希（Consistent Hash）对相同参数（如 userId）哈希到固定实例，保证会话 / 缓存亲和。
>
> **用法要点**：① 无状态服务默认轮询 / 随机即可；② 实例配置不均用权重策略；③ 需要会话粘性或本地缓存命中用一致性哈希（同 key 落同实例）；④ 一致性哈希要注意节点增减时的数据迁移（用虚拟节点缓解）；⑤ 结合注册中心健康实例列表，避免转发到宕机节点；⑥ 面试常考：各策略优缺点与适用场景。

## 6. 熔断限流

### 6.1 Sentinel

**核心功能**：流量控制、熔断降级、系统负载保护

```java
// 定义资源
@SentinelResource(value = "getOrder", fallback = "getOrderFallback")
public Order getOrder(Long id) {
    return orderMapper.selectById(id);
}

public Order getOrderFallback(Long id, Throwable e) {
    return new Order(); // 降级返回
}
```

**熔断策略**：
- **慢调用比例**：响应时间超过阈值的比例达到阈值则熔断
- **异常比例**：异常比例达到阈值则熔断
- **异常数**：异常数达到阈值则熔断

> 🔍 **知识点深度解析**
>
> **作用**：Sentinel 是面向分布式系统的流量控制与熔断降级组件，保护服务不被突发流量或下游故障拖垮，是微服务高可用的关键。
>
> **原理**：以"资源"为最小保护单位（@SentinelResource 标注方法 / 接口）。核心是插槽链（Slot Chain）：统计插槽实时统计 QPS / 线程数 / 异常，限流插槽按规则拒流，熔断插槽按错误率 / 慢调用比例打开熔断器。熔断后走 fallback 降级方法返回兜底结果。
>
> **用法要点**：① 用 @SentinelResource 定义资源，配 fallback 兜底；② 熔断有三种策略：慢调用比例、异常比例、异常数；③ 规则可在 Sentinel Dashboard 动态配置（内存态，生产需持久化到 Nacos）；④ 限流模式：QPS 或线程数；⑤ 降级方法要轻量（返回默认值 / 缓存 / 友好提示）；⑥ 与 Hystrix 区别：Sentinel 更轻量、规则更丰富、中文生态好。

### 6.2 限流算法

| 算法 | 原理 | 优缺点 |
|------|------|--------|
| 计数器 | 固定时间窗口计数 | 简单，但有临界突发问题 |
| 滑动窗口 | 细分窗口滑动统计 | 平滑，实现稍复杂 |
| 漏桶 | 固定速率流出 | 平滑，无法应对突发 |
| 令牌桶 | 固定速率生成令牌 | 允许突发，最常用 |

> 🔍 **知识点深度解析**
>
> **作用**：限流算法决定"如何限制单位时间请求量"，是在系统容量边界保护服务的核心机制。
>
> **原理**：计数器（固定窗口）在窗口内累计计数，简单但窗口边界可能突发两倍流量（临界问题）；滑动窗口细分窗口、平滑统计，缓解临界突发；漏桶（Leaky Bucket）以固定速率流出，强制平滑、不允突发；令牌桶（Token Bucket）以固定速率生成令牌存入桶，请求取令牌，桶容量允许一定突发，最常用。
>
> **用法要点**：① 绝大多数场景用令牌桶（兼顾平滑与突发）；② 固定窗口简单但临界突发需注意（如整点翻倍）；③ 滑动窗口更精确，适合对突发敏感场景；④ 漏桶适合需严格匀速的场景（如保护下游第三方）；⑤ 网关限流常用 Redis + Lua 实现令牌桶（分布式计数）；⑥ 限流阈值要压测确定，过低误杀、过高无保护；⑦ 被限流要友好降级（返回 429 / 排队提示）。

> 🔍 **知识点深度解析**
>
> **作用**：熔断限流保护系统不被流量冲垮，是微服务高可用的关键。
>
> **原理**：熔断器模式（Circuit Breaker）有三种状态：Closed（关闭，正常调用）→ Open（打开，直接降级，不调用下游）→ Half-Open（半开，放行少量请求探测）。当下游错误率/慢调用比例达到阈值，熔断器从 Closed 变为 Open，经过冷却时间后进入 Half-Open，探测成功则 Closed，失败则继续 Open。限流通过限制单位时间请求数保护系统，令牌桶算法最常用（固定速率生成令牌，请求取令牌，取不到则拒绝，桶容量允许突发）。
>
> **用法要点**：① 熔断在调用方配置（保护自己不被下游拖垮）；② 降级返回要合理（默认值、缓存、友好提示）；③ 限流在网关或服务层配置；④ Sentinel 支持控制台动态配置规则；⑤ 面试常考：熔断器状态机、限流算法、Sentinel vs Hystrix、降级策略。

## 7. 链路追踪

### 7.1 核心概念

- **Trace**：一次请求的完整链路，唯一 TraceID
- **Span**：链路中的一个操作（一次 RPC 调用），有 SpanID 和 ParentSpanID
- **Annotation**：事件标注（cs/cr/ss/sr）

> 🔍 **知识点深度解析**
>
> **作用**：Trace / Span 是分布式链路追踪的数据模型，理解它们才能正确使用追踪系统定位跨服务问题。
>
> **原理**：一次用户请求产生一个 Trace（全局唯一 TraceID）。请求每经过一个服务 / 一次 RPC 调用产生一个 Span（有 SpanID 和 ParentSpanID，形成树状调用链）。Annotation 标记关键时间点：cs（Client Send 客户端发请求）、sr（Server Receive 服务端收）、ss（Server Send 服务端回）、cr（Client Receive 客户端收），用时间戳差算网络 / 处理耗时。
>
> **用法要点**：① TraceID 贯穿整条链路（网关生成，逐层传递）；② Span 的 parent 关系还原调用树；③ cs→sr 是网络耗时，sr→ss 是服务端处理耗时；④ 把 TraceID 打进日志（MDC），便于按链路检索；⑤ 采样率权衡（全量影响性能，生产用比例采样 / 自适应采样）；⑥ 面试常考：Trace / Span / ParentSpanID 关系、四种 Annotation 含义。

### 7.2 SkyWalking

- Java Agent 无侵入埋点
- 支持分布式追踪、服务拓扑、性能分析
- 自动上报 Trace 数据到 OAP 服务端

> 🔍 **知识点深度解析**
>
> **作用**：SkyWalking 是国产 APM / 链路追踪系统，无侵入接入，提供调用链、服务拓扑、性能分析，是微服务可观测性的常用方案。
>
> **原理**：使用 Java Agent（字节码增强，Instrumentation API）在类加载时向目标方法插入埋点代码，业务代码零改动。埋点数据（Trace / Span / 指标 / JVM）上报到 OAP（Observability Analysis Platform）服务端，存 ES / MySQL 等，UI 展示调用链、拓扑图、慢端点。还支持服务网格（Istio）和多种语言探针。
>
> **用法要点**：① 接入只需加 -javaagent:skywalking-agent.jar + 配置 agent.config（服务名、OAP 地址）；② 无侵入是最大优势（不污染业务代码）；③ 采样率配置避免性能损耗（agent.sample_n_per_3_secs）；④ 存储用 ES 性能最佳；⑤ 服务端拓扑图帮助发现环路 / 慢调用；⑥ 与 Zipkin / Jaeger 对比：SkyWalking 功能更全（含指标 / 告警），Zipkin 更轻量。

### 7.3 TraceID 传递

- HTTP：通过 Header 传递（`traceparent`、`sw8`）
- MQ：通过消息属性传递
- 线程池：需手动传递（TransmittableThreadLocal）

> 🔍 **知识点深度解析**
>
> **作用**：链路追踪定位微服务中的性能瓶颈和错误，是排查分布式问题的必备工具。
>
> **原理**：请求进入网关时生成唯一 TraceID，每次服务间调用生成新的 SpanID，通过 Header（HTTP）或消息属性（MQ）传递 TraceID 和 ParentSpanID。各服务将 Span 数据上报到追踪系统，追踪系统根据 TraceID 聚合成完整调用链。SkyWalking 用 Java Agent（字节码增强）在类加载时插入追踪代码，对业务无侵入。OpenTelemetry 是 CNCF 的统一标准，正在成为行业规范。
>
> **用法要点**：① TraceID 要打印到日志中，便于关联；② 异步调用（线程池）需手动传递上下文（TTL）；③ 采样率配置（全量采样影响性能，生产用比例采样）；④ 面试常考：Trace/Span 概念、链路追踪原理、SkyWalking 实现、TraceID 传递。

## 8. 远程调用

### 8.1 OpenFeign

```java
@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {
    @GetMapping("/api/users/{id}")
    User getUser(@PathVariable("id") Long id);
    
    @PostMapping("/api/users")
    void createUser(@RequestBody UserCreateRequest request);
}
```

**特点**：
- 声明式 HTTP 客户端，像调用本地方法一样调用远程服务
- 集成 Ribbon/LoadBalancer 负载均衡
- 支持 Sentinel 熔断降级

> 🔍 **知识点深度解析**
>
> **作用**：OpenFeign 是声明式 HTTP 客户端，让远程调用像调本地接口一样简单，降低服务间调用的样板代码。
>
> **原理**：接口 + @FeignClient 注解定义远程服务与方法，启动时 Feign 生成动态代理。调用方法时，代理按注解拼 URL、序列化参数、经 LoadBalancer 选实例、发 HTTP 请求、反序列化响应。集成 LoadBalancer（服务名→实例）、Sentinel（熔断降级）、拦截器（统一 Header / 鉴权）。
>
> **用法要点**：① 用接口 + @GetMapping / @PostMapping 定义远程方法，避免手写 RestTemplate；② name 指定服务名（配合 LoadBalancer 服务发现）；③ fallback 指定降级类（需 @FeignClient(fallback=...) + Sentinel 开启）；④ 超时 / 重试在配置中设置（feign.client.config）；⑤ 请求 / 响应用 DTO，避免大对象；⑥ 与 RestTemplate 区别：声明式、更简洁、易维护；⑦ 日志级别（feign.Logger.Level）按需开启排查。

### 8.2 Dubbo

- 高性能 RPC 框架，基于 TCP 协议（Hessian2 序列化）
- 面向接口代理，服务治理能力强
- 适合内部服务间高性能调用

> 🔍 **知识点深度解析**
>
> **作用**：Dubbo 是高性能 RPC 框架，适合内部服务间高频、低延迟调用，服务治理能力强。
>
> **原理**：基于 TCP 长连接 + Hessian2（默认）等高效序列化，比 HTTP / JSON 性能更好。面向接口代理（@DubboReference / @DubboService），注册中心（Nacos / ZK）做服务发现，三层 RPC 调用（消费者→提供者）。内置负载均衡、集群容错、服务治理（路由、降级、权重）。
>
> **用法要点**：① 接口契约独立成 api 模块，提供 / 消费方共用；② 序列化选 Hessian2 / Kryo（性能优于 JSON）；③ 适合内网高性能 RPC，跨语言用 Triple（gRPC 协议）；④ 服务治理：权重、路由规则、Mock 降级；⑤ 与 OpenFeign / HTTP 对比：性能更高但耦合语言 / 接口；⑥ 超时（timeout）与重试（retries）合理配置，避免级联超时。
