# 分布式锁知识点系统梳理（优化版）

> **文档说明**：系统梳理分布式锁的实现方案，涵盖 Redis 分布式锁、Redisson、Zookeeper 分布式锁、数据库锁，以及各种方案的优缺点和面试考点。

---

## 1. 概述

分布式锁是控制分布式系统中**多个进程对共享资源互斥访问**的机制。在单体应用中用 synchronized 或 Lock 即可，但分布式部署后，JVM 级别的锁无法跨进程生效，需要分布式锁。

**分布式锁的要求**：
1. **互斥性**：同一时间只有一个客户端持有锁
2. **防死锁**：持有锁的客户端崩溃后，锁能自动释放
3. **解铃还须系铃人**：加锁和解锁必须是同一个客户端
4. **可重入**：同一客户端可多次获取同一把锁
5. **高可用**：锁服务本身高可用
6. **阻塞/非阻塞**：支持等待获取锁

## 2. Redis 分布式锁

### 2.1 基础实现（SETNX）

```bash

> 🔍 **知识点深度解析**
>
> **作用**：Redis SETNX 是最基础的分布式锁实现，利用 key 不存在时才设置成功的原子操作保证互斥。
>
> **原理**：SET key value NX EX 30：NX 保证 key 不存在时才设置（互斥），EX 设置过期时间（防死锁）。value 必须是唯一标识（UUID+线程ID），释放锁时用 Lua 脚本先判断 value 再删除（避免误删他人锁）。SETNX 缺陷：不可重入、锁续期需手动、主从切换可能丢锁（RedLock 争议）。
>
> **用法要点**：① SET key value NX EX seconds 原子加锁，不用 SETNX+EXPIRE 两条命令  ② value 用 UUID 唯一标识，释放时 Lua 脚本比对后删除  ③ 过期时间需大于业务执行时间，或用看门狗自动续期  ④ Redisson 封装了可重入锁、看门狗、联锁等高级特性  ⑤ 面试常考：SETNX 原子性、value 唯一标识、Lua 释放、锁续期

# 加锁：SET key value NX EX timeout
SET lock:order:1001 "client-uuid" NX EX 30
# NX：key 不存在才设置（互斥）
# EX 30：30秒过期（防死锁）

# 解锁：需要判断 value 是否是自己加的锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

```java
// Java 实现
public boolean tryLock(String key, String requestId, int expireTime) {
    String result = jedis.set(key, requestId, "NX", "EX", expireTime);
    return "OK".equals(result);
}

public void unlock(String key, String requestId) {
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
    jedis.eval(script, Collections.singletonList(key), Collections.singletonList(requestId));
}
```

> 🔍 **知识点深度解析**
>
> **作用**：Redis 分布式锁是最常用的分布式锁实现，性能好、实现简单。
>
> **原理**：`SET key value NX EX timeout` 是原子操作，NX 保证互斥（key 不存在才设置成功），EX 设置过期时间防止死锁（客户端崩溃后锁自动过期）。value 用唯一标识（UUID），解锁时先判断 value 是否等于自己的标识，再删除——这两步必须用 Lua 脚本保证原子性，否则可能出现：A 判断 value 相等 → 锁过期 → B 获取锁 → A 删除 B 的锁。
>
> **用法要点**：① 必须用 SET NX EX 原子命令，不要用 setnx + expire 分两步（中间崩溃会死锁）；② value 必须唯一（UUID），解锁要判断 value；③ 解锁用 Lua 脚本保证原子性；④ 过期时间要大于业务执行时间，但不能太长（崩溃后等待久）；⑤ 面试常考：Redis 锁原理、锁误删问题、Lua 脚本、过期时间设置。

### 2.2 存在的问题

1. **锁过期但业务未执行完**：业务执行超过过期时间，锁被释放，其他客户端获取锁
2. **主从切换丢锁**：Redis 主节点加锁后未同步到从节点就宕机，从节点提升为主后锁丢失
3. **不可重入**：基础实现不支持重入
4. **无阻塞获取**：获取失败直接返回，不支持等待

> 🔍 **知识点深度解析**
>
> **作用**：指出基础 Redis 锁（SETNX + 手动过期）的四大固有缺陷，帮助理解为什么生产环境不能用裸实现，必须引入 Redisson 或 ZooKeeper。
>
> **原理**：① 锁过期业务未完成：EX 过期时间是静态的，业务执行超时则锁提前被 Redis 释放，其他客户端趁机加锁进入临界区导致并发；② 主从切换丢锁：主库加锁后未同步到从库即宕机，哨兵将从库提升为新主库，新主库没有这把锁，另一客户端可再加锁成功；③ 不可重入：同一 key 已存在，同一线程二次加锁会失败（自死锁）；④ 无阻塞：加锁失败立即返回 false，需业务自己轮询或 sleep 重试。
>
> **用法要点**：① 锁过期时间要大于业务最大耗时，或对持锁线程做续期（看门狗）；② 高可靠场景用 RedLock 或多节点方案缓解主从丢锁；③ 可重入需求用 Redisson（Hash 计数）；④ 阻塞获取用订阅通知（Redisson）而非自旋 sleep；⑤ 这些缺陷正是 Redisson / ZK 方案存在的价值，选方案前先认清它们。

## 3. Redisson 分布式锁（推荐）

Redisson 是 Redis 客户端，提供了完善的分布式锁实现，解决了基础 Redis 锁的各种问题。

### 3.1 可重入锁

```java
RLock lock = redissonClient.getLock("lock:order:1001");
// 尝试加锁，最多等待100秒，上锁后10秒自动过期
boolean locked = lock.tryLock(100, 10, TimeUnit.SECONDS);
try {
    if (locked) {
        // 业务逻辑
    }
} finally {
    if (locked) {
        lock.unlock();
    }
}
```

> 🔍 **知识点深度解析**
>
> **作用**：可重入锁允许同一线程多次获取同一把锁（如递归调用、多个加锁方法嵌套调用），避免"自己锁住自己"造成的死锁。
>
> **原理**：Redisson 用 Redis Hash 结构记录锁：`field = UUID:threadId`（标识持有线程），`value = 重入次数`。加锁时若锁不存在则创建并把 value 设为 1；若 field 已存在（同一线程重入）则 value + 1；释放时 value - 1，减到 0 才真正删除 key。tryLock(wait, lease, unit) 会在 wait 时间内通过发布订阅等待获取，lease 为锁自动过期时间。
>
> **用法要点**：① 优先用 tryLock（带等待时间）而非 lock（lock 无限等待可能死等）；② 重入计数要配对：加几次锁释放几次，finally 中 unlock 一次即可，Redisson 内部按计数释放；③ 必须在 finally 释放，否则重入计数不归零、锁永不释放；④ lease 时间要覆盖最长重入链路的耗时；⑤ 可重入对递归 / 嵌套调用至关重要，否则会自死锁。

### 3.2 核心特性

- **可重入**：用 Hash 结构存储，field 是客户端标识，value 是重入次数
- **看门狗（Watchdog）**：业务未执行完时自动续期（默认每 10s 检查，续期到 30s）
- **阻塞等待**：基于发布订阅机制，锁释放时通知等待线程
- **公平锁**：按请求顺序获取锁
- **读写锁**：读共享、写互斥
- **联锁/红锁**：多 Redis 节点，解决单点问题

> 🔍 **知识点深度解析**
>
> **作用**：Redisson 是生产级 Redis 分布式锁，解决了基础实现的所有问题。
>
> **原理**：可重入锁用 Hash 结构：`key = 锁名, field = 客户端ID+线程ID, value = 重入次数`。加锁时如果锁不存在或 field 已存在（重入），则 value+1；否则返回剩余过期时间（获取失败）。看门狗机制：如果未指定 leaseTime，启动后台线程每 10s 检查锁是否还被持有，是则续期到 30s，防止业务未执行完锁就过期。阻塞等待用 Redis 发布订阅：等待线程订阅锁释放频道，锁释放时发布消息，等待线程被唤醒重试。
>
> **用法要点**：① 生产环境优先用 Redisson，不要自己实现；② tryLock 要设置等待时间和过期时间；③ 解锁必须在 finally 中，且判断是否持有锁；④ 看门狗默认续期，指定 leaseTime 则不续期；⑤ 面试常考：Redisson 原理、看门狗机制、可重入实现、阻塞等待。

### 3.3 红锁（RedLock）

在多个独立 Redis 节点上加锁，超过半数成功才算获取成功，解决单点故障问题。但存在争议（时钟漂移问题），一般用主从+哨兵足够。

> 🔍 **知识点深度解析**
>
> **作用**：RedLock 在多个相互独立（无主从复制）的 Redis 节点上加锁，解决单点 / 主从切换丢锁问题，追求更高的加锁安全性。
>
> **原理**：客户端依次向 N 个独立节点申请锁（SET NX EX），当在多数节点（> N/2，如 5 节点需 3 个）获取成功，且总加锁耗时小于锁有效期，才算加锁成功。释放时向所有节点发送解锁（Lua）。它不依赖单点持久化，只要多数节点存活即可保证锁存在。
>
> **用法要点**：① 节点必须相互独立（无主从复制），否则失去意义；② 可用业务时间 = 锁有效时间 − 实际加锁总耗时，要留足余量；③ 争议：Martin Kleppmann 指出时钟漂移 / GC 停顿可能导致锁重叠，实践中多数业务用主从 + 哨兵已足够；④ Redisson 提供 RedissonRedLock 实现；⑤ 只有强一致要求极高才考虑 RedLock，否则 Redisson 单节点 + 看门狗更实用；⑥ 不要用 RedLock 做严格金融强一致（考虑 ZK / etcd）。

## 4. Zookeeper 分布式锁

### 4.1 实现原理

利用 ZK 的**临时顺序节点**：

1. 客户端在 `/locks` 下创建临时顺序节点，如 `/locks/lock-0000000001`
2. 获取 `/locks` 下所有子节点，判断自己是否是最小的
3. 是最小的则获取锁；否则监听前一个节点的删除事件
4. 前一个节点被删除（释放锁或客户端断开），收到通知后再次判断
5. 执行完业务，删除自己的节点（释放锁）

```java
// Curator 框架实现
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");
if (lock.acquire(100, TimeUnit.SECONDS)) {
    try {
        // 业务逻辑
    } finally {
        lock.release();
    }
}
```

> 🔍 **知识点深度解析**
>
> **作用**：Zookeeper 分布式锁可靠性高，支持阻塞等待，适合对一致性要求高的场景。
>
> **原理**：临时节点的特性是客户端会话断开后自动删除（防死锁），顺序节点保证节点名单调递增。每个客户端创建自己的临时顺序节点，只监听前一个节点（不是监听所有，避免羊群效应）。前一个节点删除时触发 Watch 通知，当前节点被唤醒后再次检查自己是否最小。这种实现天然支持阻塞等待和公平锁（按创建顺序获取）。
>
> **用法要点**：① 用 Curator 框架，不要自己写 ZK 锁；② 临时节点会话超时时间要合理；③ ZK 锁性能不如 Redis（每次加锁要创建节点、网络通信）；④ 面试常考：ZK 锁原理、临时顺序节点、羊群效应、与 Redis 锁对比。

### 4.2 羊群效应

如果每个节点都监听最小节点，最小节点释放时所有等待节点同时被唤醒（羊群效应）。用监听前一个节点的方式避免，只有下一个节点被唤醒。

> 🔍 **知识点深度解析**
>
> **作用**：羊群效应（惊群）指锁释放时大量等待线程被同时唤醒、一拥而上争抢锁，造成瞬间资源浪费和无效竞争。ZK 锁通过"只监听前一节点"来避免。
>
> **原理**：若所有等待节点都监听最小节点，最小节点释放时 Watch 事件会同时通知所有等待者，它们一起抢锁（只有一个成功，其余失败重试），产生惊群。优化方案：每个节点只监听比自己序号小一位的前驱节点，前驱释放时只唤醒"下一位"，形成串行唤醒链，避免集体争抢。
>
> **用法要点**：① Curator 的 InterProcessMutex 已内置"监听前一节点"，无需自己实现；② 监听前驱节点是避免羊群效应的关键设计；③ 对比 Redis 锁：Redisson 用发布订阅按锁维度通知，同样避免了惊群；④ 面试常考：羊群效应成因、ZK 如何避免、与 Redis 锁通知机制对比。

## 5. 数据库分布式锁

### 5.1 唯一索引

```sql
-- 创建锁表
CREATE TABLE distributed_lock (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  lock_key VARCHAR(255) NOT NULL UNIQUE,
  holder VARCHAR(255) NOT NULL,
  expire_time DATETIME NOT NULL
);

-- 加锁：插入成功则获取锁（唯一索引保证互斥）
INSERT INTO distributed_lock(lock_key, holder, expire_time)
VALUES('order:1001', 'client-uuid', DATE_ADD(NOW(), INTERVAL 30 SECOND));

-- 解锁：删除自己的锁
DELETE FROM distributed_lock WHERE lock_key = 'order:1001' AND holder = 'client-uuid';

> 🔍 **知识点深度解析**
>
> **作用**：基于数据库唯一索引的分布式锁实现最简单，利用 INSERT 唯一键冲突保证互斥，适合没有 Redis / ZK 等中间件的简单场景。
>
> **原理**：建一张锁表，以 lock_key 建唯一索引。加锁 = INSERT 一条记录（唯一键冲突即获取失败，保证互斥）；解锁 = DELETE 该记录（需带 holder 条件防误删他人锁）。expire_time 字段用于过期清理（定时任务或惰性删除）。
>
> **用法要点**：① 唯一索引是互斥的核心，绝不能去掉；② 解锁要带 holder 条件（DELETE WHERE lock_key=? AND holder=?），防止误删别人的锁；③ 过期清理：用定时任务删除 expire_time 已过期的记录，否则客户端崩溃会死锁；④ 性能差（数据库磁盘 IO），不适合高并发；⑤ 非阻塞（INSERT 失败即返回），需业务层自旋重试；⑥ 不推荐作为主方案，仅在无中间件时兜底。
```

### 5.2 缺点

- 性能差（数据库 IO）
- 单点故障（数据库挂了锁服务不可用）
- 非阻塞（插入失败直接返回）
- 不可重入
- 过期需要定时任务清理

一般不推荐，只适合简单场景。

> 🔍 **知识点深度解析**
>
> **作用**：明确数据库锁的固有缺陷，帮助在选型时避免误用，清楚它的能力边界。
>
> **原理**：数据库锁每次加解锁都要走数据库磁盘 IO，吞吐远低于 Redis / ZK；数据库本身可能成为单点（挂了锁服务不可用）；INSERT 失败即返回，无法阻塞等待；无重入（同一 key 重复 INSERT 冲突）；过期依赖外部定时任务清理，存在窗口期；依赖唯一索引冲突表达"获取失败"，语义较粗糙。
>
> **用法要点**：① 性能敏感 / 高并发场景禁用数据库锁；② 数据库锁不提供阻塞等待，需业务自旋；③ 单点风险：数据库主从切换可能丢锁（主库锁未同步）；④ 仅适合低频、简单、无其他中间件的内部工具场景；⑤ 生产推荐 Redis（Redisson）或 ZK。

## 7. 常见问题与解决方案

### 7.1 锁过期业务未完成

- **Redisson 看门狗**：自动续期（推荐）
- **延长过期时间**：预估业务时间，设置足够长的过期时间
- **守护线程续期**：自己实现后台线程续期

> 🔍 **知识点深度解析**
>
> **作用**：解决"业务没跑完、锁先过期"导致的并发安全问题，这是分布式锁最实际、最高频的风险点。
>
> **原理**：锁的过期时间是静态配置的，而业务耗时是动态变化的。一旦业务耗时超过锁有效期，锁被 Redis 自动释放，其他客户端拿到锁进入临界区，出现并发。续期方案：客户端持锁期间启动后台线程定期检查自己是否仍持有锁，是则延长过期时间（Redisson 看门狗默认每 10s 续到 30s）。
>
> **用法要点**：① 生产首选 Redisson 看门狗（自动续期，省心）；② 自己实现续期：守护线程 + 定时 EXPIRE / PEXPIRE，注意只续自己持有的锁；③ 也可预估业务最大耗时设较长 expireTime，但不灵活；④ 续期线程本身也要高可用（进程挂了续期停）；⑤ 业务要保证能在合理时间内完成，避免锁长期不释放（长事务应拆分）。

### 7.2 主从切换丢锁

- **红锁**：多节点半数加锁（有争议）
- **ZK 锁**：CP 模型，一致性高
- **容忍**：大部分场景主从切换概率低，可接受

> 🔍 **知识点深度解析**
>
> **作用**：说明 Redis 异步复制在主从切换时可能丢锁，帮助评估一致性风险并选择对策。
>
> **原理**：Redis 主从复制是异步的。客户端在主库加锁成功后，主库宕机且锁未同步到从库，哨兵将从库提升为新主库，新主库没有这把锁，另一客户端可在新主库加同一把锁，出现两个客户端同时持锁。
>
> **用法要点**：① 多数互联网业务可接受此极小概率（主从切换少）并结合业务幂等兜底；② 高可靠用 RedLock（多独立节点）或 ZK / etcd（CP，强一致）；③ 用 WAIT 命令（同步复制）可降低丢锁概率但拉低性能；④ 评估：是否真的需要强互斥？若丢锁后果严重（超卖 / 重复扣款）才升级方案；⑤ 配合幂等 / 对账兜底更稳妥。

### 7.3 锁误删

- **value 唯一标识 + Lua 原子解锁**：必须实现
- **Redisson**：框架已处理

> 🔍 **知识点深度解析**
>
> **作用**：防止客户端 A 误删客户端 B 的锁，避免"自己释放了别人的锁"导致并发失控。
>
> **原理**：若解锁直接 DEL key 而不校验持有者，会出现：A 加锁 → 锁过期 → B 加锁 → A 业务结束执行 DEL，把 B 的锁删了 → C 又加锁成功，临界区并发。解决：加锁 value = 唯一标识（UUID），解锁时用 Lua 脚本先 GET 比对 value 相等才 DEL，两步原子化。
>
> **用法要点**：① value 必须全局唯一（UUID 或 UUID:threadId），标识锁持有者；② 解锁必须用 Lua 脚本保证"判断 + 删除"原子，否则 GET 与 DEL 之间锁可能过期被抢；③ Redisson 内部已用 UUID + Lua，使用 RLock 无需关心；④ 在 finally 中解锁，且只对成功获取的锁解锁；⑤ 面试常考：锁误删成因、Lua 防误删原理。

### 7.4 死锁

- **过期时间**：必须设置
- **ZK 临时节点**：会话断开自动删除
- **finally 解锁**：代码规范

> 🔍 **知识点深度解析**
>
> **作用**：死锁指锁永远不被释放（持有者崩溃或代码未解锁），导致后续请求永久阻塞。分布式锁必须从设计上规避，而不是事后处理。
>
> **原理**：死锁常见成因：① 客户端加锁后崩溃、未执行解锁代码，锁无过期则永久占用；② 代码异常路径没走到 unlock（未在 finally 释放）；③ 锁过期时间设为 0 / 无穷大且无续期。规避手段：锁必须有自动过期时间（EX），且解锁放 finally；ZK 临时节点会话断开自动删除（天然防死锁）。
>
> **用法要点**：① 加锁必须设过期时间（EX / NX 一步到位），杜绝"永久锁"；② 解锁放在 finally 块，保证异常也能释放；③ ZK 临时节点：会话断开自动删除；④ Redis 锁：过期时间 + 看门狗续期（业务长跑也安全）；⑤ 避免在锁内做阻塞 / 外部调用（拖长持锁时间）；⑥ 监控：长时间未释放的锁要告警。

## 📝 精简总结

- 分布式锁解决多进程互斥访问共享资源的问题
- Redis 锁：SET NX EX 原子加锁，Lua 原子解锁，value 唯一防误删
- Redisson：生产级方案，可重入（Hash）、看门狗续期、发布订阅阻塞
- ZK 锁：临时顺序节点，监听前一个节点，可靠性高但性能一般
- 数据库锁：唯一索引，简单但性能差，不推荐
- 选型：性能优先用 Redisson，一致性优先用 ZK
- 核心问题：死锁（过期时间）、误删（Lua+唯一标识）、续期（看门狗）
