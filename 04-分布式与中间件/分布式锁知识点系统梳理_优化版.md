# 分布式锁知识点系统梳理（优化版）

> **文档说明**：系统梳理分布式锁的实现方案，涵盖 Redis 分布式锁、Redisson、Zookeeper 分布式锁、数据库锁，以及各种方案的优缺点和面试考点。

---

## 1. 概述

分布式锁是控制分布式系统中**多个进程对共享资源互斥访问**的机制。在单体应用中用 synchronized 或 Lock 即可，但分布式部署后，JVM 级别的锁无法跨进程生效，需要分布式锁。

**分布式锁的要求**：
1. **互斥性**：同一时间只有一个客户端持有锁
2. **防死锁**：持有锁的客户端崩溃后，锁能自动释放
3. **解铃还须系铃人**：加锁和解锁必须是同一个客户端
4. **可重入**：同一客户端可多次获取同一把锁
5. **高可用**：锁服务本身高可用
6. **阻塞/非阻塞**：支持等待获取锁

## 2. Redis 分布式锁

### 2.1 基础实现（SETNX）

```bash
# 加锁：SET key value NX EX timeout
SET lock:order:1001 "client-uuid" NX EX 30
# NX：key 不存在才设置（互斥）
# EX 30：30秒过期（防死锁）

# 解锁：需要判断 value 是否是自己加的锁（Lua 脚本保证原子性）
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

```java
// Java 实现
public boolean tryLock(String key, String requestId, int expireTime) {
    String result = jedis.set(key, requestId, "NX", "EX", expireTime);
    return "OK".equals(result);
}

public void unlock(String key, String requestId) {
    String script = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
    jedis.eval(script, Collections.singletonList(key), Collections.singletonList(requestId));
}
```

> 🔍 **知识点深度解析**
>
> **作用**：Redis 分布式锁是最常用的分布式锁实现，性能好、实现简单。
>
> **原理**：`SET key value NX EX timeout` 是原子操作，NX 保证互斥（key 不存在才设置成功），EX 设置过期时间防止死锁（客户端崩溃后锁自动过期）。value 用唯一标识（UUID），解锁时先判断 value 是否等于自己的标识，再删除——这两步必须用 Lua 脚本保证原子性，否则可能出现：A 判断 value 相等 → 锁过期 → B 获取锁 → A 删除 B 的锁。
>
> **用法要点**：① 必须用 SET NX EX 原子命令，不要用 setnx + expire 分两步（中间崩溃会死锁）；② value 必须唯一（UUID），解锁要判断 value；③ 解锁用 Lua 脚本保证原子性；④ 过期时间要大于业务执行时间，但不能太长（崩溃后等待久）；⑤ 面试常考：Redis 锁原理、锁误删问题、Lua 脚本、过期时间设置。

### 2.2 存在的问题

1. **锁过期但业务未执行完**：业务执行超过过期时间，锁被释放，其他客户端获取锁
2. **主从切换丢锁**：Redis 主节点加锁后未同步到从节点就宕机，从节点提升为主后锁丢失
3. **不可重入**：基础实现不支持重入
4. **无阻塞获取**：获取失败直接返回，不支持等待

## 3. Redisson 分布式锁（推荐）

Redisson 是 Redis 客户端，提供了完善的分布式锁实现，解决了基础 Redis 锁的各种问题。

### 3.1 可重入锁

```java
RLock lock = redissonClient.getLock("lock:order:1001");
// 尝试加锁，最多等待100秒，上锁后10秒自动过期
boolean locked = lock.tryLock(100, 10, TimeUnit.SECONDS);
try {
    if (locked) {
        // 业务逻辑
    }
} finally {
    if (locked) {
        lock.unlock();
    }
}
```

### 3.2 核心特性

- **可重入**：用 Hash 结构存储，field 是客户端标识，value 是重入次数
- **看门狗（Watchdog）**：业务未执行完时自动续期（默认每 10s 检查，续期到 30s）
- **阻塞等待**：基于发布订阅机制，锁释放时通知等待线程
- **公平锁**：按请求顺序获取锁
- **读写锁**：读共享、写互斥
- **联锁/红锁**：多 Redis 节点，解决单点问题

> 🔍 **知识点深度解析**
>
> **作用**：Redisson 是生产级 Redis 分布式锁，解决了基础实现的所有问题。
>
> **原理**：可重入锁用 Hash 结构：`key = 锁名, field = 客户端ID+线程ID, value = 重入次数`。加锁时如果锁不存在或 field 已存在（重入），则 value+1；否则返回剩余过期时间（获取失败）。看门狗机制：如果未指定 leaseTime，启动后台线程每 10s 检查锁是否还被持有，是则续期到 30s，防止业务未执行完锁就过期。阻塞等待用 Redis 发布订阅：等待线程订阅锁释放频道，锁释放时发布消息，等待线程被唤醒重试。
>
> **用法要点**：① 生产环境优先用 Redisson，不要自己实现；② tryLock 要设置等待时间和过期时间；③ 解锁必须在 finally 中，且判断是否持有锁；④ 看门狗默认续期，指定 leaseTime 则不续期；⑤ 面试常考：Redisson 原理、看门狗机制、可重入实现、阻塞等待。

### 3.3 红锁（RedLock）

在多个独立 Redis 节点上加锁，超过半数成功才算获取成功，解决单点故障问题。但存在争议（时钟漂移问题），一般用主从+哨兵足够。

## 4. Zookeeper 分布式锁

### 4.1 实现原理

利用 ZK 的**临时顺序节点**：

1. 客户端在 `/locks` 下创建临时顺序节点，如 `/locks/lock-0000000001`
2. 获取 `/locks` 下所有子节点，判断自己是否是最小的
3. 是最小的则获取锁；否则监听前一个节点的删除事件
4. 前一个节点被删除（释放锁或客户端断开），收到通知后再次判断
5. 执行完业务，删除自己的节点（释放锁）

```java
// Curator 框架实现
InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");
if (lock.acquire(100, TimeUnit.SECONDS)) {
    try {
        // 业务逻辑
    } finally {
        lock.release();
    }
}
```

> 🔍 **知识点深度解析**
>
> **作用**：Zookeeper 分布式锁可靠性高，支持阻塞等待，适合对一致性要求高的场景。
>
> **原理**：临时节点的特性是客户端会话断开后自动删除（防死锁），顺序节点保证节点名单调递增。每个客户端创建自己的临时顺序节点，只监听前一个节点（不是监听所有，避免羊群效应）。前一个节点删除时触发 Watch 通知，当前节点被唤醒后再次检查自己是否最小。这种实现天然支持阻塞等待和公平锁（按创建顺序获取）。
>
> **用法要点**：① 用 Curator 框架，不要自己写 ZK 锁；② 临时节点会话超时时间要合理；③ ZK 锁性能不如 Redis（每次加锁要创建节点、网络通信）；④ 面试常考：ZK 锁原理、临时顺序节点、羊群效应、与 Redis 锁对比。

### 4.2 羊群效应

如果每个节点都监听最小节点，最小节点释放时所有等待节点同时被唤醒（羊群效应）。用监听前一个节点的方式避免，只有下一个节点被唤醒。

## 5. 数据库分布式锁

### 5.1 唯一索引

```sql
-- 创建锁表
CREATE TABLE distributed_lock (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  lock_key VARCHAR(255) NOT NULL UNIQUE,
  holder VARCHAR(255) NOT NULL,
  expire_time DATETIME NOT NULL
);

-- 加锁：插入成功则获取锁（唯一索引保证互斥）
INSERT INTO distributed_lock(lock_key, holder, expire_time)
VALUES('order:1001', 'client-uuid', DATE_ADD(NOW(), INTERVAL 30 SECOND));

-- 解锁：删除自己的锁
DELETE FROM distributed_lock WHERE lock_key = 'order:1001' AND holder = 'client-uuid';
```

### 5.2 缺点

- 性能差（数据库 IO）
- 单点故障（数据库挂了锁服务不可用）
- 非阻塞（插入失败直接返回）
- 不可重入
- 过期需要定时任务清理

一般不推荐，只适合简单场景。

## 6. 方案对比

| 方案 | 性能 | 可靠性 | 可重入 | 阻塞 | 实现复杂度 | 适用场景 |
|------|------|--------|--------|------|------------|----------|
| Redis SETNX | 高 | 中（单点） | 否 | 否 | 低 | 简单场景 |
| Redisson | 高 | 中高 | 是 | 是 | 中（用框架） | 生产推荐 |

| 数据库 | 低 | 低 | 否 | 否 | 低 | 简单/无其他中间件 |

## 7. 常见问题与解决方案

### 7.1 锁过期业务未完成

- **Redisson 看门狗**：自动续期（推荐）
- **延长过期时间**：预估业务时间，设置足够长的过期时间
- **守护线程续期**：自己实现后台线程续期

### 7.2 主从切换丢锁

- **红锁**：多节点半数加锁（有争议）
- **ZK 锁**：CP 模型，一致性高
- **容忍**：大部分场景主从切换概率低，可接受

### 7.3 锁误删

- **value 唯一标识 + Lua 原子解锁**：必须实现
- **Redisson**：框架已处理

### 7.4 死锁

- **过期时间**：必须设置
- **ZK 临时节点**：会话断开自动删除
- **finally 解锁**：代码规范

## 8. 面试高频考点

1. **Redis 分布式锁原理**：SET NX EX、value 唯一、Lua 解锁
2. **锁误删问题**：如何避免（Lua + 唯一标识）
3. **锁过期业务未完成**：看门狗机制、续期
4. **Redisson 原理**：可重入（Hash）、看门狗、阻塞（发布订阅）
5. **ZK 分布式锁**：临时顺序节点、羊群效应
6. **Redis vs ZK 锁**：性能、可靠性、适用场景
7. **红锁**：原理、争议（时钟漂移）
8. **分布式锁要求**：互斥、防死锁、可重入、高可用
9. **数据库锁**：唯一索引实现、缺点
10. **公平锁**：ZK 天然支持，Redisson 也支持

## 📝 精简总结

- 分布式锁解决多进程互斥访问共享资源的问题
- Redis 锁：SET NX EX 原子加锁，Lua 原子解锁，value 唯一防误删
- Redisson：生产级方案，可重入（Hash）、看门狗续期、发布订阅阻塞
- ZK 锁：临时顺序节点，监听前一个节点，可靠性高但性能一般
- 数据库锁：唯一索引，简单但性能差，不推荐
- 选型：性能优先用 Redisson，一致性优先用 ZK
- 核心问题：死锁（过期时间）、误删（Lua+唯一标识）、续期（看门狗）
