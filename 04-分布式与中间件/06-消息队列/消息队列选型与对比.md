# 消息队列选型与对比

> 消息队列是分布式系统的核心基础设施，用于解耦、异步、削峰。不同MQ在吞吐量、延迟、可靠性、功能特性上差异巨大，选错MQ会导致架构瓶颈。本文从多维度对比主流MQ，提供选型决策框架。
>
> **核心维度**：吞吐量、延迟、可靠性、消息模型、运维复杂度、生态成熟度。

---

## 一、概述：消息队列的作用

### 1.1 三大核心作用

| 作用 | 说明 | 典型场景 |
|------|------|---------|
| 解耦 | 生产者和消费者无需知道对方存在 | 订单创建后通知库存、物流、积分系统 |
| 异步 | 非核心逻辑异步处理，减少响应时间 | 注册后异步发送邮件、短信 |
| 削峰 | 高峰期请求暂存队列，消费者按能力消费 | 秒杀、大促流量洪峰 |

### 1.2 主流MQ概览

```text
消息队列
├── 高吞吐日志型
│   ├── Kafka      — 大数据/日志/流处理标准
│   └── Pulsar     — 云原生、存算分离、多租户
├── 传统企业级
│   ├── RabbitMQ   — 功能丰富、路由灵活、低延迟
│   └── ActiveMQ   — 老牌、JMS标准、逐渐没落
├── 金融级可靠
│   └── RocketMQ   — 阿里开源、事务消息、顺序消息
└── 轻量级/云原生
    ├── Redis Stream — 轻量、简单场景
    └── NATS         — 云原生、超轻量、边缘计算
```

## 二、底层原理：核心架构对比

### 2.1 架构模型对比

| MQ | 架构模型 | 存储方式 | 消费模型 |
|----|---------|---------|---------|
| Kafka | 分布式分区日志 | 顺序写磁盘（Partition） | 拉模式（Pull），消费者组 |
| RabbitMQ | Broker+Exchange | 内存/磁盘（Queue） | 推模式（Push），智能Broker |
| RocketMQ | NameServer+Broker | CommitLog（顺序写） | 拉模式，消费者组 |
| Pulsar | Broker+BookKeeper | 存算分离（Bookie存储） | 拉模式，消费者组 |

### 2.2 消息可靠性对比

```text
可靠性等级（从低到高）：
At most once  — 最多一次（可能丢失，不重复）
At least once — 至少一次（不丢失，可能重复）← 大多数MQ默认
Exactly once  — 精确一次（不丢失，不重复）← Kafka事务/Pulsar

消息确认机制：
Kafka:   消费者手动提交offset（commit offset）
RabbitMQ: ACK机制（手动/自动）
RocketMQ: 消费者ACK，失败重试+死信队列
```

## 三、实操：多维度详细对比

### 3.1 性能对比

| 维度 | Kafka | RabbitMQ | RocketMQ | Pulsar |
|------|-------|----------|----------|--------|
| 单机吞吐量 | 10万+ TPS | 1万~3万 TPS | 10万+ TPS | 10万+ TPS |
| 端到端延迟 | ms级（批量） | us级（低延迟） | ms级 | ms级 |
| 消息堆积能力 | 百万~亿级（磁盘） | 万级（内存敏感） | 亿级（磁盘） | 亿级（磁盘） |
| 单机连接数 | 数千 | 数千~万 | 数千 | 数千 |

### 3.2 功能特性对比

| 特性 | Kafka | RabbitMQ | RocketMQ | Pulsar |
|------|-------|----------|----------|--------|
| 消息顺序 | 分区内有序 | 单队列有序 | 队列有序 | 分区有序 |
| 延迟消息 | 不原生支持 | 插件支持 | 原生支持（18级） | 原生支持 |
| 事务消息 | 支持（0.11+） | 不支持 | 原生支持（半消息） | 支持 |
| 死信队列 | 需自行实现 | 原生支持 | 原生支持 | 原生支持 |
| 消息回溯 | 支持（offset重置） | 不支持 | 支持（按时间） | 支持 |
| 消息过滤 | 客户端过滤 | Broker路由过滤 | Broker+Tag过滤 | 原生支持 |
| 多租户 | 不原生 | vhost隔离 | 不原生 | 原生（多租户） |
| 流处理 | Kafka Streams | 无 | 无 | Pulsar Functions |

### 3.3 运维与生态对比

| 维度 | Kafka | RabbitMQ | RocketMQ | Pulsar |
|------|-------|----------|----------|--------|
| 运维复杂度 | 高（ZK/KRaft） | 低 | 中 | 高（BookKeeper） |
| 监控生态 | 完善（JMX/Prometheus） | 完善（管理界面） | 中（Dashboard） | 中 |
| 客户端语言 | 全语言 | 全语言 | Java为主 | 全语言 |
| 社区活跃度 | 极高 | 高 | 中（国内高） | 中（增长快） |
| 文档质量 | 优秀 | 优秀 | 良好 | 良好 |
| 商业支持 | Confluent | VMware | 阿里云 | StreamNative |

### 3.4 适用场景推荐

| 场景 | 推荐MQ | 理由 |
|------|--------|------|
| 日志收集/大数据管道 | Kafka | 高吞吐、生态完善、与大数据栈集成 |
| 业务系统解耦/异步 | RabbitMQ | 功能丰富、路由灵活、低延迟、易运维 |
| 电商/金融交易 | RocketMQ | 事务消息、顺序消息、高可靠、阿里验证 |
| 云原生/多租户/SaaS | Pulsar | 存算分离、多租户、弹性扩展、Geo复制 |
| 简单异步/轻量场景 | Redis Stream | 无需额外组件、简单够用 |
| IoT/边缘计算 | NATS | 超轻量、低延迟、边缘友好 |
| 流处理/实时计算 | Kafka | Kafka Streams/Flink集成标准 |

## 四、常见问题与排查

### 4.1 消息丢失排查

```text
消息丢失可能发生在三个环节：
1. 生产者 → Broker：网络抖动、Broker宕机
   解决：生产者确认机制（acks=all / publisher confirm）
         重试机制 + 本地消息表

2. Broker内部：刷盘前宕机、副本不同步
   解决：同步刷盘（flush）+ 多副本（replication≥3）
         最小同步副本数（min.insync.replicas≥2）

3. Broker → 消费者：消费者宕机未处理
   解决：手动ACK（处理完成后再确认）
         幂等消费（防止重复消费副作用）
```

### 4.2 消息重复消费

**原因**：网络重传、消费者Rebalance、ACK超时重试。

**解决**：幂等设计
```text
1. 唯一消息ID + 去重表（Redis/DB）
2. 数据库唯一约束（如订单号唯一索引）
3. 状态机控制（订单状态只能从待支付→已支付）
4. 乐观锁（UPDATE ... WHERE version = ?）
```

### 4.3 消息堆积

| 原因 | 解决 |
|------|------|
| 消费者处理慢 | 优化消费逻辑、增加消费者实例、批量消费 |
| 分区/队列数不足 | 增加分区数（Kafka）、增加队列数 |
| 下游服务故障 | 熔断降级、临时扩容消费者 |
| 消息量突增 | 弹性伸缩消费者、限流生产者 |

### 4.4 选型决策树

```text
需要消息队列？
├── 已有Redis且场景简单？→ Redis Stream
├── 大数据/日志/流处理？→ Kafka
├── 金融/电商/事务消息？→ RocketMQ
├── 云原生/SaaS/多租户？→ Pulsar
├── 业务解耦/低延迟/功能丰富？→ RabbitMQ
└── IoT/边缘/超轻量？→ NATS
```

## 五、进阶与最佳实践

### 5.1 生产环境配置建议

**Kafka**：
```text
broker配置：
- num.partitions=3（至少3分区）
- default.replication.factor=3
- min.insync.replicas=2
- log.retention.hours=168（7天）
- log.segment.bytes=1GB

生产者：
- acks=all
- retries=3
- enable.idempotence=true
- batch.size=16384
- linger.ms=5

消费者：
- enable.auto.commit=false（手动提交）
- max.poll.records=500
- session.timeout.ms=30000
```

**RabbitMQ**：
```text
- 队列持久化（durable=true）
- 消息持久化（delivery_mode=2）
- 手动ACK（auto_ack=false）
- 消费者预取数（prefetch_count=10）
- 镜像队列（ha-mode=all）
- 死信交换机（DLX）
```

### 5.2 最佳实践清单

- [ ] 消息体控制在1MB以内（大消息用对象存储+消息传URL）
- [ ] 生产者使用确认机制，确保消息到达Broker
- [ ] 消费者手动ACK，处理完成后再确认
- [ ] 消费逻辑幂等，防止重复消费
- [ ] 配置死信队列，处理消费失败的消息
- [ ] 监控堆积量、消费延迟、错误率
- [ ] 消息设置过期时间（TTL），防止无限堆积
- [ ] 关键消息使用本地消息表+定时补偿
- [ ] 消费者组命名规范，避免Rebalance混乱
- [ ] 分区/队列数规划预留30%余量
- [ ] 定期清理过期消息，释放磁盘空间
