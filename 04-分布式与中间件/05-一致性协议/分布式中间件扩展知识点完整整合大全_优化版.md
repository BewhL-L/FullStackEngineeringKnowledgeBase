## 一、Elasticsearch 搜索与分析

### 1.1 概述
ES 是基于 Lucene 的分布式搜索引擎，擅长全文检索、日志分析与聚合。核心概念：索引(Index) → 类型(已废弃) → 文档(Doc) → 分片(Shard)。

<div style="background:linear-gradient(135deg,#13c2c2,#36cfc9);color:#fff;padding:14px 18px;border-radius:10px;margin:12px 0;">
<b>倒排索引</b>：Term → 文档ID 列表，使「包含某词」的查询从 O(N) 降为 O(1) 查表。
</div>

### 1.2 常用用法
```json
// 创建索引并写入
PUT /blog
{ "mappings": { "properties": {
    "title": { "type": "text", "analyzer": "ik_max_word" },
    "ts": { "type": "date" } } } }

POST /blog/_doc
{ "title": "分布式系统设计", "ts": "2026-08-25" }

// 查询 + 高亮
GET /blog/_search
{ "query": { "match": { "title": "分布式" } },
  "highlight": { "fields": { "title": {} } } }
```

| 场景 | 做法 | 坑 |
|------|------|----|
| 深分页 | `search_after` | `from+size` 超 1w 易 OOM |
| 中文分词 | `ik_max_word` | 默认 standard 按字切 |
| 写入密集 | 批量 `bulk` | 单条写入吞吐极低 |

### 1.3 注意事项
💡 **深度讲解**：`from+size` 深翻页要在协调节点收集 `(from+size)×分片数` 条结果再截断，深度越大越慢；用 `search_after` + 业务游标替代。

📝 **精简总结**：中文必装 IK 分词；深翻页用 `search_after`；写入走 `bulk`；监控堆内存避免 `fielddata` 爆炸。

🔍 **知识点深度解析**
- **作用**：海量文档近实时检索。
- **原理**：倒排索引 + 分段(Segment)不可变 + 刷新(refresh)可见。
- **用法要点**：冷热架构降成本；避免 wildcard 前缀通配拖垮集群。

## 二、RabbitMQ 消息队列

### 2.1 概述
RabbitMQ 是 AMQP 协议实现，以「交换机 Exchange → 队列 Queue → 绑定 Binding」路由模型见长，适合复杂路由与可靠投递。

### 2.2 常用用法
```python
import pika
conn = pika.BlockingConnection(pika.ConnectionParameters("localhost"))
ch = conn.channel()
ch.exchange_declare(exchange="logs", exchange_type="fanout")
ch.queue_declare(queue="q1", durable=True)
ch.basic_publish(exchange="logs", routing_key="",
                 body="hi", properties=pika.BasicProperties(delivery_mode=2))
# 手动 ACK + 限流
ch.basic_qos(prefetch_count=1)
ch.basic_consume(queue="q1", on_message_callback=cb, auto_ack=False)
```

| 交换机 | 路由语义 | 典型场景 |
|--------|----------|----------|
| direct | 精确 routing_key | 点对点任务 |
| topic | 通配 `#` `*` | 按业务分级 |
| fanout | 广播 | 日志扩散 |
| headers | 头部匹配 | 少用 |

### 2.3 注意事项
💡 **深度讲解**：`auto_ack=False` + 手动 `basic_ack` 才能保「至少一次」；配合消费幂等（去重表）解决重复投递。

📝 **精简总结**：队列 `durable` + 消息 `delivery_mode=2` 防重启丢；消费端手动 ACK 与幂等；死信队列(DLX)承接失败消息做重试/告警。

🔍 **知识点深度解析**
- **作用**：解耦 + 异步 + 削峰。
- **原理**：Broker 持久化 + 确认机制。
- **用法要点**：`prefetch_count` 防消费端被压垮；死信Exchange处理异常。

## 三、Kafka 高吞吐流平台

### 3.1 概述
Kafka 以「分区 Partition + 顺序写 + 零拷贝」实现百万级 TPS，适合日志流、事件溯源、流计算。

### 3.2 常用用法
```java
// 生产者
props.put("acks", "all");          // 全 ISR 确认
props.put("enable.idnempotence", true);
// 消费组再均衡监听
consumer.subscribe(List.of("topic"), new ConsumerRebalanceListener(){...});
// 手动提交位移防丢失
consumer.commitSync();
```

| 概念 | 说明 | 调优 |
|------|------|------|
| Partition | 并行度单位 | 按吞吐设 3~12 |
| ISR | 同步副本集 | `acks=all` 保不丢 |
| Consumer Group | 分摊消费 | 实例数≤分区数 |

### 3.3 注意事项
💡 **深度讲解**：消费滞后(Lag) = `最新位移 - 已提交位移`。Lag 持续上涨说明消费速度 < 生产速度，需加分区或消费实例。

📝 **精简总结**：`acks=all` + 幂等生产者防丢防重；监控 Lag；消费逻辑幂等；避免「消费后再提交」导致重投时重复处理。

🔍 **知识点深度解析**
- **作用**：高吞吐事件管道。
- **原理**：分区顺序追加 + 页缓存 + sendfile 零拷贝。
- **用法要点**：分区数是并行上限，前期规划好；Exactly-Once 依赖事务+幂等。

## 四、分布式 ID 生成

### 4.1 概述
分布式下需全局唯一、趋势递增、高性能的 ID。弃用单库自增（分库冲突）。

### 4.2 常用用法
```java
// 雪花算法 Snowflake: 41bit时间戳 | 10bit机器 | 12bit序列
long id = (timestamp << 22) | (workerId << 12) | sequence;
// 号段模式：一次取 1000 个本地发，降低 DB 压力
UPDATE id_segment SET max=max+1000 WHERE biz='order';
```

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 无中心 | 无序、索引碎片 |
| Snowflake | 趋势递增、本地生成 | 时钟回拨 |
| 号段 | 性能好 | 依赖 DB/Redis |
| Redis INCR | 简单 | 持久化注意 |

### 4.3 注意事项
💡 **深度讲解**：雪花算法时钟回拨会让 ID 可能重复——需「等待时钟追平」或「回拨报警 + 借用扩展位」兜底。

📝 **精简总结**：内部用 Snowflake/号段；对外暴露用 UUID 防遍历；时钟回拨是雪花第一风险点。

🔍 **知识点深度解析**
- **作用**：跨节点唯一标识。
- **原理**：时间戳占位保证趋势递增，机器位保证不冲突。
- **用法要点**：workerId 用 ZK/Redis 分配，避免硬编码冲突。

## 五、分布式锁

### 5.1 概述
跨进程互斥，保护共享资源（如抢券、防重提交）。Redis `SET NX` 是主流轻量方案。

### 5.2 常用用法
```java
// Redis 原子加锁（带唯一值+过期，防误删他人锁）
String val = UUID.randomUUID().toString();
Boolean ok = redis.set(key, val, "NX", "EX", 30);
// 释放用 Lua 保证「只删自己的」
if (val.equals(redis.get(key))) redis.del(key);   // 伪代码，应用 Lua
// Redisson 看门狗自动续期
RLock lock = redisson.getLock("order:"+id);
lock.lock();   // 默认 30s，看门狗每 10s 续期
```

| 方案 | 可靠性 | 场景 |
|------|--------|------|
| Redis SET NX | 高（需正确处理过期） | 大多数业务锁 |
| Redlock | 争议中 | 强一致要求慎用 |
| ZooKeeper | 强一致 | 选主、配置 |

### 5.3 注意事项
💡 **深度讲解**：「设置过期时间」与「加锁」必须原子（一条 `SET NX EX`），否则进程在设置过期前崩溃会留死锁。释放必须用 Lua 校验 value，防止删掉他人持有的锁。

📝 **精简总结**：锁必设过期；释放校验持有者；用 Redisson 看门狗解决「业务未跑完锁已过期」；锁粒度越小竞争越少。

🔍 **知识点深度解析**
- **作用**：跨节点临界区保护。
- **原理**：Redis 单线程使 `SET NX` 原子。
- **用法要点**：红锁(Redlock)在网损下并非绝对安全，Martin Kleppmann 有专文质疑；常规业务 Redis 锁足够。

## 六、限流与熔断

### 6.1 概述
限流保护系统不被突发流量冲垮；熔断在依赖故障时快速失败，避免雪崩。

### 6.2 常用用法
```java
// 令牌桶（Guava RateLimiter）
RateLimiter rl = RateLimiter.create(100);   // 100 QPS
if (rl.tryAcquire()) { handle(); } else { reject(); }

// Sentinel 规则
FlowRule rule = new FlowRule("resA").setCount(100).setGrade(RuleConstant.FLOW_GRADE_QPS);
// 熔断：慢调用比例 > 50% 且 5s 内 10 次则打开
DegradeRule dr = new DegradeRule("resB").setStatIntervalMs(5000);
```

| 算法 | 特点 | 适用 |
|------|------|------|
| 令牌桶 | 允许突发 | 一般接口 |
| 漏桶 | 严格平滑 | 需整形 |
| 滑动窗口 | 精确计数 | 限 QPS |
| 计数器 | 简单 | 粗粒度 |

### 6.3 注意事项
💡 **深度讲解**：熔断三态（关闭→打开→半开）。打开后放少量请求探活，成功则恢复，失败则继续打开——给依赖「喘息」时间。

📝 **精简总结**：入口限流 + 依赖熔断双保险；限流算法按「是否允许突发」选型；熔断阈值结合 RT 与错误率。

🔍 **知识点深度解析**
- **作用**：系统稳定性兜底。
- **原理**：限流控制入量；熔断切断故障传播链。
- **用法要点**：限流值需压测得出，拍脑袋易误伤；熔断半开探活防震荡。

## 七、Service Mesh（Istio）

### 7.1 概述
把通信、重试、mTLS、观测等「基础设施能力」从业务代码下沉到 Sidecar 代理（Envoy），业务只管业务逻辑。

### 7.2 常用用法
```yaml
# VirtualService 灰度 90% v1 / 10% v2
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  hosts: ["svc"]
  http:
  - route:
    - destination: { host: svc, subset: v1 }
      weight: 90
    - destination: { host: svc, subset: v2 }
      weight: 10
```

| 能力 | 归属 | 价值 |
|------|------|------|
| mTLS | Sidecar | 零改代码加密 |
| 重试/超时 | Sidecar | 弹性内建 |
| 流量切分 | VS | 灰度/金丝雀 |
| 指标 | Mixer/Telemetry | 全链路观测 |

### 7.3 注意事项
💡 **深度讲解**：Mesh 增加一跳网络延迟（Sidecar 拦截），但与「业务零侵入 + 统一治理」收益相比通常可接受；运维复杂度上升是主要代价。

📝 **精简总结**：Mesh 适合多语言微服务统一治理；小团队先用网关+SDK；mTLS/灰度/重试由 Sidecar 统一接管。

🔍 **知识点深度解析**
- **作用**：通信治理与业务解耦。
- **原理**：iptables 透明拦截流量进 Sidecar。
- **用法要点**：先上 mTLS + 观测，灰度次之；控制平面用 Istiod。

## 八、一致性协议简述（Raft / Paxos）

### 8.1 概述
分布式共识让多个节点对「某值」达成一致，是 etcd/ZooKeeper/副本选主的基础。Raft 以「易理解」取代 Paxos 的晦涩。

### 8.2 常用用法
```text
Raft 三角色：Leader / Follower / Candidate
任期 Term 单调递增；选举超时随机防分裂投票
日志复制：Leader 追加 → 多数派确认 → 提交
```

| 协议 | 易用性 | 应用 |
|------|--------|------|
| Raft | 高（有现成库） | etcd、Consul、TiKV |
| Paxos | 低（理论完备） | 早期 Chubby |
| ZAB | 中 | ZooKeeper |

### 8.3 注意事项
💡 **深度讲解**：Raft 将「共识」拆为「领导选举 + 日志复制 + 安全性」三子问题，比 single-decree Paxos 更易工程落地；多数派（N/2+1）是容错下限。

📝 **精简总结**：工程优先 Raft（etcd 等）；理解「多数派即安全」；选主期间不可写，需客户端重试。

🔍 **知识点深度解析**
- **作用**：多副本状态一致。
- **原理**：日志全序复制 + 任期权威。
- **用法要点**：节点数取奇数（3/5）以容忍 1/2 故障且多数派唯一。
