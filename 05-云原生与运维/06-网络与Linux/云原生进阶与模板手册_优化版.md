## 一、渐进式交付：Argo Rollouts

### 1.1 模板（金丝雀）
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: web }
spec:
  strategy:
    canary:
      steps:
      - setWeight: 10
      - pause: { duration: 5m }      # 观察 5 分钟
      - setWeight: 50
      - pause: { duration: 5m }
      - setWeight: 100
  template:
    spec:
      containers:
      - name: web
        image: web:1.0.0
```

### 1.2 要点
💡 **深度讲解**：渐进交付把「全量发布」变「小流量验证 + 自动暂停 + 异常回滚」，是降低线上事故率的利器；与 Prometheus 指标联动可做自动分析。
📝 **精简总结**：用 Rollout 替代 Deployment；金丝雀分步 + 暂停观察；接分析器自动判稳；失败一键 rollback。
🔍 **知识点深度解析**：作用=安全发布；原理=流量比例切换；要点=指标驱动 + 快速回滚。

## 二、多集群管理

### 2.1 做法
| 模式 | 说明 | 工具 |
|------|------|------|
| 主从 | 中心管控多子集群 | Karmada / OCM |
| 联邦 | 资源跨集群分发 | KubeFed |
| 多活 | 地域级容灾 | 服务网格 + GSLB |

💡 **深度讲解**：多集群解决「单集群爆炸半径 + 区域容灾」。核心挑战是「身份/网络/策略」跨集群一致，需用联邦控制面统一。
📝 **精简总结**：按容灾/隔离需求选型；用 Karmada 做分发；网络用 Submariner/Cilium 互联；统一镜像与策略源。
🔍 **知识点深度解析**：作用=高可用 + 隔离；原理=控制面联邦；要点=一致身份与网络。

## 三、FinOps 成本优化

### 3.1 杠杆
| 杠杆 | 做法 | 收益 |
|------|------|------|
| 右-sizing | 按实际用量调 request/limit | 降 20~40% |
| Spot/抢占 | 无状态批处理用抢占实例 | 降 60~90% |
| 定时缩容 | 非工作时段 HPA=0 | 降闲置 |
| 闲置清理 | 回收孤儿资源 | 降浪费 |

💡 **深度讲解**：FinOps = 工程 + 财务协同。「显示每服务的单位成本」让团队为用量负责；右-sizing 与 Spot 是最大两块红利。
📝 **精简总结**：先可见(成本按标签分摊)再优化；右-sizing + 抢占实例 + 定时缩容；设预算告警防失控。
🔍 **知识点深度解析**：作用=降本；原理=用量归因；要点=标签化 + 持续治理。

## 四、混沌工程（Chaos）

### 4.1 做法
```yaml
# Chaos Mesh 注入 Pod 故障
kubectl apply -f - <<EOF
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: { name: kill-web }
spec:
  action: pod-kill
  mode: one
  selector: { labelSelectors: { app: web } }
  scheduler: { cron: "@every 10m" }
EOF
```

💡 **深度讲解**：混沌工程主动注入故障（杀 Pod/断网/延时），验证系统「在乱中仍可用」。前提是「有监控 + 有自动恢复」，否则变真事故。
📝 **精简总结**：先建稳态指标再注入；从小爆炸半径开始；配合自动恢复与告警；形成「演练→发现→加固」闭环。
🔍 **知识点深度解析**：作用=暴露隐性脆弱；原理=故障注入 + 稳态验证；要点=可控 + 可恢复。

## 五、架构决策记录 ADR

### 5.1 模板
```markdown
# ADR-001 选用 PostgreSQL 而非 MySQL
## 状态：已采纳
## 背景：需要 JSONB + 全文检索 + 向量(pgvector)
## 决策：采用 PostgreSQL 16
## 后果：+ 原生 JSONB/向量；- 团队需补 PG 运维经验
```

💡 **深度讲解**：ADR 把「为什么这样选」固化下来，避免新人反复追问或无意推翻历史决策。轻量、不可删(只追加「废弃/替代」)。
📝 **精简总结**：重大决策必写 ADR；含状态/背景/决策/后果；只追加不修改；入库随代码评审。
🔍 **知识点深度解析**：作用=决策可追溯；原理=文档即记忆；要点=轻量 + 评审入库。

## 六、SLO / SLI 可观测性实践

### 6.1 定义
| 概念 | 含义 | 示例 |
|------|------|------|
| SLI | 实际指标 | 成功率 99.5% |
| SLO | 目标 | 月可用 99.9% |
| 错误预算 | 容错额度 | 0.1%  downtime |

💡 **深度讲解**：SLO 把「可靠性」变成可谈判的数字。错误预算耗尽则冻结新功能、先修稳定性——是研发与 SRE 的共同语言。
📝 **精简总结**：先定用户关心的 SLI；设可达 SLO；用错误预算治理节奏；告警接burn-rate 而非单次。
🔍 **知识点深度解析**：作用=可靠性治理；原理=指标 + 预算；要点=用户导向 + 预算驱动。
