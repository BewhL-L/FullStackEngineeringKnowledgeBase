## 1. 关系型数据库总览与选型

### 1.1 概述

关系型数据库以表、行、SQL 和 ACID 事务为核心。主流：MySQL（Web 主流）、PostgreSQL（功能强/可扩展）、Oracle（企业）、SQL Server。选型看事务强度、复杂查询、生态与成本。

> 🔍 **知识点深度解析**
>
> **作用**：选型决定后续架构上限——事务型用 MySQL/PG，分析型用列存（ClickHouse），文档灵活用 MongoDB。
>
> **原理**：关系模型用二维表 + 外键约束保证结构一致；ACID 由日志（redo/undo）与锁实现；MVCC 让读写不互斥。NoSQL 放宽约束换扩展与性能。
>
> **用法要点**：① 强一致事务用关系型；② 半结构/高写入用文档/列族；③ 缓存用 Redis 不替代库；④ PG 适合 JSON/地理/复杂查询；⑤ 分析用 OLAP 列存。

### 1.2 核心特性

**SQL 标准**：DDL/DML/DCL，JOIN、窗口函数、CTE。

**事务 ACID**：原子/一致/隔离/持久。

**索引**：B+树（关系型默认）、哈希、倒排（ES）。

**对比**：MySQL 易用生态广；PG 标准合规+扩展强；OceanBase/TiDB 分布式。

> 🔍 **知识点深度解析**
>
> **作用**：懂特性才能合理设计表、索引与事务边界。
>
> **原理**：B+树叶链表利于范围扫描，是关系型索引主流；MVCC 靠 undo 版本链+ReadView 实现快照读；窗口函数（ROW_NUMBER/RANK）在不聚合下做排名。
>
> **用法要点**：① 高频范围/排序建 B+树索引；② 事务边界尽量小；③ 复杂分析用 CTE 提升可读；④ 分布式库看分片键设计；⑤ 读写分离走从库。

### 1.3 常用用法

```sql
-- 窗口函数：按部门排名
SELECT dept, name, salary,
       RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rk
FROM emp;

-- CTE 公用表表达式
WITH dept_avg AS (
  SELECT dept, AVG(salary) a FROM emp GROUP BY dept
)
SELECT e.* FROM emp e JOIN dept_avg d ON e.dept=d.dept WHERE e.salary > d.a;
```

> 🔍 **知识点深度解析**
>
> **作用**：窗口函数与 CTE 是复杂分析利器，避免自连接与子查询地狱。
>
> **原理**：`OVER (PARTITION BY ... ORDER BY ...)` 在分组内排序但不折叠行；CTE 把子查询命名化，可读且可复用。
>
> **用法要点**：① 排名/累计/同比用窗口函数；② CTE 提升可读性（PG 还支持递归 CTE）；③ 大数据量注意窗口函数内存；④ 配合索引加速 PARTITION 内排序。

### 1.4 注意事项

1. **选型错配**：用 Redis 存强一致数据、用 MySQL 做实时分析都错位
2. **事务过大**：长事务持锁致主从延迟与死锁
3. **索引滥用**：多索引拖慢写入、占空间
4. **字符集**：统一 utf8mb4，避免乱码
5. **连接池**：应用连接数受数据库 max_connections 约束

> 💡 **深度讲解**：数据库选型是架构第一步。强一致、复杂关系、事务优先关系型（MySQL/PG）；高写入半结构用 MongoDB；海量分析用 ClickHouse 等列存；缓存用 Redis（不是数据库）。关系型里 MySQL 胜在生态与易用，PG 胜在标准合规与扩展（JSONB/PostGIS/自定义类型）。索引默认 B+树（范围友好），事务靠 ACID+MVCC。最大坑：事务过大（持锁长、主从延迟）、索引滥用（拖写入）、字符集不一致（乱码）。理解"什么数据该放哪"比会写 SQL 更重要。

> 📝 **精简总结**：选型=事务型(MySQL/PG)/文档(MongoDB)/列存分析(ClickHouse)/缓存(Redis)；特性=SQL+ACID+B+树索引+MVCC；高级=窗口函数/CTE；注意=选型错配/大事务/索引滥用/字符集/连接池。

## 2. MySQL 核心

### 2.1 概述

MySQL 最流行开源关系库，InnoDB 默认引擎（事务/行锁/外键/MVCC）。核心是索引（B+树）、事务隔离、锁、执行计划（EXPLAIN）。

> 🔍 **知识点深度解析**
>
> **作用**：MySQL 是后端面试与实战核心，索引与事务是性能与正确性的命脉。
>
> **原理**：InnoDB 聚簇索引叶子存整行，二级索引叶子存主键（回表）；MVCC 用 undo 版本链+ReadView 实现 RR 可重复读；redo log 保证持久，binlog 用于复制与恢复。
>
> **用法要点**：① 主键自增 BIGINT；② 字符集 utf8mb4；③ 金额 DECIMAL；④ 用 EXPLAIN 看 type/key/rows/Extra；⑤ 默认 RR，一般不需要改。

### 2.2 核心特性

**索引**：聚簇/二级/覆盖索引、最左前缀、索引下推（ICP）。

**事务**：4 隔离级别，RR 默认（MVCC+间隙锁防幻读）。

**锁**：行锁、间隙锁、临键锁、意向锁。

**优化**：EXPLAIN、慢查询日志、索引设计。

> 🔍 **知识点深度解析**
>
> **作用**：索引让查从 O(n) 到 O(log n)；隔离级别平衡一致与并发；锁防并发错。
>
> **原理**：联合索引 (a,b,c) 遵循最左前缀，等值在前范围在后；覆盖索引查询字段都在索引免回表；间隙锁锁索引间隙防幻读；临键锁=行锁+间隙锁（左开右闭）。
>
> **用法要点**：① 高频查建索引，低基数字段不建；② 联合索引顺序按区分度与查询；③ 避免索引失效（函数/隐式转换/前模糊）；④ 死锁固定加锁顺序；⑤ 大事务拆小。

### 2.3 常用用法

```sql
-- 覆盖索引 + 最左前缀
CREATE INDEX idx_status_ctime ON `order`(status, create_time);
SELECT id, status FROM `order` WHERE status=1 ORDER BY create_time DESC LIMIT 10;  -- 覆盖+有序

-- 查看执行计划
EXPLAIN SELECT * FROM user WHERE username='tom';
-- 关注 type(至少 range)、key(实际索引)、rows(扫描行)、Extra(Using index/ filesort)
```

```sql
-- 深分页优化（延迟关联）
SELECT * FROM user WHERE id > (SELECT id FROM user ORDER BY id LIMIT 1000000,1) LIMIT 10;
```

> 🔍 **知识点深度解析**
>
> **作用**：覆盖索引避免回表、延迟关联解决深分页性能悬崖。
>
> **原理**：`idx_status_ctime` 让 WHERE+ORDER BY 都用索引且覆盖查询列；深分页 `LIMIT 1000000,10` 扫 100 万行，子查询先取 id 再回表仅 10 行。
>
> **用法要点**：① 只查必要的列争取覆盖；② ORDER BY 字段进索引免 filesort；③ 深分页用游标（WHERE id>lastId）或延迟关联；④ 定期 EXPLAIN 审计慢 SQL。

### 2.4 注意事项

1. **索引失效**：函数/隐式转换/like '%x'/OR 非索引 → 全表扫描
2. **SELECT ***：增 IO、破坏覆盖、占内存
3. **大事务**：持锁长，死锁与主从延迟风险
4. **utf8 非 utf8mb4**：emoji 乱码
5. **主从延迟**：读写分离下强一致读走主库

> 💡 **深度讲解**：MySQL 性能三板斧——索引、SQL、表结构。索引是 B+树，聚簇索引决定行物理序，二级索引靠主键回表（覆盖索引可免）。事务靠 redo（持久）+undo（回滚/MVCC），RR 默认靠 MVCC+间隙锁防幻读。排查慢查询：开 slow_query_log，用 EXPLAIN 看 type（ALL 全表要优化）、key、rows、Extra（Using filesort/temporary 要优化）。深分页、索引失效、大事务是三大常见坑。读写分离要正视主从延迟——强一致读必须走主库。

> 📝 **精简总结**：MySQL=InnoDB(B+树/MVCC/行锁)；索引=聚簇/二级/覆盖+最左前缀；事务=ACID+RR默认；优化=EXPLAIN/覆盖索引/深分页延迟关联；注意=索引失效/SELECT*/大事务/主从延迟。

## 3. Redis 核心

### 3.1 概述

Redis 内存 KV 数据库，10万+ QPS，结构丰富（String/Hash/List/Set/ZSet+Bitmap/HLL/Geo/Stream），支持持久化（RDB/AOF）与高可用（主从/哨兵/Cluster）。缓存是首要用途。

> 🔍 **知识点深度解析**
>
> **作用**：Redis 是缓存/会话/排行榜/分布式锁/消息队列基石，性能极高但"是缓存非数据库"。
>
> **原理**：单线程执行命令（6.0 多线程 IO），内存操作+IO 多路复用；底层编码自动优化（小 ziplist、大 hashtable/skiplist）；过期用惰性+定期删除；淘汰用 LRU/LFU。
>
> **用法要点**：① 缓存用 allkeys-lru/lfu；② 对象用 Hash（字段可改）；③ 排行榜 ZSet；④ 锁用 Redisson（看门狗续期）；⑤ 三大问题：穿透（布隆+空值）/击穿（锁+逻辑过期）/雪崩（TTL 随机）。

### 3.2 核心特性

**结构**：String（计数/锁）、Hash（对象）、List（队列）、Set（去重）、ZSet（排序）、Stream（消息）。

**持久化**：RDB（快、丢数据）、AOF（安全、大）、混合。

**高可用**：主从（读写分离）、哨兵（故障转移）、Cluster（16384 槽分片）。

> 🔍 **知识点深度解析**
>
> **作用**：丰富结构让 Redis 不止缓存；持久化保重启数据；高可用保服务不中断。
>
> **原理**：Cluster 把 key 哈希到 16384 槽（`CRC16(key)%16383`），槽分给主节点，MOVED 重定向；哨兵 quorum 判定客观下线选从提升；AOF everysec 最多丢 1 秒。
>
> **用法要点**：① 中小用哨兵，大规模用 Cluster；② Cluster 多键用 Hash Tag 同槽；③ 不用大 key/热 key（分片/本地缓存）；④ 不用 KEYS *（用 SCAN）；⑤ 持久化按重要度选。

### 3.3 常用用法

```java
// 缓存三件套：Cache Aside（读）
User u = redis.get("user:"+id);
if (u==null) { u = dao.get(id); if(u!=null) redis.setex("user:"+id, 3600+rand, u); else redis.setex("null:"+id, 60, ""); }
// 写：先更新 DB 再删缓存
dao.update(u); redis.del("user:"+u.id);
```

```bash
# 持久化与高可用配置要点
CONFIG SET maxmemory 2gb
CONFIG SET maxmemory-policy allkeys-lru
```

> 🔍 **知识点深度解析**
>
> **作用**：Cache Aside 是最常用缓存模式；TTL 随机防雪崩，空值短缓存防穿透。
>
> **原理**：读未命中查库并写缓存（TTL 加随机防同时失效雪崩）；查不到写空值短缓存防穿透；写先 DB 后删缓存（避免并发脏数据）。`allkeys-lru` 内存满淘汰最近最少用。
>
> **用法要点**：① 缓存是最终一致，强一致走库；② TTL 必加随机；③ 空值缓存短（60s）；④ 分布式锁用 Redisson 而非裸 SETNX；⑤ 内存上限必设淘汰策略。

### 3.4 注意事项

1. **一致性**：缓存与 DB 有窗口不一致，高一致用延迟双删/binlog
2. **大/热 key**：阻塞删除、单点瓶颈，拆分或本地缓存
3. **KEYS ***：阻塞主线程，用 SCAN
4. **强一致数据**：余额等勿存 Redis
5. **fork 阻塞**：大内存 bgsave fork 耗时，控 maxmemory

> 💡 **深度讲解**：Redis 核心是"内存 + 丰富结构 + 单线程"。单线程避免锁竞争，IO 多路复用支撑高 QPS。三大缓存问题各有解法：穿透（布隆过滤器+缓存空值）、击穿（互斥锁/逻辑过期）、雪崩（TTL 随机+高可用）。持久化用 AOF everysec（最多丢 1 秒）+ RDB 备份；高可用中小哨兵、大规模 Cluster（16384 槽）。分布式锁用 Redisson（可重入+看门狗续期）而非裸 SETNX。铁律：Redis 是缓存不是数据库，不存强一致数据，不用大/热 key，不用 KEYS *。

> 📝 **精简总结**：Redis=内存KV(单线程高QPS)；结构=String/Hash/List/Set/ZSet+Stream；持久化=RDB+AOF+混合；高可用=主从/哨兵/Cluster(16384槽)；缓存=Cache Aside+穿透/击穿/雪崩；锁=Redisson；注意=一致性/大热key/不用KEYS*/非强一致。

## 4. MongoDB 文档数据库

### 4.1 概述

MongoDB 文档型 NoSQL，存 BSON（类 JSON），模式灵活，水平扩展易（分片）。适合半结构数据、内容管理、日志、物联网。

> 🔍 **知识点深度解析**
>
> **作用**：当结构易变、写入高、关系弱时，MongoDB 比关系型更灵活高效。
>
> **原理**：文档聚合同条记录相关字段（减少 JOIN），_id 为主键（默认 ObjectId）；WiredTiger 存储引擎用 B+树索引；副本集（一主多从）保高可用，分片（shard key）水平扩展。
>
> **用法要点**：① 嵌入式 vs 引用（一对少用嵌入）；② 高频查建索引；③ 用副本集保可用；④ 大数据量用分片（选好 shard key）；⑤ 事务（4.0+多文档）谨慎用。

### 4.2 核心特性

**数据模型**：文档/集合、嵌套、数组、GridFS（大文件）。

**索引**：单字段、复合、多键（数组）、文本、地理。

**高可用**：副本集（选举）、分片集群。

**聚合**：Aggregation Pipeline（类 Unix 管道）。

> 🔍 **知识点深度解析**
>
> **作用**：聚合管道是 MongoDB 的分析核心；分片解决海量水平扩展。
>
> **原理**：Aggregation Pipeline 多 stage（$match/$group/$sort）流式处理；副本集主节点挂掉后从节点选举新主；分片按 shard key 把数据分布到多 shard，查询路由（mongos）聚合。
>
> **用法要点**：① $match 前置减少数据量；② 分片键选高基散列避免热点；③ 文本索引做全文检索；④ 聚合注意内存上限（allowDiskUse）；⑤ 不用事务替代关系设计。

### 4.3 常用用法

```javascript
// 聚合：按城市统计平均年龄
db.users.aggregate([
  { $match: { age: { $gte: 18 } } },
  { $group: { _id: "$city", avgAge: { $avg: "$age" }, cnt: { $sum: 1 } } },
  { $sort: { cnt: -1 } }
])

// 建索引与查询
db.users.createIndex({ city: 1, age: -1 })
db.users.find({ city: "BJ", age: { $gt: 20 } })
```

> 🔍 **知识点深度解析**
>
> **作用**：聚合管道 `$match→$group→$sort` 等价于 SQL 的 WHERE→GROUP BY→ORDER BY，但更灵活。
>
> **原理**：各 stage 输出作为下一流入；`$group` 按 `_id` 分组聚合；复合索引 `{city:1, age:-1}` 支持等值+范围+排序。
>
> **用法要点**：① $match 尽早过滤；② 索引匹配查询与排序顺序；③ 聚合超内存加 allowDiskUse:true；④ 用 explain() 看执行计划；⑤ 避免全集合扫描。

### 4.4 注意事项

1. **模式设计**：误用嵌入式致文档过大或更新频繁，权衡嵌入/引用
2. **事务成本**：多文档事务有性能与一致限制，尽量靠设计规避
3. **分片键**：选错致热点 shard，扩容困难
4. **内存**：聚合/排序超内存需落盘
5. **一致性**：默认主读可能读从滞后，关注读关注（readConcern）

> 💡 **深度讲解**：MongoDB 的灵活在于"文档即记录"——相干数据嵌入一文档，少 JOIN。但灵活是把双刃剑：嵌入过度会造大文档、引用过度回退到 JOIN。设计准则是"一对少嵌入、一对多引用、多对多中间集合"。高可用靠副本集（自动选举），海量靠分片（shard key 决定分布，选高基散列避免热点）。聚合管道是分析主力，写法类似 Unix 管道。`事务`4.0+ 支持但成本高，能靠模式设计规避就别用。读一致性用 readConcern 控制。

> 📝 **精简总结**：MongoDB=文档(BSON)模式灵活；模型=嵌入(一对少)/引用(一对多)；HA=副本集+分片(shard key)；分析=Aggregation Pipeline；注意=模式设计/事务成本/分片键热点/内存/读关注。

## 5. PostgreSQL 进阶

### 5.1 概述

PostgreSQL 功能强大的开源关系库，标准合规高、扩展性强（JSONB、PostGIS、自定义类型、插件）。适合复杂查询、地理、异构数据、HTAP 边缘。

> 🔍 **知识点深度解析**
>
> **作用**：当业务需要 JSON + 关系混合、地理空间、复杂约束与扩展时，PG 比 MySQL 更顺手。
>
> **原理**：MVCC 实现并发；堆表（无聚簇索引，表按物理顺序）；索引多样（B-tree/GiST/GIN/BRIN）；JSONB 二进制存储支持索引与包含查询；扩展以动态库加载（如 pgvector）。
>
> **用法要点**：① 半结构用 JSONB（可建 GIN 索引）；② 地理用 PostGIS；③ 向量检索用 pgvector；④ 复杂约束/枚举/域类型保质量；⑤ 分区表管大表。

### 5.2 核心特性

**数据类型**：JSONB、数组、范围、UUID、几何、自定义。

**索引**：B-tree、GIN（数组/JSONB）、GiST（全文/地理）、BRIN（有序大表）、部分索引。

**扩展**：PostGIS、pgvector、FDW（外部表）、逻辑复制。

**高级**：CTE（递归）、窗口、物化视图、分区表。

> 🔍 **知识点深度解析**
>
> **作用**：丰富类型是 PG 差异化优势；GIN 索引让 JSONB/数组可高效查。
>
> **原理**：GIN（Generalized Inverted Index）适合多值/复合（数组元素、JSONB 键）倒排；GiST 适合地理/全文；BRIN 对按序大表极省空间（仅存块范围）；部分索引只对满足谓词的行建索引。
>
> **用法要点**：① JSONB 配 GIN 索引做包含查询；② 大时序表用 BRIN+分区；③ 物化视图缓存聚合结果（需刷新）；④ 递归 CTE 处理树；⑤ FDW 直查外部数据源。

### 5.3 常用用法

```sql
-- JSONB 包含查询 + GIN 索引
CREATE INDEX idx_doc_gin ON docs USING GIN (data jsonb_path_ops);
SELECT * FROM docs WHERE data @> '{"status":"active"}';

-- 向量检索（pgvector）
CREATE EXTENSION vector;
CREATE TABLE items (id serial, emb vector(1536));
CREATE INDEX ON items USING ivfflat (emb vector_cosine_ops) WITH (lists=100);
SELECT id FROM items ORDER BY emb <-> '[...]' LIMIT 5;   -- 最近邻
```

> 🔍 **知识点深度解析**
>
> **作用**：JSONB+GIN 让"关系库里查半结构"高效；pgvector 让 PG 直接做向量检索，省专库。
>
> **原理**：`@>` 是 JSONB 包含运算符，GIN 索引加速；`ivfflat` 是 PG 的 ANN 索引，`<->` 为余弦距离算子，ORDER BY ... LIMIT 取近邻。
>
> **用法要点**：① 混合检索优先 PG+pgvector（省运维）；② GIN 索引体积大但查快；③ ivfflat lists 调精度/速度；④ JSONB 比 JSON 支持索引；⑤ 大向量表注意索引构建资源。

### 5.4 注意事项

1. **膨胀**：MVCC 产生死元组，需定期 VACUUM（autovacuum 调参）
2. **索引多样但体积**：GIN 较大，权衡读写
3. **扩展依赖**：插件需装且与版本匹配
4. **锁**：DDL 可能锁表，大表改结构用 CONCURRENTLY
5. **连接**：进程级连接重，用连接池（PgBouncer）

> 💡 **深度讲解**：PostgreSQL 是"最像标准 SQL 且最可扩展"的开源库。差异化在：JSONB（半结构+索引）、PostGIS（地理）、pgvector（向量，让一个库兼当关系库与向量库）、FDW（跨数据源查询）。索引种类最丰富——GIN 服务数组/JSONB、GiST 服务地理/全文、BRIN 服务按序大表、部分索引瘦身。代价是 MVCC 死元组需 VACUUM（调好 autovacuum），连接是进程级较重需 PgBouncer。结论：需要"关系+JSON+向量+地理"一体、或复杂查询与扩展，选 PG。

> 📝 **精简总结**：PG=强标准+可扩展；类型=JSONB/数组/几何/自定义；索引=GIN(JSONB)/GiST(地理)/BRIN(大表)/部分；扩展=PostGIS/pgvector/FDW；注意=VACUUM膨胀/索引体积/连接池/锁表DDL。

## 6. 向量数据库与语义检索

### 6.1 概述

向量库存 Embedding 并提供 ANN 检索，是 RAG/语义搜索底座。代表：Milvus、Qdrant、Chroma、Weaviate、PgVector（复用 PG）。

> 🔍 **知识点深度解析**
>
> **作用**：语义检索（"找意思像的"）是传统 SQL 做不到的，向量库是 AI 应用基础设施。
>
> **原理**：文本经 Embedding 成高维向量，ANN 索引（HNSW/IVF）毫秒返回 Top-K；距离用余弦/内积/L2。与关系库互补：结构化查 SQL，语义查向量。
>
> **用法要点**：① 规模选库（Chroma原型/Qdrant中型/Milvus海量/PgVector复用）；② 距离与 Embedding 匹配；③ 元数据走 payload 过滤；④ 换模型重建索引；⑤ 混合检索（向量+BM25）提召回。

### 6.2 核心特性

**索引**：HNSW（快占内存）、IVF（可扩）、IVF_PQ（量化省内存）、Flat（精确）。

**能力**：相似检索、元数据过滤、多向量、量化压缩。

**与关系库关系**：pgvector 让 PG 兼当向量库，减少组件。

> 🔍 **知识点深度解析**
>
> **作用**：索引在精度/速度/内存三角权衡；pgvector 降低架构复杂度。
>
> **原理**：HNSW 多层图贪心近邻；IVF 聚类只搜最近簇；PQ 分段码本压缩向量；pgvector 的 ivfflat 是 PG 内 ANN。
>
> **用法要点**：① 原型 HNSW 默认；② 亿级 Milvus IVF_PQ；③ 已用 PG 直接 pgvector；④ ef_construction/ef 调 HNSW；⑤ 过滤与向量联合查。

### 6.3 常用用法

```python
# pgvector 混合检索（SQL 直接做）
import psycopg2
cur.execute("""
  SELECT id, content, 1 - (emb <=> %s::vector) AS score
  FROM knowledge
  WHERE tenant = %s
  ORDER BY emb <=> %s::vector
  LIMIT 5
""", (query_vec, tenant, query_vec))
```

> 🔍 **知识点深度解析**
>
> **作用**：用 SQL 直接在 PG 内做向量检索 + 租户过滤，零额外组件。
>
> **原理**：`<->` 余弦距离算子，ORDER BY + LIMIT 取 Top-K；`tenant=` 为标量过滤（payload 等价），实现"语义+权限"联合。
>
> **用法要点**：① 中小规模 pgvector 足够；② 过滤条件放 WHERE 缩小候选；③ 大模型量换专用向量库；④ 距离度量与 Embedding 一致；⑤ 建 ivfflat 索引加速。

### 6.4 注意事项

1. **维度一致**：换 Embedding 模型必须重建索引
2. **度量匹配**：余弦/内积/L2 选错结果失真
3. **规模成本**：HNSW 吃内存，海量用量化
4. **过滤过严**：元数据过滤过窄召回不足
5. **一致性**：分布式同步与可见性

> 💡 **深度讲解**：向量库是语义检索引擎。选型看规模：Chroma 原型、Qdrant 中型、Milvus 海量、PgVector 复用现有 PG（架构最简）。核心铁律——Embedding 维度与距离度量全局一致，换模型必重建索引。索引 HNSW 是默认甜点（快但吃内存），亿级用 IVF_PQ。元数据过滤（payload/tenant）实现"语义+权限"联合检索，但过滤过窄会召回不足。与关系库是互补而非替代：结构化精确查走 SQL，语义相似查走向量。

> 📝 **精简总结**：向量库=ANN语义检索；索引=HNSW(快)/IVF(扩)/PQ(省内存)；选型=Chroma/Qdrant/Milvus/pgvector；要点=维度一致/度量匹配/payload过滤；注意=换模型重建/过滤过严。

## 7. 分库分表与读写分离

### 7.1 概述

单库遇写入/数据量瓶颈时，用读写分离（主写从读）与分库分表（按片键水平拆分）扩展。是海量数据架构的关键。

> 🔍 **知识点深度解析**
>
> **作用**：单机容量/连接/写入有上限，分片是把"不能放一台"的数据分布到多节点。
>
> **原理**：读写分离基于主从复制，写主读从，分摊读压力；分表按片键（用户ID 哈希/时间范围）把表拆到多库多表；分片键决定路由与热点，需高基散列。
>
> **用法要点**：① 先垂直拆分（按业务库），再水平（按片键）；② 片键选高基、少跨片查询的字段；③ 读写分离强一致读走主；④ 用中间件（ShardingSphere/MyCat）透明路由；⑤ 跨片查询/事务是难点。

### 7.2 核心特性

**拆分方式**：垂直（按业务）、水平（按片键）。

**分片策略**：哈希取模、范围、一致性哈希、目录路由。

**中间件**：ShardingSphere、MyCat、Vitess（MySQL）。

**挑战**：分布式事务、跨片 JOIN、全局 ID、扩容。

> 🔍 **知识点深度解析**
>
> **作用**：策略与中间件决定可维护性与扩展性；挑战是分布式固有成本。
>
> **原理**：哈希取模均分但扩容需迁移（一致性哈希缓解）；范围分片易热点（最新数据集中）；ShardingSphere 解析 SQL 按规则路由到对应库表；分布式事务用 Seata/2PC/TCC。
>
> **用法要点**：① 片键避免用会范围查询的字段（否则扫全片）；② 全局 ID 用雪花/号段；③ 跨片用冗余或应用层聚合；④ 扩容优先一致性哈希或双写迁移；⑤ 能不分就不分（先加从/加缓存）。

### 7.3 常用用法

```sql
-- 雪花 ID（示意，应用生成全局唯一）
-- 41位时间戳 + 10位机器 + 12位序列
-- 分片路由（伪）：shard = hash(user_id) % 16

-- ShardingSphere 配置（逻辑表 → 实际表）
-- spring.shardingsphere.rules.sharding.tables.t_order.actual-data-nodes=ds$->{0..15}.t_order_$->{0..15}
```

> 🔍 **知识点深度解析**
>
> **作用**：全局 ID 与分片路由是分库分表落地的两个基本功。
>
> **原理**：雪花 ID 趋势递增且全局唯一（避免分片后主键冲突）；ShardingSphere 用逻辑表屏蔽物理分片，应用无感。
>
> **用法要点**：① 全局 ID 用雪花/号段（别用自增）；② 分片规则配 actual-data-nodes；③ 广播表/绑定表优化 JOIN；④ 路由键必须进 SQL 否则全路由；⑤ 监控各片均衡度。

### 7.4 注意事项

1. **片键选择**：错选致热点/全片扫描，极难改
2. **跨片事务**：分布式事务复杂，尽量避（本地事务+最终一致）
3. **扩容迁移**：取模分片扩容需迁数据，提前用一致性哈希/双写
4. **跨片 JOIN**：性能差，用冗余字段或应用聚合
5. **全局 ID**：自增冲突，必用分布式 ID

> 💡 **深度讲解**：分库分表是"单机装不下"时的必然选择，但代价巨大——分布式事务、跨片 JOIN、全局 ID、扩容迁移全是难题。原则：**能不分就不分**，先加从库（读写分离）、加缓存、优化索引。必须分时，先垂直（按业务拆库）再水平（按片键拆表）。片键是命门：选高基、少跨片查询的字段（如 user_id 哈希），避免用时间范围（热点）。全局 ID 用雪花/号段。中间件 ShardingSphere 透明路由，但跨片查询仍要谨慎。扩容用一致性哈希或双写迁移降低停服。

> 📝 **精简总结**：扩展=读写分离(主写从读)+分库分表(片键水平)；策略=哈希/范围/一致性哈希；中间件=ShardingSphere/MyCat；挑战=分布式事务/跨片JOIN/全局ID/扩容；注意=片键选择/能不分就不分/雪花生ID。

## 8. 主从复制、备份与恢复

### 8.1 概述

主从复制把主库变更同步到从库，实现读写分离、高可用与备份源。备份分逻辑（mysqldump/PG dump）与物理（xtrabackup/快照），恢复演练是底线。

> 🔍 **知识点深度解析**
>
> **作用**：没有复制与备份，数据库既无扩展也无安全网——数据丢失是致命级事故。
>
> **原理**：MySQL 主库写 binlog，从库 IO 线程拉取存 relay log，SQL 线程重放；PG 用 WAL 流复制。备份逻辑备份可跨版本但慢，物理备份快但需同版本/平台。
>
> **用法要点**：① 主从用于读扩展+备份；② 半同步复制降数据丢失；③ 定期全量+增量；④ 恢复必演练（备份不可恢复=没备份）；⑤ 监控复制延迟与中断。

### 8.2 核心特性

**复制模式**：异步（默认，可能丢）、半同步（折中）、全同步（强一致慢）。

**备份**：逻辑（dump，可跨版）、物理（xtrabackup，快）、增量、PITR（按时间点恢复）。

**恢复**：全量恢复、PITR（WAL/ binlog 回放）、从库提升。

> 🔍 **知识点深度解析**
>
> **作用**：复制模式在性能与一致权衡；备份策略决定 RPO/RTO。
>
> **原理**：异步复制主提交即从返回，从滞后可能丢；半同步等至少一个从确认；PITR 用全量+后续 WAL 回放到指定时间。从库可提升为新主实现故障切换。
>
> **用法要点**：① 金融用半同步/全同步；② PITR 依赖连续 WAL 归档；③ 备份加密与异地；④ 恢复演练验证；⑤ 监控 Seconds_Behind_Master。

### 8.3 常用用法

```bash
# MySQL 逻辑备份 + 恢复
mysqldump -u root -p --single-transaction --routines mydb > mydb.sql
mysql -u root -p mydb < mydb.sql

# PITR：全量 + binlog 回放
mysqlbinlog --stop-datetime="2026-08-25 10:00:00" mysql-bin.000123 | mysql -u root -p
```

```bash
# PostgreSQL 物理备份（pg_basebackup）+ WAL 归档
pg_basebackup -D /backup/data -Ft -z -P
```

> 🔍 **知识点深度解析**
>
> **作用**：`--single-transaction` 一致性快照不锁表；binlog 回放实现时间点恢复。
>
> **原理**：mysqldump 加 `--single-transaction` 用 MVCC 拿一致性视图；PITR 先恢复全量再按 binlog 重放到目标时间，挽回误删。
>
> **用法要点**：① 大库用物理备份（快）；② 异地+加密存储；③ 恢复前先演练；④ binlog/WAL 连续归档是 PITR 前提；⑤ 监控复制延迟防读旧数据。

### 8.4 注意事项

1. **主从延迟**：读从可能读旧，强一致走主
2. **备份不可恢复**：未演练=无备份，定期恢复验证
3. **PITR 依赖**：WAL/binlog 须连续归档，断档则无法回放
4. **异步丢数**：主宕从未同步则丢，金融用半同步
5. **权限与加密**：备份含全量数据，严控访问与加密

> 💡 **深度讲解**：复制与备份是数据库的"保险"。主从复制实现读扩展、高可用与备份源，模式分异步（快可能丢）/半同步（折中）/全同步（强一致慢），按业务选。备份分逻辑（dump，可跨版、慢）与物理（xtrabackup，快、需同版本）。PITR（按时间点恢复）靠全量+连续 WAL/binlog 归档，是误删/勒索的救命手段。最致命的误区是"有备份"却从不演练——备份不可恢复等于没备份。主从延迟会让读从看到旧数据，强一致读必须走主库。备份须加密、异地、限权。

> 📝 **精简总结**：复制=异步/半同步/全同步(性能↔一致)；备份=逻辑(dump)/物理(xtrabackup)/增量/PITR；恢复=全量+PITR/从库提升；注意=主从延迟/备份必演练/PITR依赖连续归档/异步丢数/加密限权。
