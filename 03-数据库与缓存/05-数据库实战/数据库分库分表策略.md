# 数据库分库分表策略


> 当单表数据量超过千万级、单库QPS超过万级时，单机数据库的CPU、IO、连接数都会成为瓶颈。分库分表通过水平/垂直拆分将数据分散到多个节点，是支撑海量数据与高并发的核心架构手段。
>
> **核心问题**：分片键选择、跨片查询、分布式事务、数据迁移、扩容缩容、全局ID。

---

## 一、概述：为什么需要分库分表

### 1.1 单机数据库的瓶颈

| 瓶颈类型 | 阈值参考 | 表现 |
|---------|---------|------|
| 单表数据量 | > 2000万行（InnoDB） | 查询变慢、索引膨胀、DDL耗时 |
| 单库QPS | > 8000~10000 | CPU飙升、连接池耗尽、响应延迟 |
| 单库存储 | > 500GB~1TB | 备份恢复慢、磁盘IO瓶颈 |
| 连接数 | > 1000~2000 | Too many connections错误 |

### 1.2 拆分策略总览

```text
数据库拆分
├── 垂直拆分（按业务/功能）
│   ├── 垂直分库：用户库、订单库、商品库
│   └── 垂直分表：热点字段与冷字段分离（大表拆宽表）
└── 水平拆分（按数据范围/哈希）
    ├── 水平分库：同一逻辑表分散到多个物理库
    └── 水平分表：同一库内将大表拆为多张子表
```

### 1.3 适用场景与反模式

**适用**：
- 数据量持续增长，已有索引优化无法解决性能问题
- 读写QPS远超单机承载能力
- 业务天然可分片（如按用户ID、订单ID）

**反模式（不要分库分表）**：
- 数据量<500万行，单纯因为"听说要分"而分
- 业务需要频繁跨片JOIN、聚合、排序
- 团队缺乏分布式运维能力，分库分表引入的复杂度远超收益

## 二、底层原理：分片算法与数据路由

### 2.1 常见分片算法

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| 取模分片 | hash(key) % N | 数据均匀、实现简单 | 扩容需全量迁移 | 用户ID、订单ID |
| 范围分片 | 按ID/时间区间 | 扩容方便、范围查询高效 | 数据可能倾斜 | 时间序列数据、自增ID |
| 一致性哈希 | 虚拟节点环 | 扩容只影响相邻节点 | 实现复杂、数据均匀性一般 | 缓存集群、动态扩缩容 |
| 枚举分片 | 按业务类型固定映射 | 简单可控 | 分片数固定、扩展性差 | 按地区/业务线拆分 |

### 2.2 分片键选择原则

```text
好的分片键 = 高基数 + 查询高频 + 分布均匀 + 不可变

反例：
- 用 status 字段分片（基数低，数据严重倾斜）
- 用 create_time 分片（范围查询多但最新数据集中在少数片）
- 用可更新的字段分片（更新后需迁移数据）
```

### 2.3 数据路由流程

```text
应用层 SQL: SELECT * FROM t_order WHERE user_id = 12345
         ↓
ShardingSphere 解析 SQL → 提取分片键 user_id=12345
         ↓
分片算法: 12345 % 4 = 1  → 路由到 ds1.t_order_1
         ↓
执行真实 SQL: SELECT * FROM ds1.t_order_1 WHERE user_id = 12345
         ↓
结果合并（单分片直接返回，多分片需归并排序）
```

## 三、实操：ShardingSphere-JDBC 分库分表

### 3.1 环境搭建

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.1</version>
</dependency>
```

### 3.2 分库分表配置（YAML）

```yaml
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/order_db_0?useSSL=false
        username: root
        password: root
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        jdbc-url: jdbc:mysql://localhost:3306/order_db_1?useSSL=false
        username: root
        password: root
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..1}
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: database-inline
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: table-inline
        sharding-algorithms:
          database-inline:
            type: INLINE
            props:
              algorithm-expression: ds$->{user_id % 2}
          table-inline:
            type: INLINE
            props:
              algorithm-expression: t_order_$->{order_id % 2}
```

### 3.3 分布式主键（雪花算法）

```yaml
    rules:
      sharding:
        key-generators:
          snowflake:
            type: SNOWFLAKE
            props:
              worker-id: 1
        tables:
          t_order:
            key-generate-strategy:
              column: order_id
              key-generator-name: snowflake
```

### 3.4 读写分离配置

```yaml
    rules:
      readwrite-splitting:
        data-sources:
          readwrite-ds:
            write-data-source-name: ds0
            read-data-source-names: ds0-slave, ds1-slave
            load-balancer-name: round-robin
        load-balancers:
          round-robin:
            type: ROUND_ROBIN
```

## 四、常见问题与排查

### 4.1 跨片查询与聚合

**问题**：`SELECT COUNT(*) FROM t_order WHERE status='PAID'` 需要扫描所有分片。

**解决方案**：
1. **建立宽表/汇总表**：将统计结果预计算到 `t_order_summary`
2. **使用搜索引擎**：将数据同步到 Elasticsearch 做复杂查询
3. **应用层并行查询**：多线程同时查各分片，内存中合并结果
4. **避免跨片排序分页**：`LIMIT 10000, 10` 在分库分表下需各片取 10010 条再排序，性能极差

### 4.2 分布式事务

| 方案 | 一致性 | 性能 | 适用场景 |
|------|--------|------|---------|
| 2PC（XA） | 强一致 | 低 | 金融核心、资金交易 |
| TCC | 最终一致 | 中 | 可补偿业务（库存、积分） |
| 本地消息表 | 最终一致 | 高 | 异步解耦场景 |
| Saga | 最终一致 | 高 | 长事务、跨服务编排 |

### 4.3 数据迁移与扩容

**平滑扩容步骤（双写方案）**：
```text
1. 新分片集群部署完成
2. 应用层双写：同时写旧分片和新分片（旧分片为准）
3. 历史数据迁移：使用工具将旧数据按新分片规则导入新集群
4. 数据校验：对比新旧数据一致性
5. 切读：读流量逐步切到新分片（灰度10%→50%→100%）
6. 切写：写流量切到新分片，停止双写
7. 下线旧分片
```

### 4.4 热点分片问题

**现象**：某个分片的QPS/数据量远超其他分片（如大V用户、热门商品）。

**解决**：
- 分片键加盐：`user_id + random_salt` 打散热点
- 二级分片：先按 user_id 分库，再按 order_id 分表
- 热点数据缓存：将热点行放入 Redis，减少DB压力

## 五、进阶与最佳实践

### 5.1 分库分表中间件对比

| 中间件 | 架构 | 语言 | 侵入性 | 性能 | 适用场景 |
|--------|------|------|--------|------|---------|
| ShardingSphere-JDBC | 客户端层 | Java | 高（依赖） | 高 | Java应用、中小规模 |
| ShardingSphere-Proxy | 代理层 | Java | 低（透明） | 中 | 多语言、运维统一 |
| MyCat | 代理层 | Java | 低 | 中 | 传统项目、已使用MyCat |
| Vitess | 代理层 | Go | 低 | 高 | Kubernetes、超大规模 |
| 自研路由层 | 应用层 | - | 高 | 最高 | 极致定制、大厂 |

### 5.2 分片数量规划

```text
分片数 = ceil(预估3年数据量 / 单表最优数据量)

示例：
- 预估3年订单量：10亿条
- 单表最优：500万~1000万条
- 分表数 = 10亿 / 800万 ≈ 125 → 取 128（2的幂，方便扩容）
- 若分4个库，每库32张表

原则：
1. 分片数取2的幂（2,4,8,16,32,64,128），方便翻倍扩容
2. 一次规划到位，避免频繁扩容
3. 预留30%~50%余量
```

### 5.3 监控与运维

- **分片均衡监控**：各分片数据量、QPS、连接数差异
- **慢SQL监控**：跨片查询、全表扫描
- **主从延迟监控**：读写分离场景下的延迟
- **容量预警**：磁盘使用率、单表行数
