# 数据库迁移工具实战

> **文档说明**：数据库迁移工具实现数据库Schema的版本化管理，支持团队协作、环境同步、版本回滚。本文档覆盖Flyway和Liquibase两大工具的配置、使用、最佳实践和对比选型。
>
> **适用人群**：后端工程师、需要管理数据库变更的开发者
>
> **前置知识**：SQL、Spring Boot

---

## 一、为什么需要数据库迁移工具

### 1.1 手动管理SQL的问题

| 问题 | 说明 |
|------|------|
| 环境不一致 | 开发/测试/生产数据库结构不同步 |
| 无版本管理 | 不知道哪个SQL执行过，无法回滚 |
| 团队协作难 | 多人修改数据库，冲突无法追踪 |
| 部署风险 | 手动执行SQL容易遗漏或顺序错误 |
| 无审计 | 谁在什么时候改了数据库无记录 |

### 1.2 迁移工具核心能力

- **版本化**：每个SQL脚本有版本号，按顺序执行
- **自动执行**：应用启动时自动检测并执行未执行的脚本
- **环境同步**：所有环境执行相同的迁移脚本，保证一致
- **回滚支持**：支持回滚到指定版本
- **审计记录**：记录每次迁移的执行时间、执行人、结果

## 二、Flyway实战

### 2.1 核心概念

```mermaid
flowchart LR
    A[迁移脚本] -->|按版本排序| B[Flyway]
    B -->|检查历史| C[schema_version表]
    C -->|未执行| D[执行迁移]
    D -->|记录| C
```

| 概念 | 说明 |
|------|------|
| **Migration** | 迁移，一个版本的变更 |
| **Version** | 版本号，如1.0.0、20240101_120000 |
| **Schema History Table** | 迁移历史表（flyway_schema_history） |
| **Baseline** | 基线，已有数据库的初始版本 |

### 2.2 命名规范

```text
src/main/resources/db/migration/
├── V1__init_schema.sql          # 版本1：初始化表结构
├── V2__add_user_table.sql       # 版本2：添加用户表
├── V2.1__add_index.sql          # 版本2.1：添加索引
├── V3__alter_order_table.sql    # 版本3：修改订单表
├── R__create_view.sql           # 可重复迁移（每次checksum变化时执行）
└── U2__undo_add_user.sql        # 撤销迁移（Undo，专业版）
```

| 前缀 | 说明 |
|------|------|
| **V** | Versioned migration，版本化迁移，只执行一次 |
| **U** | Undo migration，撤销迁移（专业版） |
| **R** | Repeatable migration，可重复迁移，checksum变化时执行 |

### 2.3 Spring Boot集成

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true      # 已有数据库时创建基线
    baseline-version: 0           # 基线版本
    validate-on-migrate: true     # 迁移前校验
    out-of-order: false           # 不允许乱序执行
    clean-disabled: true          # 禁用clean（生产环境必须）
    table: flyway_schema_history  # 历史表名
    encoding: UTF-8
```

### 2.4 迁移脚本示例

```sql
-- V1__init_schema.sql
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    password VARCHAR(255) NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_username (username),
    INDEX idx_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- V2__add_order_table.sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    amount DECIMAL(10,2) NOT NULL DEFAULT 0,
    status TINYINT NOT NULL DEFAULT 0,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';

-- V3__add_phone_to_users.sql
ALTER TABLE users ADD COLUMN phone VARCHAR(20) AFTER email;
ALTER TABLE users ADD INDEX idx_phone (phone);
```

### 2.5 命令行使用

```bash
# 迁移
mvn flyway:migrate

# 查看信息
mvn flyway:info

# 校验
mvn flyway:validate

# 修复（修复失败的迁移记录）
mvn flyway:repair

# 基线
mvn flyway:baseline

# 命令行工具
flyway migrate -url=jdbc:mysql://localhost:3306/db -user=root -password=root
flyway info
flyway repair
```

### 2.6 迁移历史表

```sql
-- flyway_schema_history表结构
CREATE TABLE flyway_schema_history (
    installed_rank INT PRIMARY KEY,
    version VARCHAR(50),
    description VARCHAR(200),
    type VARCHAR(20),
    script VARCHAR(1000),
    checksum INT,
    installed_by VARCHAR(100),
    installed_on TIMESTAMP,
    execution_time INT,
    success TINYINT
);
```

## 三、Liquibase实战

### 3.1 核心概念

| 概念 | 说明 |
|------|------|
| **ChangeSet** | 变更集，一个原子变更单元 |
| **Changelog** | 变更日志文件，包含多个ChangeSet |
| **DATABASECHANGELOG** | 变更历史表 |
| **Precondition** | 前置条件，满足才执行 |

### 3.2 配置

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.liquibase</groupId>
    <artifactId>liquibase-core</artifactId>
</dependency>
```

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:db/changelog/db.changelog-master.xml
    default-schema: public
```

### 3.3 ChangeLog示例（XML格式）

```xml
<!-- db.changelog-master.xml -->
<databaseChangeLog xmlns="http://www.liquibase.org/xml/ns/dbchangelog">
    <include file="db/changelog/changes/001-init-schema.xml"/>
    <include file="db/changelog/changes/002-add-order-table.xml"/>
</databaseChangeLog>

<!-- 001-init-schema.xml -->
<databaseChangeLog>
    <changeSet id="001-init-schema" author="developer">
        <createTable tableName="users">
            <column name="id" type="BIGINT" autoIncrement="true">
                <constraints primaryKey="true" nullable="false"/>
            </column>
            <column name="username" type="VARCHAR(50)">
                <constraints nullable="false" unique="true"/>
            </column>
            <column name="email" type="VARCHAR(100)">
                <constraints nullable="false"/>
            </column>
        </createTable>
        <createIndex tableName="users" indexName="idx_email">
            <column name="email"/>
        </createIndex>
    </changeSet>
</databaseChangeLog>
```

### 3.4 YAML格式（推荐）

```yaml
# db.changelog-master.yaml
databaseChangeLog:
  - include:
      file: db/changelog/changes/001-init-schema.yaml

# 001-init-schema.yaml
databaseChangeLog:
  - changeSet:
      id: 001-init-schema
      author: developer
      changes:
        - createTable:
            tableName: users
            columns:
              - column:
                  name: id
                  type: BIGINT
                  autoIncrement: true
                  constraints:
                    primaryKey: true
                    nullable: false
              - column:
                  name: username
                  type: VARCHAR(50)
                  constraints:
                    nullable: false
                    unique: true
```

### 3.5 SQL格式（最灵活）

```sql
-- liquibase formatted sql
-- changeset developer:001-init-schema
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE
);
-- rollback DROP TABLE users;

-- changeset developer:002-add-email
ALTER TABLE users ADD COLUMN email VARCHAR(100);
-- rollback ALTER TABLE users DROP COLUMN email;
```

### 3.6 回滚支持

```bash
# 回滚到指定版本
mvn liquibase:rollback -Dliquibase.rollbackCount=1
mvn liquibase:rollback -Dliquibase.rollbackToTag=v1.0
mvn liquibase:rollback -Dliquibase.rollbackDate=2024-01-01
```

## 四、Flyway vs Liquibase

| 维度 | Flyway | Liquibase |
|------|--------|-----------|
| 学习曲线 | 低（纯SQL） | 中（XML/YAML/SQL） |
| 迁移方式 | SQL脚本 | 支持SQL/XML/YAML/JSON |
| 回滚 | 社区版不支持，专业版支持 | 原生支持 |
| 多数据库 | 支持 | 支持更好（抽象层） |
| 灵活性 | 低（SQL固定） | 高（条件执行、上下文） |
| 插件生态 | 中 | 丰富 |
| 适用 | 简单项目、SQL优先 | 复杂项目、多数据库 |
| 国内流行度 | 高 | 中 |

## 五、最佳实践

### 5.1 命名规范

```text
Flyway: V{版本号}__{描述}.sql
  版本号：时间戳格式推荐（20240101_120000）
  描述：下划线分隔，清晰说明变更内容

Liquibase: {序号}-{描述}.xml/yaml
  序号：3位数字（001、002）
  ChangeSet id: 序号-描述，author: 开发者
```

### 5.2 开发流程

```text
1. 开发新功能 → 编写迁移脚本
2. 本地执行迁移 → 验证脚本正确性
3. 提交代码 → Code Review（包含迁移脚本）
4. 合并到测试分支 → 自动执行迁移
5. 测试验证 → 确认数据正确
6. 生产部署 → 自动执行迁移（应用启动时）
```

### 5.3 注意事项

1. **迁移脚本不可修改**：已执行的脚本不能修改，需新建脚本变更
2. **小步提交**：每个变更一个脚本，避免大脚本失败影响大
3. **幂等设计**：脚本尽量幂等（IF NOT EXISTS）
4. **禁止破坏性变更**：删除表/列需先废弃，下个版本再删
5. **大表DDL**：大表加字段/索引用pt-online-schema-change，避免锁表
6. **数据迁移**：数据变更和Schema变更分开
7. **备份先行**：生产迁移前必须备份数据库
8. **禁用clean**：生产环境flyway.clean-disabled=true

### 5.4 常见问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 校验失败 | 已执行的脚本被修改 | 不要修改已执行脚本，用repair或新建 |
| 迁移失败 | SQL错误 | 修复SQL，repair后重试 |
| 乱序执行 | 旧版本脚本后提交 | out-of-order=true或确保顺序 |
| 锁表 | 大表DDL | 在线DDL工具/低峰执行 |
| 数据丢失 | 破坏性变更 | 先备份，分阶段迁移 |

## 补充：概述

数据库迁移（Database Migration）是指对数据库的 Schema（表结构、索引、约束）和数据进行版本化管理和变更的过程。在团队协作和持续交付中，数据库变更必须像代码一样**可版本控制、可重复执行、可回滚、可审计**，否则会出现开发环境与生产环境不一致、多人修改冲突、发布时手动执行 SQL 出错等问题。

| 迁移工具 | 语言 | 配置方式 | 特点 |
|---------|------|---------|------|
| **Flyway** | Java/JVM | SQL 脚本 | 简单直接、约定优于配置、企业级 |
| **Liquibase** | Java/JVM | XML/YAML/JSON/SQL | 功能强大、支持多种格式、回滚能力强 |
| **Alembic** | Python | Python 脚本 | SQLAlchemy 生态、轻量、灵活 |
| **Django Migrations** | Python | Python 自动生成 | Django 内置、自动检测模型变化 |
| **Ruby on Rails Migration** | Ruby | Ruby DSL | Rails 内置、简洁优雅 |
| **golang-migrate** | Go | SQL 脚本 | 轻量、多数据库支持、CLI 友好 |
| **MyBatis Migration** | Java | SQL 脚本 | MyBatis 生态、简单 |
| **Bytebase** | - | Web UI | 团队协作、审批流程、多环境管理 |

**迁移的核心原则**：
1. **版本化**：每个迁移脚本有唯一版本号，按顺序执行
2. **幂等性**：迁移脚本可以重复执行而不出错（用 IF NOT EXISTS 等）
3. **向前兼容**：数据库变更先于代码发布，保证新旧代码都能运行
4. **小步快跑**：每次迁移只做一件事，避免大变更导致长时间锁表
5. **可回滚**：重要变更要有回滚方案（虽然不是所有工具都支持自动回滚）
6. **禁止手动改库**：所有 Schema 变更必须通过迁移工具，禁止直接在生产执行 DDL

## 补充：底层原理

### 迁移版本管理原理

所有迁移工具的核心都是一张**版本记录表**（schema_version / flyway_schema_history）：

| 字段 | 说明 |
|------|------|
| `installed_rank` | 执行顺序 |
| `version` | 迁移版本号（如 1.0.0, 20260101_001） |
| `description` | 迁移描述 |
| `type` | 类型（SQL/JAVA/...） |
| `script` | 脚本文件名 |
| `checksum` | 脚本内容校验和（防止已执行的脚本被修改） |
| `installed_by` | 执行人 |
| `installed_on` | 执行时间 |
| `execution_time` | 执行耗时 |
| `success` | 是否成功 |

**执行流程**：
```text
启动 → 检查版本表是否存在（不存在则创建）→ 扫描迁移脚本目录 → 对比已执行版本 → 
按顺序执行未执行的脚本 → 记录版本和 checksum → 完成
```

**Checksum 校验**：每次执行时计算脚本的 checksum 并存储。下次启动时，如果已执行的脚本内容被修改（checksum 不匹配），工具会报错——这保证了已执行的迁移不会被偷偷修改导致环境不一致。

### 在线 DDL 原理

大表的 DDL（如加列、加索引、改类型）可能锁表几分钟甚至几小时，在线 DDL 工具通过**拷贝表**的方式实现无锁变更：

| 工具 | 原理 |
|------|------|
| **MySQL Online DDL**（5.6+） | In-place 或 Copy，支持 ALGORITHM=INPLACE/COPY，LOCK=NONE |
| **pt-online-schema-change** | 创建影子表 → 拷贝数据 → 触发器同步增量 → RENAME 切换 |
| **gh-ost** | 创建影子表 → 从 Binlog 同步增量 → 拷贝数据 → RENAME 切换（无触发器） |
| **PostgreSQL** | 加列有默认值时重写表（11+ 有优化），CREATE INDEX CONCURRENTLY 不锁表 |

**gh-ost 执行流程**：
```text
1. 创建 _表名_gho 影子表（应用新 Schema）
2. 创建 _表名_ghc 变更控制表（记录状态）
3. 连接从库读取 Binlog，将增量变更应用到影子表
4. 分批拷贝原表数据到影子表（INSERT ... SELECT，每批 1000 行）
5. 拷贝完成后，等待 Binlog 追平
6. RENAME TABLE 原表 TO _表名_del, 影子表 TO 原表（原子操作）
7. 删除原表（可延迟删除）
```

### 迁移与发布的配合（扩展-收缩模式）

数据库变更不能像代码那样快速回滚（数据已经变了），需要用**扩展-收缩（Expand-Contract）**模式：

| 阶段 | 动作 | 说明 |
|------|------|------|
| **扩展（Expand）** | 新增列/表，不删除旧的 | 新旧代码都能运行，双写 |
| **迁移数据** | 后台任务将旧数据迁移到新结构 | 不影响线上 |
| **切换读** | 代码切换到读新列/新表 | 验证新结构数据正确 |
| **切换写** | 代码切换到写新列/新表 | 停止双写 |
| **收缩（Contract）** | 删除旧列/旧表 | 确认无依赖后清理 |

**示例**：将 `users.name` 拆分为 `first_name` + `last_name`：
1. 扩展：`ALTER TABLE users ADD COLUMN first_name VARCHAR(50), ADD COLUMN last_name VARCHAR(50)`
2. 双写：应用层写入 name 的同时写入 first_name/last_name
3. 数据迁移：`UPDATE users SET first_name = SPLIT_PART(name, ' ', 1), last_name = SPLIT_PART(name, ' ', 2)`
4. 切换读：应用层改为读 first_name/last_name
5. 切换写：应用层不再写 name
6. 收缩：`ALTER TABLE users DROP COLUMN name`
