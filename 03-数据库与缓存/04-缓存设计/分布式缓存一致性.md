# 分布式缓存一致性


> 分布式缓存是提升系统性能的核心手段，但缓存与数据库的数据一致性是经典难题。本文从缓存三大问题（穿透/击穿/雪崩）到双写一致性方案，系统讲解分布式缓存一致性的原理与实战。
>
> **核心矛盾**：性能（缓存）vs 一致性（数据库），根据业务场景选择最终一致或强一致方案。

---

## 一、概述：缓存一致性问题

### 1.1 为什么需要缓存

| 维度 | 无缓存 | 有缓存 |
|------|--------|--------|
| 响应时间 | 100ms+（DB查询） | 1ms（Redis查询） |
| 吞吐量 | 1000 QPS（DB上限） | 10万+ QPS（Redis） |
| 数据库压力 | 高（所有请求直达DB） | 低（缓存拦截90%+请求） |
| 一致性 | 强一致（直接读DB） | 最终一致（缓存可能过期） |

### 1.2 缓存一致性挑战

```text
读操作：先读缓存 → 命中则返回 → 未命中则读DB → 写缓存 → 返回
写操作：更新DB + 更新/删除缓存 → 两者之间存在时间差 → 不一致窗口

核心问题：
1. 缓存三大问题：穿透、击穿、雪崩
2. 双写一致性：先更新DB还是先操作缓存？
3. 并发场景：多线程同时读写导致的数据不一致
4. 分布式场景：多节点缓存同步
```

---

## 二、底层原理：缓存三大问题

### 2.1 缓存穿透

**定义**：查询一个不存在的数据，缓存未命中，请求直达数据库，导致数据库压力增大。

**场景**：恶意攻击，大量查询不存在的用户ID/商品ID。

**解决方案**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 缓存空值 | 不存在的key也缓存（值为null，短TTL） | 简单 | 占用内存，可能缓存大量空值 |
| 布隆过滤器 | 查询前先过布隆过滤器，不存在直接返回 | 内存占用小 | 存在误判率，无法删除 |
| 参数校验 | 接口层校验参数合法性（ID范围、格式） | 最简单 | 无法覆盖所有非法请求 |

```java
// 布隆过滤器实现（Guava）
BloomFilter<Long> bloomFilter = BloomFilter.create(
    Funnels.longFunnel(),
    1000000,  // 预期插入数量
    0.01      // 误判率
);

// 初始化：将所有存在的用户ID加入布隆过滤器
userMapper.selectAllIds().forEach(bloomFilter::put);

// 查询时先过布隆过滤器
public User getUser(Long id) {
    if (!bloomFilter.mightContain(id)) {
        return null;  // 一定不存在，直接返回
    }
    // 可能存在，继续查缓存和DB
    User user = redis.get("user:" + id);
    if (user == null) {
        user = userMapper.selectById(id);
        if (user != null) {
            redis.set("user:" + id, user, 3600);
        } else {
            redis.set("user:" + id, "", 60);  // 缓存空值
        }
    }
    return user;
}
```

### 2.2 缓存击穿

**定义**：某个热点key过期的瞬间，大量并发请求同时到达，全部直达数据库，导致数据库压力骤增。

**场景**：秒杀商品信息、热门文章，缓存过期瞬间大量请求。

**解决方案**：

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| 互斥锁 | 缓存未命中时加锁，只让一个请求查DB并回写缓存 | 大多数场景 |
| 逻辑过期 | 缓存不设TTL，value中存逻辑过期时间，过期后异步更新 | 极高并发、允许短暂不一致 |
| 热点key永不过期 | 热点数据不设过期时间，后台定时更新 | 确定的热点数据 |

```java
// 互斥锁方案
public User getUserWithLock(Long id) {
    String key = "user:" + id;
    User user = redis.get(key);
    if (user != null) {
        return user;
    }
    // 加互斥锁
    String lockKey = "lock:user:" + id;
    boolean locked = redis.setIfAbsent(lockKey, "1", 10);  // 10秒超时
    if (locked) {
        try {
            // 双重检查（获取锁后再查一次缓存）
            user = redis.get(key);
            if (user == null) {
                user = userMapper.selectById(id);
                if (user != null) {
                    redis.set(key, user, 3600);
                }
            }
        } finally {
            redis.delete(lockKey);  // 释放锁
        }
    } else {
        // 未获取到锁，等待后重试
        Thread.sleep(50);
        return getUserWithLock(id);  // 递归重试
    }
    return user;
}
```

```java
// 逻辑过期方案
public class CacheData<T> {
    private T data;
    private LocalDateTime expireTime;  // 逻辑过期时间
}

public User getUserWithLogicalExpire(Long id) {
    String key = "user:" + id;
    CacheData<User> cacheData = redis.get(key);
    if (cacheData == null) {
        return null;
    }
    // 未过期，直接返回
    if (cacheData.getExpireTime().isAfter(LocalDateTime.now())) {
        return cacheData.getData();
    }
    // 已过期，异步更新缓存（返回旧数据）
    String lockKey = "lock:user:" + id;
    if (redis.setIfAbsent(lockKey, "1", 10)) {
        try {
            // 异步线程更新缓存
            executorService.submit(() -> {
                User dbUser = userMapper.selectById(id);
                CacheData<User> newCache = new CacheData<>();
                newCache.setData(dbUser);
                newCache.setExpireTime(LocalDateTime.now().plusMinutes(30));
                redis.set(key, newCache);
            });
        } finally {
            redis.delete(lockKey);
        }
    }
    return cacheData.getData();  // 返回旧数据
}
```

### 2.3 缓存雪崩

**定义**：大量缓存key在同一时间过期，或缓存服务宕机，导致大量请求同时直达数据库，数据库压力骤增甚至宕机。

**场景**：
- 批量导入数据时设置了相同的过期时间
- Redis集群宕机
- 大促前缓存集中过期

**解决方案**：

| 方案 | 原理 |
|------|------|
| 过期时间加随机值 | TTL = baseTTL + random(0, 300s)，避免同时过期 |
| 多级缓存 | 本地缓存(Caffeine) + 分布式缓存(Redis)，Redis挂了还有本地缓存 |
| 缓存高可用 | Redis Sentinel/Cluster，避免单点故障 |
| 限流降级 | 数据库前加限流，超过阈值返回降级数据 |
| 缓存预热 | 大促前提前加载热点数据到缓存 |

```java
// 过期时间加随机值
public void setWithRandomTTL(String key, Object value) {
    int baseTTL = 3600;  // 基础1小时
    int randomTTL = ThreadLocalRandom.current().nextInt(0, 300);  // 0-5分钟随机
    redis.set(key, value, baseTTL + randomTTL);
}

// 多级缓存（Caffeine + Redis）
@Cacheable(value = "user", key = "#id")
public User getUser(Long id) {
    // 1. 查Caffeine本地缓存（Spring Cache抽象，自动处理）
    // 2. 查Redis
    // 3. 查DB
    // 4. 回写Redis和Caffeine
    return userMapper.selectById(id);
}
```

## 三、实操：缓存与数据库双写一致性

### 3.1 四种双写方案对比

| 方案 | 操作顺序 | 一致性 | 性能 | 适用场景 |
|------|---------|--------|------|---------|
| 先更新DB，再更新缓存 | DB→Cache | 低（并发问题） | 高 | 不推荐 |
| 先更新缓存，再更新DB | Cache→DB | 低 | 高 | 不推荐 |
| 先删除缓存，再更新DB | Cache→DB | 中（有不一致窗口） | 高 | 常用 |
| 先更新DB，再删除缓存 | DB→Cache | 高（不一致窗口小） | 高 | 推荐（Cache Aside Pattern） |

### 3.2 Cache Aside Pattern（推荐方案）

```text
读操作：
1. 先读缓存，命中则返回
2. 未命中则读数据库
3. 数据库结果写入缓存
4. 返回结果

写操作：
1. 先更新数据库
2. 再删除缓存（不是更新缓存）
```

**为什么是删除缓存而不是更新缓存？**
- 更新缓存可能写入无效数据（并发场景下）
- 删除缓存更简单，下次读取时自动从DB加载最新数据
- 懒加载，只缓存真正被访问的数据

### 3.3 先更新DB再删缓存的不一致问题

```text
场景：并发读写导致不一致
1. 缓存刚好失效
2. 线程A读缓存未命中，去读DB（得到旧值）
3. 线程B更新DB（新值），然后删除缓存
4. 线程A将旧值写入缓存
→ 缓存中是旧值，不一致！

但这个场景发生的概率很低：
- 需要缓存刚好失效
- 需要读DB比写DB+删缓存慢（通常读比写快）
- 发生后缓存有TTL，最终会一致
```

### 3.4 延迟双删（强一致方案）

```java
public void updateUser(User user) {
    // 1. 先删除缓存
    redis.delete("user:" + user.getId());
    // 2. 更新数据库
    userMapper.updateById(user);
    // 3. 延迟一段时间（如500ms），再删除缓存
    //    确保读线程已完成（旧值已写入缓存），再次删除
    new Thread(() -> {
        try {
            Thread.sleep(500);
            redis.delete("user:" + user.getId());
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }).start();
}
```

**延迟双删的问题**：
- 延迟时间难以确定（不同业务读DB时间不同）
- 异步线程可能失败
- 吞吐量下降

### 3.5 基于MQ的最终一致性方案

```java
// 更新DB后发送消息，异步删除缓存
@Transactional
public void updateUser(User user) {
    userMapper.updateById(user);
    // 发送消息到MQ（事务消息，确保DB和消息一致）
    mq.send("cache-invalidation", "user:" + user.getId());
}

// 消费者删除缓存
@RabbitListener(queues = "cache-invalidation")
public void handleCacheInvalidation(String key) {
    redis.delete(key);
    // 可重试机制，确保删除成功
}
```

### 3.6 订阅binlog实现缓存更新（Canal）

```text
架构：MySQL → binlog → Canal → MQ → 缓存更新服务 → Redis

优点：
- 业务代码无侵入（不需要在每个更新方法里删缓存）
- 可靠性高（binlog不丢失）
- 适合复杂场景（多表关联缓存更新）

缺点：
- 架构复杂，需要维护Canal
- 延迟比直接删缓存高
```

## 四、常见问题与排查

### 4.1 缓存与DB不一致排查

```text
排查步骤：
1. 确认缓存key的TTL是否合理（太短频繁失效，太长不一致时间长）
2. 检查是否有并发写操作（多实例同时更新同一数据）
3. 查看缓存删除是否失败（网络问题、Redis异常）
4. 检查是否有绕过缓存的直接DB更新（脚本、定时任务）
5. 查看binlog订阅是否正常（如果用Canal方案）
6. 确认是否有缓存预热逻辑写入了旧数据
```

### 4.2 缓存监控指标

| 指标 | 说明 | 告警阈值 |
|------|------|---------|
| 缓存命中率 | 命中请求/总请求 | < 80%告警 |
| 缓存平均响应时间 | Redis查询耗时 | > 5ms告警 |
| 缓存穿透率 | 空值查询/总查询 | > 5%告警 |
| 缓存内存使用率 | used_memory / maxmemory | > 80%告警 |
| 缓存key数量 | 当前key总数 | 突增告警 |
| 缓存淘汰数 | evicted_keys | > 0告警（说明内存不足） |

### 4.3 缓存key设计规范

```text
命名规范：业务:实体:ID:字段
示例：
- user:123:info        — 用户123的基本信息
- product:456:stock    — 商品456的库存
- order:789:detail     — 订单789的详情
- cart:user123:items   — 用户123的购物车

TTL规范：
- 热点数据：不过期（逻辑过期）或长TTL（24h+）
- 普通数据：1-6小时
- 临时数据：1-5分钟
- 空值缓存：30-60秒

序列化规范：
- 使用JSON序列化（可读性好）
- 大对象使用Protobuf/Kryo（节省空间）
- 避免使用Java序列化（版本兼容问题）
```

## 五、进阶与最佳实践

### 5.1 缓存一致性方案选型

| 业务场景 | 一致性要求 | 推荐方案 |
|---------|-----------|---------|
| 商品详情、文章内容 | 最终一致（分钟级） | Cache Aside + TTL |
| 库存、余额 | 强一致 | 分布式锁 + 延迟双删 |
| 配置、字典 | 最终一致（小时级） | Cache Aside + 长TTL |
| 会话、Token | 强一致 | 只写缓存，不写DB |
| 排行榜、计数 | 最终一致 | Redis为主，定期持久化 |
| 多表关联查询 | 最终一致 | Canal订阅binlog更新 |

### 5.2 最佳实践清单

- [ ] 读操作：先缓存后DB，未命中回写缓存
- [ ] 写操作：先更新DB，再删除缓存（Cache Aside）
- [ ] 缓存key设计规范（业务:实体:ID）
- [ ] TTL加随机值，避免缓存雪崩
- [ ] 热点key使用互斥锁或逻辑过期
- [ ] 不存在的数据缓存空值或布隆过滤器
- [ ] 多级缓存（本地+分布式）提升可用性
- [ ] 缓存高可用（Sentinel/Cluster）
- [ ] 缓存监控（命中率、响应时间、内存使用）
- [ ] 关键数据使用延迟双删或MQ最终一致
- [ ] 定期清理无效缓存，避免内存泄漏

### 5.3 缓存降级策略

```text
缓存不可用时的降级方案：
1. 本地缓存兜底（Caffeine/Guava Cache）
2. 限流（只允许部分请求直达DB）
3. 返回默认值/静态页面
4. 熔断（快速失败，避免DB被打垮）
5. 异步重建缓存（后台线程预热）

示例（Resilience4j熔断）：
@CircuitBreaker(name = "userCache", fallbackMethod = "getUserFallback")
public User getUser(Long id) {
    // 查缓存+DB
}

public User getUserFallback(Long id, Exception e) {
    // 降级：返回默认用户或从本地缓存取
    return localCache.get(id);
}
```
