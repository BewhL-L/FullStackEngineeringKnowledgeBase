# 项目启动文档模板

> **文档说明**：提供完整可复用的项目启动文档（Kickoff Document）模板，涵盖项目背景、目标范围、干系人、需求清单、技术方案、里程碑计划、风险管理、沟通机制、验收标准等核心模块，含填写示例和使用说明，适用于全栈项目、开源项目、企业内部项目的启动阶段。
>
> **适用人群**：项目经理、技术负责人、全栈开发者、需要规范项目启动流程的团队
>
> **前置知识**：[[开源项目README规范]]、[[敏捷开发与Scrum]]、项目管理基础

---

## 一、概述

### 1. 为什么需要项目启动文档

项目启动文档（Project Kickoff Document）是项目正式开始前的**纲领性文件**，它的核心价值是：

| 价值 | 说明 |
|------|------|
| **对齐认知** | 所有干系人对项目背景、目标、范围达成一致 |
| **明确边界** | 清晰定义做什么、不做什么，避免范围蔓延 |
| **风险前置** | 在项目开始前识别主要风险，制定应对策略 |
| **责任到人** | 明确每个角色的职责和决策权限 |
| **可追溯** | 项目过程中的变更可以对照启动文档评估影响 |
| **减少返工** | 需求和方案在启动阶段确认，避免开发中反复修改 |

**没有启动文档的后果**：
- 项目进行到一半发现目标理解不一致
- 需求不断增加，工期无限延长
- 出了问题互相推诿，找不到责任人
- 技术方案临时拍脑袋，后期大量重构
- 验收时甲乙双方对"完成"的定义不一致

### 2. 启动文档 vs 其他项目文档

| 文档 | 阶段 | 侧重点 | 粒度 |
|------|------|--------|------|
| **项目启动文档** | 启动前 | 目标、范围、方案、风险、计划 | 中高层 |
| **需求文档（PRD）** | 需求阶段 | 功能需求、用户故事、交互细节 | 详细 |
| **技术方案文档** | 设计阶段 | 架构设计、技术选型、接口定义 | 技术细节 |
| **项目计划（甘特图）** | 计划阶段 | 任务分解、时间节点、依赖关系 | 任务级 |
| **复盘文档** | 项目结束 | 经验总结、问题分析、改进措施 | 回顾 |

启动文档是**其他文档的总纲**，PRD、技术方案、项目计划都应该在启动文档的框架下展开。

### 3. 适用场景

| 场景 | 是否需要 | 简化程度 |
|------|---------|---------|
| **企业级项目（3人以上，1个月以上）** | 必须 | 完整填写所有模块 |
| **全栈实战项目** | 推荐 | 填写核心模块，可简化部分 |
| **开源项目** | 推荐 | 重点写背景、目标、路线图、贡献指南 |
| **个人小项目（1人，1周内）** | 可选 | 只写目标、范围、里程碑即可 |
| **Bug 修复/小迭代** | 不需要 | 用 Issue/PR 描述即可 |

## 9. 质量保障

### 9.1 质量标准

| 维度 | 标准 | 度量方式 |
|------|------|---------|
| 代码质量 | 代码评审通过率 100%，Lint 零错误 | 代码评审记录、CI 检查 |
| 测试覆盖 | 单元测试覆盖率 > 80%，核心模块 > 90% | 覆盖率报告 |

## 三、使用说明

### 1. 填写顺序建议

```mermaid
graph LR
    A[1. 项目背景] --> B[2. 目标与范围]
    B --> C[3. 干系人与角色]
    C --> D[4. 需求清单]
    D --> E[5. 技术方案]
    E --> F[6. 里程碑计划]
    F --> G[7. 风险管理]
    G --> H[8. 沟通机制]
    H --> I[9. 质量保障]
    I --> J[10. 部署运维]
    J --> K[11. 验收标准]
```

### 2. 不同规模项目的裁剪

| 项目规模 | 保留模块 | 简化模块 | 可省略模块 |
|---------|---------|---------|-----------|
| **大型项目（5人+，3月+）** | 全部 | - | - |
| **中型项目（3-5人，1-3月）** | 全部 | 需求清单可简化 | 术语表可省略 |
| **小型项目（1-3人，2周-1月）** | 1,2,3,5,6,7,11 | 干系人可简化 | 4,8,9,10 可合并简化 |
| **个人项目（1人，2周内）** | 1,2,6,11 | 全部简化 | 3,4,5,7,8,9,10 可省略 |

### 3. 填写注意事项

| 注意事项 | 说明 |
|---------|------|
| **目标要 SMART** | 具体（Specific）、可衡量（Measurable）、可达成（Achievable）、相关（Relevant）、有时限（Time-bound） |
| **范围要明确** | 不仅要写"做什么"，更要写"不做什么"，避免范围蔓延 |
| **风险要具体** | 不要写"可能有技术风险"，要写"XX 技术在高并发下可能不稳定，概率中，影响高" |
| **计划要现实** | 不要过度乐观，预留 20% 缓冲时间应对意外 |
| **责任要到人** | 每个任务、每个风险都要有明确的负责人，不能写"团队" |
| **文档要活的** | 启动文档不是写完就锁起来，项目过程中要定期更新变更记录 |
| **要评审确认** | 启动文档完成后要组织所有干系人评审，确认后签字生效 |

### 4. 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 目标模糊（"提升用户体验"） | 无法衡量是否达成 | 具体可衡量（"用户满意度从 80% 提升到 90%"） |
| 范围不明确 | 范围蔓延，工期失控 | 明确列出"做什么"和"不做什么" |
| 风险只列不应对 | 风险发生时手忙脚乱 | 每个风险都有应对策略和具体措施 |
| 计划过于乐观 | 不断延期，团队疲惫 | 参考历史数据，预留缓冲 |
| 责任不清晰 | 出问题互相推诿 | RACI 矩阵，每个任务明确 R 和 A |
| 文档写完不更新 | 文档与实际脱节，失去价值 | 定期更新，变更走审批 |
| 不评审直接执行 | 理解不一致，后期返工 | 组织评审会，所有干系人确认 |
