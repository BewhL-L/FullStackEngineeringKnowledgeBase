# 前后端联调规范与流程

> **文档说明**：系统讲解前后端联调的完整流程和规范，包括联调前准备、接口设计规范、接口文档管理、Mock 方案、联调流程、问题排查、协作规范，以及生产级最佳实践和常见问题。
>
> **适用人群**：全栈开发者、前端开发工程师、后端开发工程师、项目经理、需要前后端协作的团队
>
> **前置知识**：[[CORS跨域解决方案实战]]、[[RESTfulAPI设计原则]]、[[接口测试与Postman实战]]、[[API安全最佳实践]]

## 一、概述

### 1. 什么是前后端联调

**前后端联调**是指前端和后端开发者在各自完成开发后，将前端页面与后端接口进行对接调试，确保数据流转正确、功能完整可用的过程。

### 2. 联调目标

- [ ] **接口对齐**：前后端对接口定义达成一致
- [ ] **数据正确**：请求参数和响应数据格式正确
- [ ] **功能完整**：业务流程端到端跑通
- [ ] **异常处理**：错误场景处理完善
- [ ] **性能达标**：接口响应时间满足要求
- [ ] **减少返工**：提前发现问题，降低后期修改成本

### 3. 联调常见痛点

| 痛点 | 说明 | 解决方案 |
|------|------|---------|
| **接口变更频繁** | 后端改接口不通知前端 | 接口文档版本管理、变更通知 |
| **字段不一致** | 前端期望字段与后端返回不同 | 统一接口文档、Mock 数据 |
| **联调环境问题** | 环境不稳定、数据不一致 | 稳定的联调环境、Mock 数据 |
| **错误处理缺失** | 只测正常流程，不测异常 | 异常场景用例、错误码规范 |
| **沟通成本高** | 来回沟通接口细节 | 接口文档先行、自动化工具 |
| **进度不同步** | 前端等后端、后端等前端 | 并行开发、Mock 先行 |

## 二、联调前准备

### 1. 接口文档先行

**接口文档是联调的基础**，必须在开发前完成并评审。

```text
接口文档应包含：
1. 接口基本信息：名称、路径、方法、描述
2. 请求参数：参数名、类型、是否必填、说明、示例
3. 响应数据：字段名、类型、说明、示例
4. 错误码：错误码、错误信息、说明
5. 请求示例：完整的请求示例
6. 响应示例：成功和失败的响应示例
7. 备注：特殊说明、注意事项
```

### 2. 接口文档工具

| 工具 | 特点 | 适用场景 |
|------|------|---------|
| **Swagger/OpenAPI** | 代码注解自动生成、标准规范 | Spring Boot 项目 |
| **Apifox** | 接口设计+文档+Mock+测试一体化 | 团队协作、全流程 |
| **YApi** | 开源、接口管理+Mock | 内网部署、开源团队 |
| **Postman** | 接口测试+文档+Mock | 接口测试为主 |
| **ShowDoc** | 轻量文档工具 | 简单文档需求 |
| **Confluence** | 通用文档平台 | 企业知识库 |

### 3. 环境准备

| 环境 | 用途 | 数据 |
|------|------|------|
| **开发环境** | 前后端各自开发 | Mock 数据 / 开发库 |
| **联调环境** | 前后端联调 | 稳定的测试数据 |
| **测试环境** | QA 测试 | 完整测试数据 |
| **预发布环境** | 上线前验证 | 生产数据快照 |
| **生产环境** | 正式上线 | 真实数据 |

### 4. 联调 Checklist

- [ ] 接口文档已评审并确认
- [ ] 接口 Mock 已就绪
- [ ] 联调环境已部署
- [ ] 测试数据已准备
- [ ] 跨域配置已完成
- [ ] 认证授权已打通
- [ ] 错误码规范已统一
- [ ] 联调时间已约定

## 三、接口设计规范

### 1. RESTful 规范

详细参考 [[RESTfulAPI设计原则]]。

```text
URL 设计：
- 使用名词复数：/users, /orders
- 使用小写和连字符：/user-profiles
- 层级不超过 3 层：/users/{id}/orders

HTTP 方法：
- GET：查询
- POST：创建
- PUT：全量更新
- PATCH：部分更新
- DELETE：删除
```

### 2. 请求规范

```json
// 请求头
Content-Type: application/json
Authorization: Bearer <token>
X-Request-Id: <唯一请求ID，用于追踪>

// 请求体（JSON）
{
  "name": "张三",
  "email": "zhangsan@example.com",
  "age": 25
}
```

### 3. 响应规范

```json
// 成功响应（直接返回数据）
{
  "id": 123,
  "name": "张三",
  "createdAt": "2026-08-27T10:00:00Z"
}

// 列表响应（含分页）
{
  "data": [
    { "id": 1, "name": "张三" },
    { "id": 2, "name": "李四" }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 100,
    "totalPages": 5
  }
}

// 错误响应（统一格式）
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数校验失败",
    "details": [
      { "field": "email", "message": "邮箱格式不正确" }
    ],
    "requestId": "req-abc123",
    "timestamp": "2026-08-27T10:00:00Z"
  }
}
```

### 4. 错误码规范

| HTTP 状态码 | 错误码 | 说明 |
|------------|--------|------|
| 400 | VALIDATION_ERROR | 参数校验失败 |
| 401 | AUTH_REQUIRED | 未认证 |
| 401 | TOKEN_EXPIRED | Token 过期 |
| 403 | FORBIDDEN | 无权限 |
| 404 | NOT_FOUND | 资源不存在 |
| 409 | DUPLICATE | 资源重复 |
| 429 | RATE_LIMITED | 请求过于频繁 |
| 500 | INTERNAL_ERROR | 服务器内部错误 |

### 5. 字段命名规范

| 规范 | 说明 | 示例 |
|------|------|------|
| **camelCase** | JSON 字段小驼峰 | `userName`, `createdAt` |
| **时间格式** | ISO 8601 UTC | `"2026-08-27T10:00:00Z"` |
| **布尔值** | true/false | `"active": true` |
| **枚举** | 字符串 | `"status": "ACTIVE"` |
| **ID** | 字符串（防精度丢失） | `"id": "1234567890"` |
| **金额** | 分为单位整数 | `"amount": 1000` |

## 四、Mock 方案

### 1. Mock 的价值

- [ ] **并行开发**：前端不依赖后端接口完成开发
- [ ] **稳定数据**：Mock 数据稳定，不受后端影响
- [ ] **异常模拟**：方便模拟各种异常场景
- [ ] **演示可用**：产品演示时不依赖后端
- [ ] **减少等待**：前端提前完成页面开发

### 2. Apifox Mock（推荐）

Apifox 支持智能 Mock，根据字段名和类型自动生成合理数据：

```text
Apifox Mock 功能：
1. 智能 Mock：根据字段名自动生成（name→姓名、phone→手机号）
2. 自定义 Mock：使用 Mock.js 语法自定义
3. 期望 Mock：根据请求参数返回不同响应
4. 脚本 Mock：使用 JavaScript 脚本动态生成
5. 云端 Mock：团队共享 Mock 数据
```

### 3. Mock.js

```javascript
// Mock.js 示例
import Mock from 'mockjs'

// 拦截请求，返回 Mock 数据
Mock.mock('/api/users', 'get', {
  'data|10-20': [{
    'id|+1': 1,
    'name': '@cname',           // 中文名字
    'email': '@email',          // 邮箱
    'phone': /^1[3-9]\d{9}$/,   // 手机号正则
    'avatar': '@image("100x100")',  // 图片
    'createdAt': '@datetime',   // 日期时间
    'status|1': ['ACTIVE', 'INACTIVE']  // 枚举
  }],
  'pagination': {
    'page': 1,
    'pageSize': 20,
    'total|100-500': 100
  }
})

// 模拟错误响应
Mock.mock('/api/users/error', 'get', {
  'error': {
    'code': 'INTERNAL_ERROR',
    'message': '服务器内部错误'
  }
})
```

## 五、联调流程

### 1. 完整联调流程

```mermaid
graph LR
    A[1.需求评审] --> B[2.接口设计]
    B --> C[3.接口评审]
    C --> D[4.后端开发+Mock]
    D --> E[5.前端开发+Mock]
    E --> F[6.后端自测]
    F --> G[7.前端自测]
    G --> H[8.前后端联调]
    H --> I[9.问题修复]
    I --> J[10.测试验收]
    J --> K[11.上线发布]
```

### 2. 各阶段说明

| 阶段 | 参与方 | 产出 | 时间 |
|------|--------|------|------|
| **需求评审** | 产品+前后端+测试 | 需求文档、原型 | 需求阶段 |
| **接口设计** | 后端主导，前端参与 | 接口文档初稿 | 设计阶段 |
| **接口评审** | 前后端+测试 | 确认的接口文档 | 设计阶段 |
| **Mock 搭建** | 前端或后端 | 可用的 Mock 接口 | 开发前 |
| **并行开发** | 前后端各自 | 前端页面+后端接口 | 开发阶段 |
| **联调** | 前后端 | 联调通过的功能 | 开发后期 |
| **测试** | QA+前后端 | 测试报告 | 测试阶段 |
| **上线** | 运维+前后端 | 生产环境 | 发布阶段 |

### 3. 联调会议

```text
联调会议议程：
1. 确认联调范围和优先级
2. 逐个接口验证：
   - 正常流程
   - 参数校验
   - 异常处理
   - 边界条件
3. 记录问题和责任人
4. 约定修复时间和回归时间
5. 下次联调时间

联调会议产出：
- 联调问题清单（问题描述、责任人、截止时间）
- 未解决问题列表
- 下次联调计划
```

## 六、联调问题排查

### 1. 常见问题分类

| 类别 | 问题 | 排查方向 |
|------|------|---------|
| **网络问题** | 接口不通、超时 | 网络、防火墙、代理、CORS |
| **参数问题** | 400 错误、参数缺失 | 请求参数、类型、格式 |
| **认证问题** | 401/403 | Token、权限、Header |
| **数据问题** | 字段不一致、数据为空 | 响应字段、数据类型、Mock |
| **逻辑问题** | 业务结果不对 | 业务逻辑、数据状态 |
| **性能问题** | 响应慢、超时 | 慢查询、大数据量、缓存 |

### 2. 排查工具

| 工具 | 用途 |
|------|------|
| **浏览器 DevTools** | 查看请求/响应、Network 面板 |
| **Postman/Apifox** | 独立测试接口，排除前端问题 |
| **后端日志** | 查看请求是否到达、参数、异常 |
| **接口文档** | 核对接口定义 |
| **charles/Fiddler** | 抓包分析 |
| **X-Request-Id** | 全链路追踪 |

### 3. 排查流程

```text
1. 确认问题：复现问题，记录请求和响应
2. 定位层级：
   - 用 Postman 测试接口 → 正常？→ 前端问题
   - 用 Postman 测试接口 → 异常？→ 后端问题
3. 前端问题：
   - 检查请求 URL、方法、参数
   - 检查请求头（Content-Type、Authorization）
   - 检查响应处理逻辑
4. 后端问题：
   - 查看后端日志
   - 检查参数绑定
   - 检查业务逻辑
   - 检查数据库查询
5. 跨域问题：参考 [[CORS跨域解决方案实战]]
```

## 七、协作规范

### 1. 沟通规范

- [ ] **接口变更通知**：接口变更必须提前通知前端，更新文档
- [ ] **问题记录**：联调问题记录在共享文档，明确责任人和时间
- [ ] **及时响应**：联调期间问题及时响应，不超过 2 小时
- [ ] **每日同步**：联调期间每日站会同步进度和问题
- [ ] **版本管理**：接口版本化，变更走版本流程

### 2. 接口变更流程

```text
接口变更流程：
1. 后端提出变更需求
2. 更新接口文档
3. 通知前端评审
4. 双方确认变更影响
5. 后端实现变更（保留旧版本兼容）
6. 前端适配
7. 联调验证
8. 旧版本下线（确认无使用后）
```

### 3. 代码规范

- [ ] **前端**：API 层统一封装，错误处理统一，类型定义完整
- [ ] **后端**：参数校验、统一响应格式、错误码规范、日志完整
- [ ] **共同**：接口文档与代码同步更新

### 4. 前端 API 层封装

```typescript
// api/request.ts
import axios, { AxiosError } from 'axios'
import { ElMessage } from 'element-plus'

const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10000,
  withCredentials: true
})

// 请求拦截器
request.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) {
    config.headers.Authorization = `Bearer ${token}`
  }
  config.headers['X-Request-Id'] = generateRequestId()
  return config
})

// 响应拦截器
request.interceptors.response.use(
  response => response.data,
  (error: AxiosError) => {
    const status = error.response?.status
    const data = error.response?.data as any

    switch (status) {
      case 401:
        // 未认证，跳登录
        router.push('/login')
        break
      case 403:
        ElMessage.error('无权限访问')
        break
      case 429:
        ElMessage.error('请求过于频繁，请稍后重试')
        break
      case 500:
        ElMessage.error(data?.error?.message || '服务器错误')
        break
      default:
        ElMessage.error(data?.error?.message || '请求失败')
    }
    return Promise.reject(error)
  }
)

export default request
```

## 八、最佳实践

### 1. 提升联调效率

- [ ] **接口先行**：先定接口，再写代码
- [ ] **Mock 先行**：Mock 就绪后前端并行开发
- [ ] **自动化测试**：后端接口自动化测试，保证质量
- [ ] **契约测试**：Pact 等契约测试，防止接口破坏
- [ ] **容器化环境**：Docker 一键启动联调环境
- [ ] **数据脚本**：测试数据初始化脚本，一键重置
- [ ] **实时沟通**：联调期间集中办公或视频会议

### 2. 质量保障

- [ ] **后端自测**：后端用 Postman/Apifox 自测通过后再联调
- [ ] **前端自测**：前端用 Mock 自测页面逻辑
- [ ] **异常测试**：联调必须覆盖异常场景
- [ ] **边界测试**：空值、最大值、特殊字符
- [ ] **性能测试**：核心接口响应时间达标
- [ ] **安全测试**：权限、越权、注入

### 3. 文档维护

- [ ] **文档即代码**：Swagger 注解自动生成，代码与文档同步
- [ ] **版本管理**：接口文档版本化，变更可追溯
- [ ] **变更日志**：记录接口变更历史
- [ ] **定期清理**：下线旧版本接口，清理废弃文档

## 九、常见问题与排查

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **接口字段不一致** | 文档未更新 / 沟通不及时 | 以文档为准，更新文档，通知对方 |
| **前端等后端** | 后端开发慢 / 未提供 Mock | 提前搭建 Mock，前端并行开发 |
| **联调环境不稳定** | 频繁部署 / 数据被改 | 稳定联调环境，数据隔离，禁止随意改数据 |
| **接口频繁变更** | 需求变更 / 设计不完善 | 需求评审充分，接口评审严格，变更走流程 |
| **错误处理不统一** | 错误码不规范 / 前端未处理 | 统一错误码规范，前端统一错误处理 |
| **跨域问题** | CORS 未配置 | 参考 [[CORS跨域解决方案实战]] |
| **认证不通** | Token 传递问题 / 过期 | 检查 Authorization 头、Token 刷新机制 |
| **文件上传失败** | Content-Type / 大小限制 | 不手动设 Content-Type，检查大小限制 |
| **分页数据不对** | 分页参数不一致 | 统一分页参数名和响应格式 |
| **时间格式不一致** | 时区 / 格式问题 | 统一 ISO 8601 UTC，前端处理时区 |
| **大数字精度丢失** | Long 类型 JS 精度丢失 | ID 用字符串，或后端转 String |
| **枚举值不匹配** | 前后端枚举定义不同 | 文档明确枚举值，共享类型定义 |
| **Mock 与真实接口差异** | Mock 数据不真实 | Mock 尽量贴近真实数据格式 |
| **联调进度慢** | 问题堆积 / 沟通不畅 | 每日同步、问题清单、及时修复 |
| **环境数据污染** | 多人共用数据互相影响 | 每人独立测试账号 / 数据隔离 |
