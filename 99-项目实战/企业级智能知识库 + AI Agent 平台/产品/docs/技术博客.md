# 从零搭建一个 RAG 企业知识库问答系统（技术博客）

> 这是一篇可发布到掘金/知乎/CSDN 的技术博客初稿，记录从 0 到 1 的实现过程。

## 为什么要做 RAG

大模型很强大，但它有三个硬伤：知识有截止日期、会"一本正经地胡说八道"（幻觉）、不知道企业内部资料。

微调（Fine-tuning）能改变模型能力，但成本高、更新慢，而且不适合"灌入"大量知识。

RAG（Retrieval-Augmented Generation，检索增强生成）提供了另一种思路：**不在模型里记知识，而是回答前先去知识库里翻资料**。模型只负责理解问题、组织语言，知识全部来自你提供的文档。这带来三个好处：答案可溯源、知识实时更新、大幅降低幻觉。

## 系统整体架构

系统采用前后端分离架构：

- **前端**：Vue3 + TypeScript + Element Plus，负责知识库管理和聊天界面
- **后端**：FastAPI，提供 RESTful API 和 SSE 流式接口
- **关系数据库**：SQLite（SQLAlchemy ORM），存用户、知识库、对话等业务数据
- **向量数据库**：Chroma，存文档切片的向量
- **大模型**：通过 OpenAI 兼容接口调用，方便切换不同厂商

## 核心流程拆解

### 第一步：文档入库（离线索引）

文档上传后，要经历一条流水线：

```
原始文档 → 文本解析 → 文本切片 → Embedding 向量化 → 存入向量库
```

**文本解析**：PDF 用 PyPDF2，Word 用 python-docx，纯文本直接读。需要注意 PDF 提取的文本经常有断行，要做清洗。

**文本切片（Chunking）**是最影响效果的一环。我没有简单地按固定字数硬切，而是按段落、句子边界切，超长段落再按句子拆，并用贪心策略把句子聚合成块。相邻块之间保留 50 字的 overlap，避免一句话被拦腰截断、上下文丢失。

**为什么切片这么重要？** 因为检索的最小单位就是一个 chunk。块太大，检索回来的内容噪声多，还浪费 token；块太小，语义不完整。我最终用 500 字左右，是在"语义完整"和"检索精准"之间的折中。

### 第二步：语义检索

用户提问时，把问题也送进 Embedding 模型转成向量，然后在向量库里做余弦相似度检索，取最相关的 Top 5 片段。

传统的关键词搜索（like 模糊匹配）只能匹配字面相同的词，而向量检索能匹配语义——比如"退货"和"退款政策"字面不同，但语义相近，向量检索能召回。

### 第三步：拼接 Prompt 并生成

我把检索到的片段编号、标注来源，塞进系统提示词，并明确要求模型：

1. 只基于资料回答，不能编造；
2. 资料里没有就明说，不要硬答；
3. 回答条理清晰。

这样把模型"约束"在知识库范围内。模型输出后，我把每个片段对应的文档名、相似度一起返回，前端可以展开"参考来源"，做到答案可溯源。

## 两个有技术含量的点

### 1. SSE 流式输出，实现打字机效果

普通 HTTP 请求要等整个答案生成完才返回，大模型生成几百字可能要十几秒，体验很差。

我用 SSE（Server-Sent Events）做流式输出：后端用 FastAPI 的 StreamingResponse，每生成一个 token 就 yield 一个 SSE 事件；前端用 fetch 的 ReadableStream 读取数据流，逐字追加到聊天气泡。这里有个坑：**Nginx 默认会缓冲响应**，导致流式失效、变成整段返回，需要在响应头加 `X-Accel-Buffering: no` 并关闭 `proxy_buffering`。

### 2. 用 Function Calling 实现 AI Agent

RAG 只能回答知识库里的问题，但有些问题需要"动手"，比如"现在几点""帮我算一下折扣"。

我基于 Function Calling 实现了 Agent：把工具的名称、描述、参数 Schema 一起发给模型，模型自己判断要不要调工具、调哪个、传什么参数。后端执行函数拿到结果，再喂回模型，模型据此组织最终回答。这个"思考 → 调用工具 → 拿到结果 → 再思考"的循环，是 Agent 区别于普通问答的关键。

我还特意用 Python 的 AST 模块做了一个安全的计算器，而不是用 `eval`，避免代码注入风险。

## 工程上的一些处理

- **异步文档处理**：文档解析向量化可能耗时，放在后台线程执行，上传接口秒返回，前端轮询状态
- **JWT 鉴权**：登录返回 token，接口用依赖注入校验，数据按用户隔离
- **多知识库隔离**：每个知识库对应一个向量 collection
- **级联删除**：删除知识库时同步清理数据库记录、原始文件和向量数据

## 部署

用 Docker 多阶段构建：前端 Node 构建后交给 Nginx 托管，Nginx 同时负责把 `/api` 请求反向代理到后端，`docker-compose up` 一键启动。

## 总结

这个项目让我完整走通了一个 AI 产品的全链路：从文档解析、切片策略、向量检索、Prompt 工程，到流式输出、Agent 工具调用，再到容器化部署。最大的体会是：**RAG 的难点不在"调通"，而在"调好"**——切片策略、检索质量、Prompt 约束，每一处都直接影响最终效果。
