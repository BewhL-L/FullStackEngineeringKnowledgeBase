# 微调（Fine-tuning）vs RAG 选型指南

很多人一上来就想"微调一个自己的模型"，这在工程上往往是错误的第一选择。两者解决的是**不同层面的问题**。

## 一、本质区别

| 维度 | RAG（检索增强生成） | Fine-tuning（微调） |
|---|---|---|
| 解决什么 | **知识从哪来**（事实、数据、最新信息） | **怎么说 / 会不会某项技能**（风格、格式、行为模式） |
| 知识更新 | 改文档即可，分钟级生效 | 需重新训练，成本高、周期长 |
| 可解释/可溯源 | 能给出处，便于核对 | 黑盒，难定位错误来源 |
| 幻觉控制 | 强（约束在资料内） | 弱 |
| 数据需求 | 少量文档即可 | 通常需要数百~数千条高质量样本 |
| 成本 | 低（无需训练） | 高（训练 + 算力 + 维护） |
| 适合冷启动 | ✅ 非常适合 | ❌ 不适合 |

## 二、决策顺序（重要）

```
1. 先做 RAG，把"知识"问题解决
2. 再做 Prompt 工程 + 上下文工程，把"行为"调好
3. 只有当 RAG + Prompt 都无法稳定满足时，才考虑微调
```

## 三、什么时候才真正需要微调

- **固定的输出风格 / 语气 / 品牌调性**，Prompt 怎么写都不稳定（如特定行业话术、法律文书格式）
- **需要模型掌握一项"技能"**，而非知识（如固定的结构化抽取格式、特定分类任务，且对延迟/成本敏感）
- **领域语言高度特殊**（如某些医疗/化学/代码方言），通用模型理解困难
- **有大量、稳定、高质量的历史样本**（≥ 几百条，且可持续积累）
- **需要降低单次调用成本/延迟**：用小模型微调后替代大模型

## 四、什么时候不该微调（你的项目初期都属于这类）

- 知识经常变（产品价格、政策、库存）→ 微调进去的知识很快过时，用 RAG
- 数据很少 / 质量参差 → 微调会放大噪声、降低泛化
- 只是"想让它知道我们公司的资料" → 这是知识问题，**RAG 才是正解**
- 没有评测基线 → 无法判断微调是否真的变好

## 五、二者可以结合（成熟形态）

> **RAG 提供知识，微调塑造行为。**

例如：用几百条高质量客服对话微调一个小模型，让它稳定输出"共情 + 分点 + 主动引导"的客服风格；同时每次回答仍通过 RAG 实时检索最新政策。本项目已为这条路径预留：
- 知识：`retrieval/` + `rag_service.py`
- 数据：`evaluation/data/golden_qa.json` 与用户反馈（点赞/点踩）是未来微调的数据来源
- 脚本：`backend/scripts/finetune/`

## 六、RAG + LLM Wiki：知识的"检索"与"编译"双层架构

在 RAG 之上，还可以叠加一层 **LLM Wiki（知识编译层）**，解决朴素 RAG「知识碎片化、新旧无关联、无沉淀」的问题：

| 层 | 时机 | 形态 | 职责 |
| --- | --- | --- | --- |
| RAG 检索层 | 查询时 | 向量 chunk | 全量数据的快速召回（便宜、高并发、可扩展） |
| LLM Wiki 编译层 | 写入时 | 结构化 Markdown 页面 | 高频核心知识的沉淀、全局一致性、跨文档冲突检测 |

工作方式：
- **写入时**：文档入库后由 LLM 抽取实体、生成/更新结构化页面、检测冲突、维护双向链接。
- **查询时**：简单事实题直接查 chunk；全局理解题（对比/总结/原理）先读 Wiki 页面，再配合原始 chunk 一起送入上下文。

> 关键认知：**LLM Wiki 不是 RAG 的替代品，而是分层叠加**。RAG 仍是海量数据的底座，Wiki 只覆盖高频核心知识——因为编译成本随实体数线性增长，不适合百万级全量编译。详见开发指导中的《11-LLM Wiki 编译型知识库深度指南》。

## 七、面试怎么讲（差异化）

> "我没有盲目微调。我先用评测集定位问题：如果是检索不到/知识缺失，我优化检索（混合检索、Rerank、查询改写）；如果检索到了但表达不稳定，我做 Prompt 和上下文工程；只有当问题稳定地出现在'输出风格/技能'层面、且我积累了足够高质量样本时，才会用微调。微调前后我都会用同一套评测集做 A/B，确保是可量化的提升而不是'感觉变好了'。"

这套"**先诊断、再决定优化手段、用指标验证**"的思路，正是资深工程师和"调包侠"的区别。
