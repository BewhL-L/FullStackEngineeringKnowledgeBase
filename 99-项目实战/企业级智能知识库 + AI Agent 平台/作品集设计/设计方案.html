01

设计命题

THE PROBLEM

作品集不是「把简历搬到网页上」，而是一次针对三类读者的、有说服力的演示。

1.1 三类读者，三种读法
读者停留他想确认什么对应设计
招聘 HR / 猎头8–15 秒方向对不对、能不能投、在哪个城市首屏一句话主张 + 状态条 + Now 屏的四格信息
技术面试官90 秒–8 分钟深度是真是假，能不能扛追问证据抽屉、能力剖面、项目深潜页、不会清单
同行 / 社区3 分钟品味、方法论、有没有自己的东西检索式导航、写作、方法章节、彩蛋
1.2 要避开的五个通病
通病为什么致命本方案的解法
紫色渐变 + 玻璃卡片 + 漂浮 3D 球模板味，一眼看出是套壳墨／纸两色 + 发丝线 + 宋体，靠排版而不是特效
logo 墙当技术栈只能证明「用过」，不能证明「会」能力剖面：分层 + 深度 + 证据 + 不会清单
「精通 / 熟练掌握」不可验证，等同没说只写能白板手写的东西，其余标 3/5
项目卡只有截图 + 一句话看不出你的判断力六段式：问题 / 约束 / 决策 / 证据 / 复盘 / 如果重做
动效堆叠：滚动劫持、鼠标光晕炫技且伤体验，暴露审美判断不足全站只有一个动词：解析。其余一律克制
1.3 三条设计原则

P1证据优先于形容词

页面上出现的每个数字，都必须能点开看到来源：测试输出、评测报告、文件路径、部署状态。写不出出处的数字，删掉。

P2一个动词贯穿全站

「解析」（parse）——滚动是解析、检索是解析、证据是解析结果。所有动效、图标、文案都服务这一个隐喻，而不是各玩各的。

P3网站本身就是作品

用真实 BM25 做站内检索、用真实测试数做首屏指标、用真实评测数据做图表。与其说「我懂性能」，不如让 LCP 跑进 1.2 秒。

P4给两类人各一条路径

速览模式只留结论与证据，深潜模式展开完整叙事。不是响应式，是「阅读意图」的响应式。

02

核心概念

THE IDEA

「AI 负责快，我负责对。」

这句话同时是主张、是筛选器、是记忆点。它把「vibe coding」这个容易被认为是「让 AI 写完就交」的词，重新定义成一种分工：AI 提供速度，人提供正确性。而那正是你项目里最稀缺、也最难被复制的东西——79 个测试、评测闭环、逐行读懂、容器上线。

2.1 概念结构：主张 → 证据 → 出处
层在页面上的形态回答的问题示例
主张 Claim宋体大标题 + 一句话你是谁、凭什么AI 负责快，我负责对。
证据 Evidence等宽数字 / 指标行 / 架构图拿什么证明79 tests · 10 层 · 3 路检索 · 5 容器
出处 Source证据条 → 右侧抽屉在哪里能查到backend/tests · pytest
CONCEPT RULE任何一个模块，如果不能同时说出「主张 / 证据 / 出处」，就不该出现在首页。这是整份方案里最硬的一条约束。
2.2 为什么是「证据链」而不是「作品集」

作品集的默认叙事是「我做过什么」，证据链的叙事是「我判断对了什么」。前者靠堆项目，后者靠暴露决策。你只有一个主项目，堆不了数量，但你有大量可展示的判断：为什么加 BM25、为什么 RRF 不看绝对分数、为什么 Nginx 要关 proxy_buffering、为什么 79 个用例比 100 个功能更能说明问题。

这些判断，恰好是面试官真正会追问的东西。把它们前置到网站上，等于提前完成了半场面试。

03

视觉语言

VISUAL LANGUAGE

墨、纸、朱砂。像一份案卷，而不是一张海报。

3.1 三声音阶：每种字体只干一件事
SERIF / 宋主张
Noto Serif SC 500
AI 负责快，我负责对。
只用于 h1 / h2 / 引文。宋体的「判词感」让口号不像广告，像结论。
MONO / 等宽证据
JetBrains Mono 400
79 TESTS · chunk_03 · Hit@K · backend/tests
只用于编号、路径、指标、时间、标签。等宽 = 可核对，天然带「原始数据」的可信度。
SANS / 黑解释
Noto Sans SC 300
正文只负责把事情说清楚，不抢戏。行高 1.72，每行不超过 62 个字符。
字重 300 让中文在小字号下更透气，但最小字号不低于 12px。

规则：一个元素只能有一种声音。标题里混等宽、正文里混宋体，都会立刻露出「拼贴感」。

3.2 色彩：四种颜色，各有配额
约束具体做法
朱砂不做大面积背景只出现在按钮、编号、印章、关键数字、链接下划线。一屏最多三处。
薄荷只表示「通过」绿色不用于装饰。它出现，就意味着某个东西被验证了。
不用第二种强调色需要层级就靠字号、字重、留白，不靠加颜色。
3.3 网格与间距
  • 12 列网格，最大内容宽 1240px，左右留白 clamp(20px, 5vw, 64px)
  • 8px 基线；区块间距 96–140px，宁可空，不要挤
  • 正文 62 个字符宽，行高 1.72；标题行高 1.02–1.15
  • 允许非对称：标题贴 1 列，正文缩进到 2 列，制造「排版过」的痕迹
3.4 形状与材质

圆角只用 1–2px，近乎直角。层级靠 1px 发丝线，不靠阴影堆叠。全站叠一层 4% 噪点，让纯黑不死板、截图不发灰。唯一允许的「玻璃」是顶部导航的背景模糊——因为它真的在滚动时起作用，不是装饰。

3.5 图像策略
用它不用它
手绘感架构 SVG（分层、数据流）AI 生成的插画、3D 小人、抽象渐变球
真实产品截图（带 UI 边缘、可放大）套在设备 mockup 里的假截图
评测前后对比图（真实数据）没有坐标轴、没有出处的「效果图」
工作照 / 手写白板照（可选，去滤镜）精修职业照、卡通头像

每张图必须带 caption，写清「这张图证明了什么」。没有 caption 的图，一律删。

3.6 动效：全站只有一个动词
入场REVEAL
上移 16px + 透明度，700–850ms，cubic-bezier(.16,1,.3,1)，只播一次。
解析PARSE
1px 朱砂线扫过标题；流程节点间有光点单向移动；检索结果条 600ms 展开。全部指向「正在读取」。
禁止NEVER
滚动劫持、鼠标跟随光晕、无限旋转、每屏视差、自动播放背景音乐。

降级：prefers-reduced-motion 下关闭全部动效与 Canvas，页面仍然完整可读。

4.3 双读者模式

速览（scan）只保留主张、数字、证据条，隐藏长段落；深潜（deep）展开叙事与决策过程。默认深潜，因为主读者是面试官；HR 可以在导航栏一键切换，切换状态记在 localStorage。

WHY IT WORKS它不是「响应式布局」，而是「响应式意图」。同一个 URL，两种密度，都不牺牲信息完整性——这本身就是一个信息设计能力的展示。
05

模块规格

MODULES

七块积木，每块都有验收标准。

M1Hero

目的：3 秒建立记忆点，同时暴露「可检索」这个钩子。

  • 宋体巨号主张，关键词用朱砂单字
  • 朱砂印章「已评测」，只此一枚
  • 检索输入框：真实 BM25，回车出 3 个 chunk
  • 右侧构建日志：真实日期与事件，不是假终端

验收：遮住正文，只看标题也能复述你是谁。

M2Now

目的：让 HR 在 10 秒内完成「投不投」的判断。

  • 四格：方向 / 城市 / 时间 / 正在做
  • 一句反共识的话：「会用 AI 已经不稀缺了」
  • 不放照片，不放自我介绍长文

验收：四格信息能被一眼扫完，不需要读句子。

M3Work

目的：用一个项目证明深度，用两个副项目证明广度。

  • 主卡：问题 / 我的动作 / 证据 三栏
  • 指标行：79 / 10 / 3 / 5，每个可点开
  • 数据流：上传→解析→切片→向量化→检索→生成
  • 副卡：只留一句问题 + 一个差异点

验收：不看深潜页，也能说出 3 个技术决策。

M4Stack

目的：不列 logo，证明「会到哪一层」。

  • 四层：界面 / 服务 / 检索与 Agent / 工程化
  • 每层：技术串 + 一句能做到什么 + 深度条 + 证据
  • 「还没吃透」清单：K8s、分布式训练、千万级向量库

验收：每一层的深度条都有对应的证据链接。

M5Method

目的：把「vibe coding」从贬义变成方法论。

  • 6 步闭环：验收→约束→读懂→手写→评测→部署复盘
  • 一张真实 prompt 卡：任务 / 约束 / 验收 / 结果
  • 3 条纪律：看不懂不进仓库、一次一个变量、每个产物有验收

验收：读者能复述你的工作流，并相信它可执行。

M6Writing

目的：证明能把技术讲清楚。

  • 只放 3 篇，宁缺毋滥
  • 类型 + 阅读时长 + 日期，不放下划线花活
  • 每篇对应一个能力：架构 / 评测 / 方法

验收：随便点开一篇，前两段没有废话。

M7Contact

目的：让联系这件事零摩擦。

  • 巨号「聊聊？」+ 一句人话
  • 邮箱一键复制（带成功反馈）
  • 简历 PDF / GitHub / 可入职时间
  • 页脚：构建时间、无统计、设计说明入口

验收：从看到页面到复制邮箱，不超过 3 次点击。

M8深潜页

目的：承接面试官的追问。

  • 六段式：问题 / 约束 / 架构 / 三个决策 / 证据 / 如果重做
  • 每个决策必须写 trade-off，而不是只写优点
  • 顶部锚点导航 + 阅读进度
  • 结尾放「这次我哪里做错了」

验收：读完能复述一个你放弃过的方案及原因。

06

亮点交互

SIGNATURE INTERACTIONS

八个交互，每一个都要能回答「为什么必须有它」。

#交互做什么为什么成立实现 / 降级
01站内 BM25 检索输入问题，返回 3 个「页面片段」+ 相似度 + 出处用你项目里的检索范式做导航，形式和内容同构；不是装饰，是真检索构建时生成倒排索引；中文 bigram + 单字，和你后端降级策略一致；失败降级为锚点跳转
02证据抽屉点任意指标，右侧滑出原始输出：测试、路径、架构、diff把「可验证」做成可操作的动作，而不只是一句口号数据放 JSON；键盘可关；无 JS 时退化为详情页锚点
03双读者模式速览 / 深潜一键切换信息密度同时服务 HR 与面试官，避免为一方牺牲另一方html[data-density] 控制显隐；localStorage 记忆
04向量场首屏稀疏点云，随鼠标轻微聚散它是 embedding 空间的隐喻，不是随机粒子特效Canvas 2D，约 80 个点，离屏暂停，reduced-motion 关闭
05朱砂印章「已评测」印章盖在主张句末中式案卷的签字动作，全站唯一的「人味」符号纯 CSS，52×52，旋转 −4°，一屏不超过一枚
06chunk 索引左侧固定编号 01–06，滚动高亮把页面当成一份被切片的文档，呼应 RAG 的 chunkIntersectionObserver；窄屏隐藏
07墨 / 纸反转整站切换深色与纸白两套主题都成立，直接展示 CSS 变量与对比度控制能力CSS 变量 + localStorage；纸白下代码块仍保持深色
08数字即入口79 / 10 / 3 / 5 每个都可点开数字是主张的锚点，点开是证据，形成闭环与证据抽屉共用一套数据源
INTERACTION BUDGET一屏最多两个主动效。第 9 个交互的想法，留到 v2。作品集的说服力来自「克制得刚好」，不是「功能很多」。
07

技术实现

BUILD

用你已有的栈，不引新框架。作品集的代码本身也是样本。

7.1 选型
层选择理由
框架Vue 3 + TypeScript + Vite与主项目一致，面试时同一套话术；构建产物小
样式手写 CSS + 变量，不引 UI 库作品集的视觉就是能力证明，Element Plus 会立刻带来「后台」气质
内容content/*.json + *.md改文案不改组件；构建时生成路由与索引
检索构建时倒排索引 + 前端 BM25无后端、无网络请求、可离线；索引 < 8KB
动效CSS transition + IntersectionObserver + Canvas 2D不引 GSAP / three.js，首屏 JS 控制在 120KB 内
部署Docker + Nginx，复用现有 compose和主项目同一套部署路径，讲得清每一层
7.2 性能预算（写进 CI）
指标预算手段
LCP< 1.2s首屏无大图；字体子集 + font-display:swap
CLS< 0.03预留字高；图片写死宽高比
首屏 JS< 120KB gzip路由级拆分；Canvas 延后到 idle
Lighthouse≥ 95（四项）CI 跑 lhci autorun，低于预算直接 fail
可访问性对比度 ≥ 4.5:1，全键盘可达focus ring、aria、跳过导航、reduced-motion
7.3 三个工程细节（面试可讲）
  • 检索索引怎么来：构建时扫描每个 section 的纯文本（剔除编号、标签、按钮），切 bigram 建倒排表，输出 JSON；运行时只做打分，不做分词。
  • 为什么不用 Algolia：作品集不该有第三方依赖和网络抖动；离线可用，也少一个隐私声明。
  • 主题反转怎么不闪：在 <head> 里内联读取 localStorage 并写 data-theme，避免首帧白闪。
08

内容策略

COPY & NARRATIVE

结构决定下限，文案决定上限。

8.1 项目叙事：六段式
段写什么知识库项目的示范
问题谁痛、痛在哪，不要写行业背景企业知识散在 PDF、Word、Wiki 里。员工找不到，客服重复答，新人上手要三个月。
约束资源、时间、技术边界一个人、8 个月、无 GPU；必须能本地跑起来，必须可评测。
架构一张图 + 三句话10 层：接入 / 网关 / 异步 / 编排 / 检索 / LLM / 输出 / 缓存 / 存储 / 部署。
三个决策每个都要写「放弃了什么」加 BM25 而不是换更强 embedding；RRF 而不是加权求和；自建评测而不是看感觉。
证据可点开的数字与文件79 用例 / 9 文件；三路召回；5 容器；13 视图。
如果重做承认一个真实错误切片策略一开始按固定长度，应该先按标题层级切，再按长度兜底。
8.2 数字纪律
HARD RULE只放能点开验证的数字。三类可用：① 代码事实（文件数、行数、接口数、视图数）；② 测试事实（用例数、通过数、覆盖模块）；③ 评测事实（Hit@K、MRR、忠实度，且附评测集与运行时间）。
「准确率 90%」「效率提升 40%」这类没有压测来源的数字，一律不上网站。
8.3 文案语气
  • 短句。一句一个判断，不用「致力于」「赋能」「打造」。
  • 少用形容词，多用动词和名词：不写「深度掌握检索」，写「能白板手写 BM25」。
  • 允许露怯：「还没吃透：K8s 调度」。诚实是最便宜的可信度。
  • 不写「热爱技术」「保持学习」，用正在做的事替代。
8.4 30 秒路径（设计给面试官）

首屏读到主张 → 扫到 79/10/3/5 → 点开「79」看到 pytest 输出 → 滑到 Work 看到三个决策 → 点「看深潜」→ 看到评测闭环 → 回 CONTACT。全程不超过 6 次交互，就能判断「这个人能不能聊」。
