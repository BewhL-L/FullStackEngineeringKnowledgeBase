# 环境与工具链配置（Windows + WSL2 + Docker Desktop）

> 目的：换机器、重装系统、或半年后回头看时，能把环境一次配回可用状态。
> 记录的是**结论和验证过的事实**，不是调试过程。排障过程见同目录另一份文档。

采集时间：2026-11-01。主机：Windows，WSL2 Ubuntu（`systemd=true`，默认用户 `luo`），Docker Desktop 29.9.2。

---

## 一、Docker 镜像源

**结论**：镜像源必须在 **Settings → Docker Engine** 里改，直接编辑 `~/.docker/daemon.json` **会被覆盖**。

证据：手工改完文件后重启 Docker，文件内容回到旧值，mtime 恰好等于重启时刻（2026-11-01 15:29）。

可用性与实测：

| 镜像源 | `/v2/` 响应 | 结论 |
|---|---|---|
| `docker.m.daocloud.io` | 401，0.9s | 可用，实测拉 360MB 用时 6m53s |
| `docker.1ms.run` | 401，0.85s | 可用 |
| `docker.xuanyuan.me` | 401，2.26s | 可用，延迟偏高 |
| `hub-mirror.c.163.com` | 0.02s 失败 | **已停服**，应从列表移除 |

推荐配置（粘贴到 Docker Engine 面板）：

```json
{
  "builder": { "gc": { "defaultKeepStorage": "20GB", "enabled": true } },
  "experimental": false,
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://docker.xuanyuan.me"
  ]
}
```

## 二、PyPI

容器内直连 `pypi.org` 会 TLS 重置（`SSL: UNEXPECTED_EOF_WHILE_READING`），必须走镜像：

```
https://mirrors.aliyun.com/pypi/simple
```

落点：

- `server/dev.Dockerfile` 里以 `ARG/ENV PIP_INDEX_URL` 注入，后续 `pip install` 自动继承；
- `docker-compose.yaml` 的入口命令额外带了 `-i`（冗余但无害）。

## 三、代理与带宽

| 项 | 值 |
|---|---|
| Windows 系统代理 | `127.0.0.1:7897`（Clash，rule 模式，TUN 关闭） |
| Docker Desktop 守护进程代理 | `http.docker.internal:3128`（转发到系统代理） |
| 容器内代理变量 | **无**（容器不继承；需要时显式 `-e HTTPS_PROXY=...`） |

WSL 侧的两个前提（`.wslconfig`），决定了"哪些流量会走代理"：

| 项 | 值 | 含义 |
|---|---|---|
| `networkingMode` | `mirrored` | 与 Windows 共享网络栈：localhost 互通（宿主能直连 WSL 内的 8888/3000）；也因此**按 IP 段区分"WSL 流量 vs 主机流量"的分流规则不成立** |
| `autoProxy` | `false` | Windows 系统代理**不会**自动传进 WSL；WSL 内程序必须靠 `.bashrc`/`.zshrc` 里的 `http_proxy` 才走代理 |

推论：本机服务（mem0 的 8888、dashboard 的 3000）必须绕过代理，`no_proxy` 里要有 `localhost,127.0.0.1,::1`。shell 配置与 `~/.hermes/.env` 各放一份——桌面端由 `start-hermes-desktop.vbs` 经 `wsl.exe` 直接拉起（非登录 shell），**不继承** shell 里的 `http_proxy`，它稳定可用的代理来源只有自己的 `.env`。

实测下载速度（同一 10MB 文件）：

| 路径 | 速度 |
|---|---|
| 走系统代理 | 0.43 MB/s |
| 绕过代理直连 | 0.71 MB/s |
| 镜像源（daocloud） | ≈0.87 MB/s |
| Docker Hub 直连（构建拉取） | **0 B/s，26 分钟零进度** |

结论：出口带宽约 6 Mbps；代理再降约 40%；Docker Hub 直连在本网络基本不可用，**镜像源是唯一稳定通路**。

## 四、WSL / Windows 互操作

| 项 | 事实 |
|---|---|
| WSL 家目录 | `\\wsl.localhost\Ubuntu\home\luo\`（Windows 侧可直接读写） |
| 主要项目 | `~/mem0`（mem0 服务）、`~/projects/hermes-kb`、`~/.hermes`（Hermes） |
| 符号链接 | 上游仓库自带的 `CLAUDE.md -> AGENTS.md`（11 处），**Windows 侧读取报 `Input/output error`** |

软链带来两个连锁问题：

1. **git 假阳性**：`git status` 显示 11 个 `M CLAUDE.md`，但 `git diff` 报 `Function not implemented`、`--stat` 为 0 行。它们是完好的软链，内容没变。
2. **Docker 构建失败**：`failed to solve: invalid file request mem0/CLAUDE.md`，构建上下文直接中断。

处置：**不要试图"修"软链**（在 Windows 侧 `git checkout` 可能把它写成实体文件，破坏上游结构）。正确做法是在 `.dockerignore` 里排除：

```
**/CLAUDE.md
**/__pycache__
**/*.pyc
```

排除后构建上下文从 16.4MB 降到 22KB。

另一条 9p 限制（2026-10-31 实测）：

- 经 `\\wsl.localhost` 从 Windows 写入的文件，**`chmod` 不生效**——新建 644 的文件执行 `chmod 600`、`chmod 705`，`stat` 始终回报 644（9p 服务端不接受 SETATTR）。
- 后果：这类文件在 Linux 侧可能拿不到执行位，`execve` 返回 `EACCES`（表现为 `spawn ... EACCES`，而 `ls -l` 仍显示 `-rwxr-xr-x`，具有误导性）。
- 处置：需要可执行的脚本，在 **WSL 内**执行 `chmod +x`；或统一用 `bash script.sh` 调用，不依赖执行位。

## 五、Git 配置

| 问题 | 现象 | 处置 |
|---|---|---|
| DrvFs 丢失可执行位 | 7 个脚本显示 `mode change 100755 => 100644`，diff 为 0 行 | `git config core.fileMode false` |
| WSL 内 git 无身份 | `Author identity unknown`，提交失败 | 仓库级 `git config user.name/user.email`（不要动全局） |
| 远端命名 | 曾用 `origin` 指官方、`fork` 指自己的仓库 | 规范为 `origin` = 自己的 fork、`upstream` = 官方；`git config remote.pushDefault origin` |

mem0 仓库的分支职责（写的是"哪条分支放什么"，与当前检出无关）：

```
origin    https://github.com/BewhL-L/mem0.git     （fork，push 默认）
upstream  https://github.com/mem0ai/mem0.git      （官方，只 fetch）

main                 跟踪 upstream/main，等同官方镜像；不含本地修复
fix/startup-wait-db  本地修复（wait_for_db 等 6 条）只在这条分支上，推到 origin
```

三条使用约定：

1. 要带修复的环境，checkout `fix/startup-wait-db`；克隆 fork 后默认落在 `main`，**拿不到修复**。
2. 在 `main` 上 `git pull` 拉的是官方代码；同步自己的分支要 `git pull origin fix/startup-wait-db`。
3. 不要把修复直接提交到 `main`——那会让"main = 官方镜像"这条约定失效，将来 rebase 上游会冲突。

> 这里刻意不写"当前在哪个分支、领先几条"：那是随 checkout 变的快照，写进文档必然过期。
> 需要看实时状态时用 `git status -sb`，别信文档。

## 七、症状速查

| 症状 | 最可能原因 | 第一步 |
|---|---|---|
| `failed to resolve host 'postgres'`（`EAI_NONAME`） | 依赖容器没起，名字不在 DNS 里 | `docker compose ps`；确认数据库 running |
| `Connection refused` | 端口不通 / 进程没监听 | `pg_isready -h 127.0.0.1 -p 8432` |
| 容器反复 `Restarting` | 入口脚本失败（pip 网络、alembic 报错） | `docker logs --tail 30 <容器>` |
| 构建报 `invalid file request XXX` | 上下文里有 Windows 读不了的软链 | 在 `.dockerignore` 排除 |
| 镜像拉取长时间 0 进度 | 走了 Docker Hub 直连 | 换镜像源，或先 `docker pull <mirror>/...` 再打标签 |
| 容器 `Up` 但接口超时（`curl` 返回 000） | `--reload` 时读到半截文件，进程已死 | `docker exec <容器> touch /app/main.py` |
| `502 Bad Gateway`，body 含 `upstream connect failed ... os error 10061` | 目标其实是**本机服务**，却被代理转发（`no_proxy` 未覆盖 localhost） | `curl --noproxy '*' <url>` 对比；把 `localhost,127.0.0.1` 加进 `no_proxy` |
| `Mem0 sync failed` 且 `Connection refused` / `timed out` / `502` 交替出现 | 两层叠加：容器没起（refused）+ 代理劫持（502/timeout） | 先 `docker compose ps` 起栈，再查 `no_proxy`；只修一层仍会失败 |
| `spawn ... EACCES` 但 `ls -l` 显示可执行 | 文件经 `\\wsl.localhost` 由 Windows 写入，Linux 侧无执行位 | 在 WSL 内 `chmod +x`，或改用 `bash script.sh` |
| `git status` 一堆 M 但 diff 为空 | fileMode 变化，或软链读取失败 | `git diff --summary` 看是否 `mode change` |

## 八、在 Git Bash 里操作容器的注意事项

Git Bash 会把 Linux 绝对路径改写成 Windows 路径（`/home/luo/...` → `D:/.../home/luo/...`）。执行 `docker exec` 带容器内路径时，需要：

```bash
export MSYS_NO_PATHCONV=1
docker exec -w /app <容器> python -m pytest tests/ -q
```

这是工具层的坑，不影响容器本身。

## 九、定时任务

| 任务 | 触发 | 做什么 | 日志 |
|---|---|---|---|
| `Hermes Memory Snapshot` | 每日 21:00 | Hermes 记忆导出 + 提交 + 推送 | `C:/Users/23981/Desktop/AI文档/Hermes日志/snapshot.log` |
| `Git Auto Push` | 每日 21:05 + 登录时 | 推送两个本地代码仓库的已提交内容 | `%LOCALAPPDATA%\GitAutoPush\push-YYYY-MM.log` |

**为什么是 21:05 而不是 21:00**：错开 Hermes 快照，避免两个 `git push` 同时挤同一个代理（7897），也方便从日志里分辨哪个失败。

**`Hermes Memory Snapshot` 的失败语义**（2026-11-01 21:00 实测）：

- 推送依赖 Clash 在运行（HTTPS 经 `127.0.0.1:7897`）。代理不在时日志写 `推送：失败 … Failed to connect to github.com:443 over proxy`，毫秒级失败、不等待重试。
- 失败只影响**远端**：`hot/` 与 `exports/` 已写入本地并提交，提交留在本地仓库不会丢；推送每天都会尝试一次，**下次运行会把它一并推上去**（不依赖当天是否有新提交）。
- 判断快照是否健康看两行：`导出 mem0：导出 N 条`（本地是否成功）与 `推送：成功`（远端是否同步）。前者失败才是数据问题，后者失败只是延迟。

**`Git Auto Push` 的设计约束**（脚本 `C:\Users\23981\bin\git-autopush.ps1`）：

1. **只推已提交的内容**，从不 `git add` / `git commit`。原因：拉取式自动提交会把半成品、临时文件、私有文档一起塞进历史（本仓库 2026-10-27 出过 `git add -A` 把指导书推上公开仓库的事故）。
2. **只做快进推送**，被拒绝就记日志跳过，绝不 `--force`。
3. 覆盖两个仓库：`kb-agent-platform`（`main`）与 mem0 fork（`fix/startup-wait-db`）。
4. Obsidian Vault 不在此列：obsidian-git 已经每 10 分钟自动提交+推送，且它把嵌套的代码仓库整个忽略了。

**注册方式**（需要管理员权限，任务写进系统级 Task Scheduler）：

```
右键 → 以管理员身份运行
C:\Users\23981\bin\setup-git-autopush-task.ps1
```

脚本会创建一条任务、两个触发器（每日 21:05、登录时补跑），并设置"错过时间则尽快执行"（`StartWhenAvailable`）。

**验证**：

```powershell
Get-ScheduledTask -TaskName 'Git Auto Push' | Select-Object TaskName, State
# 手动跑一次，然后看日志
powershell -NoProfile -ExecutionPolicy Bypass -File C:\Users\23981\bin\git-autopush.ps1
Get-Content "$env:LOCALAPPDATA\GitAutoPush\push-$(Get-Date -Format yyyy-MM).log" -Tail 10
```

正常输出形如：

```
--- run start ---
[kb-agent-platform] nothing to push on main
[mem0-fork] nothing to push on fix/startup-wait-db
--- run end ---
```

**失败排查**：日志里出现 `PUSH FAILED` 时，先确认 Clash 在运行、7897 端口可连；再手工执行一次 `git push` 看具体报错。代理不可用时任务不会自动改直连——这是有意的，避免在不知情的情况下走出不同网络路径。

**首次注册与实测（2026-11-01 22:23）**：

- 触发器核对：`MSFT_TaskDailyTrigger At=21:05`、`MSFT_TaskLogonTrigger`；
- `Start-ScheduledTask` 手动触发 → `LastTaskResult=0`，`NextRunTime=2026-11-02 21:05`；
- 日志两个仓库均为 `nothing to push`（当时无待推内容）；
- 非交互环境下 `git ls-remote` 两个仓库均成功，说明凭据管理器（GCM）里的令牌可用，任务不会卡在认证上。

> 注：`nothing to push` 不经过网络，所以"推送本身"要等第一次真有提交时才真正验证；失败会在日志里留下 `PUSH FAILED`。

## 十、Git 提交工作流

任务只负责推，**提交仍是手动的**。三步循环：

```bash
git status -sb     # 看：当前分支、领先/落后几个、改了哪些文件
git diff           # 挑之前先看清改了什么
git add -p         # 逐块选（y/n），精确到行；不要用 git add -A
git commit -v      # 提交时 diff 摊在编辑器下方，边看边写消息
```

两个仓库的入口：

| 仓库 | 终端 | 路径 |
|---|---|---|
| kb-agent-platform | Windows（PowerShell 或 Git Bash） | `C:\Users\23981\Desktop\AI文档\...\企业级智能知识库 + AI Agent 平台` |
| mem0（fork） | **WSL**（避开软链假阳性） | `~/mem0` |

提交消息模板（沿用仓库既有风格）：

```
fix(范围): 一句话说做了什么

为什么改（根因/动机）。
怎么验证的（命令或日志结论）。
```

完整命令表见 `全栈工程知识库/07-通用工具/01-Git版本控制/Git命令速查表.md`。

**Obsidian 与嵌套仓库的关系**（解释为什么 Vault 不在自动推送列表里）：

1. Obsidian Vault 根是 `全栈工程知识库`，obsidian-git 每 10 分钟 commit + push 一次；
2. Vault 的 `.gitignore` 第 16 行**整目录忽略** `99-项目实战/企业级智能知识库 + AI Agent 平台/...`；
3. 该目录是独立仓库（远端 `kb-agent-platform`），因此 Obsidian 永远不会推它 —— 代码仓库必须走 `Git Auto Push` 或手动 `git push`。

## 十一、Windows 提权（装任务、改系统设置时）

| 方式 | 说明 |
|---|---|
| 右键 `.ps1` | **没有"以管理员身份运行"**：Win11 只对 `.exe`/`.lnk` 注册了 `runas` 动词，`.ps1` 只有"使用 PowerShell 运行"（普通权限） |
| `sudo` | Win11 内置，本机已启用（`C:\Windows\system32\sudo.exe`，版本 1.0.1）。默认**新开窗口**执行，必须加 `-NoExit` 才能看到输出 |
| `Start-Process -Verb RunAs` | 不依赖 sudo，从普通 PowerShell 弹 UAC，通用性最好 |

三种写法（等价）：

```powershell
sudo powershell -NoProfile -NoExit -ExecutionPolicy Bypass -File C:\path\to\script.ps1

Start-Process powershell -Verb RunAs -ArgumentList '-NoProfile','-NoExit','-ExecutionPolicy','Bypass','-File','C:\path\to\script.ps1'
```

Windows 的 sudo 与 Linux 的差异：不支持 `>` 重定向与管道；提权后是新会话，不继承当前目录与环境变量。
