## 一、起因

后端启动报错，重启一次就恢复：

```
sqlalchemy.exc.OperationalError: (psycopg.OperationalError)
failed to resolve host 'postgres': [Errno -2] Name or service not known
```

最初误判为"配置写错"，实际是**依赖容器没起时，`postgres` 这个名字在 Docker 内嵌 DNS 里根本不存在**。重启恰好把数据库一起拉起来了，于是看起来"重启治好了"。

## 二、三个根因

| # | 根因 | 表现 |
|---|---|---|
| 1 | Docker 内嵌 DNS 只为 **running** 容器保留 A 记录，容器停掉即摘除 | `EAI_NONAME`，不是 `Connection refused` |
| 2 | 首次建连发生在入口 `alembic upgrade head`，不在应用 lifespan | 迁移阶段直接抛错，容器退出并进入重启循环 |
| 3 | 入口每次启动都 `pip install mem0ai`，且直连 PyPI | 网络抖动即启动失败（`SSL: UNEXPECTED_EOF`） |

## 四、核心实现

### 4.1 `wait_for_db()`（`server/db.py`）

```python
def wait_for_db(max_attempts=None, base_delay=None, max_delay=None) -> None:
    attempts = max_attempts or int(os.environ.get("DB_CONNECT_MAX_ATTEMPTS", "30"))
    for attempt in range(1, attempts + 1):
        try:
            with engine.connect() as conn:
                conn.execute(text("SELECT 1"))
        except DBAPIError as exc:
            if attempt >= attempts:
                raise                      # 交给 compose 的 restart 策略
            delay = min(base * 2 ** (attempt - 1), ceiling) * (0.5 + random.random())
            logger.warning("database unavailable (attempt %s/%s): %s", ...)
            time.sleep(delay)
        else:
            return
```

契约（已由 `server/tests/test_wait_for_db.py` 覆盖，4 例）：

| 场景 | 行为 |
|---|---|
| 首次成功 | 立即返回，只建连 1 次 |
| 持续失败 | 重试 N 次后抛出最后一次异常 |
| 中途恢复 | 恢复那次即返回 |
| 凭据含 `@ : /` | DSN 百分比编码，且仍是 `str` |

### 4.2 三个调用点

```
容器入口:  pip install → python scripts/wait_for_db.py → alembic upgrade head → uvicorn
应用内:    lifespan: db_target() 日志 → wait_for_db() → yield
测试/脚本: 直接 import wait_for_db
```

### 4.3 DSN 构造

```python
URL.create("postgresql+psycopg", username=..., password=...,
           host=..., port=..., database=...).render_as_string(hide_password=False)
```

`URL.create()` 负责转义（`p@ss` → `p%40ss`）；`render_as_string()` 负责还原成 `str` —— **alembic 的 `config.set_main_option()` 只接受字符串**，返回 `URL` 对象会 `TypeError`。

## 六、五个可迁移的教训

1. **名称解析失败 ≠ 连接失败**。`EAI_NONAME` 说明名字不存在（依赖没起），`Connection refused` 才是端口/进程问题。两者的修法完全不同。
2. **启动顺序是隐藏依赖**。`depends_on` 只保证"容器起来了"，不保证"能提供服务"；真正兜底要靠应用侧退避重试。
3. **`uvicorn --reload` + 非原子写 = 服务中断**。用 `>` 重定向覆盖 `main.py` 时，reloader 读到半截文件，报 `Attribute "app" not found` 且不再自恢复，需 `touch` 或重启。正确做法：写临时文件再 `mv`。
4. **类型边界会在最远的调用点爆炸**。`URL.create()` 在自己模块里一切正常，崩在 alembic 那句 `set_main_option` 上。凡是"改返回值类型"的重构，都要搜索所有调用点。
5. **Windows 侧读不了 WSL 软链**。`CLAUDE.md -> AGENTS.md` 让 `git status` 出现 11 个假阳性，并直接导致 Docker 构建上下文失败（`invalid file request`）。解法是 `.dockerignore` 排除，而不是去"修复"软链。
