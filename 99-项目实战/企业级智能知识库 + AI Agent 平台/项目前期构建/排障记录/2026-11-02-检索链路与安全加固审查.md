## 二、三个静默失败（A 类）

### 2.1 生产环境向量检索永远返回空

`retrieval/hybrid.py` 里这样写：

```python
from ..services.vector_store import vector_store   # 模块级 Chroma 单例
```

而向量库是**可切换**的（`VECTOR_PROVIDER=chroma | qdrant`），正确入口是 `get_vector_store()`。

于是生产配置（`docker-compose.yml` 里 `VECTOR_PROVIDER=qdrant`）下：

```
写入路径：文档处理 → get_vector_store() → Qdrant   ✅ 数据在 Qdrant
查询路径：hybrid.retrieve() → vector_store 单例 → Chroma（空）  ❌ 永远查不到
```

结果：混合检索退化成**纯 BM25 单路**。系统照样答得出问题，只是答得不如本地准。**没有任何报错、没有任何日志**。

这类 bug 的可怕之处在于它"看起来像效果问题"：你会以为是切片大小没调好、是 embedding 模型不行、是 Prompt 写得不好，于是花几天去调参——而真因是一行 import。

**为什么单测抓不到**：测试环境默认 `VECTOR_PROVIDER=chroma`，写入和查询都走 Chroma，路径恰好一致。**配置分支的 bug，只有跑第二个配置才暴露。**

**修法**：改走 `get_vector_store()`；同时把"禁止直接 import 单例"写进代码注释。

### 2.2 Wiki 编译"成功"但生成 0 页

`wiki/compiler.py` 同样的病，但表现更隐蔽：

```python
self.vector_store = VectorStore()      # 硬编码 Chroma，无视配置
```

Wiki 编译的第一步是 `get_document_chunks()` 取原文，而它从这个"空 Chroma"读 → 返回 `[]` → 后续实体抽取、页面生成全部跳过 → **接口返回 200，日志写"编译完成"，页面上一个页面都没有**。

和 2.1 是同一个根因的第二个实例。**同一个错误出现在两处，说明它不是笔误，是缺少约束**——所以修法不止于改两行，而是统一入口（见 §6.1）。

### 2.3 LLM 精排的结果被二次排序覆盖

这条最讽刺：项目花钱调了 LLM 精排，然后**亲手把它的结论丢掉**。

三处代码（`rag_service.retrieve_across_kbs`、`retrieval/self_rag.py::_merge`，加上跨库那条）：

```python
merged.sort(key=lambda x: x.get("score", 0), reverse=True)   # ❌ 按原始召回分重排
```

而 `score` 是**两路量纲不同**的分（见 §3.1）。精排已经用 `rerank_rank` 给出了正确顺序，这一行把它整个覆盖：精排排第 1 的片段，只要它的原始 cosine 分不高，就会掉到后面去。

结果：**精排的 token 花了，效果等于没开**。而且因为"关掉精排"和"开着精排"在这个环节的结果都被同一行覆盖，你会得到"精排没用"的错误结论，进而把好功能下线。

## 三、四个设计缺陷（B 类）

### 3.1 量纲不可比的 score 混排

| 召回路径 | score 含义 | 取值范围 |
|---|---|---|
| 向量（Chroma / Qdrant） | `1 - cosine_distance` | `[0, 1]` |
| BM25 | `Σ IDF × TF 归一化` | `[0, +∞)`，长文档可到 10 以上 |

把这两列数放进一个 `sort` 里，**BM25 来源的片段会一律压过向量来源的**——不是因为更相关，只因为量纲大。

正确做法是**放弃 score，用名次**：RRF 就是这么干的（`1/(k+rank)`），对量纲不敏感。三路之后还有精排时，排序键就是 `rerank_rank`。

> 一句话：**不同来源的分数不能比大小，只能比名次。**

### 3.2 稀疏路没有相关性阈值

稠密路一直有 `SIMILARITY_THRESHOLD = 0.3`，稀疏路只有：

```python
if score > 0:      # ❌ 只要命中一个词就算候选
```

「的」「是」「怎么」这种词命中一次也能进候选池，然后挤占精排额度（精排只处理 Top-N）。两路召回**阈值不对称**，等于让最差的那一路拥有最大的候选配额。

修法：加 `BM25_MIN_SCORE`，默认 `0.5`。推导如下（`_idf = log(1 + (N-n+0.5)/(n+0.5))`）：

| 词出现在多少比例的切片里 | IDF 量级 | 是否该留 |
|---|---|---|
| 90% | ≈ 0.11 | 否 |
| 60% | ≈ 0.51 | 边界 |
| 10% | ≈ 2.2 | 是 |

`0.5` 大致等价于"出现在超过 60% 切片里的词直接不算分"。

**但这个修法本身埋了第二个坑——而且是跑测试才炸出来的。** 第一版实现是纯绝对阈值：

```python
scored = [(s, d) for s, d in scored if s >= settings.BM25_MIN_SCORE]   # ❌ 只在"大语料"下成立
```

问题在于 **BM25 的绝对分随语料规模变化**。IDF = `log(1 + (N-n+0.5)/(n+0.5))`：

| 语料规模 | 一个只见于 1 个切片的词，单次命中的 IDF | 绝对阈值 0.5 的后果 |
|---|---|---|
| 1–2 个切片（测试、演示库） | ≈ 0.29 | **全部候选被滤掉 → 检索返回空** |
| 500 个切片、词见于 10% 切片 | ≈ 2.29 | 正常过滤常见词 |

也就是说：**同一个阈值，在小语料上会让整条检索链路静默失效，在大语料上才是"过滤常见词"**。而它失效时同样不报错——`search()` 返回 `[]`，混合检索退化成纯向量路，看起来只是"检索不太准"。

修法是给绝对阈值配一个**相对下限**：

```python
top = max(s for s, _ in scored)
floor = min(settings.BM25_MIN_SCORE, top * settings.BM25_MIN_SCORE_RATIO)   # 0.25
scored = [(s, d) for s, d in scored if s >= floor]
```

- 大语料：`top` 很大，`min()` 取到绝对阈值 0.5 → 按原意过滤常见词；
- 小语料：`top` 只有 0.29，`min()` 取到 `0.073` → 退化为"相对头名 25%"，绝不团灭。

这个写法带来一条**可证明的不变量**：`floor ≤ 0.25 × top < top`，所以**头名永远不会被自己的阈值滤掉**。这条不变量现在由 `test_bm25_never_filters_top_candidate` 盯着——它把阈值临时调到 999，断言头名依然在结果里；改回纯绝对阈值实现时该用例立刻变红。

> [!important] 这一条比阈值本身值钱
> **凡是"用绝对数值做门槛"的地方，都要先问一句：这个数值的尺度会不会随数据量变化？**
> 分页大小、超时时间、批量条数不会；而 BM25 分、相似度分、计数类指标会。
> 尺度会变的地方，用"相对头名/相对基线"或"绝对+相对取小"，比反复调参可靠得多。

### 3.3 索引粒度错配：BM25 索引父块，向量索引子块

父子分块的设计是"**用子块建索引保精度，用父块返回保完整**"（250 字 / 1000 字）。向量路做对了，BM25 没做：

```python
BM25Index(kb_id).add(parent_texts, ...)   # ❌ 拿 1000 字父块建索引
```

两个后果：

1. **词频被稀释**。一个型号在 250 字里出现 3 次（密度高），在 1000 字里还是 3 次（密度低）→ BM25 的 TF 项打不上去；
2. **长度归一化被拖累**。BM25 的 `B` 参数按文档长度惩罚，父块长度是子块的 4 倍，同一个词在父块里的得分必然更低。

而 BM25 存在的**全部意义**就是处理"型号、专有名词、编号"这类精确词项（README 关键设计第 1 条自己写的）。用父块建索引，等于把它的看家本领让掉了。

修法：索引和返回**分成两个字段**（见 §6.3）。

### 3.4 一次检索 = 2 次 LLM + N 次 embedding + N 次整文件落盘

一次 `/api/chat` 的检索环节：

| 步骤 | 调用 | 成本 |
|---|---|---|
| 多查询改写 | 1 次 LLM | 小 |
| 改写后逐条 embedding | **N 次**（N = 改写条数，通常 3） | 每轮都是新文本，**缓存必然 miss** |
| LLM 精排 | 1 次 LLM | **20 个候选 × 1000 字父块 ≈ 2 万字符 ≈ 1.2–1.5 万 token** |
| BM25 索引 | N 次整文件写 | 每次 `_save` 全量 dump |

两个最值得改的点：

- **精排的输入不该是父块**。精排要回答的只是"这段和问题相关吗"，相关度信号在前 200 字就出现了，后面 800 字纯属垫高账单。20 × 1000 → 20 × 200，**精排 token 降约 80%**。
- **embedding 不该逐条打**。向量库原生支持一次传多个 query embedding，N 次网络往返可以合成 1 次。

## 四、安全与配置（C 类）

### 4.1 `SECRET_KEY` 用默认值也能上线

```python
SECRET_KEY: str = "your-secret-key-change-this-in-production"   # ❌ 有默认值
```

有默认值本身不算错（本地开发要能跑），错的是**没有任何地方拦它**。部署时忘了改，JWT 就用一个公开字符串签名——攻击者可以自己签发任意用户的 token。

**这类问题的正确姿势不是"删掉默认值"**（那会让本地开发第一步就报错，然后大家去注释掉校验），而是**分环境**：

- `DEBUG=true`：允许默认值，不吭声；
- `DEBUG=false`：默认值 → 启动直接 `RuntimeError` 退出。

失败要发生在**启动时**，不能等到第一个请求。

> [!important] 加完校验还必须回头改文档，否则"修好了安全性，弄坏了上手体验"
> 这个校验有个副作用：README 的快速开始是 `cp backend/.env.example backend/.env` → `docker compose up`，
> 而 `.env.example` 里的 `SECRET_KEY` 正是那个占位值，compose 又写死 `DEBUG=false`。
> 三者一撞，**新人照文档走的第一步就是后端反复重启**——报错信息虽然清楚，但"按文档做却起不来"是最伤的体验。
>
> 所以同一轮里必须一起改：`.env.example` 标注"必改 + 生成命令"、README 快速开始加一步生成密钥、
> 指导书补一段"看到这个 `RuntimeError` 该怎么办"。
>
> **通用规则：任何"新增启动期校验"的改动，都要 grep 一遍 `快速开始` / `README` / `.env.example`，
> 确认原来的最短路径还能走通。** 校验的价值在于拦住配置错误，不在于拦住用户。

### 4.2 token 签发后无法吊销

原实现只签 `sub` + `exp`，**没有 `jti`（唯一 ID），没有吊销表**。后果：

- 用户点"退出登录"，前端删了本地 token，**服务端仍然认**；
- 改了密码、踢掉某人、发现密钥泄露——全都做不到；
- `ACCESS_TOKEN_EXPIRE_MINUTES = 10080`（7 天），泄露一个 token 就有 7 天窗口。

修法见 §6.5：签 `jti` + `iat`，登出时把 `jti` 写进 Redis（TTL = token 剩余寿命，自然过期，不用清理），校验时查一次。

### 4.3 `AUTO_CREATE_TABLES` 默认 True，两份 compose 都没关

`create_all` 只补缺失的表，**不改已有表结构**。这让"忘记写迁移"在本机空库上表现为完全正常，到生产老库上才炸。

两份 compose 都显式关掉（`AUTO_CREATE_TABLES=false`），把建表/升级交给 `scripts/db_bootstrap.py`（内部走 Alembic），空库和老库才走同一条路。

### 4.4 Redis 不可用时静默降级成内存缓存

`build_cache()` 捕获异常后 `return MemoryCache()`。在 `ASYNC_MODE=celery`（多进程）下这是**正确性事故**：API 进程和 worker 进程各有各的内存缓存，文档更新时 `retrieval_cache.bump()` 只失效了 API 进程那份，worker 继续用旧版本号 → **检索到已删除的文档**。

修法：celery 模式下 Redis 不可用直接 `RuntimeError`；单进程模式才允许降级，并且降级要**打日志 + 在 `/api/health` 里可见**。

### 4.5 跨轮持久化注入

`neutralize()` 原本只作用在当轮检索内容上，但 `history`（历史消息）和 `memory_summary`（历史压缩摘要）都是用户原文的**二手拷贝**，同样能携带 `<|im_start|>` 这类角色标记。当轮拦住了，下一轮从历史里又带回来了——**注入会跨轮存活**。

反过来说，**当前这一轮的提问故意不清洗**：它由已登录用户实时输入，注入自己的 prompt 没有收益。
判断标准不是"一律洗一遍"，而是**这段文本是谁写的、会不会被重复使用**。

### 4.6 embedding 缓存无上限

`embedding_cache.json` 每次 `_embed` 都全量读 + 全量写，条目无上限。跑久了文件到几十 MB，每 embed 一次付一次全量 IO。修法：上限 + FIFO 批量回收 + 按时间节流落盘 + `atexit` 兜底。

两个细节：

- **批量回收到 90% 而不是"超一条删一条"**：后者在稳态下每写一条都要 `list()` 一次全表、还打一行 INFO 日志，缓存越大越慢、日志越吵。
- **`atexit` 兜底要看 `_cache_dirty`**：节流会丢掉最后几秒的写入，退出时补刷一次；但没有改动就不该写，否则每次 `--reload` 都重写一遍几 MB 的 JSON。

### 4.7 流式是主产品路径，却最不全

`/api/chat/stream` 没有 `grounding`（前端拿不到溯源）、异常时不落库（留下一条空白的 AI 消息）、错误事件不带 `conversation_id`（前端无从重试）。**同步路径有的，流式也得有**——这条是通用的。

### 4.8 断连走不到 `except Exception`

补完上面的异常落库后，还有一个洞：**客户端主动断开**（关页面、切网络）抛的是 `asyncio.CancelledError`，而它在 Python 3.8+ 继承 `BaseException`，不是 `Exception`——`except Exception` **接不住**。

结果就是用户关掉页面，那条预建的 assistant 消息永远停在空 `content`。修法：

```python
except asyncio.CancelledError:
    _persist_stream_failure(message_id, full_answer, sources_data)
    raise      # 取消必须向上传播，否则 Starlette 无法正确收尾
```

`raise` 不能省：吞掉取消会让服务器以为流还活着。

## 六、核心实现

### 6.1 统一向量库入口（治 2.1 / 2.2 的根）

```python
# ❌ 两处硬编码，各错一次
from ..services.vector_store import vector_store
self.vector_store = VectorStore()

# ✅ 唯一入口
from ..services.vector_store import get_vector_store
store = get_vector_store()
```

约束写在注释里，而不是靠记性：

```python
# 必须走 get_vector_store()，不能 import vector_store 单例。
```

### 6.2 排序键：名次优先，原始分只做 tie-break

```python
ordered = list(enumerate(merged))
ordered.sort(
    key=lambda it: (
        it[1].get("rerank_rank", it[0]),        # 主键：精排名次；没有则用插入序
        -float(it[1].get("fusion_score") or 0.0),  # 次键：RRF 分（同量纲，可安全比较）
    )
)
return [s for _, s in ordered][: settings.TOP_K + 3]
```

三个设计点：

1. **主键是名次不是分数**——绕开量纲问题；
2. **`rerank_rank` 缺失时退回 `it[0]`（插入序）**，保证关掉精排时结果**可复现**，而不是随字典顺序漂移；
3. **次键用 `fusion_score`（RRF 分）而不是 `score`**——RRF 分来自名次，天然同量纲。

### 6.3 索引粒度与返回粒度分开

```python
# bm25_retriever.py
parent = parents[idx] if parents and idx < len(parents) else chunk
self.docs.append({
    "text": parent,        # 返回用：1000 字父块，保证上下文完整
    "child_text": chunk,   # 打分用：250 字子块，保证词频不被稀释
    ...
})
```

下游按用途各取所需：

| 用途 | 字段 | 理由 |
|---|---|---|
| BM25 打分 | `chunk`（子块） | 词频密度高，长度归一化不被父块拖累 |
| 最终生成 | `text`（父块） | 上下文完整，避免"检索准了但答不全" |
| 精排 / Self-RAG 判断 | `child_text` 截断 | 相关度信号在前 200 字就够 |
| 前端展示 | `child_text` | 让用户看到"命中的是哪一句" |

**契约**：`chunks` 与 `parents` 必须等长且一一对齐，**传之前不能自行去重**，否则下标错位会让返回的父块张冠李戴。

### 6.5 token 吊销

```python
# security.py
payload = {
    "sub": str(user_id),
    "exp": expire,
    "iat": now,                      # 签发时间：算剩余寿命要用
    "jti": uuid.uuid4().hex,         # 唯一 ID：吊销的抓手
}

def revoke_token(payload):
    jti = payload.get("jti")
    if not jti:
        return                       # 老 token 没有 jti，无法吊销，只能等过期
    cache.set(_REVOKE_PREFIX + jti, "1", ttl=token_remaining_seconds(payload))
```

**TTL = token 剩余寿命**，这是设计要点：吊销记录活到 token 自己过期就够了，之后它本来就无效。**不用定时清理，不会无限增长**——比"吊销表 + 定时任务"简单一个数量级。

### 6.6 缓存上限与退出落盘

```python
def _save_cache(self, force=False):
    now = time.time()
    if not force and now - self._last_flush < settings.EMBEDDING_CACHE_FLUSH_INTERVAL:
        return                        # 节流：不是每次 embed 都全量写盘
    ...

def _trim_cache(self):
    if len(self._cache) <= settings.EMBEDDING_CACHE_MAX_ENTRIES:
        return
    overflow = len(self._cache) - settings.EMBEDDING_CACHE_MAX_ENTRIES
    for key in itertools.islice(self._cache, overflow):   # FIFO，dict 有序
        del self._cache[key]
```

`atexit` 注册 `_flush_on_exit()`：节流会丢掉"最后几秒"的写入，退出时强制刷一次。

## 七、顺手修的测试替身契约漂移

改完 `query_batch` 后回头查测试，发现 `tests/conftest.py` 里的假 Chroma：

```python
def query(self, query_embeddings, n_results):
    q = query_embeddings[0]        # ❌ 只处理第一条
```

真实 `collection.query(query_embeddings=[e1, e2])` 返回的是**外层按查询嵌套**的二维结构。替身只认单条，意味着：

- 多查询改写合并成一次批量查询后，**除第一条外的结果全部丢失**；
- 而测试**依然全绿**——因为它不检查"改写的查询有没有被用上"。

**替身与真实实现契约不一致，比没有替身更危险**：没有替身你会写集成测试，替身错了你会以为已经测过了。

修法：替身按真实契约返回二维嵌套，并支持单向量写法兜底。

### 7.1 改实现之后，断言点也要跟着挪

改完 `query_batch`，`test_retrieval_cache.py` 里这条立刻失效：

```python
monkeypatch.setattr(vector_store, "query", counting_query)   # 还在数 query
assert calls_after_first > 0                                 # 永远是 0
```

它的意图是"第二次检索该命中缓存、不再打向量库"。但**计数点绑在了具体实现上**：现在走的是 `query_batch`，`query` 根本没人调。

第一次跑就红了。真正危险的是**它下次可能以另一种方式假通过**：若断言写成"第二次的调用次数不变"，那么两次都是 0，会直接绿。

修法是把计数点挪到两者共同的必经之处 —— `_embed`。任何一次真实检索都必须先算向量，所以不管上层用 `query` 还是 `query_batch`，这个计数都成立。

> [!tip] 测试要盯"不变的东西"
> 别断言"调用了某个具体方法"，要断言**"必然发生的那件事"**。
> 前者会随重构失效，后者才是真正的行为契约。

### 7.2 顺手做的一次"测测试"

新增的不变量用例（头名永不被阈值滤掉），我临时把实现改回纯绝对阈值跑了一遍，确认它**确实变红**，再恢复。

这一步很廉价，但它是"用例到底在测东西，还是在陪跑"的唯一证据。写了个永远绿的断言，比没有断言更糟——它会让你以为这块已经安全了。

## 九、可迁移的八条

1. **静默失败优先于报错处理**。看到"没报错但结果不对"，先怀疑路径没走到，而不是怀疑参数没调好。
2. **同一错误出现两次，就不要再当笔误修**。两处硬编码 `VectorStore()`，说明缺的是约束（统一入口），不是两行代码。
3. **不同来源的分数不能比大小，只能比名次**。RRF 的存在就是为了这个。
4. **两路召回，阈值必须对称**。一路有阈值、一路只要 `> 0`，等于让最差的那路拥有最大配额。
5. **用绝对数值做门槛前，先问它的尺度会不会随数据量变化**。BM25 分会，所以阈值要"绝对 + 相对取小"，并且能证明头名永不被滤掉。
6. **"索引粒度"和"返回粒度"是两件事**，能分开就该分开——这就是父子分块的全部价值。
7. **降级要打日志、要可见**。静默降级 + 多进程 = 各自的缓存，各自的真相。
8. **测试要盯"必然发生的那件事"，不是"调用了哪个方法"**。前者是行为契约，后者会随重构失效——而且失效方式往往是"假通过"。

> 还有一条关于"失败路径"的：**`except Exception` 接不住客户端断开**（`CancelledError` 继承 `BaseException`）。
> 凡是流式接口，异常落库都要写两遍：`Exception` 一遍，`CancelledError` 一遍。
