# Hermes 模型与记忆链路排障（2026-10-29 ~ 10-31）

> 对象：Hermes（WSL2 Ubuntu，`~/.hermes`）与它依赖的自托管 mem0（`~/mem0/server`）。
> 三次故障共享同一条诊断主线：**先分清"配置错、依赖没起、还是被代理劫持"**，不要一上来改代码。

采集时间：2026-10-29 ~ 10-31。文中数字均来自当时实测，测量方式随文标注。

---

## 一、模型 400：`Model does not exist`（code 20012）

### 现象

```
HTTP 400: Model does not exist. Please check it carefully.
Model 'deepseek-ai/DeepSeek-V4.1-Flash-1017' isn't available on custom.
```

`~/.hermes/logs/agent.log` 里同一行带着完整上下文：

```
provider=custom base_url=https://api.siliconflow.cn/v1 model=deepseek-ai/DeepSeek-V4.1-Flash-1017
```

### 根因

模型 ID 多了一个 `-1017` 快照后缀。SiliconFlow 实际可用 ID 是 `deepseek-ai/DeepSeek-V4.1-Flash`（`/v1/models` 实测 98 个模型里只有这一个 V4.1）。

**为什么会"录进去不报错、发请求才报错"**：Hermes 的模型目录做了名称归一化模糊匹配，日志里留有证据——

```
agent.model_metadata: Could not detect context length for model '...-1017' (probe-down)
agent.model_metadata: Using hardcoded context length 1,000,000 (catalog match on 'deepseek-v4.1-flash')
```

探测失败被 `catalog match` 兜住，于是配置阶段放行，直到真正调用才被服务端拒绝。

### 诊断链（按顺序，最多四步）

| # | 查什么 | 命令 / 文件 |
|---|---|---|
| 1 | 配置里的模型 ID | `~/.hermes/config.yaml` → `model.default` |
| 2 | 服务端确实有哪些模型 | `curl -H "Authorization: Bearer $KEY" https://api.siliconflow.cn/v1/models` |
| 3 | Hermes 缓存了哪些 | `~/.hermes/provider_models_cache.json`（按 provider 归类，本例是 `openai-api`） |
| 4 | 请求体里到底发了什么 | `~/.hermes/sessions/request_dump_*.json` → `request.body.model` |

### 修法

```bash
# 改 ~/.hermes/config.yaml 的 model.default 为服务端真实 ID，然后二选一：
#   a) TUI 内 /model 重新选一次（推荐，Hermes 自己写回配置）
#   b) 退出并重启 Hermes
```

验证：直连 `chat/completions` 返回 200 即说明 ID 正确，不必等 TUI 复现。

### 教训

- **错误码 20012 是"模型名不存在"，不是鉴权问题**。鉴权错是 401，两者不要混。
- 上下文长度探测失败（`probe-down`）是模型名不对的**早期信号**：日志里它出现在 16:42:11，400 出现在 16:42:13，**早约 2 秒**。看到它就该校验模型 ID，不必等到请求失败。
- 改完配置后，运行中的进程仍持有旧值——`config.yaml` 不是热加载的。

## 二、桌面端"在终端中打开"失败：先 `No terminal emulator found`，后 `EACCES`

### 现象与定位

`~/.hermes/logs/desktop.log`：

```
Could not open chat in a terminal: Error: No terminal emulator found
```

源码 `apps/desktop/electron/external-terminal.ts` 的候选链写死为 10 个：`x-terminal-emulator`、`gnome-terminal`、`konsole`、`xfce4-terminal`、`tilix`、`kitty`、`alacritty`、`wezterm`、`foot`、`xterm`。WSL 的 Ubuntu 镜像**一个都没有**——它是无桌面终端的最小系统。

于是按顺序验证了三层，每层结论都不同：

| 尝试 | 结果 | 结论 |
|---|---|---|
| 自建 `x-terminal-emulator` 放进 `~/.local/bin` | `[terminal] opening session ... via /home/luo/.local/bin/x-terminal-emulator` 后紧跟 `spawn ... EACCES` | 路径找对了，但文件不可执行 |
| 从 Windows 经 `\\wsl.localhost` 写该脚本，并尝试 `chmod 755` | 脚本 `stat` 显示 755，但 `execve` 仍返回 `EACCES`；另做对照实验：经同一路径新建的文件（644）执行 `chmod 600`、`chmod 705`，`stat` 恒为 644 | 对照实验证明 **9p 侧 `chmod` 不生效**（不接受 SETATTR）；据此判断该文件的执行位并未真正落地，且无法从 Windows 侧修正 |
| 改用 `bash script.sh` 方式调用 | 可运行 | 说明问题只在 exec 位，不在脚本内容 |

### 最终处置

放弃桥接，直接走 Linux 端：

```bash
hermes -c          # 续最近一次会话
```

若一定要恢复菜单项，官方路径是装一个真实终端（`/usr/bin/xterm` 优先于 `/mnt/c` 下的任何东西）：

```bash
sudo apt install -y xterm
```

### 教训

- **"找不到终端"和"找不到 Hermes"是两件事**。TUI 是程序，需要 pty 宿主；Linux 没有"默认终端"API，只能靠硬编码候选链探测。
- **Windows 侧写进 WSL 的文件，不要指望它有执行位**。需要可执行的脚本必须在 WSL 内 `chmod`，或以 `bash x.sh` 调用。这条对任何"在 Windows 编辑、在 WSL 运行"的脚本都成立。
- macOS 用 `open`（有 LaunchServices 绑定）、Windows 有 `wt.exe`/`conhost` 兜底，只有 Linux 这条路会裸奔到"没有可用的终端"。

## 三、mem0 静默停摆 13 小时：三态报错指向同一件事

### 现象

Hermes 每轮都在后台报错，但**界面上完全无感**：

```
Mem0 sync failed: [Errno 111] Connection refused
Mem0 sync failed: timed out
Mem0 sync failed: Server error '502 Bad Gateway' for url 'http://localhost:8888/memories'
```

同一时段三种错误交替出现，看起来像"网络不稳定"，实际是两层原因叠加：一层让服务消失且不会自愈，另一层把"服务不在"伪装成"网关错误"。

### 根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | mem0 服务栈没在运行 | 8888 / 3000 / 8432 三个端口从宿主直连全无响应；`docker ps` 连不上 Docker Desktop 守护进程（命名管道不存在），说明 Docker 本身也没启动 |
| 2 | 三个容器的 restart 策略形同虚设 | `mem0`、`dashboard` 为 `no`，`postgres` 为 `on-failure`（正常 stop 不触发）→ Docker 一停就不会自己回来 |
| 3 | 带代理的会话把 localhost 请求也转给了 Clash | 502 的 body 是 Clash 的文案 `upstream connect failed ... (os error 10061)` |

三种错误的对应关系：

```
桌面端（无代理变量）→ 直连 8888 → Connection refused
交互式 shell（有 http_proxy）→ 交给 7897 → Clash 连不上上游 → 502 / timed out
```

### 数据面影响

`~/mem0/server/history/history.db` 的最后一笔写入停在 **2026-10-30 01:55（+08）**，之后归零。插件的自动抽取是 **best-effort**：上一轮同步未完成就跳过本轮，**没有持久队列**——所以这段时间的对话记忆是永久丢失，只能靠显式写入补。

### 修法

三处改动（YAML 为示意，原文件是逐行块格式）：

```yaml
# ~/mem0/server/docker-compose.yaml
services:
  mem0:            { restart: unless-stopped }
  mem0-dashboard:  { restart: unless-stopped }
  postgres:        { restart: unless-stopped }   # 原为 on-failure
```

```
# ~/mem0/server/.env
MEM0_TELEMETRY=false
```

```
# ~/.hermes/mem0.json —— 每条消息送去抽取的原文长度，450 会截断长回复里的结论
{ "sync_max_chars": 1200 }
```

改完 `docker compose up -d`（restart 策略与 env 变更都要重建容器才生效）。

验证：

```bash
for c in mem0-dev-mem0-1 mem0-dev-mem0-dashboard-1 mem0-dev-postgres-1; do
  docker inspect $c --format "$c {{.HostConfig.RestartPolicy.Name}}"
done
docker exec mem0-dev-mem0-1 printenv MEM0_TELEMETRY   # 期望 false
```

### 教训

- **"不影响使用"的失败最危险**。记忆同步失败不阻断对话，于是能静默跑十几个小时；只有日志和 `history.db` 的 mtime 能发现。
- **restart 策略不是可选项**。默认 `no` 意味着"手动停掉就永远停着"，在只靠 `docker compose up -d` 维护的机器上，一次 Docker 重启就等于服务消失。
- **看错误分布而不是单条错误**。`refused`（没人监听）+ `502`（代理转发失败）同时出现，说明有两层问题，只修一层仍会失败。
