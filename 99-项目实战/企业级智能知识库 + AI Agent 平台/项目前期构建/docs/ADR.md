# 架构决策记录（ADR）

> 每条记录一个"当时为什么这么选"。面试时被问"为什么不用 X"，答案在这里。
> 格式：背景 → 决策 → 备选与取舍 → 后果 → 何时重新评估。

---

## ADR-001 检索采用混合召回，而不是纯向量

- **状态**：已采纳 ｜ 2026-10
- **背景**：企业文档里有大量型号、条款号、专有名词（"TX-200""第七条"）。纯向量检索对这类精确词项不敏感，问"TX-200 的保修期"经常召回泛泛而谈的段落。
- **决策**：向量召回 + 自研 BM25 召回，各自取 `FETCH_K=20`，用 RRF 融合后交给 LLM 精排取 Top-5。
- **备选与取舍**：

  | 方案 | 优点 | 代价 |
  |---|---|---|
  | 纯向量 | 实现最简、语义泛化好 | 精确词项差、无法解释 |
  | 纯 BM25 | 可解释、精确 | 同义词/改写无能为力 |
  | **RRF 混合（采纳）** | 两路互补，对分数量纲不敏感 | 每次多一次 BM25 + 一次精排，延迟上升 |
  | 学习型稀疏（SPLADE） | 效果更好 | 需模型服务，运维成本高 |

- **后果**：召回质量明显提升；代价是每次问答多 1 次 LLM 调用（精排），且 BM25 索引要随文档增删维护。
- **何时重估**：文档量到十万级切片（BM25 整文件读写不划算），或换用支持稀疏向量的引擎。

## ADR-002 父子分块：小块检索、大块回填

- **状态**：已采纳 ｜ 2026-10
- **背景**：500 字整块检索时噪声大；250 字小块检索准，但直接把小块喂给模型会"断章取义"。
- **决策**：父块 1000 字、子块 250 字。向量库只存子块，metadata 里带 `parent_content`；命中后返回父块给 LLM。
- **取舍**：存储放大（同一段文本存两份：子块 + 父块副本）；换来检索精度与上下文完整度同时保住。
- **后果**：`chunk_count` 按父块统计；改分块参数必须重建索引，因此需要版本号（见 ADR-006）。
- **何时重估**：文档以表格/代码为主时，固定字数切片会切断结构，应换语义/结构切片。

## ADR-003 RBAC：owner 不写入成员表

- **状态**：已采纳 ｜ 2026-10
- **背景**：知识库需要 owner / editor / viewer 三档权限；owner 天然唯一。
- **决策**：`knowledge_bases.user_id` 表示 owner，`kb_members` 只存被邀请的 editor/viewer；`require_kb_role()` 先判 owner 再查表。
- **备选**：把 owner 也写进 `kb_members`（角色统一，但要保证"有且仅有一个 owner"的约束，还得处理转让）。
- **后果**：少一张表的约束、少一次写；代价是"查所有成员"时要手动拼一条 owner 虚拟行（接口里 `id=null`）。
- **何时重估**：需要"转让所有权"或"多 owner"时，再引入成员表内的 owner 记录。

## ADR-004 A2A 默认关闭

- **状态**：已采纳 ｜ 2026-10
- **背景**：A2A 让外部 Agent 通过 JSON-RPC 调用本系统。一旦开放，等于把内部知识库暴露给任意调用方。
- **决策**：`A2A_ENABLED` 默认 `false`；开启时必须配 `A2A_TOKEN`，用常量时间比较校验；`kb_id` 必须显式传，不再回落到 1 号库。
- **取舍**：牺牲"开箱即用"的互操作演示，换取默认安全。面试演示时手动打开并说明令牌机制。
- **何时重估**：接入真实合作方时，改为 OAuth2 客户端凭证 + 按库授权。

## ADR-005 溯源用字符二元组，而不是 LLM 裁判

- **状态**：已采纳 ｜ 2026-10
- **背景**：RAG 最危险的失败是"答得顺但没依据"。需要在每次问答后判断句子有没有出处。
- **决策**：把答案切句，逐句算字符二元组在检索片段中的覆盖率；低于阈值标为 `unsupported`，整篇覆盖率低于 0.6 标 `low_coverage`。
- **备选与取舍**：

  | 方案 | 成本 | 可复现 | 对改写的容忍 |
  |---|---|---|---|
  | **二元组覆盖率（采纳）** | 0 次 LLM | ✅ 完全确定 | 差（同义改写会漏判） |
  | 每句一次 LLM 裁判 | 句子数 × 1 次调用 | ❌ | 好 |
  | NLI 模型 | 需额外服务 | ✅ | 较好 |

- **后果**：零成本、能进 CI；但它是**提示**不是**判决**，低覆盖不等于幻觉，UI 只做弱提示。
- **何时重估**：需要对外承诺"零幻觉"时，升级为 NLI 或抽样 LLM 复核。

## ADR-006 检索缓存只缓存片段，用版本号失效

- **状态**：已采纳 ｜ 2026-10
- **背景**：相同问题重复检索浪费 embedding 与精排调用；但缓存答案会踩多轮上下文、权限、时效三个坑。
- **决策**：
  - 只缓存 `retrieve()` 的片段列表，TTL 600s；
  - key = `(知识库版本号, 问题, 检索 schema 版本)`；
  - 文档增删改时 `INCR kb:{id}:ver`，旧 key 自然失效，**不做 `KEYS *` 扫描**。
- **取舍**：放弃"答案级缓存"的更高命中率，换取正确性；版本号会随文档变更增长，但只占一个整数。
- **后果**：`MemoryCache` 现在真正支持 TTL（之前 `ttl` 参数是摆设）；多实例必须用 Redis，否则各进程各一份缓存。
- **何时重估**：QPS 高到需要语义缓存时，另建"答案缓存 + 权限/上下文指纹"的独立设计，不要复用这一层。
