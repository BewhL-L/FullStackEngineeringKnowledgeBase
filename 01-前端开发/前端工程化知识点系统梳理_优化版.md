## 2. 模块化

### 2.1 模块化方案演进

| 方案 | 特点 | 环境 |
|------|------|------|
| IIFE | 立即执行函数，避免全局污染 | 浏览器 |
| CommonJS | `require/module.exports`，同步加载 | Node.js |
| AMD | `define/require`，异步加载 | 浏览器（RequireJS） |
| CMD | 类似 AMD，依赖就近 | 浏览器（SeaJS） |
| ES Module | `import/export`，静态分析，官方标准 | 浏览器 + Node.js |


> 🔍 **知识点深度解析**
>
> **作用**：了解模块化方案的演进，才能理解为什么 ES Module 成为今天的标准。
>
> **原理**：早期用 IIFE 包裹避免全局污染；CommonJS 以同步 require 服务 Node；AMD/CMD 解决浏览器异步加载；最终 ES Module 由语言标准统一，支持静态分析与 Tree Shaking。
>
> **用法要点**：① IIFE 用闭包隔离作用域，但仍需手动管理依赖  ② CommonJS 同步加载，适合服务端，不适合浏览器并发  ③ AMD（RequireJS）异步按需加载，回调风格  ④ CMD（SeaJS）依赖就近、延迟执行  ⑤ ESM 是官方标准，浏览器与 Node 双端统一

### 2.2 ES Module 详解

```javascript
// 导出
export const name = 'Tom';
export function say() {}
export default { }; // 默认导出

// 导入
import { name, say } from './module';
import defaultExport from './module';
import * as all from './module'; // 命名空间导入
import { name as userName } from './module'; // 重命名

// 动态导入（返回 Promise）
const module = await import('./module.js');
```

> 🔍 **知识点深度解析**
>
> **作用**：模块化是工程化的基础，ES Module 是当前标准。
>
> **原理**：ES Module 是静态的，import/export 必须在顶层，不能在条件语句中。这使得构建工具可以进行 Tree Shaking（移除未使用的代码）。CommonJS 是动态的，require 可以在任何地方调用，无法静态分析。ESM 在浏览器中通过 `<script type="module">` 加载，默认延迟执行（defer），CORS 限制。Node.js 12+ 原生支持 ESM（.mjs 或 package.json 中 "type": "module"）。
>
> **用法要点**：① 新项目统一用 ES Module；② `export default` 一个模块只能有一个；③ 具名导出用 `{}` 接收，默认导出直接命名；④ 循环依赖：ESM 支持但需注意导出值是绑定（实时更新），CommonJS 是值拷贝；⑤ 面试常考：ESM 与 CommonJS 区别、Tree Shaking 原理、循环依赖。

## 3. 构建工具

### 3.1 Vite（推荐）

**核心特性**：
- 开发时基于原生 ESM，无需打包，秒级启动
- 生产构建用 Rollup，Tree Shaking 优秀
- 开箱即用：TS、JSX、CSS 预处理器、HMR

```bash

> 🔍 **知识点深度解析**
>
> **作用**：Vite 是当前最主流的前端构建/开发工具，显著提升开发体验与构建效率。
>
> **原理**：开发期 Vite 不打包，直接用浏览器原生 ESM 加载源码、按需编译单文件，冷启动和 HMR 都极快；依赖预构建用 esbuild 把 CommonJS/多文件依赖转成 ESM。生产构建切换到 Rollup，借助 ESM 静态分析做更彻底的 Tree Shaking。
>
> **用法要点**：① dev 基于原生 ESM，启动秒级  ② HMR 精准更新变更模块，状态不丢失  ③ 配置 alias 用 path.resolve 而非相对路径  ④ server.proxy 做开发跨域代理，changeOrigin 改 Host  ⑤ 生产分包用 manualChunks/rollupOptions；环境变量用 import.meta.env

# 创建项目
npm create vite@latest my-app -- --template vue-ts

# 常用命令
npm run dev      # 开发服务器
npm run build    # 生产构建
npm run preview  # 预览构建结果
```

```javascript
// vite.config.ts
import { defineConfig } from 'vite';
import vue from '@vitejs/plugin-vue';
import path from 'path';

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: { '@': path.resolve(__dirname, 'src') }
  },
  server: {
    port: 3000,
    proxy: {
      '/api': { target: 'http://localhost:8080', changeOrigin: true }
    }
  },
  build: {
    outDir: 'dist',
    sourcemap: false,
    rollupOptions: {
      output: {
        manualChunks: { vue: ['vue', 'vue-router', 'pinia'] }
      }
    }
  }
});
```

### 3.2 Webpack（传统大型项目）

**核心概念**：入口（entry）、输出（output）、loader、plugin、mode

```javascript
// webpack.config.js
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  entry: './src/index.js',
  output: { path: path.resolve(__dirname, 'dist'), filename: '[name].[contenthash].js' },
  module: {
    rules: [
      { test: /\.js$/, use: 'babel-loader', exclude: /node_modules/ },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] }
    ]
  },
  plugins: [new HtmlWebpackPlugin({ template: './index.html' })],
  optimization: { splitChunks: { chunks: 'all' } }
};
```

> 🔍 **知识点深度解析**
>
> **作用**：构建工具是工程化的核心，负责代码编译、打包、优化。
>
> **原理**：Vite 开发时利用浏览器原生 ESM，只在请求时编译对应文件（按需编译），启动极快；HMR（热模块替换）在 ESM 基础上精准更新变更模块。生产构建用 Rollup，比 Webpack 的 Tree Shaking 更彻底（因为 ESM 静态分析）。Webpack 是全量打包，启动时需要构建整个依赖图，项目大了启动慢，但生态成熟、插件丰富。Vite 的 `optimizeDeps` 预构建 CommonJS 依赖（esbuild 转 ESM），解决浏览器不能直接加载 CommonJS 的问题。
>
> **用法要点**：① 新项目优先 Vite，老项目维护用 Webpack；② Vite 配置 alias 必须用 path.resolve，不要用相对路径；③ 代理配置 changeOrigin: true 修改 Host 头；④ 生产构建分包：manualChunks 分离第三方库；⑤ 环境变量用 import.meta.env（Vite）或 process.env（Webpack）；⑥ 面试常考：Vite 原理、与 Webpack 区别、HMR 实现、Tree Shaking。

## 4. 代码规范

### 4.1 ESLint

```bash

> 🔍 **知识点深度解析**
>
> **作用**：ESLint 在编码阶段发现语法与潜在逻辑问题，统一团队的代码质量基线。
>
> **原理**：ESLint 将源码解析为 AST，按规则遍历节点进行检测，可修复项通过 --fix 自动改写；规则来自 recommended 预设或插件（如 vue-eslint-parser），级别分 off/warn/error。
>
> **用法要点**：① 规则级别 off(0)/warn(1)/error(2)  ② extends 继承共享配置，plugins 提供规则  ③ parser 指定语法解析器（Vue 用 vue-eslint-parser）  ④ 与 Prettier 配合需 eslint-config-prettier 关掉格式冲突  ⑤ 保存时自动 fix 提升效率；CI 中跑 eslint 拦截不合规代码

# 安装
npm install eslint -D
npx eslint --init

# 检查和修复
npx eslint src/**/*.js
npx eslint src/**/*.js --fix
```

```javascript
// .eslintrc.cjs
module.exports = {
  env: { browser: true, es2021: true, node: true },
  extends: ['eslint:recommended', 'plugin:vue/vue3-recommended'],
  parser: 'vue-eslint-parser',
  parserOptions: { ecmaVersion: 'latest', sourceType: 'module' },
  rules: {
    'no-unused-vars': 'warn',
    'no-console': process.env.NODE_ENV === 'production' ? 'warn' : 'off',
    'vue/multi-word-component-names': 'off'
  }
};
```

> 🔍 **知识点深度解析**
>
> **作用**：代码规范保证团队代码风格一致，减少低级错误，提升可维护性。
>
> **原理**：ESLint 通过 AST（抽象语法树）分析代码，根据规则检测问题，部分问题可自动修复。Prettier 是代码格式化工具，不检测逻辑错误，只统一格式（缩进、引号、分号等）。两者配合：ESLint 管代码质量，Prettier 管代码格式。`eslint-config-prettier` 关闭 ESLint 中与 Prettier 冲突的格式规则，`eslint-plugin-prettier` 让 Prettier 规则作为 ESLint 规则运行。
>
> **用法要点**：① ESLint + Prettier 配合使用，不要让两者冲突；② VSCode 安装 ESLint 和 Prettier 插件，设置保存时自动格式化；③ 规则级别：off(0)/warn(1)/error(2)；④ 团队项目统一配置，提交到 Git；⑤ 面试常考：ESLint 与 Prettier 区别、配置方式、保存自动格式化。

## 5. Git 钩子与提交规范

### 5.1 Husky

```bash

> 🔍 **知识点深度解析**
>
> **作用**：Husky 把 Git 钩子接入前端工具链，在提交/推送等关键节点自动执行检查。
>
> **原理**：Husky 在 .husky/ 目录生成钩子脚本，Git 在对应事件（pre-commit、commit-msg、pre-push 等）触发时执行它们；通过 npm prepare 脚本在安装依赖后自动启用。
>
> **用法要点**：① pre-commit 在提交前触发，可拦截不合格代码  ② commit-msg 校验提交信息格式  ③ 常与 lint-staged 配合只对暂存文件检查  ④ husky install 需在 prepare 中执行以保证克隆后生效  ⑤ 钩子失败会让 Git 操作中断，强制修复

# 安装
npm install husky -D
npx husky install
npm set-script prepare "husky install"

# 添加 pre-commit 钩子
npx husky add .husky/pre-commit "npx lint-staged"
```

### 5.2 lint-staged

```json
// package.json
{
  "lint-staged": {
    "*.{js,ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["stylelint --fix", "prettier --write"],
    "*.md": ["prettier --write"]
  }
}
```


> 🔍 **知识点深度解析**
>
> **作用**：lint-staged 只对本次提交（暂存区）的文件跑检查，避免全量 lint 拖慢提交。
>
> **原理**：Git 提交时，lint-staged 取出 git add 的文件列表，按配置对其运行 ESLint/Prettier 等命令并自动写回修复结果，再继续提交流程。
>
> **用法要点**：① 只处理暂存文件，速度远快于全量检查  ② 配置按文件后缀匹配命令（js/ts/vue、css、md）  ③ 常与 pre-commit 钩子联动  ④ 自动 --fix/--write 会在提交前就地修改文件  ⑤ 大仓库必备，显著提升提交体验

### 5.3 Commitlint + Conventional Commits

```bash
npm install @commitlint/cli @commitlint/config-conventional -D
npx husky add .husky/commit-msg "npx commitlint --edit $1"
```

```javascript
// commitlint.config.cjs
module.exports = { extends: ['@commitlint/config-conventional'] };

**提交格式**：
```
<type>(<scope>): <subject>

> 🔍 **知识点深度解析**
>
> **作用**：Git 钩子在提交时自动检查代码，提交规范让 Git 历史清晰可读，可自动生成 CHANGELOG。
>
> **原理**：Husky 是 Git 钩子工具，在 `.husky/` 目录创建钩子脚本，Git 事件触发时执行。`pre-commit` 在提交前执行（可拦截提交），`commit-msg` 在写入提交信息后执行（校验格式）。lint-staged 只对暂存区（git add 的文件）执行检查，比全量检查快很多。Commitlint 校验提交信息是否符合 Conventional Commits 规范，不符合则拒绝提交。
>
> **用法要点**：① pre-commit 用 lint-staged 只检查暂存文件，提升速度；② commit-msg 用 commitlint 校验提交格式；③ type 必须是规定类型，subject 首字母小写、不加句号；④ 可配合 commitizen 交互式生成提交信息；⑤ 面试常考：Husky 原理、Conventional Commits 格式、lint-staged 作用。

## 6. CI/CD

### 6.1 GitHub Actions 示例

```yaml

> 🔍 **知识点深度解析**
>
> **作用**：GitHub Actions 是托管式 CI/CD，能在 push/PR 时自动跑测试、构建与部署。
>
> **原理**：工作流由仓库内 .github/workflows 的 YAML 定义，包含触发事件（on）与若干 job；每个 job 在独立 runner 虚拟机中按顺序执行 steps（checkout、装环境、跑脚本等）。
>
> **用法要点**：① on 指定触发事件（push/pr）与分支  ② actions/checkout 拉代码，setup-node 配 Node 版本  ③ 用 cache 缓存依赖（node_modules）加速  ④ npm ci 按 lockfile 精确安装，比 npm install 更适合 CI  ⑤ upload-artifact 留存构建产物供部署使用

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint
      - run: npm run test
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: dist
          path: dist
```

### 6.2 自动化部署

- **Vercel / Netlify**：前端项目一键部署，自动 HTTPS、CDN
- **GitHub Pages**：静态站点免费托管
- **Docker + Nginx**：容器化部署到自有服务器
- **OSS + CDN**：上传到阿里云/腾讯云对象存储

> 🔍 **知识点深度解析**
>
> **作用**：CI/CD 实现代码提交后自动测试、构建、部署，减少人工操作，提升交付效率。
>
> **原理**：CI（持续集成）在代码提交后自动运行测试和构建，确保代码质量。CD（持续部署/交付）在 CI 通过后自动部署到生产/预发环境。GitHub Actions 通过 YAML 配置工作流，触发事件（push/pr）后在虚拟机（runner）中执行步骤。缓存 node_modules 加速安装，`npm ci` 比 `npm install` 更严格（按 lockfile 精确安装）。
>
> **用法要点**：① CI 必须包含：安装依赖 → 代码检查 → 测试 → 构建；② 用 actions/cache 缓存依赖，提升速度；③ 生产构建禁用 sourcemap，开启 gzip/br 压缩；④ 部署用 hash 文件名（contenthash）利用浏览器缓存；⑤ 面试常考：CI/CD 概念、GitHub Actions 配置、部署方案。

## 7. 性能优化

### 7.1 构建性能

- Vite 天然快，Webpack 用 cache-loader、thread-loader、DLL
- 合理配置 alias，减少模块搜索
- 排除不必要的依赖（externals）


> 🔍 **知识点深度解析**
>
> **作用**：构建性能决定开发期启动速度与 CI 构建耗时，影响团队日常效率。
>
> **原理**：构建工具把源码编译打包，瓶颈在依赖图解析与转换；Vite 开发期免打包、按需编译所以快，Webpack 可借缓存与多线程 loader 提速，合理配置 alias/externals 减少搜索与打包范围。
>
> **用法要点**：① Vite 开发期天然快，Webpack 用 cache-loader/thread-loader 并行与缓存  ② 配置 alias 缩短模块解析路径  ③ externals 把不变的大依赖排除出打包  ④ 生产构建用持久化缓存（Vite 的 node_modules/.vite）  ⑤ DLL 预打包（Webpack 旧方案）已被 Vite 预构建取代；CI 中缓存依赖与构建产物

### 7.2 加载性能

| 优化手段 | 说明 |
|----------|------|
| 代码分割 | 路由懒加载、第三方库分包 |
|  Tree Shaking | 移除未使用代码（ESM） |
| 图片优化 | WebP/AVIF、懒加载、响应式图片 |
| 压缩 | Gzip/Brotli、HTML/CSS/JS 压缩 |
| CDN | 静态资源 CDN 加速 |
| 缓存 | HTTP 强缓存+协商缓存、Service Worker |
| 预加载 | `<link rel="preload">`、`prefetch` |


> 🔍 **知识点深度解析**
>
> **作用**：加载性能直接决定用户的首屏等待与留存，是前端性能优化的核心战场。
>
> **原理**：加载优化围绕“减少请求数、减小资源体积、利用缓存与并行”展开：代码分割按需加载、Tree Shaking 删死代码、图片用现代格式与懒加载、Gzip/Brotli 压缩、CDN 就近分发、HTTP 缓存避免重复请求、preload/prefetch 提前获取关键资源。
>
> **用法要点**：① 路由懒加载是最有效的代码分割手段  ② Tree Shaking 依赖 ESM 静态分析，移除未使用导出  ③ 图片用 WebP/AVIF 并 loading="lazy"  ④ 开启 Gzip/Brotli 与 CDN 加速静态资源  ⑤ 强缓存（Cache-Control）+ 协商缓存（ETag）配合 hash 文件名；preload 关键资源、prefetch 预测资源

### 7.3 运行性能

- 虚拟列表（大数据量渲染）
- 防抖节流（频繁事件）
- requestAnimationFrame（动画）
- 避免强制同步布局（layout thrashing）
- Web Worker（耗时计算）

```javascript
// 路由懒加载
const Home = () => import('@/views/Home.vue');

// 图片懒加载
<img loading="lazy" src="image.jpg" alt="">

// 防抖
function debounce(fn, delay = 300) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}
```

> 🔍 **知识点深度解析**
>
> **作用**：性能优化提升用户体验，是前端高级能力的体现。
>
> **原理**：加载性能核心是减少请求数和请求体积。代码分割按需加载（路由懒加载），首屏只加载必要代码。Tree Shaking 依赖 ESM 静态分析，移除未引用的导出。图片用现代格式（WebP 比 JPG 小 25-35%，AVIF 更小），`loading="lazy"` 原生懒加载。HTTP 缓存：强缓存（Cache-Control: max-age）不发请求，协商缓存（ETag/Last-Modified）发请求验证。运行性能核心是减少 JS 执行时间和避免重排重绘。
>
> **用法要点**：① 首屏加载时间（FCP/LCP）是核心指标；② 路由懒加载是最有效的代码分割；③ 大图片必须压缩，用 WebP 格式；④ 列表超过 100 条考虑虚拟列表；⑤ 滚动/输入事件用防抖节流；⑥ 面试常考：性能优化方案、懒加载实现、缓存策略、首屏优化。

## 8. 测试

### 8.1 单元测试（Vitest / Jest）

```bash
npm install vitest -D
```

```javascript
// sum.test.js
import { describe, it, expect } from 'vitest';
import { sum } from './sum';

describe('sum', () => {
  it('should add two numbers', () => {
    expect(sum(1, 2)).toBe(3);
  });
});
```


> 🔍 **知识点深度解析**
>
> **作用**：单元测试验证最小代码单元（函数/模块）的正确性，是质量保障的第一道防线。
>
> **原理**：测试框架提供 describe/it/expect 组织用例与断言，运行器在隔离环境执行并通过断言判断通过/失败；Vitest 基于 Vite 生态、原生 ESM、速度快，Jest 生态成熟、自带 mock。
>
> **用法要点**：① 用例三件套：分组 describe、单测 it、断言 expect  ② 纯函数测试最直接，重点覆盖边界与异常  ③ Vitest 兼容 Jest API，迁移成本低  ④ 用 mock 隔离外部依赖（定时器、请求）  ⑤ 配合覆盖率（coverage）衡量测试完整性

### 8.2 组件测试（Vue Test Utils）

```javascript
import { mount } from '@vue/test-utils';
import Button from './Button.vue';

it('emits click event', async () => {
  const wrapper = mount(Button);
  await wrapper.trigger('click');
  expect(wrapper.emitted('click')).toBeTruthy();
});
```


> 🔍 **知识点深度解析**
>
> **作用**：组件测试验证 UI 组件的行为（渲染、交互、事件发射），弥补单元测试对视图的盲区。
>
> **原理**：@vue/test-utils 的 mount/shallowMount 把组件挂载到测试环境，返回 wrapper，可查询 DOM、触发事件、断言 props/emitted，配合 Vitest/Jest 运行。
>
> **用法要点**：① mount 渲染完整子树，shallowMount 只渲染当前组件（子组件打桩）  ② wrapper.find 定位元素，trigger 模拟交互  ③ 用 emitted() 断言组件抛出的事件  ④ props/data 可在挂载时注入以覆盖场景  ⑤ 关注交互结果而非内部实现，降低脆弱性

### 8.3 E2E 测试（Cypress / Playwright）

```javascript
// cypress/e2e/login.cy.js
describe('Login', () => {
  it('should login successfully', () => {
    cy.visit('/login');
    cy.get('[data-testid=username]').type('admin');
    cy.get('[data-testid=password]').type('123456');
    cy.get('[data-testid=submit]').click();
    cy.url().should('include', '/dashboard');
  });
});
```

---


> 🔍 **知识点深度解析**
>
> **作用**：E2E 测试模拟真实用户在浏览器中走通完整业务流程，保障端到端可用性。
>
> **原理**：E2E 框架启动真实/无头浏览器，按脚本访问页面、操作元素、断言结果；Cypress 自带交互式 runner，Playwright 支持多浏览器与并行，均通过选择器定位元素。
>
> **用法要点**：① 站在用户视角验证关键链路（如登录、下单）  ② 用稳定选择器（data-testid）而非易变的样式/文本  ③ 命令链式调用，自动等待元素可交互  ④ 需起服务/数据库等完整环境，成本高、跑得慢  ⑤ 与单元/组件测试分层，E2E 只覆盖最核心路径
