## 1. 概述

Java 并发编程是利用多线程同时执行多个任务以提升程序吞吐量和响应性的技术体系。其核心是围绕**线程安全**展开，通过同步机制、锁、原子操作、并发容器等工具解决多线程环境下的数据竞争和一致性问题。

**核心定位**：
- 充分利用多核 CPU 资源，提升计算密集型任务性能
- 提高 I/O 密集型应用的吞吐量（线程等待 I/O 时可处理其他任务）
- 构建高并发、高可用的后端服务
- 是 Java 高级开发和面试的核心考点

**版本演进**：

| 版本 | 关键特性 |
|------|---------|
| Java 1.0 | 基础 Thread 类、synchronized、wait/notify |
| Java 5 (JDK 1.5) | JUC 包（java.util.concurrent）：线程池、并发集合、锁框架、原子类、Future |
| Java 7 | Fork/Join 框架、工作窃取算法 |
| Java 8 | CompletableFuture、Lambda 与函数式编程、StampedLock |
| Java 9 | Reactive Streams（Flow API） |
| Java 21 | 虚拟线程（Virtual Threads）、结构化并发（预览） |

### 2.1 线程基础与生命周期

线程是 CPU 调度的最小单位，Java 线程状态共 6 种（Thread.State 枚举）：

| 状态 | 说明 |
|------|------|
| NEW | 新建，尚未调用 start() |
| RUNNABLE | 可运行（包含运行中 + 就绪） |
| BLOCKED | 阻塞，等待获取锁 |
| WAITING | 无限等待，需被唤醒（wait/join/LockSupport.park） |
| TIMED_WAITING | 限时等待（sleep/wait(timeout)/join(timeout)） |
| TERMINATED | 终止，run() 执行完毕 |

> 🔍 **知识点深度解析**
>
> **作用**：线程状态模型是理解并发编程的基础，它描述了线程从创建到销毁的完整生命周期，是排查并发问题（死锁、活锁、线程饥饿）的关键依据。
>
> **原理**：Java 线程状态映射到 OS 线程状态，但不完全等同。JVM 的 RUNNABLE 包含了 OS 的 Ready 和 Running 两种状态（JVM 不区分就绪和运行中，因为线程调度由 OS 完成）。BLOCKED 仅发生在等待 synchronized 锁时，而 WAITING 是调用 wait/join/park 后主动进入的。状态转换由 JVM 和 OS 共同维护，每个 Java 对象都关联一个 monitor（管程），线程获取 monitor 失败则进入 BLOCKED，调用 wait 则释放 monitor 并进入 WAITING。
>
> **用法要点**：① 用 `jstack <pid>` 或 `Thread.getState()` 查看线程状态，死锁线程会显示 BLOCKED；② WAITING 状态的线程必须被 notify/notifyAll 唤醒，否则永久等待；③ sleep 不释放锁，wait 释放锁——这是面试高频考点；④ 线程池中的线程通常处于 WAITING（等待任务）或 TIMED_WAITING（keepAliveTime 超时回收）。

### 2.2 synchronized 与锁升级

synchronized 是 JVM 内置锁，基于对象头 Mark Word 实现，锁会随竞争升级：

1. **无锁** → 2. **偏向锁**（偏向第一个获取的线程，无竞争时几乎无开销）→ 3. **轻量级锁**（CAS 自旋，适用于短时间竞争）→ 4. **重量级锁**（OS 互斥量，线程阻塞挂起）

**锁优化**：自适应自旋、锁消除（逃逸分析）、锁粗化（合并相邻同步块）、偏向锁批量重偏向/撤销。

> 🔍 **知识点深度解析**
>
> **作用**：synchronized 是 Java 最基础的互斥同步机制，保证同一时刻只有一个线程执行临界区代码，从而保证原子性、可见性和有序性。它是解决数据竞争的首选方案（简单、稳定、JVM 持续优化）。
>
> **原理**：每个 Java 对象的对象头（Mark Word，64位）中存储了锁信息。无竞争时，Mark Word 记录偏向线程ID（偏向锁，仅一次CAS开销）；出现竞争时撤销偏向锁，升级为轻量级锁——线程在栈帧中创建 Lock Record，用 CAS 将 Mark Word 指向 Lock Record，成功则获取锁，失败则自旋等待；自旋一定次数仍失败则升级为重量级锁，关联 ObjectMonitor，线程进入 OS 级阻塞（park）。锁只能升级不能降级（除偏向锁可批量撤销）。
>
> **用法要点**：① 锁对象必须是不可变的（不要用 String 常量/Boolean/Integer 等可能被共享的对象）；② 同步方法锁的是 this，静态同步方法锁的是 Class 对象；③ 锁粒度要小但不要过小（频繁加解锁有开销），锁粗化是JVM自动优化；④ JDK 15 后偏向锁默认禁用（`-XX:+UseBiasedLocking`），因为高并发下偏向锁撤销开销大于收益；⑤ 用 `synchronized` 而非自己用 Lock 实现简单互斥，除非需要 tryLock/公平锁/读写锁等高级功能。

### 2.3 JUC 并发工具类

`java.util.concurrent` 包提供了丰富的并发工具：

| 类别 | 工具类 |
|------|--------|
| 锁框架 | ReentrantLock、ReadWriteLock、StampedLock |
| 原子类 | AtomicInteger、AtomicReference、LongAdder |
| 并发集合 | ConcurrentHashMap、CopyOnWriteArrayList、BlockingQueue |
| 同步工具 | CountDownLatch、CyclicBarrier、Semaphore、Exchanger |
| 线程池 | ThreadPoolExecutor、ScheduledThreadPoolExecutor |
| 异步任务 | Future、CompletableFuture、CompletionService |

> 🔍 **知识点深度解析**
>
> **作用**：JUC（java.util.concurrent）是 Java 5 引入的并发工具包，由 Doug Lea 设计，提供了比 synchronized 更灵活、更高效的并发原语，覆盖锁、原子操作、并发集合、同步工具、线程池等全场景，是 Java 并发编程的核心库。
>
> **原理**：JUC 的底层基石是 CAS（Compare-And-Swap，由 Unsafe 类提供的 CPU 原子指令）和 AQS（AbstractQueuedSynchronizer，队列同步器）。AQS 用一个 volatile int state 表示同步状态，用 CLH 队列（双向链表）管理等待线程，ReentrantLock/Semaphore/CountDownLatch 等都基于 AQS 实现。原子类基于 CAS 无锁更新，并发集合通过分段锁/CAS/COW 等技术实现线程安全。
>
> **用法要点**：① ReentrantLock 必须在 finally 中 unlock，否则锁泄漏；② ReadWriteLock 适合读多写少（读读不互斥），但写线程可能饥饿；③ LongAdder 比 AtomicLong 在高并发下性能更好（分段累加，最后汇总）；④ ConcurrentHashMap 不允许 null key/value；⑤ CountDownLatch 是一次性的（计数到0后不能重置），CyclicBarrier 可重置复用；⑥ Semaphore 可实现限流（控制并发访问数）。

### 2.4 线程池

线程池通过复用线程避免频繁创建销毁的开销，核心参数：

- `corePoolSize`：核心线程数
- `maximumPoolSize`：最大线程数
- `keepAliveTime`：非核心线程空闲存活时间
- `workQueue`：任务队列（ArrayBlockingQueue/LinkedBlockingQueue/SynchronousQueue）
- `threadFactory`：线程工厂
- `handler`：拒绝策略（AbortPolicy/CallerRunsPolicy/DiscardPolicy/DiscardOldestPolicy）

> 🔍 **知识点深度解析**
>
> **作用**：线程池是并发编程中最重要的性能优化工具，它通过复用线程减少创建销毁开销（线程创建需分配栈内存、OS 系统调用，约毫秒级），同时控制并发线程数避免资源耗尽（CPU/内存），是高并发服务的基础设施。
>
> **原理**：ThreadPoolExecutor 采用"核心线程 + 队列 + 非核心线程"三级缓冲策略。任务提交时：① 核心线程数未满 → 创建核心线程执行；② 核心线程满 → 任务入队列；③ 队列满 → 创建非核心线程（不超过 maximumPoolSize）；④ 非核心线程也满 → 执行拒绝策略。非核心线程空闲超过 keepAliveTime 后被回收。Worker 内部类继承 AQS，runWorker 循环从队列取任务执行。
>
> **用法要点**：① 必须用有界队列（ArrayBlockingQueue），无界队列（LinkedBlockingQueue 默认 Integer.MAX_VALUE）可能导致 OOM；② 核心线程数设置：CPU 密集型 = CPU核数+1，IO 密集型 = CPU核数*2（或根据实际压测调整）；③ 拒绝策略默认 AbortPolicy（抛异常），生产环境建议自定义（记录日志+告警+降级）；④ 用 ThreadPoolExecutor 显式创建，不要用 Executors 工厂方法（FixedThreadPool/SingleThreadPool 用无界队列，CachedThreadPool 最大线程数无限）；⑤ 线程池要优雅关闭（shutdown 等待任务完成，shutdownNow 中断正在执行的任务）。

### 2.5 Java 内存模型（JMM）

JMM 定义了多线程环境下变量的访问规则，解决三大问题：

- **原子性**：一个操作不可中断（synchronized、Lock、原子类）
- **可见性**：一个线程修改变量后，其他线程能立即看到（volatile、synchronized、final）
- **有序性**：禁止指令重排序（volatile、内存屏障、happens-before 原则）

**happens-before 原则**：程序顺序规则、监视器锁规则、volatile 规则、线程启动规则、线程终止规则、传递性。

> 🔍 **知识点深度解析**
>
> **作用**：JMM（Java Memory Model）是 Java 虚拟机规范的一部分，它定义了线程和主内存之间的抽象关系，解决了多线程环境下"一个线程的写操作何时对其他线程可见"的问题，是理解 volatile、synchronized、并发 bug 的理论基础。
>
> **原理**：JMM 是一个抽象模型，不直接对应硬件。它规定所有变量存储在主内存，每个线程有自己的工作内存（对应 CPU 缓存/寄存器），线程操作变量时先从主内存拷贝到工作内存，操作完再写回主内存。这就导致了可见性问题（线程A改了还没写回，线程B看不到）。JMM 通过 8 种原子操作（read/load/use/assign/store/write/lock/unlock）和内存屏障（LoadLoad/StoreStore/LoadStore/StoreLoad）来规范读写顺序。volatile 会在写操作后加 StoreStore+StoreLoad 屏障，读操作前加 LoadLoad 屏障，从而保证可见性和禁止重排序。
>
> **用法要点**：① volatile 只保证可见性和有序性，不保证原子性（i++ 不是原子操作）；② volatile 的典型用法：状态标记（boolean flag）、双重检查锁（DCL）的单例变量；③ happens-before 是判断可见性的规则——如果 A happens-before B，则 A 的写对 B 可见；④ 不要用 volatile 替代锁，它适合一写多读的状态标记场景；⑤ final 字段的可见性由 JMM 保证（构造函数完成后 final 字段一定对其他线程可见），这也是不可变对象线程安全的原因。

## 3. 常用用法

### 3.1 线程创建与启动

```java
// 方式1：继承 Thread
class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("线程执行: " + Thread.currentThread().getName());
    }
}
new MyThread().start();

// 方式2：实现 Runnable（推荐，解耦任务和线程）
Runnable task = () -> System.out.println("Runnable 任务");
new Thread(task, "my-thread").start();

// 方式3：实现 Callable（有返回值，可抛异常）
FutureTask<Integer> future = new FutureTask<>(() -> {
    Thread.sleep(1000);
    return 42;
});
new Thread(future).start();
Integer result = future.get(); // 阻塞等待结果
```

> 🔍 **知识点深度解析**
>
> **作用**：线程创建是并发编程的起点，三种方式各有适用场景。Runnable 是最常用的（任务与线程解耦，可提交到线程池），Callable 用于需要返回结果的异步任务，继承 Thread 仅在需要重写线程行为时使用。
>
> **原理**：调用 `start()` 后，JVM 会调用 native 方法 `start0()`，通过 OS 系统调用（pthread_create）创建内核线程，然后 OS 调度线程执行 `run()` 方法。注意：直接调用 `run()` 只是普通方法调用，不会创建新线程。FutureTask 同时实现了 Runnable 和 Future，内部用 state 变量（NEW/COMPLETING/NORMAL/EXCEPTIONAL/CANCELLED/INTERRUPTING/INTERRUPTED）管理任务状态，get() 时如果未完成则用 LockSupport.park() 阻塞等待。
>
> **用法要点**：① 实际开发中不要手动 new Thread，用线程池；② 必须给线程命名（setName 或 ThreadFactory），方便排查问题；③ 未捕获异常会导致线程终止，用 UncaughtExceptionHandler 处理；④ Callable 的异常会包装在 ExecutionException 中，get() 时需 try-catch；⑤ 虚拟线程（Java 21）用 `Thread.ofVirtual().start(runnable)` 创建，可创建百万级而不消耗 OS 线程。

### 3.2 synchronized 与 ReentrantLock

```java
// synchronized
public synchronized void syncMethod() { /* 临界区 */ }

public void syncBlock() {
    synchronized (this) { /* 临界区 */ }
}

// ReentrantLock
private final ReentrantLock lock = new ReentrantLock();
public void lockMethod() {
    lock.lock();
    try {
        // 临界区
    } finally {
        lock.unlock(); // 必须在 finally 中释放
    }
}

// 尝试获取锁（带超时）
if (lock.tryLock(3, TimeUnit.SECONDS)) {
    try { /* 临界区 */ } finally { lock.unlock(); }
} else {
    // 获取锁失败，降级处理
}

// 公平锁（先到先得，性能略低）
ReentrantLock fairLock = new ReentrantLock(true);
```

> 🔍 **知识点深度解析**
>
> **作用**：ReentrantLock 是 JUC 提供的可重入互斥锁，功能比 synchronized 更丰富（可中断、可超时、公平锁、多条件变量），适用于需要高级锁控制的场景。synchronized 是 JVM 内置锁，简单稳定，是日常开发的首选。
>
> **原理**：ReentrantLock 基于 AQS 实现，内部有 NonfairSync（非公平，默认）和 FairSync（公平）两种实现。非公平锁：线程进来直接 CAS 抢锁，抢不到才入队列；公平锁：线程先检查队列是否有等待者，有则入队排队。可重入通过 state 计数实现（同一线程每次 lock 则 state+1，unlock 则 state-1，state=0 时释放锁）。Condition 替代了 Object 的 wait/notify，一个 ReentrantLock 可创建多个 Condition（如 ArrayBlockingQueue 用 notEmpty/notFull 两个条件）。
>
> **用法要点**：① 简单互斥用 synchronized，需要 tryLock/可中断/公平锁/多 Condition 时才用 ReentrantLock；② lock() 必须在 finally 中 unlock，建议用 try-finally 模板；③ 公平锁会降低吞吐量（约降低10-20%），除非有明确的公平性需求否则用非公平；④ Condition 的 await/signal/signalAll 对应 wait/notify/notifyAll，必须在 lock 持有期间调用；⑤ synchronized 锁优化（偏向/轻量/重量）是 JVM 自动的，ReentrantLock 没有锁升级但性能接近重量级锁。

### 3.3 原子类与 CAS

```java
// AtomicInteger
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();          // 原子自增
count.compareAndSet(expect, update); // CAS
count.addAndGet(5);               // 原子加

// LongAdder（高并发下比 AtomicLong 性能好）
LongAdder adder = new LongAdder();
adder.increment();
long sum = adder.sum();

// AtomicReference（原子更新引用）
AtomicReference<User> userRef = new AtomicReference<>();
userRef.compareAndSet(oldUser, newUser);
```

> 🔍 **知识点深度解析**
>
> **作用**：原子类基于 CAS 实现无锁并发，在高并发下性能优于锁（无阻塞、无上下文切换），适用于计数器、序列号生成器、引用更新等场景。LongAdder 是 AtomicLong 的高并发优化版。
>
> **原理**：CAS（Compare-And-Swap）是 CPU 提供的原子指令（x86 是 cmpxchg），它比较内存值是否等于预期值，等于则更新为新值并返回 true，否则返回 false。AtomicInteger 的 incrementAndGet 内部是一个 CAS 自旋循环（do-while），失败则重试。ABA 问题（值从A变B又变回A，CAS 误以为没变）用 AtomicStampedReference（加版本号）解决。LongAdder 的优化思路是：高并发时将value拆成多个 Cell，每个线程只更新自己的 Cell（通过线程探针哈希定位），最后 sum() 时累加所有 Cell，从而减少 CAS 竞争。
>
> **用法要点**：① 原子类适合简单的原子操作，复杂的多步操作仍需锁；② CAS 自旋在竞争激烈时会消耗大量 CPU（活锁），此时用锁更好；③ LongAdder 的 sum() 在并发修改时结果不精确（最终一致），适合统计不适合精确计算；④ AtomicReferenceFieldUpdater 可对已有类的字段做原子更新（不修改原类）；⑤ 不要用原子类的多个方法组合实现复合操作（如先 get 再 set），那不是原子的。

### 3.4 线程池配置与使用

```java
// 标准创建方式（推荐）
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    4,                              // corePoolSize 核心线程数
    8,                              // maximumPoolSize 最大线程数
    60, TimeUnit.SECONDS,           // keepAliveTime 空闲存活时间
    new ArrayBlockingQueue<>(100),  // 有界队列
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(),
    new RejectedExecutionHandler() { // 自定义拒绝策略
        @Override
        public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
            log.error("任务被拒绝，活跃线程:{}, 队列大小:{}", e.getActiveCount(), e.getQueue().size());
            // 降级处理：写入MQ或返回默认值
        }
    }
);

// 提交任务
executor.execute(() -> doSomething());           // 无返回值
Future<String> future = executor.submit(() -> "result"); // 有返回值

// 优雅关闭
executor.shutdown(); // 不再接受新任务，等待已提交任务完成
executor.awaitTermination(60, TimeUnit.SECONDS); // 等待终止
```

> 🔍 **知识点深度解析**
>
> **作用**：线程池的正确配置是高并发服务稳定性的关键。不合理的配置（无界队列、过大的最大线程数、不合适的拒绝策略）会导致 OOM、CPU 飙高、请求雪崩。标准创建方式让每个参数都可控可监控。
>
> **原理**：线程池的核心是 Worker 内部类，它继承 AQS 并实现 Runnable。runWorker() 方法是一个 while 循环，不断从 getTask() 取任务执行。getTask() 中：如果当前线程数 > corePoolSize 且空闲超时（poll(keepAliveTime)）则返回 null，线程退出；否则 take() 阻塞等待。allowCoreThreadTimeOut(true) 可让核心线程也超时回收。prestartAllCoreThreads() 可预热核心线程。
>
> **用法要点**：① 队列大小根据业务峰值和内存设置，太小会频繁触发拒绝策略，太大可能 OOM；② 核心线程数根据任务类型设置（CPU密集=核数+1，IO密集=核数*2~10），最佳值需压测确定；③ 监控线程池指标（活跃线程数、队列大小、任务完成数、拒绝次数），用 Micrometer 或自定义监控；④ 不同业务用不同线程池，避免一个业务慢导致所有业务阻塞（线程池隔离）；⑤ Spring Boot 中用 @Async 时要自定义 ThreadPoolTaskExecutor，不要用默认的 SimpleAsyncTaskExecutor（每次新建线程）。

### 3.5 CompletableFuture 异步编程

```java
// 异步执行
CompletableFuture<String> future = CompletableFuture.supplyAsync(() -> {
    return queryUser(); // 异步查询
}, executor);

// 链式调用（thenApply 转换结果）
CompletableFuture<Integer> ageFuture = future
    .thenApply(user -> user.getAge())
    .thenApply(age -> age + 1);

// thenAccept 消费结果（无返回值）
future.thenAccept(user -> System.out.println(user));

// thenCompose 扁平化嵌套（避免 CompletableFuture<CompletableFuture<T>>）
CompletableFuture<Order> orderFuture = future
    .thenCompose(user -> queryOrderAsync(user.getId()));

// 组合两个 Future
CompletableFuture<String> combined = future
    .thenCombine(orderFuture, (user, order) -> user.getName() + order.getId());

// 异常处理
future.exceptionally(ex -> {
    log.error("查询失败", ex);
    return "default"; // 返回默认值
});

// 等待所有完成
CompletableFuture.allOf(future1, future2, future3).join();

// 任一完成即返回
CompletableFuture.anyOf(future1, future2).join();
```

> 🔍 **知识点深度解析**
>
> **作用**：CompletableFuture 是 Java 8 引入的异步编程工具，实现了 Future 和 CompletionStage 接口，支持链式调用、组合、异常处理、回调，解决了传统 Future 的 get() 阻塞问题，是构建异步非阻塞服务的核心工具。
>
> **原理**：CompletableFuture 内部用一个 result 字段存储结果（正常结果或 AltResult 包装的异常），用一个 stack（Treiber 栈，无锁并发栈）存储依赖的后续操作（Completion）。当异步任务完成时，会触发 postComplete() 遍历 stack 执行所有依赖的 Completion。每个链式方法（thenApply/thenAccept/thenCompose）都会创建一个新的 CompletableFuture 和对应的 Completion，压入前一个 Future 的 stack。异步执行默认用 ForkJoinPool.commonPool()，也可指定自定义 Executor。
>
> **用法要点**：① 生产环境必须指定自定义 Executor，不要用默认的 commonPool（它的线程数=CPU核数-1，IO密集型任务会阻塞所有线程）；② thenApply（同步）vs thenApplyAsync（异步），后者会提交到线程池执行；③ thenCompose 用于返回 CompletableFuture 的函数（扁平化），thenApply 用于返回普通值的函数；④ exceptionally 只处理异常，handle 同时处理正常结果和异常；⑤ allOf 返回 Void，需配合 thenApply 收集各 Future 结果；⑥ join() 会抛 CompletionException（非受检异常），get() 抛 ExecutionException（受检异常）。

### 3.6 并发集合

```java
// ConcurrentHashMap（线程安全的 HashMap）
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.put("key", 1);
map.computeIfAbsent("key", k -> 0); // 原子计算
map.forEach((k, v) -> System.out.println(k + ":" + v));

// CopyOnWriteArrayList（写时复制，读多写少）
CopyOnWriteArrayList<String> list = new CopyOnWriteArrayList<>();
list.add("item");
list.forEach(System.out::println); // 遍历不需要加锁

// BlockingQueue（阻塞队列，生产者消费者模式）
BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);
queue.put(task);  // 满则阻塞
Task t = queue.take(); // 空则阻塞
```

> 🔍 **知识点深度解析**
>
> **作用**：并发集合是多线程环境下的安全数据结构，避免了手动加锁的繁琐和错误。ConcurrentHashMap 是最常用的高并发 Map，CopyOnWriteArrayList 适合读多写少的监听列表，BlockingQueue 是实现生产者消费者模式的天然选择。
>
> **原理**：ConcurrentHashMap（JDK 8+）用 CAS + synchronized 实现并发安全。put 时：如果桶为空则 CAS 插入；如果桶不为空则 synchronized 锁住桶头节点，然后链表/红黑树插入。size() 用 baseCount + CounterCell 数组（类似 LongAdder）统计。JDK 7 用分段锁（Segment），JDK 8 改为桶级锁，粒度更细性能更好。CopyOnWriteArrayList 的写操作会复制整个数组（Arrays.copyOf），替换引用，读操作无锁直接读（数组不可变）。BlockingQueue 用 ReentrantLock + 两个 Condition（notEmpty/notFull）实现阻塞。
>
> **用法要点**：① ConcurrentHashMap 的复合操作（如先判断再put）不是原子的，用 compute/merge/computeIfAbsent 等原子方法；② CopyOnWriteArrayList 写操作开销大（复制数组），只适合写极少读极多的场景（如监听器列表、配置列表）；③ ArrayBlockingQueue 有界（必须指定容量），LinkedBlockingQueue 可选有界（默认 Integer.MAX_VALUE，注意 OOM）；④ PriorityBlockingQueue 是无界的，按优先级出队；⑤ 不要用 Collections.synchronizedMap（全表锁，性能差）替代 ConcurrentHashMap。

### 3.7 同步工具类

```java
// CountDownLatch：等待多个线程完成
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) {
    executor.execute(() -> {
        try { doWork(); } finally { latch.countDown(); }
    });
}
latch.await(); // 阻塞直到计数为0

// CyclicBarrier：多个线程互相等待到同一屏障点
CyclicBarrier barrier = new CyclicBarrier(3, () -> System.out.println("全部到达"));
executor.execute(() -> { barrier.await(); /* 继续执行 */ });

// Semaphore：限流（控制并发数）
Semaphore semaphore = new Semaphore(10); // 最多10个并发
semaphore.acquire(); // 获取许可
try { doWork(); } finally { semaphore.release(); }
```

> 🔍 **知识点深度解析**
>
> **作用**：同步工具类是 JUC 提供的高级线程协作原语，用于实现复杂的线程间协调。CountDownLatch 实现"一个线程等待多个线程完成"，CyclicBarrier 实现"多个线程互相等待到同一点"，Semaphore 实现"控制并发访问数（限流）"。
>
> **原理**：三者都基于 AQS。CountDownLatch 用 state 表示计数，countDown() 每次 state-1（CAS），state=0 时唤醒所有等待线程（共享模式 release）。CyclicBarrier 用 ReentrantLock + Condition 实现，内部有 generation（代）概念，所有线程到达后 trip 唤醒并重置下一代（可复用）。Semaphore 用 state 表示许可数，acquire() 尝试 state-1（CAS），失败则入队阻塞，release() 则 state+1 并唤醒等待线程。公平/非公平语义由 AQS 的 FairSync/NonfairSync 控制。
>
> **用法要点**：① CountDownLatch 是一次性的（计数到0后不能重置），CyclicBarrier 可重置复用（reset()）；② CyclicBarrier 的 await() 会抛 BrokenBarrierException（屏障被破坏时，如某线程中断或超时）；③ Semaphore 可实现连接池/限流，release() 必须在 finally 中；④ Exchanger 用于两个线程交换数据（适合配对工作场景）；⑤ Phaser（JDK 7）是更灵活的 CyclicBarrier，支持动态注册参与者、多阶段同步。

### 3.8 虚拟线程（Java 21）

```java
// 创建虚拟线程
Thread.ofVirtual().name("virtual-", 0).start(() -> {
    System.out.println("虚拟线程: " + Thread.currentThread());
});

// 用 ExecutorService 创建大量虚拟线程
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10000; i++) {
        executor.submit(() -> {
            Thread.sleep(Duration.ofSeconds(1)); // IO阻塞不消耗OS线程
            return i;
        });
    }
} // try-with-resources 自动等待所有任务完成

// 结构化并发（预览）
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<User> user = scope.fork(() -> queryUser(id));
    Subtask<Order> order = scope.fork(() -> queryOrder(id));
    scope.join().throwIfFailed();
    return new Result(user.get(), order.get());
}
```

> 🔍 **知识点深度解析**
>
> **作用**：虚拟线程（Virtual Threads，项目 Loom）是 Java 21 的革命性特性，它是 JVM 管理的轻量级线程，不直接绑定 OS 线程，可以创建百万级而几乎不消耗资源，彻底解决了传统线程模型在 IO 密集型场景下的限制。
>
> **原理**：虚拟线程由 JVM 调度，挂载到 OS 载体线程（ForkJoinPool）上执行。当虚拟线程遇到阻塞操作（IO/sleep/park）时，JVM 会将其"卸载"（unmount），释放载体线程去执行其他虚拟线程；阻塞操作完成后，虚拟线程被"挂载"（mount）到任意可用载体线程继续执行。这通过字节码改写（在阻塞调用处插入 yield 点）和 Continuation（续体，保存/恢复调用栈）实现。synchronized 块会 pin（固定）载体线程（不卸载），所以虚拟线程中尽量用 ReentrantLock。
>
> **用法要点**：① 虚拟线程适合 IO 密集型任务（数据库/网络调用），不适合 CPU 密集型（不会比平台线程快）；② 不要池化虚拟线程（它们很轻量，每次创建即可，池化反而限制并发）；③ 虚拟线程中避免 synchronized 长时间持有（会 pin 载体线程），用 ReentrantLock 替代；④ 用 `Executors.newVirtualThreadPerTaskExecutor()` 替代传统线程池；⑤ 结构化并发（StructuredTaskScope）让并发任务的生命周期与代码块绑定，避免线程泄漏，是虚拟线程的最佳搭档；⑥ 注意 ThreadLocal 在虚拟线程中的使用（每个虚拟线程都有自己的 ThreadLocal，百万虚拟线程会占用大量内存，用 ScopedValue 替代）。

## 4. 注意事项

1. **不可变对象优先**：不可变对象（final 字段、无修改方法）天生线程安全，不需要同步。优先设计不可变类（如 String、LocalDateTime），减少同步需求。

2. **synchronized vs Lock 选择**：简单互斥用 synchronized（JVM 优化、自动释放），需要 tryLock/可中断/公平锁/多条件变量时用 ReentrantLock。不要为了"高级"而用 Lock。

3. **volatile 不保证原子性**：volatile 只保证可见性和有序性，`i++`（读-改-写）不是原子操作，需要用 AtomicInteger 或 synchronized。

4. **线程池必须用有界队列**：无界队列（LinkedBlockingQueue 默认容量）会导致任务无限堆积，最终 OOM。用 ArrayBlockingQueue 或指定容量的 LinkedBlockingQueue。

5. **线程池大小设置**：CPU 密集型 = 核数+1，IO 密集型 = 核数*2~10。最佳值需压测确定，不要盲目设置过大（上下文切换开销）或过小（资源利用率低）。

6. **死锁避免**：死锁四条件（互斥、持有并等待、不可剥夺、循环等待）。避免方法：固定加锁顺序、用 tryLock 超时、减少锁嵌套、用并发集合替代手动锁。用 jstack 检测死锁。

7. **ThreadLocal 内存泄漏**：ThreadLocal 的 Entry 是弱引用（key 弱引用，value 强引用），线程池中的线程不会死亡，value 永远无法回收。必须在 finally 中调用 remove()。

8. **wait/notify 用 while 循环**：用 while 而非 if 判断条件，防止虚假唤醒（spurious wakeup）和多消费者竞争。标准模式：`while (!condition) { wait(); }`。

9. **Future.get 设置超时**：future.get() 无超时会永久阻塞（任务卡死时）。用 `get(timeout, unit)` 并处理 TimeoutException，或用 CompletableFuture 的 orTimeout()。

10. **避免循环创建线程**：new Thread() 开销大（OS 系统调用、栈内存分配），且无法控制并发数。必须用线程池管理。

11. **并发集合复合操作非原子**：ConcurrentHashMap 的 `if (!map.containsKey(k)) map.put(k, v)` 不是原子的，用 `putIfAbsent` 或 `computeIfAbsent`。

12. **虚拟线程适用场景**：虚拟线程适合 IO 密集型，不适合 CPU 密集型。避免在虚拟线程中长时间持有 synchronized（pin 载体线程），用 ReentrantLock。

---

> 💡 **深度讲解**：并发编程的本质是"正确性 + 性能"的平衡。正确性靠线程安全（原子性、可见性、有序性）保障，性能靠减少锁竞争和上下文切换提升。synchronized 的锁升级机制是 JVM 的精妙优化：无竞争时偏向锁几乎零开销（只记录线程ID），轻度竞争时轻量级锁用 CAS 自旋不挂起线程（避免 OS 上下文切换），重度竞争才升级为重量级锁（OS 互斥量，线程挂起等待）。这解释了为什么 JDK 1.6 后 synchronized 性能大幅提升，也解释了为什么不要盲目用 Lock 替代 synchronized。线程池是并发性能的核心——它通过复用线程避免创建销毁开销，通过有界队列和最大线程数控制资源消耗，通过拒绝策略保护系统不被压垮。CompletableFuture 则把异步编程从"回调地狱"中解放出来，用链式调用实现声明式的异步编排。Java 21 的虚拟线程是革命性的——它让"每个请求一个线程"的简单编程模型在 IO 密集型场景下也能支撑百万级并发，不再需要异步框架（Netty/Reactor）的复杂编程模型。理解了这些机制，就能在面试和实战中写出正确且高性能的并发代码。
>
> **📝 精简总结**：Java 并发核心是线程安全三要素（原子性/可见性/有序性），synchronized 有锁升级（偏向→轻量→重量），JUC 提供 Lock/原子类/并发集合/同步工具/线程池；线程池必须用有界队列+合理大小，CompletableFuture 实现链式异步编排；注意 volatile 不保证原子性、ThreadLocal 必须 remove、Future.get 设超时、死锁避免、虚拟线程适合 IO 密集型用 ReentrantLock 替代 synchronized。
