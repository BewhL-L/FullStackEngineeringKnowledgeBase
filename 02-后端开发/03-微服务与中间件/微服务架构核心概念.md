# 微服务架构核心概念

> 微服务架构的核心概念、设计原则、关键组件与落地实践。

## 概述

微服务架构（Microservices Architecture）是一种将单个应用程序开发为一组小型、独立服务的架构风格。每个服务运行在自己的进程中，通过轻量级机制（通常是 HTTP REST API 或消息队列）通信。

**与单体架构对比**：

| 维度 | 单体架构 | 微服务架构 |
|------|---------|-----------|
| 部署 | 一个包部署所有功能 | 每个服务独立部署 |
| 扩展 | 整体扩展 | 按需扩展单个服务 |
| 技术栈 | 统一技术栈 | 各服务可选择不同技术栈 |
| 故障影响 | 一个bug可能导致整个应用崩溃 | 故障隔离在单个服务内 |
| 开发协作 | 多人修改同一代码库，冲突多 | 团队独立开发各自服务 |
| 运维复杂度 | 低 | 高（需要服务治理、监控等） |

**适用场景**：
- 大型复杂应用，团队规模大
- 需要独立扩展不同功能模块
- 需要快速迭代和独立部署
- 不同模块有不同的技术需求

**不适用场景**：
- 小型简单应用（微服务增加不必要的复杂度）
- 团队规模小（<5人）
- 业务边界不清晰
- 缺乏运维和DevOps能力

## 原理

### 微服务的核心设计原则

1. **单一职责（Single Responsibility）**：每个服务只负责一个业务领域的功能
2. **服务自治（Service Autonomy）**：每个服务独立开发、部署、运行、数据存储
3. **去中心化（Decentralization）**：去中心化治理、去中心化数据管理
4. **容错设计（Fault Tolerance）**：假设服务会失败，设计降级和熔断机制
5. **API优先（API First）**：服务间通过明确定义的API通信
6. **可观测性（Observability）**：日志、指标、链路追踪三位一体

### 微服务架构的核心组件

```
客户端 → API网关 → 服务A / 服务B / 服务C
              ↓
         服务注册中心
              ↓
         配置中心
              ↓
    服务间通信（REST/gRPC/消息队列）
              ↓
    分布式追踪 / 日志聚合 / 监控告警
```

**关键组件详解**：

1. **API网关（API Gateway）**：
   - 统一入口，路由请求到后端服务
   - 负责认证、限流、熔断、日志
   - 常见实现：Spring Cloud Gateway、Kong、Nginx

2. **服务注册与发现（Service Registry & Discovery）**：
   - 服务启动时注册自己的地址
   - 调用方从注册中心获取服务实例列表
   - 常见实现：Nacos、Eureka、Consul、Zookeeper

3. **配置中心（Configuration Center）**：
   - 集中管理所有服务的配置
   - 支持动态刷新配置
   - 常见实现：Nacos、Apollo、Spring Cloud Config

4. **服务间通信**：
   - **同步**：REST（HTTP）、gRPC（高性能二进制协议）
   - **异步**：消息队列（Kafka、RabbitMQ、RocketMQ）
   - 选择原则：需要即时响应用同步，需要解耦和削峰用异步

5. **熔断与限流（Circuit Breaker & Rate Limiting）**：
   - 熔断：下游服务故障时快速失败，防止级联故障
   - 限流：保护服务不被突发流量打垮
   - 常见实现：Sentinel、Resilience4j、Hystrix（已停更）

6. **分布式追踪（Distributed Tracing）**：
   - 追踪请求在多个服务间的调用链路
   - 常见实现：SkyWalking、Jaeger、Zipkin

7. **日志聚合（Log Aggregation）**：
   - 集中收集所有服务的日志
   - 常见实现：ELK（Elasticsearch+Logstash+Kibana）、Loki

### 分布式事务

微服务架构下，一个业务操作可能涉及多个服务的数据变更，需要分布式事务保证一致性。

**常见方案**：

1. **两阶段提交（2PC）**：强一致性，性能差，不推荐
2. **TCC（Try-Confirm-Cancel）**：最终一致性，业务侵入性强
3. **Saga模式**：最终一致性，通过补偿事务回滚，适合长流程
4. **本地消息表**：最终一致性，简单可靠
5. **事务消息（RocketMQ）**：最终一致性，半消息机制

**CAP定理**：分布式系统无法同时满足一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance），只能三选二。微服务架构通常选择AP（可用性+分区容错），通过最终一致性保证数据正确。

## 实操

### 1. Spring Cloud 微服务项目结构

```
my-microservices/
├── my-gateway/          # API网关
├── my-user-service/     # 用户服务
├── my-order-service/    # 订单服务
├── my-product-service/  # 商品服务
├── my-common/           # 公共模块（DTO、工具类）
└── pom.xml              # 父POM
```

### 2. 服务注册（Nacos）

```yaml
# application.yml
spring:
  application:
    name: user-service
  cloud:
    nacos:
      discovery:
        server-addr: localhost:8848
        namespace: dev
      config:
        server-addr: localhost:8848
        file-extension: yaml
```

### 3. 服务间调用（OpenFeign）

```java
@FeignClient(name = "product-service")
public interface ProductClient {
    @GetMapping("/api/products/{id}")
    ProductDTO getProduct(@PathVariable("id") Long id);

    @PostMapping("/api/products/deduct")
    Result<Void> deductStock(@RequestBody DeductStockRequest request);
}
```

### 4. 熔断降级（Sentinel）

```java
@Service
public class OrderService {
    @SentinelResource(
        value = "createOrder",
        blockHandler = "createOrderBlockHandler",
        fallback = "createOrderFallback"
    )
    public Order createOrder(OrderRequest request) {
        // 正常业务逻辑
        ProductDTO product = productClient.getProduct(request.getProductId());
        // ...
    }

    // 限流/熔断触发时执行
    public Order createOrderBlockHandler(OrderRequest request, BlockException ex) {
        throw new BusinessException("系统繁忙，请稍后重试");
    }

    // 异常降级
    public Order createOrderFallback(OrderRequest request, Throwable ex) {
        log.error("创建订单失败", ex);
        throw new BusinessException("创建订单失败，请稍后重试");
    }
}
```

### 5. 分布式事务（Saga模式 - Seata）

```java
@GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
public void createOrder(OrderRequest request) {
    // 1. 创建订单
    orderMapper.insert(order);
    // 2. 扣减库存（远程调用商品服务）
    productClient.deductStock(request.getProductId(), request.getQuantity());
    // 3. 扣减余额（远程调用用户服务）
    userClient.deductBalance(request.getUserId(), request.getAmount());
    // 任一环节失败，Seata自动回滚所有分支
}
```

## 问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 服务间调用超时 | 网络延迟 / 下游服务慢 / 连接池耗尽 | 设置合理超时 / 熔断降级 / 异步调用 / 优化下游性能 |
| 分布式事务数据不一致 | 网络分区 / 服务宕机 / 补偿失败 | 用Seata等框架 / 本地消息表 / 定期对账 / 人工补偿 |
| 服务雪崩 | 一个服务故障导致级联失败 | 熔断（Sentinel）/ 限流 / 降级 / 隔离（线程池/信号量） |
| 注册中心服务列表不准 | 服务异常退出未注销 / 网络分区 | 心跳检测 / 健康检查 / 服务摘除 / 多注册中心 |
| 配置不生效 | 配置中心推送失败 / 客户端未刷新 / 缓存 | 检查配置中心连接 / 用@RefreshScope / 手动刷新 / 检查配置格式 |
| 链路追踪找不到 | 未接入Agent / traceId未传递 / 采样率低 | 正确配置Agent / 跨服务传递traceId / 提高采样率 / 检查网络 |
| 接口版本不兼容 | 服务升级后API变更 | API版本管理（/v1, /v2）/ 向下兼容 / 灰度发布 / 契约测试 |
| 数据一致性难保证 | 每个服务独立数据库，跨服务事务复杂 | 最终一致性（Saga/TCC/消息）/ 避免跨服务事务 / 领域驱动设计划清边界 |
