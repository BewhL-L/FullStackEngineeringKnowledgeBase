# 微服务架构设计模式

> 微服务架构的核心设计模式：服务拆分、通信、数据管理、可靠性、可观测性、安全六大类模式详解。

## 概述

微服务架构设计模式是在微服务实践中总结出的可复用解决方案，针对微服务架构中的常见问题提供标准化的设计方法。掌握这些模式是从"会用微服务框架"到"能设计微服务架构"的关键。

**微服务设计模式的六大类**：
```
1. 服务拆分模式：如何将单体拆分为微服务
2. 通信模式：服务间如何通信
3. 数据管理模式：如何管理分布式数据
4. 可靠性模式：如何保证系统稳定
5. 可观测性模式：如何监控和调试
6. 安全模式：如何保护微服务
```

## 原理

### 1. 服务拆分模式

#### 1.1 按业务能力拆分（Decompose by Business Capability）
- 定义：按业务领域的能力划分服务，如订单服务、用户服务、商品服务
- 适用：业务边界清晰的系统
- 优点：服务职责明确，团队对齐业务
- 缺点：业务能力识别需要领域知识

#### 1.2 按子域拆分（Decompose by Subdomain）
- 定义：基于领域驱动设计（DDD）的限界上下文划分
- 核心域：业务差异化的核心（如电商的推荐算法）
- 支撑域：支持核心域运行（如订单管理）
- 通用域：多个系统共用（如认证、通知）
- 优点：技术与业务对齐，边界稳定
- 缺点：需要 DDD 经验，前期分析成本高

#### 1.3 绞杀者模式（Strangler Fig Pattern）
- 定义：逐步用新微服务替换旧单体功能，而不是一次性重写
- 步骤：
  1. 在单体前面加 API 网关，路由新功能到新服务
  2. 逐步将功能从单体迁移到微服务
  3. 最终单体被完全"绞杀"
- 优点：风险低，可渐进式迁移
- 缺点：过渡期需要维护两套系统

### 2. 通信模式

#### 2.1 API 网关模式（API Gateway）
- 定义：统一入口，负责路由、认证、限流、熔断、协议转换
- 优点：客户端简化、统一治理、安全隔离
- 缺点：单点风险（需高可用）、增加延迟

#### 2.2 服务发现模式（Service Discovery）
- 客户端发现：客户端从注册中心获取实例列表，自己选择（Ribbon）
- 服务端发现：客户端请求负载均衡器，由其选择（Nginx+Consul）
- 自注册：服务启动时自己注册到注册中心（Eureka）
- 第三方注册：由其他进程负责注册（Registrar）

#### 2.3 断路器模式（Circuit Breaker）
- 状态：关闭（正常）→ 打开（故障，快速失败）→ 半开（试探恢复）
- 目的：防止级联故障，保护系统稳定性
- 实现：Sentinel、Resilience4j、Hystrix

#### 2.4 重试模式（Retry）
- 定义：调用失败时自动重试
- 策略：固定间隔、指数退避、随机抖动
- 注意：幂等性（重试不会产生副作用）

#### 2.5 超时模式（Timeout）
- 定义：设置调用超时，避免长时间等待
- 配合：断路器 + 超时 + 重试 + 降级

#### 2.6 舱壁模式（Bulkhead）
- 定义：隔离线程池/连接池，防止一个服务故障耗尽所有资源
- 实现：按服务分配独立线程池

### 3. 数据管理模式

#### 3.1 每服务一个数据库（Database per Service）
- 定义：每个微服务拥有自己的数据库，服务间不直接共享数据库
- 优点：服务自治、技术选型自由、故障隔离
- 缺点：分布式事务复杂、数据一致性挑战

#### 3.2 Saga 模式（分布式事务）
- 定义：用一系列本地事务 + 补偿事务实现最终一致性
- 编排式（Choreography）：服务通过事件驱动，无中心协调
- 指挥式（Orchestration）：有中心协调器指挥各服务执行
- 优点：长事务适用、性能好
- 缺点：补偿逻辑复杂、无隔离性

#### 3.3 CQRS 模式（命令查询职责分离）
- 定义：写操作（Command）和读操作（Query）使用不同的模型
- 写库：规范化，保证一致性
- 读库：反规范化，优化查询性能
- 同步：通过事件最终一致
- 适用：读写比例悬殊、查询复杂的系统

#### 3.4 事件溯源模式（Event Sourcing）
- 定义：不存储当前状态，而是存储所有状态变更的事件
- 优点：完整审计日志、时间旅行、天然事件驱动
- 缺点：查询复杂、事件版本管理难

#### 3.5 本地消息表模式
- 定义：在本地事务中同时写业务数据和消息表，定时任务扫描消息表发送
- 优点：简单可靠、不依赖事务消息
- 缺点：有延迟、需要定时任务

### 4. 可靠性模式

#### 4.1 幂等模式（Idempotency）
- 定义：多次执行同一操作结果相同
- 实现：唯一请求ID + 状态检查 + 数据库唯一约束

#### 4.2 降级模式（Fallback）
- 定义：服务不可用时返回默认值或缓存值
- 示例：推荐服务故障时返回热门商品

#### 4.3 限流模式（Rate Limiting）
- 算法：令牌桶、漏桶、滑动窗口
- 维度：IP、用户、接口、服务
- 实现：Sentinel、Guava RateLimiter、Redis+Lua

#### 4.4 熔断模式（Circuit Breaker）
- 详见通信模式

### 5. 可观测性模式

#### 5.1 分布式追踪（Distributed Tracing）
- TraceID：贯穿整个请求链路
- SpanID：单个服务内的操作
- 实现：SkyWalking、Jaeger、Zipkin、OpenTelemetry

#### 5.2 日志聚合（Log Aggregation）
- 集中收集所有服务日志
- 实现：ELK（Elasticsearch+Logstash+Kibana）、Loki+Grafana

#### 5.3 指标监控（Metrics）
- 黄金指标：延迟、流量、错误率、饱和度
- 实现：Prometheus + Grafana、Micrometer

#### 5.4 健康检查（Health Check）
- 存活探针（Liveness）：进程是否存活
- 就绪探针（Readiness）：是否能接收请求
- 实现：Spring Boot Actuator、K8s Probe

### 6. 安全模式

#### 6.1 访问令牌模式（Access Token）
- JWT：无状态、自包含
- OAuth2：授权框架
- 实现：Spring Security + JWT

#### 6.2 零信任模式（Zero Trust）
- 永不信任，始终验证
- 服务间认证（mTLS）
- 细粒度授权

## 实操

### 1. 断路器配置（Sentinel）

```java
@Configuration
public class SentinelConfig {
    @PostConstruct
    public void initRules() {
        // 熔断规则
        List<DegradeRule> rules = new ArrayList<>();
        DegradeRule rule = new DegradeRule();
        rule.setResource("orderService");
        rule.setGrade(RuleConstant.DEGRADE_GRADE_EXCEPTION_RATIO);
        rule.setCount(0.5);           // 异常率50%
        rule.setTimeWindow(60);       // 熔断60秒
        rule.setMinRequestAmount(10); // 最小请求数
        rules.add(rule);
        DegradeRuleManager.loadRules(rules);
    }
}
```

### 2. 分布式事务（Seata Saga 模式）

```java
@GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
public void createOrder(OrderRequest request) {
    // 1. 创建订单（本地事务）
    orderMapper.insert(order);
    // 2. 扣减库存（远程调用，失败自动回滚）
    productClient.deductStock(request.getProductId(), request.getQuantity());
    // 3. 扣减余额（远程调用，失败自动回滚）
    userClient.deductBalance(request.getUserId(), request.getAmount());
}
```

### 3. API 网关配置（Spring Cloud Gateway）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/users/**
          filters:
            - StripPrefix=1
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10
                redis-rate-limiter.burstCapacity: 20
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
          filters:
            - StripPrefix=1
```

### 4. 幂等性实现

```java
// 基于唯一请求ID的幂等
public Result createOrder(OrderRequest request, String requestId) {
    // 1. 检查请求是否已处理
    if (redisTemplate.hasKey("idempotent:" + requestId)) {
        return Result.success("重复请求，已处理");
    }
    // 2. 执行业务
    orderService.create(request);
    // 3. 标记请求已处理（设置过期时间）
    redisTemplate.opsForValue().set("idempotent:" + requestId, "1", 24, TimeUnit.HOURS);
    return Result.success();
}
```

## 问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 服务拆分过细 | 过度设计，导致服务间调用过多 | 按业务能力拆分，一个服务2-5人维护，避免纳米服务 |
| 分布式事务数据不一致 | 网络分区/服务宕机/补偿失败 | 用Seata/Saga/本地消息表，最终一致性，定期对账，人工补偿 |
| 服务雪崩 | 一个服务故障导致级联失败 | 熔断+限流+降级+舱壁隔离+超时 |
| 接口版本不兼容 | 服务升级后API变更 | API版本管理(/v1,/v2)，向下兼容，灰度发布，契约测试 |
| 链路追踪找不到 | 未接入Agent/traceId未传递 | 正确配置Agent，跨服务传递traceId，检查采样率 |
| 配置不生效 | 配置中心推送失败/客户端未刷新 | 检查连接，用@RefreshScope，手动刷新，检查配置格式 |
| 注册中心服务列表不准 | 服务异常退出未注销/网络分区 | 心跳检测，健康检查，服务摘除，多注册中心 |
| 数据库性能瓶颈 | 单库压力大/未分库分表 | 读写分离，分库分表（ShardingSphere），缓存，索引优化 |

## 拓展

**深入学习方向**：
1. **领域驱动设计（DDD）**：限界上下文、聚合根、领域事件，指导服务拆分
2. **事件驱动架构**：Kafka/RabbitMQ 事件驱动，解耦服务
3. **服务网格（Service Mesh）**：Istio/Linkerd，将服务治理下沉到基础设施
4. **Serverless 架构**：函数即服务，按需计费，自动伸缩
5. **微服务测试**：契约测试（Pact）、集成测试、端到端测试
6. **混沌工程**：Chaos Monkey，主动注入故障验证系统韧性
