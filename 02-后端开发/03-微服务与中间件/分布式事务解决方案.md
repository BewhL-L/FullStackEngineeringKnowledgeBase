# 分布式事务解决方案

> 分布式事务的核心理论、五种解决方案（2PC/TCC/Saga/本地消息表/事务消息）、Seata 实战、选型指南。

## 概述

分布式事务是指在分布式系统中，一个业务操作涉及多个服务或多个数据源，需要保证这些操作要么全部成功，要么全部失败。在微服务架构下，每个服务有独立的数据库，无法使用本地事务，需要分布式事务方案。

**为什么分布式事务难**：
- CAP 定理：无法同时满足一致性、可用性、分区容错性
- 网络分区：服务间调用可能超时、失败
- 数据异构：每个服务可能用不同的数据库
- 性能权衡：强一致性性能差，最终一致性复杂

**核心理论**：
- **CAP 定理**：一致性(C)、可用性(A)、分区容错性(P)，三选二
- **BASE 理论**：基本可用(Basically Available)、软状态(Soft state)、最终一致性(Eventual consistency)
- 微服务架构通常选择 AP + 最终一致性，而非 CP + 强一致性

## 原理

### 五种分布式事务方案对比

| 方案 | 一致性 | 性能 | 实现复杂度 | 业务侵入 | 适用场景 |
|------|--------|------|-----------|---------|---------|
| 2PC（两阶段提交） | 强一致 | 差 | 中 | 低 | 传统分布式数据库，短事务 |
| TCC | 最终一致 | 中 | 高 | 高 | 资金类、对一致性要求高 |
| Saga | 最终一致 | 好 | 中 | 中 | 长流程、多步骤业务 |
| 本地消息表 | 最终一致 | 好 | 低 | 中 | 异步场景、对实时性要求不高 |
| 事务消息（RocketMQ） | 最终一致 | 好 | 低 | 低 | 有RocketMQ基础设施 |

### 方案1：2PC（两阶段提交）

```
阶段1（准备阶段 Prepare）：
  协调者 → 所有参与者：准备提交？
  参与者 → 执行事务，但不提交，锁定资源
  参与者 → 协调者：可以提交 / 不能提交

阶段2（提交阶段 Commit）：
  如果所有参与者都同意：
    协调者 → 所有参与者：提交
    参与者 → 提交事务，释放资源
  如果有任何一个参与者反对或超时：
    协调者 → 所有参与者：回滚
    参与者 → 回滚事务，释放资源
```

**优点**：强一致性，实现相对简单
**缺点**：
- 同步阻塞：参与者锁定资源，性能差
- 单点故障：协调者宕机，参与者一直阻塞
- 数据不一致：阶段2网络分区，部分提交部分回滚
- 不适合高并发微服务场景

### 方案2：TCC（Try-Confirm-Cancel）

```
Try 阶段：预留资源（不真正执行业务）
  - 冻结金额（不是扣减）
  - 预占库存（不是扣减）

Confirm 阶段：确认执行（所有Try都成功）
  - 扣减冻结的金额
  - 扣减预占的库存

Cancel 阶段：取消执行（有Try失败）
  - 解冻金额
  - 释放预占库存
```

**优点**：
- 性能比2PC好（不长期锁定资源）
- 灵活性高，业务自定义
- 最终一致性

**缺点**：
- 业务侵入性强（每个服务要写Try/Confirm/Cancel三个接口）
- 实现复杂（空回滚、幂等、悬挂问题）
- 开发成本高

**TCC 的三个关键问题**：
1. **空回滚**：Try没收到，直接收到Cancel → Cancel要识别并直接返回成功
2. **幂等**：Confirm/Cancel可能重复调用 → 要保证多次调用结果一致
3. **悬挂**：Cancel先于Try到达 → Try要识别并不再执行

### 方案3：Saga 模式

```
业务流程：T1 → T2 → T3 → T4
每个Ti有对应的补偿操作Ci

正常执行：T1 → T2 → T3 → T4（全部成功）

失败回滚（T3失败）：
  T1 → T2 → T3(失败)
  执行补偿：C2 → C1（反向回滚已完成的步骤）
```

**两种实现方式**：
1. **编排式（Choreography）**：服务通过事件驱动，无中心协调
   - T1完成发事件 → T2监听事件执行 → T2完成发事件 → ...
   - 失败时发补偿事件 → 前面的服务监听并补偿
2. **指挥式（Orchestration）**：有中心协调器指挥
   - 协调器调用T1 → T1成功 → 调用T2 → ...
   - 失败时协调器调用补偿操作

**优点**：
- 性能好，无长期锁定
- 适合长流程业务（如订单创建涉及多个服务）
- 一阶段提交，吞吐高

**缺点**：
- 补偿逻辑复杂（每个操作都要写补偿）
- 无隔离性（中间状态可见，可能读到脏数据）
- 实现难度中等

### 方案4：本地消息表

```
1. 业务操作和写消息表在同一个本地事务中
   BEGIN;
     UPDATE account SET balance = balance - 100 WHERE id = 1;
     INSERT INTO message (id, content, status) VALUES (1, '扣款100', '待发送');
   COMMIT;

2. 定时任务扫描消息表，发送到消息队列
   每5秒扫描 status='待发送' 的消息，发送到MQ

3. 消费端消费消息，执行业务
   消费成功 → 更新消息状态为'已发送'
   消费失败 → 重试，超过次数人工处理
```

**优点**：
- 简单可靠，不依赖特殊中间件
- 性能好
- 最终一致性

**缺点**：
- 消息表和业务表耦合
- 有延迟（定时任务扫描）
- 需要保证消息幂等

### 方案5：事务消息（RocketMQ）

```
1. 生产者发送半消息（Half Message）到MQ
   - 半消息对消费者不可见

2. MQ返回半消息发送成功

3. 生产者执行本地事务

4. 根据本地事务结果，向MQ发送Commit或Rollback
   - 本地事务成功 → Commit，消息对消费者可见
   - 本地事务失败 → Rollback，删除消息

5. 如果MQ长时间没收到Commit/Rollback，回查生产者
   - 生产者查询本地事务状态，返回Commit/Rollback
```

**优点**：
- 性能好，实时性高
- 业务侵入低（不需要消息表）
- 最终一致性

**缺点**：
- 依赖 RocketMQ（其他MQ不支持）
- 需要实现事务回查接口
- 消费端需要保证幂等

## 实操

### 1. Seata 分布式事务（AT 模式）

Seata 是阿里开源的分布式事务框架，支持 AT、TCC、Saga、XA 四种模式。

```java
// 1. 配置 Seata（application.yml）
seata:
  enabled: true
  application-id: order-service
  tx-service-group: my_tx_group
  service:
    vgroup-mapping:
      my_tx_group: default
  registry:
    type: nacos
    nacos:
      server-addr: localhost:8848

// 2. 使用全局事务（只需一个注解）
@Service
public class OrderService {
    @Autowired
    private ProductClient productClient;
    @Autowired
    private AccountClient accountClient;

    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void createOrder(OrderRequest request) {
        // 1. 创建订单（本地事务）
        orderMapper.insert(new Order(request));

        // 2. 扣减库存（远程调用商品服务）
        productClient.deductStock(request.getProductId(), request.getQuantity());

        // 3. 扣减余额（远程调用账户服务）
        accountClient.deductBalance(request.getUserId(), request.getAmount());

        // 任一环节抛出异常，Seata自动回滚所有分支
    }
}
```

**AT 模式原理**：
```
1. 解析SQL，找到要修改的数据
2. 查询修改前的数据（前镜像 before image）
3. 执行业务SQL
4. 查询修改后的数据（后镜像 after image）
5. 生成回滚日志，插入undo_log表

全局提交：异步删除undo_log
全局回滚：根据undo_log生成反向SQL，恢复数据
```

### 2. TCC 模式实现（Seata）

```java
// 1. 定义 TCC 接口
@LocalTCC
public interface AccountService {
    @TwoPhaseBusinessAction(name = "deductBalance", commitMethod = "commit", rollbackMethod = "rollback")
    boolean tryDeduct(@BusinessActionContextParameter(paramName = "userId") Long userId,
                      @BusinessActionContextParameter(paramName = "amount") BigDecimal amount);

    boolean commit(BusinessActionContext context);
    boolean rollback(BusinessActionContext context);
}

// 2. 实现
@Service
public class AccountServiceImpl implements AccountService {
    @Override
    public boolean tryDeduct(Long userId, BigDecimal amount) {
        // Try：冻结金额（不是扣减）
        accountMapper.freezeBalance(userId, amount);
        return true;
    }

    @Override
    public boolean commit(BusinessActionContext context) {
        // Confirm：扣减冻结的金额
        Long userId = Long.valueOf(context.getActionContext("userId").toString());
        BigDecimal amount = new BigDecimal(context.getActionContext("amount").toString());
        accountMapper.deductFrozenBalance(userId, amount);
        return true;
    }

    @Override
    public boolean rollback(BusinessActionContext context) {
        // Cancel：解冻金额
        Long userId = Long.valueOf(context.getActionContext("userId").toString());
        BigDecimal amount = new BigDecimal(context.getActionContext("amount").toString());
        accountMapper.unfreezeBalance(userId, amount);
        return true;
    }
}
```

### 3. 本地消息表实现

```java
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private MessageMapper messageMapper;
    @Autowired
    private RocketMQTemplate rocketMQTemplate;

    @Transactional(rollbackFor = Exception.class)
    public void createOrder(OrderRequest request) {
        // 1. 创建订单
        Order order = new Order(request);
        orderMapper.insert(order);

        // 2. 写消息表（和订单在同一个事务）
        Message message = new Message();
        message.setId(UUID.randomUUID().toString());
        message.setContent(JSON.toJSONString(order));
        message.setStatus("PENDING"); // 待发送
        messageMapper.insert(message);
    }
}

// 定时任务扫描并发送消息
@Component
public class MessageScheduler {
    @Scheduled(fixedDelay = 5000) // 每5秒
    public void sendPendingMessages() {
        List<Message> messages = messageMapper.selectByStatus("PENDING");
        for (Message msg : messages) {
            try {
                rocketMQTemplate.syncSend("order-topic", msg.getContent());
                messageMapper.updateStatus(msg.getId(), "SENT");
            } catch (Exception e) {
                // 失败下次重试，超过次数标记为失败人工处理
                log.error("发送消息失败: {}", msg.getId(), e);
            }
        }
    }
}
```

## 问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 分布式事务数据不一致 | 网络分区/服务宕机/补偿失败 | 最终一致性 + 定期对账 + 人工补偿 + 监控告警 |
| TCC空回滚/悬挂/幂等 | 网络延迟导致请求顺序错乱 | 记录Try/Confirm/Cancel状态 / 幂等设计 / 状态机控制 |
| Saga补偿失败 | 补偿操作本身也可能失败 | 重试机制 / 人工介入 / 告警通知 / 对账系统 |
| 消息重复消费 | MQ至少一次投递语义 | 消费端幂等（唯一ID+状态表 / 数据库唯一约束） |
| 消息丢失 | 生产者发送失败 / MQ宕机 / 消费失败 | 生产者确认机制 / MQ持久化 / 消费端手动ACK / 本地消息表 |
| 2PC协调者单点故障 | 协调者宕机，参与者阻塞 | 用协调者集群（主备）/ 超时机制 / 改用其他方案 |
| 性能太差 | 强一致性方案同步阻塞 | 用最终一致性方案（Saga/消息）/ 优化业务流程 / 减少跨服务事务 |
| 不知道选哪种方案 | 场景不明确 | 按一致性要求+性能+复杂度选型：强一致用TCC，长流程用Saga，异步用消息 |
