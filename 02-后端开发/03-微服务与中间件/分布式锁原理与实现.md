# 分布式锁原理与实现

> 分布式锁的核心原理、三种实现方案（Redis/Zookeeper/数据库）、Redlock算法、使用场景和最佳实践。

## 概述

分布式锁是在分布式系统中控制多个进程/服务对共享资源互斥访问的机制。在单体应用中可以用 JVM 锁（synchronized、ReentrantLock），但分布式系统中多个服务运行在不同 JVM，需要跨进程的锁机制。

**为什么需要分布式锁**：
- 多个服务实例同时操作同一资源（如库存扣减、订单创建）
- 防止重复执行（如定时任务多实例同时运行）
- 保证数据一致性（如分布式事务的预占）

**分布式锁的核心要求**：
1. **互斥性**：同一时间只有一个客户端持有锁
2. **防死锁**：即使持有锁的客户端崩溃，锁也能自动释放
3. **可重入**：同一个客户端可以多次获取同一把锁
4. **高可用**：锁服务本身不能成为单点故障
5. **高性能**：加锁和解锁的开销要小
6. **公平性**（可选）：按请求顺序获取锁

## 原理

### 分布式锁的三种实现方案对比

| 方案 | 实现原理 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| Redis | SETNX + 过期时间 | 性能高、实现简单 | 可能丢锁、需要Redlock | 高并发、性能要求高 |
| Zookeeper | 临时顺序节点 | 强一致、支持公平锁、自动释放 | 性能一般、实现复杂 | 强一致性要求、并发不高 |
| 数据库 | 唯一索引/行锁 | 简单、利用现有数据库 | 性能差、单点风险 | 低并发、简单场景 |

### Redis 分布式锁原理

#### 基础实现
```
加锁：SET lock_key unique_value NX PX 30000
  - NX：只在key不存在时设置（互斥）
  - PX 30000：30秒后自动过期（防死锁）
  - unique_value：唯一标识，解锁时验证（防误删）

解锁：先验证unique_value，再删除（Lua脚本保证原子性）
```

#### 为什么需要 unique_value？
- 客户端A获取锁，设置过期30秒
- A执行超过30秒，锁自动释放
- 客户端B获取了同一把锁
- A执行完，删除锁（此时锁是B的）
- 用 unique_value 验证，A发现不是自己的锁，不删除

#### 为什么用 Lua 脚本解锁？
- 解锁需要两步：GET 验证 + DEL 删除
- 两步之间可能有其他客户端操作
- Lua 脚本在 Redis 中原子执行，保证验证和删除的原子性

#### Redlock 算法（多节点Redis）
- 问题：单节点 Redis 锁，如果主节点宕机，锁可能丢失
- 方案：部署 N 个独立 Redis 节点（通常5个），向多数节点（≥3）同时加锁
- 步骤：
  1. 获取当前时间戳
  2. 依次向5个节点加锁（相同key和value，短超时）
  3. 计算加锁耗时，超过锁有效期则失败
  4. 如果≥3个节点加锁成功，且总耗时<锁有效期，则加锁成功
  5. 否则，向所有节点发送解锁命令

### Zookeeper 分布式锁原理

#### 临时顺序节点实现
```
1. 在 /locks 节点下创建临时顺序节点：/locks/lock-000000001
2. 获取 /locks 下所有子节点，判断自己是否是最小的
3. 如果是最小的，获取锁成功
4. 如果不是，监听前一个节点的删除事件
5. 前一个节点被删除（释放锁或客户端崩溃），收到通知，回到步骤2
```

**优点**：
- 临时节点：客户端崩溃自动删除（防死锁）
- 顺序节点：天然支持公平锁（先来先得）
- 监听机制：不需要轮询，事件驱动
- 强一致性：Zookeeper 是 CP 系统

**缺点**：
- 性能不如 Redis（写操作需要半数以上节点确认）
- 实现复杂，需要维护 Zookeeper 集群
- 频繁创建删除节点有一定开销

### 数据库分布式锁原理

#### 方案1：唯一索引
```sql
-- 加锁：插入一条记录，唯一索引保证互斥
INSERT INTO distributed_lock (lock_key, holder, expire_time)
VALUES ('order:123', 'service-A', NOW() + INTERVAL 30 SECOND);
-- 插入成功=获取锁，插入失败=锁已被持有

-- 解锁：删除记录
DELETE FROM distributed_lock WHERE lock_key = 'order:123' AND holder = 'service-A';
```

#### 方案2：行锁（SELECT ... FOR UPDATE）
```sql
-- 加锁：查询并加行锁
BEGIN;
SELECT * FROM resource WHERE id = 123 FOR UPDATE;
-- 执行业务逻辑
COMMIT; -- 提交事务释放锁
```

**缺点**：性能差、数据库单点、锁表风险，仅适合低并发简单场景。

## 实操

### 1. Redis 分布式锁完整实现（Java + Redisson）

Redisson 是 Redis 官方推荐的 Java 客户端，内置了完善的分布式锁实现。

```java
// 1. 配置 Redisson
@Configuration
public class RedissonConfig {
    @Bean
    public RedissonClient redissonClient() {
        Config config = new Config();
        config.useSingleServer()
              .setAddress("redis://localhost:6379")
              .setPassword("password")
              .setDatabase(0);
        return Redisson.create(config);
    }
}

// 2. 使用分布式锁
@Service
public class OrderService {
    @Autowired
    private RedissonClient redissonClient;

    public void createOrder(Long productId, int quantity) {
        String lockKey = "lock:product:" + productId;
        RLock lock = redissonClient.getLock(lockKey);

        try {
            // 尝试加锁：等待10秒，锁持有30秒后自动释放
            boolean acquired = lock.tryLock(10, 30, TimeUnit.SECONDS);
            if (!acquired) {
                throw new BusinessException("系统繁忙，请稍后重试");
            }

            // 执行业务逻辑（扣减库存、创建订单）
            productService.deductStock(productId, quantity);
            orderMapper.insert(new Order(productId, quantity));

        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new BusinessException("获取锁被中断");
        } finally {
            // 释放锁（检查是否是当前线程持有）
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 2. Redis 分布式锁手动实现（Lua 脚本）

```java
@Component
public class RedisDistributedLock {
    @Autowired
    private StringRedisTemplate redisTemplate;

    private static final String LOCK_SCRIPT =
        "if redis.call('set', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then return 1 else return 0 end";

    private static final String UNLOCK_SCRIPT =
        "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";

    /**
     * 加锁
     * @param key 锁的key
     * @param value 唯一标识（通常用UUID）
     * @param expireTime 过期时间（毫秒）
     * @return true=加锁成功
     */
    public boolean tryLock(String key, String value, long expireTime) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(LOCK_SCRIPT, Long.class);
        Long result = redisTemplate.execute(script, Collections.singletonList(key), value, String.valueOf(expireTime));
        return result != null && result == 1;
    }

    /**
     * 解锁（验证value后删除，原子操作）
     */
    public boolean unlock(String key, String value) {
        DefaultRedisScript<Long> script = new DefaultRedisScript<>(UNLOCK_SCRIPT, Long.class);
        Long result = redisTemplate.execute(script, Collections.singletonList(key), value);
        return result != null && result == 1;
    }
}
```

### 3. Zookeeper 分布式锁（Curator 框架）

```java
// Curator 是 Apache 的 Zookeeper 客户端，内置分布式锁
public class ZkLockExample {
    public static void main(String[] args) throws Exception {
        // 1. 创建 Curator 客户端
        CuratorFramework client = CuratorFrameworkFactory.newClient(
            "localhost:2181", new ExponentialBackoffRetry(1000, 3));
        client.start();

        // 2. 创建分布式锁
        InterProcessMutex lock = new InterProcessMutex(client, "/locks/order");

        // 3. 使用锁
        try {
            // 尝试获取锁，最多等待10秒
            if (lock.acquire(10, TimeUnit.SECONDS)) {
                try {
                    // 执行业务逻辑
                    System.out.println("获取锁成功，执行业务");
                } finally {
                    lock.release(); // 释放锁
                }
            }
        } finally {
            client.close();
        }
    }
}
```

### 4. 看门狗机制（Redisson 自动续期）

Redisson 的锁默认支持"看门狗"机制：如果业务执行时间超过锁的过期时间，自动续期。

```java
// 不指定 leaseTime，启用看门狗（默认每10秒检查，续期到30秒）
RLock lock = redissonClient.getLock("lock:order:123");
lock.lock(); // 看门狗自动续期，直到调用unlock

// 原理：
// 1. 加锁成功后，启动一个定时任务（每 lockWatchdogTimeout/3 执行一次）
// 2. 如果锁还被当前线程持有，就续期到 lockWatchdogTimeout（默认30秒）
// 3. 调用 unlock 后，取消定时任务
```

## 问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 锁过期但业务没执行完 | 业务执行时间超过锁过期时间 | 用Redisson看门狗自动续期 / 合理设置过期时间 / 拆分长任务 |
| Redis主从切换导致锁丢失 | 主节点加锁后未同步到从节点就宕机 | 用Redlock多节点 / 用Zookeeper(强一致) / 接受小概率丢失（业务可容忍） |
| 锁被其他客户端误删 | 没有验证锁的持有者 | 加锁时设置唯一value，解锁时验证value后再删除（Lua脚本原子操作） |
| 死锁（锁永远不释放） | 客户端崩溃未释放锁 / 解锁代码未执行 | 设置过期时间自动释放 / finally中解锁 / Zookeeper临时节点自动删除 |
| 锁竞争激烈导致性能差 | 热点key大量请求竞争同一把锁 | 锁粒度细化（按用户/商品分锁）/ 乐观锁替代 / 本地锁+分布式锁组合 |
| 可重入问题 | 同一线程多次获取同一把锁失败 | 用Redisson（支持可重入）/ 记录重入次数 / Zookeeper锁也支持可重入 |
| 锁公平性问题 | 后来的请求可能先获取锁 | 用Zookeeper顺序节点（公平锁）/ Redis锁不保证公平，业务上接受 |
| 数据库锁性能差 | 数据库本身性能瓶颈 / 锁表 | 用Redis/Zookeeper替代 / 只在低并发场景用数据库锁 |
