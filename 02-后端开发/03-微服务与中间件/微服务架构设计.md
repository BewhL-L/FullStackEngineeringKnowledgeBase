# 微服务架构设计

> 从单体到微服务的完整架构设计方法论：服务拆分、技术选型、架构演进、落地步骤、最佳实践。

## 概述

微服务架构设计是将大型复杂应用系统拆分为一组小型、独立、可自治服务的过程。设计的核心挑战在于：如何合理拆分服务、如何保证系统可用性、如何管理分布式复杂度。

**微服务架构设计的核心原则**：
1. **单一职责**：每个服务只做一件事，且做好
2. **服务自治**：独立开发、部署、运行、数据存储
3. **去中心化**：去中心化治理、去中心化数据
4. **容错设计**：假设服务会失败，设计降级和熔断
5. **API优先**：服务间通过明确定义的API通信
6. **可观测性**：日志、指标、链路追踪三位一体

**什么时候该用微服务**：
- 系统规模大，团队多人协作
- 不同模块有不同的扩展需求
- 需要独立部署和快速迭代
- 技术栈需要多样化
- 有足够的运维和DevOps能力

**什么时候不该用微服务**：
- 小型简单应用（微服务增加不必要复杂度）
- 团队规模小（<5人）
- 业务边界不清晰
- 缺乏基础设施和运维能力
- 初创公司早期（优先验证业务，而非架构）

## 原理

### 微服务架构设计的完整流程

```
1. 业务领域分析
   ↓ 领域驱动设计（DDD）
2. 服务拆分设计
   ↓ 按业务能力/子域拆分
3. 技术选型
   ↓ 框架/中间件/数据库
4. 服务间通信设计
   ↓ 同步(REST/gRPC) / 异步(消息队列)
5. 数据架构设计
   ↓ 每服务一库 / 分布式事务
6. 可靠性设计
   ↓ 熔断/限流/降级/重试
7. 可观测性设计
   ↓ 日志/指标/链路追踪
8. 安全设计
   ↓ 认证/授权/加密
9. 部署架构设计
   ↓ 容器化/K8s/CI/CD
10. 演进路线
   ↓ 绞杀者模式逐步迁移
```

### 服务拆分方法论

#### 方法一：按业务能力拆分
```
电商系统
├── 用户服务（注册/登录/个人信息）
├── 商品服务（商品管理/分类/搜索）
├── 订单服务（下单/支付/退款）
├── 库存服务（库存管理/预占/扣减）
├── 支付服务（支付渠道/对账/退款）
├── 物流服务（发货/跟踪/签收）
├── 营销服务（优惠券/促销/积分）
└── 通知服务（短信/邮件/推送）
```

#### 方法二：按 DDD 限界上下文拆分
- **核心域**：业务差异化核心（如电商的推荐算法、定价引擎）
- **支撑域**：支持核心域（如订单管理、商品管理）
- **通用域**：多系统共用（如认证、通知、文件存储）

#### 拆分的判断标准
- 一个服务 2-5 人维护
- 服务可以独立部署
- 服务有清晰的业务边界
- 服务间通信不过于频繁（避免分布式单体）
- 数据可以独立存储

### 技术选型参考

| 层面 | 选型建议 |
|------|---------|
| 开发框架 | Spring Cloud（Java）/ Go-Micro（Go）/ FastAPI（Python） |
| 注册中心 | Nacos / Consul / Eureka / Zookeeper |
| 配置中心 | Nacos / Apollo / Spring Cloud Config |
| API网关 | Spring Cloud Gateway / Kong / APISIX / Nginx |
| 服务间通信 | OpenFeign(REST) / gRPC / Dubbo |
| 消息队列 | Kafka / RocketMQ / RabbitMQ / Pulsar |

| 链路追踪 | SkyWalking / Jaeger / Zipkin / OpenTelemetry |

| 监控 | Prometheus + Grafana |
| 容器 | Docker + Kubernetes |
| CI/CD | Jenkins / GitLab CI / GitHub Actions / ArgoCD |

### 架构演进路线

```
阶段1：单体应用
  ↓ 业务增长，团队扩大
阶段2：模块化单体
  ↓ 按模块拆分代码，但仍一个部署单元
阶段3：前后端分离
  ↓ 前端独立部署，后端提供API
阶段4：核心服务拆分
  ↓ 用绞杀者模式，先拆核心业务（如订单、用户）
阶段5：全面微服务
  ↓ 所有服务独立部署，完善服务治理
阶段6：服务网格（可选）
  ↓ Istio/Linkerd，治理下沉到基础设施
```

### 2. 服务间调用示例

```java
// 订单服务调用商品服务
@FeignClient(name = "product-service", fallback = ProductClientFallback.class)
public interface ProductClient {
    @GetMapping("/api/products/{id}")
    Result<ProductDTO> getProduct(@PathVariable("id") Long id);

    @PostMapping("/api/products/deduct-stock")
    Result<Void> deductStock(@RequestBody DeductStockRequest request);
}

// 降级实现
@Component
public class ProductClientFallback implements ProductClient {
    @Override
    public Result<ProductDTO> getProduct(Long id) {
        return Result.error("商品服务暂时不可用");
    }
    @Override
    public Result<Void> deductStock(DeductStockRequest request) {
        return Result.error("库存服务暂时不可用");
    }
}
```

### 3. 统一响应与异常处理

```java
// 统一响应
@Data
@AllArgsConstructor
public class Result<T> {
    private Integer code;
    private String message;
    private T data;

    public static <T> Result<T> success(T data) {
        return new Result<>(200, "success", data);
    }
    public static <T> Result<T> error(String message) {
        return new Result<>(500, message, null);
    }
}

// 全局异常处理
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(BusinessException.class)
    public Result<Void> handleBusinessException(BusinessException e) {
        return Result.error(e.getMessage());
    }
    @ExceptionHandler(Exception.class)
    public Result<Void> handleException(Exception e) {
        log.error("系统异常", e);
        return Result.error("系统繁忙，请稍后重试");
    }
}
```

## 问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 服务拆分过细导致调用过多 | 过度设计，按技术层而非业务拆分 | 按业务能力拆分，合并高耦合服务，避免纳米服务 |
| 分布式事务数据不一致 | 网络分区/服务宕机/补偿失败 | 最终一致性（Saga/本地消息表），定期对账，人工补偿 |
| 服务雪崩 | 一个服务故障级联影响 | 熔断+限流+降级+舱壁隔离+超时+重试 |
| 接口版本不兼容 | 服务升级API变更 | API版本管理(/v1,/v2)，向下兼容，灰度发布，契约测试 |
| 链路追踪找不到 | 未接入Agent/traceId未传递 | 正确配置Agent，跨服务传递traceId，检查采样率 |
| 配置不生效 | 配置中心推送失败/客户端未刷新 | 检查连接，用@RefreshScope，手动刷新，检查配置格式 |
| 注册中心服务列表不准 | 服务异常退出未注销/网络分区 | 心跳检测，健康检查，服务摘除，多注册中心 |
| 数据库性能瓶颈 | 单库压力大/未分库分表 | 读写分离，分库分表（ShardingSphere），缓存，索引优化 |
| 团队协作冲突 | 服务边界不清/接口变更频繁 | 明确服务负责人，API契约测试，Code Review，文档化 |
| 运维复杂度高 | 服务多/配置多/故障排查难 | 完善可观测性，自动化运维（K8s+CI/CD），标准化部署 |

## 拓展

**深入学习方向**：
1. **领域驱动设计（DDD）**：限界上下文、聚合根、领域事件、事件风暴
2. **事件驱动架构**：Kafka/RocketMQ 事件驱动，CQRS，事件溯源
3. **服务网格（Service Mesh）**：Istio/Linkerd，流量管理，安全，可观测性
4. **Serverless 架构**：函数即服务，按需计费，自动伸缩
5. **微服务测试**：契约测试（Pact），集成测试，端到端测试，混沌工程
6. **高可用架构**：多活机房，异地容灾，流量调度，故障演练
7. **性能优化**：缓存策略，数据库优化，异步化，并行处理
