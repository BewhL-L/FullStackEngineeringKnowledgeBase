## 一、虚拟内存分页：用 mmap 看文件映射

### 1.1 原理
进程看到的是「虚拟地址」，由 MMU + 页表映射到物理页帧。文件可用 `mmap` 直接映射进虚拟地址空间，省去 read/write 拷贝。

### 1.2 可运行代码（Python）
```python
import mmap, os
# 准备一个文件
with open("demo.bin", "wb") as f: f.write(b"hello-mmap" * 1000)
with open("demo.bin", "r+b") as f:
    mm = mmap.mmap(f.fileno(), 0)        # 映射整个文件
    print("首字节:", mm[0:5])            # 直接按内存读
    mm[0:5] = b"HELLO"                   # 改内存即改文件
    mm.flush()                           # 刷回磁盘
print("文件大小:", os.path.getsize("demo.bin"))
```

### 1.3 现象与解释
💡 **深度讲解**：`mmap` 把文件「伪装」成一段内存，读写经由页缓存，缺页时由 OS 调页。相比 `read()` 少了一次内核→用户拷贝，大文件处理更快。
📝 **精简总结**：mmap = 文件即内存；flush 才保证落盘；适合大文件随机访问。
🔍 **知识点深度解析**：作用=零拷贝访问；原理=虚拟页→物理页映射；要点=flush 与共享映射一致性。

## 二、缓存行伪共享（False Sharing）实测

### 2.1 原理
CPU 缓存以「缓存行(通常 64 字节)」为单位。两个线程各改**不同变量**但若在同一缓存行，会反复使对方缓存行失效，性能骤降——即伪共享。

### 2.2 可运行代码（Python 演示竞争加剧）
```python
import threading, time
# 两个计数器放在同一对象(易同缓存行)
class Counters:
    def __init__(self): self.a = 0; self.b = 0
c = Counters()
def inc_a():
    for _ in range(5_000_000): c.a += 1
def inc_b():
    for _ in range(5_000_000): c.b += 1
t0=time.time()
ta=threading.Thread(target=inc_a); tb=threading.Thread(target=inc_b)
ta.start(); tb.start(); ta.join(); tb.join()
print("耗时", round(time.time()-t0,2), "s  a=", c.a, "b=", c.b)
# C 语言可用 __attribute__((aligned(64))) 把 a,b 分到不同缓存行，速度显著提升
```

### 2.3 现象与解释
💡 **深度讲解**：本例因 GIL 在 Python 中并不能完美复现硬件伪共享（仅示概念）；真正复现需在 C/C++/Rust 中用 `alignas(64)` 分隔变量，再对比带/不带对齐的耗时差。
📝 **精简总结**：伪共享 = 不同变量同缓存行被多核互踢；解法 = 缓存行对齐/填充；高性能并发数据结构必考虑。
🔍 **知识点深度解析**：作用=理解多核性能陷阱；原理=MESI 缓存一致性协议；要点=对齐到 64 字节边界。

## 三、进程 vs 线程上下文切换成本

### 3.1 原理
线程切换共享地址空间、成本低；进程切换需换页表、TLB 刷新、成本高。下面用时间近似对比。

### 3.2 可运行代码（Python）
```python
import threading, multiprocessing, time
def noop(): pass
def bench(target, n=20000):
    t0=time.time()
    procs=[target(target=noop) for _ in range(n)]
    for p in procs: p.start()
    for p in procs: p.join()
    return time.time()-t0
# 进程版
print("进程创建开销:", round(bench(multiprocessing.Process), 200), "s")
# 线程版（轻量）
def bench_t(n=20000):
    t0=time.time()
    ts=[threading.Thread(target=noop) for _ in range(n)]
    for t in ts: t.start()
    for t in ts: t.join()
    return time.time()-t0
print("线程创建开销:", round(bench_t(),2), "s")
```

### 3.3 现象与解释
💡 **深度讲解**：创建/切换进程涉及独立内存空间与内核资源，开销明显高于线程；故高并发 IO 用线程/协程，CPU 密集用进程避开 GIL。
📝 **精简总结**：线程轻、进程重；切换成本差异来自地址空间与 TLB；按任务选模型（呼应 Python 大全并发章）。
🔍 **知识点深度解析**：作用=选对并发单元；原理=地址空间隔离；要点=进程隔离换安全、线程共享换效率。

## 四、编译期常量折叠观察

### 4.1 原理
编译器在编译期把「常量表达式」直接算出结果（常量折叠），运行时不计算。可用反汇编/字节码观察。

### 4.2 可运行代码（Python 字节码）
```python
import dis
def f():
    return 60 * 60 * 24          # 常量表达式
dis.dis(f)
# 输出会看到 LOAD_CONST 86400 —— 已被折叠为结果
```

### 4.3 现象与解释
💡 **深度讲解**：`dis` 显示 `f` 不再做三次乘法，而是直接 `LOAD_CONST 86400`，证明折叠发生在编译期；C/C++ 的 `-O2` 同理且更激进。
📝 **精简总结**：常量表达式在编译期求值；`dis` 可验证 Python 字节码；JIT(如 PyPy)进一步运行时优化。
🔍 **知识点深度解析**：作用=理解编译优化；原理=编译期求值；要点=不影响语义但提速、降体积。

### 1. 计算机组成：CPU 缓存与伪共享

```c
// 伪共享（False Sharing）示例：两个线程修改同一缓存行的不同变量
#include <pthread.h>
#include <stdio.h>
#include <stdint.h>

// 没有缓存行对齐：两个变量在同一个缓存行（64字节）
struct NoPadding {
    volatile uint64_t a;
    volatile uint64_t b;
};

// 有缓存行对齐：每个变量独占一个缓存行
struct WithPadding {
    volatile uint64_t a;
    char padding1[56];  // 填充到 64 字节
    volatile uint64_t b;
    char padding2[56];
};

struct NoPadding np;
struct WithPadding wp;

void* inc_a_np(void* arg) { for (int i = 0; i < 100000000; i++) np.a++; return NULL; }
void* inc_b_np(void* arg) { for (int i = 0; i < 100000000; i++) np.b++; return NULL; }
void* inc_a_wp(void* arg) { for (int i = 0; i < 100000000; i++) wp.a++; return NULL; }
void* inc_b_wp(void* arg) { for (int i = 0; i < 100000000; i++) wp.b++; return NULL; }

// 编译运行：gcc -O2 -pthread false_sharing.c -o fs && time ./fs
// 预期结果：有缓存行对齐的版本快 2-3 倍（避免了缓存行失效）
```

### 2. 操作系统：进程 vs 线程创建开销对比

```python
import time
import threading
import multiprocessing

def worker():
    pass  # 空任务，只测量创建开销

# 测量线程创建开销
start = time.time()
threads = []
for _ in range(10000):
    t = threading.Thread(target=worker)
    t.start()
    threads.append(t)
for t in threads:
    t.join()
thread_time = time.time() - start
print(f"创建 10000 个线程耗时: {thread_time:.3f}s")

# 测量进程创建开销
start = time.time()
processes = []
for _ in range(1000):  # 进程创建慢，减少数量
    p = multiprocessing.Process(target=worker)
    p.start()
    processes.append(p)
for p in processes:
    p.join()
process_time = time.time() - start
print(f"创建 1000 个进程耗时: {process_time:.3f}s")
print(f"进程创建比线程慢约: {process_time/1000 / (thread_time/10000):.1f} 倍")

# 预期结果：进程创建比线程慢 10-100 倍（进程需要复制地址空间、文件描述符等）
```

### 4. 数据结构：哈希表实现与冲突解决

```python
class HashTable:
    # 简单哈希表实现，用链地址法解决冲突
    def __init__(self, capacity=16):
        self.capacity = capacity
        self.size = 0
        self.buckets = [[] for _ in range(capacity)]  # 每个桶是一个链表

    def _hash(self, key):
        # 哈希函数：Python 内置 hash + 取模
        return hash(key) % self.capacity

    def put(self, key, value):
        # 插入或更新键值对
        idx = self._hash(key)
        bucket = self.buckets[idx]
        for i, (k, v) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)  # 更新
                return
        bucket.append((key, value))  # 新增（链地址法）
        self.size += 1
        # 负载因子超过 0.75 时扩容
        if self.size / self.capacity > 0.75:
            self._resize()

    def get(self, key, default=None):
        # 获取键对应的值
        idx = self._hash(key)
        for k, v in self.buckets[idx]:
            if k == key:
                return v
        return default

    def _resize(self):
        # 扩容：容量翻倍，重新哈希所有元素
        old_buckets = self.buckets
        self.capacity *= 2
        self.buckets = [[] for _ in range(self.capacity)]
        self.size = 0
        for bucket in old_buckets:
            for k, v in bucket:
                self.put(k, v)

# 测试
ht = HashTable(capacity=4)
for i in range(20):
    ht.put(f"key{i}", f"value{i}")
print(f"容量: {ht.capacity}, 大小: {ht.size}")
print(f"key5 = {ht.get('key5')}")
print(f"不存在的键 = {ht.get('nonexist', 'default')}")
```

### 5. 算法：排序算法可视化对比

```python
import time
import random

def bubble_sort(arr):
    # 冒泡排序 O(n^2)
    n = len(arr)
    for i in range(n):
        for j in range(n - i - 1):
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]
    return arr

def quick_sort(arr):
    # 快速排序 O(n log n) 平均
    if len(arr) <= 1:
        return arr
    pivot = arr[len(arr) // 2]
    left = [x for x in arr if x < pivot]
    middle = [x for x in arr if x == pivot]
    right = [x for x in arr if x > pivot]
    return quick_sort(left) + middle + quick_sort(right)

def merge_sort(arr):
    # 归并排序 O(n log n)
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return merge(left, right)

def merge(left, right):
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result

# 性能对比
data = [random.randint(1, 100000) for _ in range(10000)]

for name, sort_fn in [("冒泡排序", bubble_sort), ("快速排序", quick_sort), ("归并排序", merge_sort)]:
    test_data = data.copy()
    start = time.time()
    sort_fn(test_data)
    elapsed = time.time() - start
    print(f"{name}: {elapsed:.4f}s")

# 预期结果：冒泡排序比快速/归并慢 100+ 倍（O(n^2) vs O(n log n)）
```

## 补充：常见问题与排查

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 多线程结果不正确 | 竞态条件、缺少同步 | 加锁（互斥锁/读写锁）、原子操作、线程安全数据结构 |
| 多线程比单线程慢 | 锁竞争、上下文切换、伪共享 | 减少锁粒度、无锁设计、缓存行对齐、线程池复用 |
| 内存泄漏 | 对象未释放、循环引用、缓存无限增长 | 内存分析工具（Valgrind/JProfiler）、弱引用、LRU 缓存 |
| 死锁 | 多个线程互相等待对方持有的锁 | 统一加锁顺序、超时锁、死锁检测、避免嵌套锁 |
| TCP 连接大量 TIME_WAIT | 主动关闭方进入 TIME_WAIT（2MSL） | 调整 tcp_tw_reuse/tcp_fin_timeout、长连接、连接池 |
| 连接被重置（RST） | 对端崩溃/拒绝/半关闭连接写数据 | 检查对端状态、心跳检测、优雅关闭 |
| 哈希表性能差 | 哈希函数分布不均、冲突多、扩容频繁 | 好的哈希函数、合适初始容量、负载因子调优 |
| 排序慢 | 用了 O(n^2) 算法、数据已有序仍用快排 | 选择合适算法（快排/归并/堆排）、小规模用插入排序 |
| 程序 CPU 100% | 死循环、频繁 GC、计算密集 | 火焰图定位热点、优化算法、增加 CPU |
| 程序内存持续增长 | 内存泄漏、缓存未淘汰、大对象 | 内存分析、LRU 淘汰、对象池、流式处理 |

底层问题排查方法论：程序异常 → 判断现象类型（性能慢/内存问题/并发问题/网络问题/崩溃）→ 使用对应分析工具（火焰图/内存分析/线程dump/tcpdump/core dump）→ 定位热点代码 → 分析根因 → 制定修复方案 → 验证修复。
