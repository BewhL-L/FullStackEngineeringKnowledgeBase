## 一、概述

### 1. 什么是测试覆盖率

**测试覆盖率（Test Coverage）** 是衡量测试代码覆盖了多少生产代码的指标，用于评估测试的充分性。它回答的问题是："我们的测试执行了多少代码？"

> **重要**：覆盖率高 ≠ 测试质量高。覆盖率只说明代码被执行了，不说明测试验证了正确的行为。

### 2. 覆盖率的价值

- [ ] **发现未测试代码**：识别没有被测试覆盖的代码区域
- [ ] **评估测试充分性**：量化测试的覆盖程度
- [ ] **指导测试编写**：优先补充高风险区域的测试
- [ ] **质量门禁**：CI/CD 中设置覆盖率门槛，防止质量退化
- [ ] **技术债务管理**：跟踪覆盖率变化，识别质量趋势

### 3. 覆盖率的局限

| 局限 | 说明 |
|------|------|
| **不验证正确性** | 代码被执行但可能没有断言，或断言错误 |
| **不覆盖所有场景** | 一行代码可能有多种输入场景，覆盖率只计一次 |
| **可被操纵** | 为了覆盖率写无意义的测试 |
| **不衡量集成测试** | 单元测试覆盖率高不代表集成测试充分 |
| **边界条件** | 覆盖率不反映边界条件和异常路径是否被测试 |

## 二、覆盖率指标

### 1. 核心覆盖率指标

| 指标 | 说明 | 计算公式 | 推荐阈值 |
|------|------|---------|---------|
| **行覆盖率（Line）** | 被执行的代码行占比 | 已执行行 / 总行数 | ≥ 70% |
| **分支覆盖率（Branch）** | if/else 等分支被覆盖比例 | 已执行分支 / 总分支数 | ≥ 60% |
| **方法覆盖率（Method）** | 被调用的方法占比 | 已调用方法 / 总方法数 | ≥ 80% |
| **类覆盖率（Class）** | 被实例化的类占比 | 已实例化类 / 总类数 | ≥ 70% |
| **指令覆盖率（Instruction）** | Java 字节码指令被执行比例 | 已执行指令 / 总指令 | ≥ 70% |
| **圈复杂度（Cyclomatic）** | 代码路径复杂度，非覆盖率指标 | 决策点 + 1 | 方法 ≤ 10 |

### 2. 行覆盖率 vs 分支覆盖率

```java
// 示例代码
public String checkStatus(int code, boolean active) {
    if (code == 200) {           // 分支1：code == 200
        if (active) {            // 分支2：active == true
            return "正常";
        } else {
            return "未激活";      // 分支3：active == false
        }
    } else {
        return "错误";            // 分支4：code != 200
    }
}

// 测试1：checkStatus(200, true) → "正常"
// 行覆盖率：4/5 = 80%（"未激活"和"错误"行未执行）
// 分支覆盖率：2/4 = 50%（只覆盖了2个分支）

// 测试2：补充 checkStatus(200, false) 和 checkStatus(404, true)
// 行覆盖率：5/5 = 100%
// 分支覆盖率：4/4 = 100%
```

> **关键**：分支覆盖率比行覆盖率更严格，能发现隐藏的逻辑分支。

### 3. 圈复杂度

**圈复杂度（Cyclomatic Complexity）** 衡量代码的独立路径数量，反映代码的复杂程度和测试难度。

| 圈复杂度 | 说明 | 测试用例数 |
|---------|------|-----------|
| 1-10 | 简单，低风险 | 1-10 |
| 11-20 | 中等，中等风险 | 11-20 |
| 21-50 | 复杂，高风险 | 21-50 |
| >50 | 极复杂，不可测试 | >50 |

```text
圈复杂度计算：
V(G) = E - N + 2P
E = 边数，N = 节点数，P = 连通分量数

简化公式：
V(G) = 决策点数量 + 1
决策点：if、for、while、case、catch、&&、||、? :
```

### 2. JaCoCo Maven 配置

```xml
<!-- pom.xml -->
<build>
    <plugins>
        <plugin>
            <groupId>org.jacoco</groupId>
            <artifactId>jacoco-maven-plugin</artifactId>
            <version>0.8.11</version>
            <executions>
                <!-- 准备代理：在测试前注入 JaCoCo agent -->

                    <goals>

                    </goals>
                </execution>
                <!-- 生成报告：测试后生成 HTML/XML/CSV 报告 -->
                <execution>
                    <id>report</id>
                    <phase>test</phase>
                    <goals>
                        <goal>report</goal>
                    </goals>
                </execution>
                <!-- 质量门禁：检查覆盖率是否达标 -->
                <execution>
                    <id>check</id>
                    <goals>
                        <goal>check</goal>
                    </goals>
                    <configuration>
                        <rules>
                            <rule>
                                <element>BUNDLE</element>
                                <limits>
                                    <limit>
                                        <counter>INSTRUCTION</counter>
                                        <value>COVEREDRATIO</value>
                                        <minimum>0.70</minimum>
                                    </limit>
                                    <limit>
                                        <counter>BRANCH</counter>
                                        <value>COVEREDRATIO</value>
                                        <minimum>0.60</minimum>
                                    </limit>
                                </limits>
                            </rule>
                        </rules>
                    </configuration>
                </execution>
            </executions>
        </plugin>
    </plugins>

```

## 四、质量度量体系

### 1. SonarQube 质量度量

**SonarQube** 是代码质量管理平台，提供静态代码分析、覆盖率、重复代码、代码异味、安全漏洞等多维度度量。

| 度量维度 | 指标 |
|---------|------|
| **可靠性** | Bug 数、严重等级、修复时间估计 |
| **安全性** | 漏洞数、热点数、安全评级 |
| **可维护性** | 代码异味、技术债务、技术债务比率 |
| **覆盖率** | 单元测试覆盖率、新代码覆盖率 |
| **重复率** | 重复代码行数、重复块数 |
| **复杂度** | 圈复杂度、认知复杂度 |
| **代码规模** | 代码行数、注释行数、文件数 |

### 2. 质量门禁（Quality Gate）

SonarQube 质量门禁定义了代码可发布的标准：

| 条件 | 阈值 | 说明 |
|------|------|------|
| 新代码覆盖率 | ≥ 80% | 新代码必须有足够测试 |
| 新代码重复率 | ≤ 3% | 新代码不能有大量重复 |
| 新代码 Bug | 0 个严重/阻断 | 新代码不能有严重 Bug |
| 新代码漏洞 | 0 个严重/阻断 | 新代码不能有安全漏洞 |
| 新代码技术债务比率 | ≤ 5% | 新代码技术债务可控 |
| 整体覆盖率 | ≥ 70% | 整体覆盖率不退化 |

### 3. 质量度量指标

| 指标 | 说明 | 计算公式 |
|------|------|---------|
| **技术债务比率** | 修复技术债务所需时间占比 | 技术债务时间 / 开发时间 |
| **代码重复率** | 重复代码占比 | 重复行数 / 总行数 |
| **注释率** | 注释占比 | 注释行数 / (代码行+注释行) |
| **认知复杂度** | 代码理解难度 | 嵌套+控制流复杂度 |
| **测试有效性** | 变异测试得分 | 存活变异体 / 总变异体 |
| **变更失败率** | 部署导致故障的比例 | 故障部署数 / 总部署数 |
| **平均修复时间** | 修复故障的平均时间 | 总修复时间 / 故障数 |

## 五、覆盖率误区与陷阱

### 1. 常见误区

| 误区 | 正解 |
|------|------|
| **100% 覆盖率 = 零 Bug** | 覆盖率只说明代码被执行，不说明逻辑正确 |
| **覆盖率越高越好** | 过高覆盖率边际收益递减，维护成本增加 |
| **只看行覆盖率** | 分支覆盖率更重要，能发现隐藏逻辑 |
| **为覆盖率写测试** | 测试应验证行为，不是为了凑覆盖率 |
| **覆盖率达标就安全** | 安全漏洞、并发问题、性能问题覆盖率无法发现 |
| **所有模块要求相同覆盖率** | 核心模块要求高，工具类/配置可低 |
| **覆盖率不下降就行** | 新代码应有更高覆盖率要求 |
| **单元测试覆盖率足够** | 集成测试和 E2E 测试同样重要 |

### 2. 覆盖率操纵（反模式）

```java
// ❌ 反模式：为了覆盖率写无意义测试
@Test
void testAllMethods() {
    // 只是调用方法，不验证结果
    userService.createUser(new User());
    userService.getUserById(1L);
    userService.deleteUser(1L);
    // 没有任何断言！
}

// ❌ 反模式：测试 getters/setters
@Test
void testSettersAndGetters() {
    User user = new User();
    user.setName("test");
    assertEquals("test", user.getName());  // 无意义的测试
}

// ✅ 正确模式：测试行为和业务规则
@Test
void shouldRejectNegativeBalance_whenWithdraw() {
    Account account = new Account(new BigDecimal("100"));
    assertThrows(InsufficientBalanceException.class, () ->
        account.withdraw(new BigDecimal("200"))
    );
}
```

### 3. 变异测试（Mutation Testing）

变异测试通过修改代码（引入变异），检查测试是否能发现变异，衡量测试的**有效性**而非覆盖率。

| 工具 | 语言 | 说明 |
|------|------|------|
| **PIT** | Java | 主流变异测试工具 |
| **Stryker** | JS/TS/C# | 多语言变异测试 |
| **mutmut** | Python | Python 变异测试 |

```text
变异测试流程：
1. 对代码引入微小变异（如 > 改为 >=、+ 改为 -）
2. 运行测试
3. 如果测试失败 → 变异被杀死（测试有效）
4. 如果测试通过 → 变异存活（测试无效，需加强测试）
5. 变异得分 = 杀死变异数 / 总变异数
```

> 变异测试比覆盖率更能反映测试质量，但运行时间长，建议在 CI 中定期运行而非每次提交。

## 六、最佳实践

### 1. 覆盖率目标设定

| 模块类型 | 行覆盖率 | 分支覆盖率 | 说明 |
|---------|---------|-----------|------|
| **核心业务逻辑** | ≥ 85% | ≥ 75% | 支付、订单、权限等 |
| **一般业务模块** | ≥ 70% | ≥ 60% | 常规 CRUD、服务 |
| **工具类/通用组件** | ≥ 80% | ≥ 70% | 被广泛使用，需高可靠 |
| **配置/启动类** | ≥ 50% | - | 逻辑简单，可降低要求 |
| **第三方集成** | ≥ 60% | ≥ 50% | Mock 外部依赖，测试集成逻辑 |
| **遗留代码** | 不降低即可 | 不降低即可 | 渐进式提升，新代码达标 |

### 2. 覆盖率管理策略

- [ ] **新代码高要求**：新代码覆盖率 ≥ 80%，防止技术债务累积
- [ ] **整体不退化**：整体覆盖率不能下降，设置质量门禁
- [ ] **分模块管理**：不同模块不同目标，不搞一刀切
- [ ] **定期审查**：定期审查覆盖率报告，识别薄弱模块
- [ ] **增量覆盖**：关注变更代码的覆盖率，而非整体绝对值
- [ ] **结合变异测试**：核心模块定期运行变异测试，验证测试有效性
- [ ] **排除合理项**：排除 DTO、配置类、生成代码等不需测试的代码

### 3. CI/CD 集成

```yaml
# GitHub Actions 示例
name: Test and Coverage
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
      - name: Run tests with coverage
        run: mvn clean verify
      - name: Upload coverage to SonarQube
        run: mvn sonar:sonar
      - name: Upload coverage report
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: target/site/jacoco/
```

### 4. 覆盖率报告使用

- [ ] **HTML 报告**：本地查看，定位未覆盖代码
- [ ] **XML 报告**：集成 SonarQube、CI 质量门禁
- [ ] **差异覆盖**：只看本次变更的覆盖率（Diff Coverage）
- [ ] **历史趋势**：跟踪覆盖率变化，防止退化
- [ ] **团队看板**：可视化各模块覆盖率，促进改进

### 5. 排除不需要测试的代码

    </excludes>

## 七、常见问题与排查

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| **覆盖率统计为 0** | JaCoCo agent 未注入 / 测试未运行 | 检查 prepare-agent 配置、确认测试执行、检查 argLine |
| **覆盖率不达标但测试很多** | 测试集中在简单代码 / 核心逻辑未覆盖 | 分析报告，补充核心模块和分支测试 |
| **分支覆盖率低** | if/else 只测了一个分支 / 异常路径未测 | 补充异常场景、边界条件、else 分支测试 |
| **CI 中覆盖率与本地不同** | 环境差异 / 测试并行 / 随机测试 | 统一环境、固定随机种子、检查测试顺序依赖 |
| **覆盖率忽高忽低** | 测试不稳定 / 并发问题 / 外部依赖 | 修复 Flaky 测试、Mock 外部依赖、确保测试独立 |
| **JaCoCo 报告不生成** | 插件配置错误 / 阶段不对 | 检查 report goal 绑定在 test 阶段、检查 outputDirectory |
| **质量门禁总是失败** | 阈值设置过高 / 遗留代码多 | 分模块设置阈值、新代码高要求、遗留代码渐进提升 |
| **覆盖率高但 Bug 多** | 测试无断言 / 只测正常路径 | 加强断言、补充异常和边界测试、引入变异测试 |
| **Spring Boot 测试覆盖率低** | @SpringBootTest 启动慢，测试少 | 切片测试（@WebMvcTest/@DataJpaTest）、Mock 依赖 |
| **私有方法无法覆盖** | 私有方法未通过公共方法调用 | 通过公共方法测试私有逻辑、或重构为独立类 |
| **静态方法覆盖率低** | 静态方法难以 Mock | 使用 Mockito-inline、或重构为实例方法 |
| **覆盖率报告包含测试代码** | 未排除测试目录 | 配置 excludes 排除 src/test |
| **多模块项目覆盖率不合并** | 各模块独立报告 | 使用 jacoco:report-aggregate 合并报告 |
