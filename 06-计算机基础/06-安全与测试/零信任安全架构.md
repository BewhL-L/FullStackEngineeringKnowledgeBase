# 零信任安全架构

> 零信任（Zero Trust）的核心原则是"永不信任，始终验证"（Never Trust, Always Verify）。传统安全模型假设内网是可信的，而零信任认为无论内外网，任何访问都必须经过身份认证、授权和加密，且每次访问都需重新验证。
>
> **三大核心**：身份为中心、最小权限、持续验证。

---

## 一、概述：从零信任的诞生说起

### 1.1 传统边界安全的失效

| 传统模型问题 | 零信任解决思路 |
|-------------|---------------|
| 内网即可信（VPN接入后横向移动无阻） | 每次访问都验证身份和设备状态 |
| 粗粒度授权（一旦授权长期有效） | 最小权限、动态授权、即时生效 |
| 依赖网络边界（防火墙/VPN） | 身份为中心，不依赖网络位置 |
| 静态安全策略 | 持续评估、自适应策略 |
| 缺乏微隔离 | 东西向流量也需认证授权 |

### 1.2 零信任发展历程

```text
2010  Forrester分析师John Kindervag提出"Zero Trust"概念
2014  Google BeyondCorp项目（零信任标杆实践）
2017  Gartner提出CARTA（持续自适应风险与信任评估）
2019  NIST SP 800-207《零信任架构》标准发布
2020+  云原生、SASE、ZTNA产品成熟，企业大规模落地
```

### 1.3 零信任核心原则（NIST SP 800-207）

1. **所有数据源和计算服务都视为资源**
2. **无论网络位置如何，所有通信都必须加密**
3. **对企业资源的访问按会话进行授权**
4. **访问权限基于动态策略（身份、设备、环境、行为）**
5. **企业持续监控和度量资产基础设施的完整性和安全状态**
6. **所有资源的认证和授权都是动态的，在允许访问之前严格执行**
7. **企业尽可能收集关于资产、网络基础设施和通信的状态信息，并用于改善安全态势**

## 二、底层原理：零信任架构组件

### 2.1 零信任逻辑组件

```text
                    ┌─────────────────────┐
                    │   策略引擎(PE)       │
                    │   Policy Engine      │
                    │  (信任算法+策略决策)  │
                    └──────────┬──────────┘
                               │ 决策
                    ┌──────────▼──────────┐
用户 → 信任评估 →  │   策略管理器(PA)      │ → 资源
(身份+设备)        │  Policy Administrator │  (应用/数据)
                    │  (执行策略+会话管理)  │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │   持续诊断与缓解(CDM)│
                    │  (设备状态+威胁情报)  │
                    └─────────────────────┘
```

### 2.2 身份为中心（Identity-Centric）

零信任将身份从"网络边界内/外"转变为"谁在访问、用什么设备、在什么环境下"。

**身份要素**：
- 用户身份（SSO统一认证、MFA多因素认证）
- 设备身份（设备证书、MDM管理、合规状态）
- 应用身份（服务间mTLS、SPIFFE/SPIRE）
- 数据身份（数据分类标签、访问审计）

### 2.3 微隔离（Micro-Segmentation）

```yaml
传统网络：VLAN隔离（粗粒度，同VLAN内自由通信）
零信任：  工作负载级隔离（每个Pod/VM都有独立策略）

示例（K8s NetworkPolicy）：
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-server-policy
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

## 三、实操：零信任落地

### 3.1 身份认证层（SSO + MFA）

```yaml
# Keycloak OIDC配置示例
# 1. 启用MFA
# 2. 配置密码策略（最小12位、大小写+数字+特殊字符）
# 3. 配置会话超时（8小时，绝对超时12小时）
# 4. 配置风险-based认证（异地登录需额外验证）

# 应用集成（Spring Boot + Keycloak）
spring:
  security:
    oauth2:
      client:
        registration:
          keycloak:
            client-id: my-app
            client-secret: ${KEYCLOAK_SECRET}
            authorization-grant-type: authorization_code
            scope: openid,profile,email
        provider:
          keycloak:
            issuer-uri: https://auth.example.com/realms/myrealm
```

### 3.2 设备信任评估

```python
# 设备合规检查脚本（MDM集成）
def check_device_compliance(device_id):
    device = mdm_api.get_device(device_id)
    checks = {
        'os_version': device.os_version >= 'Windows 11 22H2',
        'disk_encrypted': device.bitlocker_status == 'enabled',
        'antivirus': device.defender_status == 'active',
        'firewall': device.windows_firewall == 'enabled',
        'patch_level': device.last_patch_date >= (today - 30),
        'jailbroken': not device.jailbroken,
    }
    all_passed = all(checks.values())
    trust_level = 'high' if all_passed else 'medium' if sum(checks.values()) >= 4 else 'low'
    return {'compliant': all_passed, 'trust_level': trust_level, 'checks': checks}
```

### 3.3 服务间零信任（mTLS + SPIFFE）

```yaml
# Istio mTLS配置（服务间双向认证）
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: prod
spec:
  mtls:
    mode: STRICT  # 所有服务间通信必须mTLS
---
# 授权策略（最小权限）
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: order-service-policy
  namespace: prod
spec:
  selector:
    matchLabels:
      app: order-service
  rules:
  - from:
    - source:
        principals: ["cluster.local/ns/prod/sa/frontend-sa"]
    to:
    - operation:
        methods: ["GET", "POST"]
        paths: ["/api/orders/*"]
```

### 3.4 动态访问策略（ABAC）

```python
# 基于属性的访问控制（ABAC）策略引擎
def evaluate_access_policy(user, resource, context):
    policies = [
        # 策略1：工作时间内，合规设备可访问
        {
            'name': 'business_hours_access',
            'condition': lambda: (
                context.time.hour in range(9, 18) and
                context.day in ['Mon','Tue','Wed','Thu','Fri'] and
                user.device_trust == 'high'
            ),
            'effect': 'allow',
        },
        # 策略2：管理员可随时访问，但需MFA
        {
            'name': 'admin_access',
            'condition': lambda: (
                'admin' in user.roles and
                context.mfa_verified == True
            ),
            'effect': 'allow',
        },
        # 策略3：敏感数据需额外审批
        {
            'name': 'sensitive_data',
            'condition': lambda: (
                resource.sensitivity == 'high' and
                context.approval_status == 'approved'
            ),
            'effect': 'allow',
        },
    ]
    for policy in policies:
        if policy['condition']():
            return {'allowed': True, 'matched_policy': policy['name']}
    return {'allowed': False, 'reason': 'no policy matched'}
```

## 四、常见问题与排查

### 4.1 零信任落地常见阻力

| 阻力 | 应对策略 |
|------|---------|
| 用户体验下降（频繁认证） | SSO单点登录 + 记住设备 + 风险-based认证（低风险免MFA） |
| 遗留系统不支持现代认证 | 部署零信任网关（反向代理），遗留系统无需改造 |
| 策略过于严格导致业务中断 | 先观察模式（Shadow模式）收集流量，再逐步收紧策略 |
| 缺乏身份治理基础 | 先建设统一身份目录（AD/LDAP），再推进零信任 |
| 运维复杂度增加 | 采用SASE/ZTNA一体化平台，减少多组件集成 |

### 4.2 零信任不是什么

- **不是替代VPN**：零信任是架构理念，ZTNA（零信任网络访问）是替代VPN的技术方案
- **不是一个产品**：零信任是持续演进的安全模型，需要身份、网络、应用、数据多层配合
- **不是一次性项目**：零信任是持续改进过程，需要不断优化策略和监控
- **不是只面向远程办公**：零信任适用于所有访问场景，包括内网访问

### 4.3 零信任成熟度评估

| 阶段 | 特征 |
|------|------|
| 传统（0级） | 边界防火墙+VPN，内网可信 |
| 基础（1级） | SSO+MFA，部分应用接入 |
| 进阶（2级） | 设备信任评估，微隔离试点 |
| 高级（3级） | 动态策略引擎，持续监控，自动化响应 |
| 优化（4级） | AI驱动的自适应安全，全链路加密，零信任文化 |

## 五、进阶与最佳实践

### 5.1 SASE（安全访问服务边缘）

SASE将SD-WAN（网络）与安全服务（SWG、CASB、ZTNA、FWaaS）融合为云原生服务，是零信任在云时代的最佳载体。

```text
传统架构：用户 → VPN → 防火墙 → 数据中心 → 云应用
SASE架构：  用户 → 最近POP点（SASE云服务）→ 策略决策 → 目标资源
```

### 5.2 零信任落地路线图

```text
第1阶段（1-3月）：身份基础建设
- 统一身份目录（AD/LDAP/云身份）
- SSO单点登录覆盖核心应用
- MFA多因素认证强制启用

第2阶段（3-6月）：设备信任+ZTNA
- MDM设备管理部署
- 设备合规检查策略
- ZTNA替代VPN（远程访问）
- 特权访问管理（PAM）

第3阶段（6-12月）：微隔离+数据保护
- 工作负载微隔离（K8s NetworkPolicy / 主机防火墙）
- 服务间mTLS
- 数据分类分级+DLP
- 持续监控与UEBA

第4阶段（12月+）：自适应安全
- AI/ML驱动的异常检测
- 自动化响应（SOAR）
- 零信任文化建设
- 持续红蓝对抗
```

### 5.3 零信任检查清单

- [ ] 所有用户通过SSO统一认证

- [ ] 应用级访问控制（最小权限）
- [ ] 工作负载微隔离（东西向流量管控）
- [ ] 特权账号管理（PAM+JIT）
- [ ] 持续监控与审计日志
