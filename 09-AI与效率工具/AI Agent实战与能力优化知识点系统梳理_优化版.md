## 2. RAG 实战优化

### 2.1 RAG 完整流程

```
文档加载 → 文档清洗 → 文本切分 → 向量化 → 向量库存储
                                          ↓
用户查询 → 查询改写 → 向量检索 → 重排序 → 上下文拼接 → LLM 生成 → 引用标注
```


> 🔍 **知识点深度解析**
>
> **作用**：RAG 完整流程包括文档加载、切分、向量化、存储、检索、重排和生成，每一步都影响最终回答质量。
>
> **原理**：离线阶段：文档加载（PDF/网页/数据库）→ 文本切分（chunk）→ embedding 向量化 → 存入向量数据库。在线阶段：问题向量化 → 向量检索 top-k →（可选）查询改写/混合检索 → reranker 重排序 → 拼接上下文 → LLM 生成回答 → 引用来源。每一步都有优化空间：切分策略、embedding 模型、检索参数、reranker、prompt 模板。
>
> **用法要点**：① 离线：加载→切分→embedding→入库；在线：检索→重排→生成  ② 切分质量影响检索：太大引入噪声，太小丢失上下文  ③ 混合检索（向量+BM25）+ reranker 显著提升准确率  ④ 生成时必须引用来源，支持溯源验证  ⑤ 面试常考：RAG 全流程、各环节优化、chunk 策略、reranker

### 2.2 文本切分优化

| 切分策略 | 说明 | 适用场景 |
|----------|------|----------|
| 固定长度 | 按字符数切分，重叠窗口 | 通用 |
| 语义切分 | 按语义段落切分 | 结构化文档 |
| 递归切分 | 按标题/段落/句子递归 | Markdown/HTML |
| 结构化切分 | 按文档结构（标题层级） | 技术文档、论文 |

**要点**：
- 切分大小 256-1024 Token，重叠 10-20%
- 保留元数据（标题、来源、页码）
- 代码块不要切散


> 🔍 **知识点深度解析**
>
> **作用**：文本切分策略直接影响检索质量，需根据文档类型选择固定切分、语义切分或递归切分，并设置重叠。
>
> **原理**：固定长度切分：按 token/字符数切，简单但可能切断语义。递归切分：按段落→句子→词的优先级切分，尽量保持语义完整。语义切分：用 embedding 相似度判断主题边界。文档结构切分：按 Markdown 标题/HTML 标签切分。重叠（overlap）：相邻 chunk 共享部分文本，避免边界信息丢失。chunk 大小通常 256-1024 token，根据文档类型调整。
>
> **用法要点**：① 递归字符切分（RecursiveCharacterTextSplitter）最常用  ② chunk_size 512-1024，overlap 50-100 是常见配置  ③ 代码按函数/类切分，Markdown 按标题切分  ④ 语义切分质量高但计算成本大  ⑤ 面试常考：切分策略、chunk size 选择、overlap 作用、结构化文档切分

### 2.3 检索优化

- **混合检索**：向量检索 + 关键词检索（BM25），互补优势
- **查询改写**：LLM 将用户问题改写为更适合检索的查询
- **多路召回**：多种检索方式召回，合并去重
- **重排序（Rerank）**：用 Cross-Encoder 对召回结果精排，提升 Top-K 质量
- **查询分解**：复杂问题拆为多个子问题，分别检索


> 🔍 **知识点深度解析**
>
> **作用**：检索优化通过查询改写、混合检索、重排序和上下文压缩提升 RAG 检索质量。
>
> **原理**：查询改写：将口语化/指代模糊的问题改写为检索友好的查询（LLM 改写、HyDE 假设文档）。混合检索：向量检索（语义）+ BM25（关键词）结合，Reciprocal Rank Fusion（RRF）融合排序。重排序：Cross-encoder reranker 对 top-20 候选精排（比 bi-encoder 准但慢）。上下文压缩：去除检索文档中的无关段落，只保留与问题相关的句子。元数据过滤：按时间/类别/来源预过滤。
>
> **用法要点**：① HyDE：先让 LLM 生成假设答案，用假设答案 embedding 检索  ② 混合检索：向量+BM25，RRF 融合排序  ③ Reranker：Cross-encoder 精排 top-20→top-5  ④ 上下文压缩：LLM 提取检索文档中的相关片段  ⑤ 面试常考：检索优化手段、HyDE、混合检索、reranker、RRF

### 2.4 向量化模型选择

| 模型 | 特点 |
|------|------|
| text-embedding-3 | OpenAI，效果好，需 API |
| bge-large-zh | 中文效果好，开源可本地 |
| m3e | 中文多粒度，开源 |
| Cohere Embed | 多语言，效果好 |

> 🔍 **知识点深度解析**
>
> **作用**：RAG 是 Agent 知识增强的核心，检索质量直接决定回答质量。
>
> **原理**：RAG（检索增强生成）通过外部知识库补充 LLM 的知识，解决知识过时和幻觉问题。检索分召回（Recall）和排序（Rerank）两阶段：召回用向量相似度快速取回 Top-N（如50条），重排序用更精确的 Cross-Encoder 模型精排取 Top-K（如5条）。混合检索结合向量语义检索和 BM25 关键词检索，向量擅长语义匹配，BM25 擅长精确关键词匹配（如专有名词、错误码），两者互补。查询改写用 LLM 将口语化问题转为规范查询，提升召回率。切分质量影响检索粒度，太大引入噪声，太小丢失上下文。
>
> **用法要点**：① 评估 RAG 用召回率（相关文档是否被召回）和准确率（Top-K 中相关比例）；② 中文场景用 bge/m3e 等中文优化的 embedding 模型；③ 必须加 Rerank，显著提升质量；④ 面试常考：RAG 流程、切分策略、混合检索、Rerank、查询改写、RAG 评估。

## 3. 幻觉控制

### 3.1 幻觉类型

- **事实性幻觉**：编造不存在的事实
- **忠实性幻觉**：回答与提供的上下文不符
- **指令性幻觉**：不遵循指令要求


> 🔍 **知识点深度解析**
>
> **作用**：LLM 幻觉分为事实性幻觉（编造不存在的事实）和忠实性幻觉（与上下文矛盾），RAG Agent 中需重点防控。
>
> **原理**：事实性幻觉：模型编造训练数据中没有或错误的信息（虚构 API、不存在的论文）。忠实性幻觉：回答与提供的上下文矛盾（忽略检索到的文档，凭记忆回答）。RAG 场景还包括：检索到错误文档导致的幻觉、对文档过度推断、引用不存在的来源。幻觉成因包括训练数据噪声、概率生成机制、上下文信息不足和领域知识缺乏。
>
> **用法要点**：① 事实性幻觉：编造不存在的信息（虚构 API/论文/事件）  ② 忠实性幻觉：回答与检索上下文矛盾  ③ RAG 特有：检索到不相关文档、过度推断、伪造引用  ④ 幻觉不可完全消除，只能通过工程手段降低  ⑤ 面试常考：幻觉类型、幻觉成因、RAG 如何减少幻觉

### 3.2 控制方法

| 方法 | 说明 |
|------|------|
| **RAG** | 提供外部知识，让模型基于事实回答 |
| **Prompt 约束** | "只根据提供的上下文回答，不知道就说不知道" |
| **引用标注** | 要求回答标注信息来源，便于验证 |
| **自我验证** | 模型生成后自我检查是否与上下文一致 |
| **事实核查** | 用工具或另一个模型核查关键事实 |
| **降低温度** | temperature=0 减少随机性 |
| **结构化输出** | JSON Schema 约束输出格式 |


> 🔍 **知识点深度解析**
>
> **作用**：通过 Prompt 约束、RAG  grounding、温度调节、自我验证和引用强制等手段控制幻觉。
>
> **原理**：Prompt 约束：明确要求只基于上下文回答，不知道就说不知道。RAG grounding：提供准确检索内容，减少模型自由发挥。temperature=0 降低随机性。自我验证：让 LLM 检查回答是否有来源支持（Self-Consistency/Citations）。引用强制：要求每个事实标注来源 chunk。链式验证（Chain-of-Verification）：生成回答后自动提出验证问题并逐一核实。
>
> **用法要点**：① Prompt：'只基于以下上下文回答，不确定则说不知道'  ② temperature=0 / top_p=1 降低随机性  ③ 强制引用来源，无来源的信息标记为推测  ④ Chain-of-Verification：生成→提验证问题→核实→修正  ⑤ 面试常考：幻觉控制手段、RAG grounding、CoVe、引用验证

### 3.3 幻觉评估

- **忠实度（Faithfulness）**：回答是否与上下文一致
- **答案相关性（Answer Relevance）**：回答是否切题
- **上下文精度（Context Precision）**：检索的上下文是否相关
- 人工抽检 + 自动化评估（LLM-as-Judge）

---


> 🔍 **知识点深度解析**
>
> **作用**：通过事实性准确率、答案忠实度和引用准确率等指标量化幻觉程度，指导优化方向。
>
> **原理**：评估方法：构建标注测试集（问题+正确答案+来源文档），自动评估用 LLM-as-Judge 判断回答是否忠实于上下文（faithfulness）和是否回答了问题（answer relevancy）。引用准确率：检查引用的来源是否真的支持回答。RAGAS 框架专门评估 RAG：faithfulness（忠实度）、answer_relevancy（答案相关性）、context_precision/recall（上下文精确率/召回率）。
>
> **用法要点**：① faithfulness：回答中的事实是否都能在上下文中找到依据  ② answer_relevancy：回答是否切题  ③ context_precision/recall：检索到的上下文是否相关/完整  ④ RAGAS 是 RAG 专用评估框架，自动化指标计算  ⑤ 面试常考：RAG 评估指标、RAGAS、faithfulness、LLM-as-Judge

## 4. 工具调用优化

### 4.1 工具设计原则

1. **单一职责**：每个工具做一件事
2. **清晰描述**：name + description + parameters 要准确
3. **参数简单**：尽量用基本类型，避免复杂嵌套
4. **错误处理**：工具返回清晰的错误信息
5. **幂等性**：重复调用结果一致（写操作需注意）


> 🔍 **知识点深度解析**
>
> **作用**：好的工具设计需要描述清晰、参数明确、粒度适中、错误友好，是 Agent 正确使用工具的前提。
>
> **原理**：工具命名用动词+名词（get_weather/send_email），description 说明何时使用和做什么（LLM 根据 description 选择工具）。参数用 JSON Schema 严格定义类型和枚举值，减少 LLM 参数错误。粒度：一个工具做一件事，避免万能工具。错误信息应可操作（告诉 LLM 如何修正而非仅报错）。工具数量控制在 10-20 个以内，过多导致选择困难。
>
> **用法要点**：① description 是 LLM 选择工具的唯一依据，必须清晰说明使用场景  ② 参数 JSON Schema 严格定义类型/必填/枚举/描述  ③ 粒度适中：太粗 LLM 不会用，太细调用次数多  ④ 错误信息可操作：'参数 X 应为日期格式 YYYY-MM-DD'  ⑤ 面试常考：工具设计原则、description 重要性、参数校验、工具数量

### 4.2 工具选择优化

- **工具数量控制**：太多工具 LLM 选择困难，5-10 个为宜
- **工具分组**：按场景分组，动态加载相关工具
- **工具描述优化**：用清晰的自然语言描述用途和参数
- **示例引导**：在 Prompt 中提供工具使用示例


> 🔍 **知识点深度解析**
>
> **作用**：通过工具描述优化、示例引导、检索式工具选择和子 Agent 分工提升 LLM 工具选择准确率。
>
> **原理**：工具描述中加入 few-shot 示例（什么场景用什么工具）。工具太多时用检索式选择：先将工具 description embedding，根据用户意图检索 top-k 工具再传给 LLM（减少上下文干扰）。子 Agent 分工：不同领域专家 Agent 各自持有相关工具，主 Agent 路由到专家 Agent。强制工具调用：对特定意图强制使用特定工具。
>
> **用法要点**：① description 加入使用示例，提升 LLM 选择准确率  ② 工具检索（Tool RAG）：embedding 工具描述，按意图召回相关工具  ③ 子 Agent 分工：每个专家 Agent 只持有领域工具  ④ 结构化输出解析失败时重试或引导 LLM 修正格式  ⑤ 面试常考：工具选择优化、Tool RAG、子 Agent 分工、few-shot

### 4.3 工具执行安全

- 危险操作（删除、支付）需人工确认
- 沙箱执行代码，限制资源访问
- API 调用限制权限范围
- 超时控制，防止工具卡住 Agent

---


> 🔍 **知识点深度解析**
>
> **作用**：工具执行需沙箱隔离、权限控制、参数校验和审计日志，防止 Agent 执行危险操作。
>
> **原理**：代码执行在 Docker/微虚拟机沙箱中（限制网络、文件系统、资源）。文件操作限制在指定目录（chroot/路径白名单）。API 调用限制可访问的端点和方法（HTTP 方法白名单）。敏感操作（删除/支付/发送）需人工确认。参数校验在执行前检查类型和范围。全量审计日志记录每次工具调用（谁/何时/参数/结果）。
>
> **用法要点**：① 代码执行：Docker/gVisor/Firecracker 沙箱隔离  ② 最小权限：工具只授予完成任务所需的最小权限  ③ 敏感操作 Human-in-the-loop 确认  ④ 参数白名单校验 + 速率限制防滥用  ⑤ 面试常考：工具安全、沙箱方案、权限控制、审计日志

## 5. Agent 评估

### 5.1 评估维度

| 维度 | 指标 | 方法 |
|------|------|------|
| **任务完成率** | 成功完成任务的比例 | 标准测试集 |
| **步骤效率** | 完成任务的平均步数 | 日志统计 |
| **工具使用准确率** | 工具调用是否正确 | 人工/自动标注 |
| **回答质量** | 准确性、相关性、完整性 | LLM-as-Judge |
| **幻觉率** | 编造信息的比例 | 事实核查 |
| **成本** | 平均 Token 消耗 | 用量统计 |
| **延迟** | 平均响应时间 | 性能测试 |


> 🔍 **知识点深度解析**
>
> **作用**：Agent 评估覆盖任务成功率、工具使用准确率、效率（步数/Token/时间）、安全性和用户满意度。
>
> **原理**：任务成功率是核心指标：端到端完成任务的比例。工具使用：工具选择准确率、参数正确率、无效调用比例。效率：平均步数、Token 消耗、端到端延迟。安全：越权操作次数、Prompt 注入抵抗率。鲁棒性：对模糊输入和错误的恢复能力。用户满意度：人工评分或反馈率。
>
> **用法要点**：① 任务成功率（端到端）是最核心的业务指标  ② 工具使用准确率和参数正确率反映 Agent 能力  ③ 效率指标：步数/Token/延迟，影响成本和体验  ④ 安全指标：越权次数、注入抵抗率  ⑤ 面试常考：Agent 评估维度、成功率计算、效率指标

### 5.2 评估方法

- **离线评估**：固定测试集，自动化运行
- **在线评估**：生产环境 A/B 测试
- **人工评估**：专家打分
- **LLM-as-Judge**：用强模型评估弱模型输出
- **LangSmith / W&B**：专业评估平台


> 🔍 **知识点深度解析**
>
> **作用**：Agent 评估方法包括离线测试集评估、LLM-as-Judge、人工评估和在线 A/B 测试。
>
> **原理**：离线评估：构建标注测试集（任务+期望结果），自动运行 Agent 并评分。LLM-as-Judge：用强模型（GPT-4）评判 Agent 输出质量（成本低但有偏差）。人工评估：对复杂任务人工打分（准确但慢贵）。在线评估：A/B 测试对比不同 Agent 版本的成功率和用户满意度。轨迹评估：检查 Agent 的执行路径是否合理（不只是最终结果）。
>
> **用法要点**：① 离线测试集用于回归测试，每次修改后自动运行  ② LLM-as-Judge 可扩展但需校准偏差  ③ 人工评估作为金标准，定期校准自动评估  ④ 轨迹评估：检查中间步骤是否合理，不只看结果  ⑤ 面试常考：评估方法对比、LLM-as-Judge 偏差、A/B 测试

### 5.3 测试集构建

- 覆盖典型任务和边界情况
- 包含成功和失败案例
- 标注期望结果
- 定期更新

---


> 🔍 **知识点深度解析**
>
> **作用**：构建有代表性的 Agent 测试集需覆盖典型场景、边界情况和对抗样本，按难度分层。
>
> **原理**：测试集来源：真实用户日志（ anonymize）、人工设计典型任务、边界情况（空输入/超长输入/模糊指令）、对抗样本（Prompt 注入/恶意请求）。分层：简单（单步工具调用）、中等（2-3 步）、复杂（多步+规划+错误恢复）。每条测试用例包含：输入、期望结果、检查点（必须调用的工具/必须验证的条件）。
>
> **用法要点**：① 从真实日志采样保证代表性，人工补充边界 case  ② 按难度分层：单步/多步/复杂工作流  ③ 包含对抗样本测试安全性  ④ 测试集需持续更新，覆盖新发现的 bad case  ⑤ 面试常考：测试集构建方法、分层策略、对抗样本、回归测试

## 6. 成本与性能优化

### 6.1 成本优化

- **模型分级**：简单任务用小模型（GPT-3.5/Haiku），复杂任务用大模型
- **缓存**：相同查询缓存结果，减少 LLM 调用
- **Prompt 压缩**：精简上下文，去除无关信息
- **批量处理**：合并多个请求
- **早期终止**：任务完成立即停止，不要多余循环


> 🔍 **知识点深度解析**
>
> **作用**：通过模型路由、Prompt 压缩、缓存、批处理和 Token 监控降低 Agent 的 LLM 调用成本。
>
> **原理**：模型路由：简单任务用小模型（Haiku/8B），复杂推理用大模型。Prompt 压缩：对话历史摘要、系统提示精简、工具描述按需加载。缓存：相同问题缓存回答（语义缓存用 embedding 相似度匹配）。批处理：批量调用 API（Batch API 半价）。Token 监控：按用户/会话/功能统计 Token 消耗，设置预算告警。减少循环步数：优化规划能力减少无效工具调用。
>
> **用法要点**：① 模型路由：分类器判断任务难度，选择性价比模型  ② 语义缓存：相似问题直接返回缓存，命中率可达 30%+  ③ 对话历史摘要压缩，释放上下文空间  ④ Batch API 适合非实时任务，价格减半  ⑤ 面试常考：Token 成本优化、模型路由、语义缓存、Prompt 压缩

### 6.2 性能优化

- **流式输出**：提升用户体验
- **并行工具调用**：独立工具同时调用
- **异步执行**：异步 I/O 提升并发
- **向量检索优化**：ANN 索引（HNSW）、量化
- **本地模型**：简单任务用本地小模型，降低延迟

---


> 🔍 **知识点深度解析**
>
> **作用**：通过并行调用、流式输出、模型选择和架构优化降低 Agent 响应延迟。
>
> **原理**：并行工具调用：无依赖的工具同时调用（LLM 支持 parallel tool calls）。流式输出：首 Token 时间（TTFT）比完整响应更影响体验，SSE 流式返回。快速模型：简单步骤用快速小模型。预取/预测：提前加载可能需要的数据。架构优化：减少不必要的 LLM 调用（规则预处理）、工具响应精简（只返回必要字段）。
>
> **用法要点**：① parallel tool calls：无依赖工具并行执行  ② SSE 流式输出，降低首字节延迟  ③ 工具返回结果精简，避免大段 JSON 占用上下文  ④ 简单分类/提取用小模型，延迟低  ⑤ 面试常考：Agent 延迟优化、并行调用、流式输出、TTFT

## 7. 安全边界

### 7.1 Prompt 注入防护

- 系统提示与用户输入隔离
- 工具调用前验证指令合法性
- 输入过滤和清洗
- 最小权限原则


> 🔍 **知识点深度解析**
>
> **作用**：Prompt 注入通过恶意输入覆盖系统指令，诱导 Agent 执行非预期操作，需多层防护。
>
> **原理**：直接注入：用户输入中包含'忽略以上指令...'等覆盖系统提示。间接注入：工具返回内容（网页/文档）中藏有注入指令。防护：输入消毒（过滤可疑模式）、指令分层（系统指令优先级最高，用分隔符隔离用户输入）、工具权限最小化、输出编码（工具返回内容当数据而非指令处理）、敏感操作人工确认、监控异常行为。
>
> **用法要点**：① 直接注入：用户消息覆盖系统指令；间接注入：工具返回藏指令  ② 用分隔符（<user_input>）明确隔离系统指令和外部内容  ③ 工具返回内容标记为不可信数据，不作为指令执行  ④ 敏感操作人工确认是最后防线  ⑤ 面试常考：Prompt 注入类型、间接注入、防护手段、指令优先级

### 7.2 数据安全

- 敏感数据不上传云端 LLM（用本地模型）
- 输出过滤敏感信息
- 数据脱敏
- 访问控制和审计日志


> 🔍 **知识点深度解析**
>
> **作用**：Agent 数据安全涉及 PII 保护、数据脱敏、传输加密和访问控制，防止敏感信息泄露。
>
> **原理**：PII（个人身份信息）检测和脱敏：日志和记忆中不存储明文手机号/身份证/密码。传输加密：HTTPS/TLS。访问控制：RBAC 限制 Agent 可访问的数据范围。记忆安全：长期记忆中不存敏感数据，或加密存储。多租户隔离：不同用户的数据和记忆严格隔离。数据保留策略：定期清理过期数据。
>
> **用法要点**：① PII 检测脱敏：正则/NER 识别手机号/身份证/邮箱后掩码  ② 日志中不记录敏感参数和用户数据  ③ 记忆存储加密，多租户数据隔离  ④ RBAC：Agent 只能访问授权范围内的数据  ⑤ 面试常考：PII 保护、数据脱敏、多租户隔离、记忆安全

### 7.3 操作安全

- 写操作需确认
- 代码沙箱执行
- API 权限最小化
- 速率限制防滥用

---


> 🔍 **知识点深度解析**
>
> **作用**：操作安全确保 Agent 的工具调用在授权范围内，防止误操作和恶意操作造成损害。
>
> **原理**：白名单机制：Agent 只能调用预定义的工具和 API 端点。操作确认：写操作（创建/修改/删除）需确认或审批流。速率限制：防止 Agent 循环调用导致资源耗尽。回滚能力：关键操作支持撤销。审计日志：完整记录操作链以便追溯。环境隔离：生产操作和测试操作分离，Agent 默认在沙箱环境。
>
> **用法要点**：① 工具白名单 + API 端点白名单  ② 写操作需确认，删除等高危操作需人工审批  ③ 速率限制和预算上限防止失控  ④ 完整审计日志支持事后追溯  ⑤ 面试常考：操作安全、白名单、审批流、审计、回滚

## 8. 典型 Agent 实战案例

### 8.1 知识库问答 Agent

```
用户提问 → 查询改写 → 混合检索 → Rerank → 上下文拼接
→ LLM 生成（带引用）→ 自我验证 → 输出答案+来源
```


> 🔍 **知识点深度解析**
>
> **作用**：知识库问答 Agent 结合 RAG 和多轮对话，基于企业私有文档准确回答问题并引用来源。
>
> **原理**：架构：文档摄入管道（加载→切分→embedding→入库）→ 检索服务（向量+关键词混合检索+rerank）→ 对话 Agent（多轮上下文管理+引用生成）。关键优化：查询改写（将口语化问题转为检索友好查询）、多轮对话中的指代消解、引用来源标注、无答案时诚实回复'未找到相关信息'。
>
> **用法要点**：① 查询改写：将'它怎么用'改写为具体实体+问题  ② 混合检索+reranker 提升召回准确率  ③ 多轮对话需管理指代和上下文  ④ 强制引用来源，无结果时诚实回复  ⑤ 面试常考：知识库问答架构、查询改写、多轮 RAG、引用

### 8.2 数据分析 Agent

```
用户问题 → 理解需求 → 生成 SQL/Python → 执行代码
→ 检查结果 → 生成图表 → 撰写分析报告
```


> 🔍 **知识点深度解析**
>
> **作用**：数据分析 Agent 能理解自然语言分析需求，自动编写 SQL/Python 代码查询数据并生成图表和洞察。
>
> **原理**：架构：用户问题 → Schema 理解（表结构/字段描述）→ 计划分析步骤 → 生成 SQL/Python → 沙箱执行 → 观察结果 → 修正或生成可视化 → 总结洞察。关键能力：Schema 感知（将表结构注入 prompt）、代码纠错（执行报错后自动修正）、安全（只读 SQL、限制全表扫描）、结果解释（不只给数字，给业务含义）。
>
> **用法要点**：① Schema 注入：将相关表结构和字段注释提供给 LLM  ② 代码执行-观察-修正循环，SQL 报错自动修正  ③ 安全：只读权限、LIMIT 限制、禁止 DDL/DML  ④ 生成图表和业务洞察，不只是原始数据  ⑤ 面试常考：Text2SQL、代码纠错循环、数据安全、Schema 链接

### 8.3 编程 Agent

```
需求描述 → 任务规划 → 阅读代码库 → 编写代码
→ 运行测试 → 调试修复 → 提交 PR
```

---


> 🔍 **知识点深度解析**
>
> **作用**：编程 Agent 能理解代码库、编写和修改代码、运行测试并调试，代表产品有 Cursor Agent、Devin。
>
> **原理**：架构：代码库索引（文件树+符号+embedding）→ 上下文检索（相关代码片段）→ 代码生成/修改（AST 感知编辑）→ 测试执行 → 错误分析 → 修正循环。关键能力：仓库级上下文理解（RAG over code）、精确代码编辑（diff 而非重写）、终端命令执行、测试驱动（写测试→实现→通过）、长任务规划。
>
> **用法要点**：① 代码 RAG：embedding 代码片段，检索相关上下文  ② 精确编辑：生成 diff/patch 而非重写整个文件  ③ 执行测试→分析失败→修正循环  ④ 沙箱执行命令，限制危险操作  ⑤ 面试常考：编程 Agent 架构、代码 RAG、diff 编辑、Devin/Cursor

## 8.4 Agent 监控与可观测性

- **执行 Trace**：记录每一步 LLM 调用、工具调用、输入输出
- **Token 消耗监控**：按 Agent/任务/模型统计成本
- **延迟监控**：端到端响应时间、各步骤耗时
- **错误率统计**：工具调用失败率、LLM 调用失败率
- **平台**：LangSmith、Langfuse、Helicone、自建 Prometheus+Grafana


> 🔍 **知识点深度解析**
>
> **作用**：Agent 可观测性通过追踪、日志、指标和告警监控 Agent 运行状态，快速定位问题。
>
> **原理**：Trace 追踪：每次 Agent 运行记录完整执行树（LLM 调用/工具调用/耗时/Token），Langfuse/LangSmith 提供可视化。日志：结构化记录输入输出和错误。指标：成功率/延迟/Token 消耗/工具调用分布。告警：成功率下降、延迟升高、成本超预算时告警。Replay：可重放历史执行轨迹用于调试。
>
> **用法要点**：① Trace：记录每步 LLM/工具调用的输入输出耗时  ② Langfuse 开源自托管，LangSmith 云服务  ③ 关键指标：成功率、P95 延迟、Token/次、工具错误率  ④ Replay 功能重放历史轨迹调试  ⑤ 面试常考：Agent 可观测性、Trace 结构、Langfuse、监控指标

## 8.5 错误恢复与重试

| 策略 | 说明 |
|------|------|
| **指数退避重试** | 工具/LLM 调用失败，等待时间递增后重试 |
| **降级策略** | 工具不可用时切换备用方案或跳过 |
| **死循环检测** | 超过最大步数或重复调用同一工具时强制终止 |
| **超时控制** | 每个工具调用设置超时，防止卡住 |
| **状态回滚** | 失败时回滚到上一个稳定状态 |


> 🔍 **知识点深度解析**
>
> **作用**：Agent 错误恢复机制处理工具调用失败、LLM 输出解析错误和逻辑偏差，保证任务可靠完成。
>
> **原理**：工具调用失败：指数退避重试（网络错误）、换工具/换参数重试（业务错误）、降级到备选方案。解析错误：JSON 解析失败时让 LLM 修正格式或用正则提取。逻辑偏差：设置检查点验证中间结果，偏差时回退到上一步重新规划。最大重试次数限制，超过后优雅失败并报告原因。
>
> **用法要点**：① 瞬时错误（网络超时）：指数退避重试  ② 业务错误（参数错误）：让 LLM 根据错误信息修正后重试  ③ 解析失败：格式修复提示或正则提取  ④ 检查点验证+回退重规划，防止错误累积  ⑤ 面试常考：错误分类、重试策略、回退机制、优雅失败

## 8.6 人机协作（Human-in-the-loop）

- **审批节点**：敏感操作（删除、支付、发布）暂停等待人工确认
- **人工介入**：Agent 遇到无法解决的问题时请求人工帮助
- **反馈学习**：人工修正 Agent 的输出，用于后续优化
- **实现**：LangGraph 的 interrupt 机制、自定义审批队列


> 🔍 **知识点深度解析**
>
> **作用**：Human-in-the-loop 在 Agent 执行中引入人工审批、输入和纠错，平衡自动化与可控性。
>
> **原理**：典型模式：审批模式（Agent 准备方案，人工批准后执行）、协助模式（Agent 遇到不确定时请求人工输入）、纠错模式（人工可中断和修正 Agent 行为）。实现：在图工作流中设置中断点（LangGraph interrupt），暂停执行等待人工输入，超时处理。适用于高风险操作（支付/删除/发送邮件）和 Agent 不确定的决策。
>
> **用法要点**：① 审批模式：Agent 提议→人工确认→执行  ② 协助模式：Agent 主动请求人工提供信息  ③ 纠错模式：人工可中断、修改、重定向 Agent  ④ LangGraph interrupt/checkpoint 实现暂停恢复  ⑤ 面试常考：HITL 模式、中断恢复、审批流、适用场景

## 8.7 Agent 安全沙箱

- **代码执行沙箱**：隔离环境执行 LLM 生成的代码（Docker/E2B）
- **文件系统隔离**：限制 Agent 可访问的目录范围
- **网络限制**：白名单域名，禁止访问内网
- **权限最小化**：API Key 只授予必要权限
- **资源限制**：CPU/内存/执行时间上限


> 🔍 **知识点深度解析**
>
> **作用**：安全沙箱为 Agent 代码执行提供隔离环境，限制资源访问，防止恶意代码损害宿主系统。
>
> **原理**：沙箱技术层级：Docker 容器（namespace+cgroup 隔离，轻量但共享内核）、gVisor（用户态内核，更强隔离）、Firecracker（microVM，强隔离但启动慢）、WASM 沙箱（轻量安全）。限制：网络访问白名单、文件系统只读+临时目录、CPU/内存限制、系统调用过滤（seccomp）、执行超时。
>
> **用法要点**：① Docker 最常用，gVisor/Firecracker 隔离更强  ② 网络白名单：只允许访问必要的 API  ③ 文件系统：只读镜像+临时可写目录  ④ 资源限制：CPU/内存/超时，防止 fork bomb  ⑤ 面试常考：沙箱技术对比、Docker/gVisor/Firecracker、资源限制

## 8.8 成本监控与预算控制

- **Per-Agent 预算**：每个 Agent 设置 Token 消耗上限
- **模型分级**：简单任务用小模型（Haiku/GPT-4o-mini），复杂用大模型
- **缓存优化**：相同查询缓存结果，Embedding 结果缓存
- **Prompt 精简**：去除冗余上下文，压缩历史对话
- **告警**：成本超阈值时告警或自动降级

---


> 🔍 **知识点深度解析**
>
> **作用**：成本监控实时追踪 Token 消耗和 API 费用，设置预算上限和告警，防止 Agent 失控导致高额账单。
>
> **原理**：实现：每次 LLM 调用记录 model/prompt_tokens/completion_tokens/cost，按用户/会话/功能聚合。预算控制：会话级/用户级/全局预算，达到阈值时降级（换小模型）或拒绝。告警：日/月预算 80% 时通知。优化：缓存命中、模型路由、减少无效循环。OpenAI Batch API 等半价选项用于非实时任务。
>
> **用法要点**：① 按用户/会话/功能维度统计 Token 和费用  ② 多级预算：会话级/用户级/全局，阈值触发降级或停止  ③ 80% 预算告警，避免意外超支  ④ 缓存和模型路由是最有效的降本手段  ⑤ 面试常考：成本监控维度、预算控制策略、降本手段、Token 统计
