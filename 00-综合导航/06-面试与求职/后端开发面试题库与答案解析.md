## 一、Java核心

### Q1: HashMap的底层原理？JDK1.7和1.8有什么区别？

**考察点**：数据结构、并发安全、性能优化

**答案**：
- **JDK1.7**：数组+链表，头插法。扩容时链表反转，多线程下可能形成环形链表导致死循环
- **JDK1.8**：数组+链表+红黑树。尾插法，链表长度>8且数组长度>64时转红黑树。扩容时保持链表顺序，无死循环问题
- **put流程**：计算hash → 定位桶 → 空则直接放 → 链表遍历/红黑树查找 → 相同key覆盖 → 否则尾插 → 检查是否转红黑树 → 检查是否扩容
- **扩容**：容量翻倍，元素重新hash定位。1.8优化：元素要么在原位置，要么在原位置+旧容量

### Q2: ConcurrentHashMap的实现原理？

**考察点**：并发安全、锁粒度、性能

**答案**：
- **JDK1.7**：Segment分段锁，每个Segment是一个小HashMap，默认16段，并发度16
- **JDK1.8**：取消Segment，使用CAS+synchronized。数组空时CAS插入，有元素时锁住桶头节点。锁粒度更细，并发度更高
- **size计算**：CounterCell数组，无锁计数，最后累加
- **红黑树**：和HashMap一样，链表>8转红黑树

### Q3: 线程池的核心参数和工作流程？

**考察点**：并发编程、资源管理

**答案**：
- **核心参数**：corePoolSize核心线程数、maximumPoolSize最大线程数、keepAliveTime空闲时间、workQueue工作队列、threadFactory线程工厂、handler拒绝策略
- **工作流程**：
  1. 线程数<corePoolSize → 创建核心线程
  2. 线程数≥corePoolSize → 任务入队列
  3. 队列满 → 创建非核心线程（直到maximumPoolSize）
  4. 线程数=maximumPoolSize且队列满 → 执行拒绝策略
- **拒绝策略**：AbortPolicy抛异常（默认）、CallerRunsPolicy调用者执行、DiscardPolicy丢弃、DiscardOldestPolicy丢弃最旧

### Q4: volatile的作用和原理？

**考察点**：JMM、内存可见性、指令重排

**答案**：
- **两个作用**：保证可见性、禁止指令重排序
- **可见性原理**：写volatile变量时强制刷新到主内存，读时强制从主内存读取
- **禁止重排原理**：内存屏障（StoreStore/StoreLoad/LoadStore/LoadLoad）
- **不保证原子性**：volatile不能保证i++的原子性，需要synchronized或AtomicInteger
- **典型应用**：双重检查锁单例的instance变量、状态标记位

### Q5: synchronized和ReentrantLock的区别？

**考察点**：锁机制、并发编程

| 维度 | synchronized | ReentrantLock |
|------|-------------|---------------|
| 实现 | JVM层面，monitorenter/monitorexit | JDK层面，AQS |
| 释放 | 自动释放 | 必须手动unlock（finally中） |
| 公平锁 | 非公平 | 支持公平/非公平 |
| 可中断 | 不可中断 | lockInterruptibly可中断 |
| 超时 | 不支持 | tryLock超时 |
| 条件变量 | 单一条件 | 多个Condition |
| 性能 | 优化后性能好 | 功能更丰富 |

## 二、JVM

### Q6: JVM内存模型？

**考察点**：内存结构、GC

**答案**：
- **线程私有**：程序计数器、虚拟机栈、本地方法栈
- **线程共享**：堆、方法区（元空间）
- **堆**：对象存储，GC主要区域。分为新生代（Eden+S0+S1）和老年代
- **虚拟机栈**：栈帧（局部变量表、操作数栈、动态链接、返回地址）
- **方法区**：类信息、常量、静态变量。JDK8后改为元空间（本地内存）

### Q7: 垃圾回收算法和收集器？

**考察点**：GC原理、JVM调优

**答案**：
- **算法**：标记-清除（碎片）、标记-复制（新生代）、标记-整理（老年代）、分代收集
- **收集器**：
  - Serial：单线程，Client模式
  - ParNew：Serial多线程版，配合CMS
  - Parallel Scavenge：吞吐量优先
  - CMS：低延迟，标记-清除，有碎片问题
  - G1：区域化分代，可预测停顿，JDK9默认
  - ZGC：超低延迟（<10ms），JDK15正式

### Q8: 什么是Stop The World？

**考察点**：GC影响、性能优化

**答案**：
- GC时所有用户线程暂停，等待GC完成
- 所有收集器都有STW，只是时间长短不同
- 新生代GC（Minor GC）STW短，老年代GC（Full GC）STW长
- 优化方向：减少Full GC频率、缩短STW时间（G1/ZGC）

## 三、Spring

### Q9: Spring Bean的生命周期？

**考察点**：Spring原理、扩展点

**答案**：
1. 实例化（反射创建对象）
2. 属性填充（依赖注入）
3. Aware接口回调（BeanNameAware、ApplicationContextAware等）
4. BeanPostProcessor前置处理（postProcessBeforeInitialization）
5. 初始化（@PostConstruct、InitializingBean、init-method）
6. BeanPostProcessor后置处理（postProcessAfterInitialization）→ AOP代理在此创建
7. 使用
8. 销毁（@PreDestroy、DisposableBean、destroy-method）

### Q10: SpringBoot自动装配原理？

**考察点**：SpringBoot原理、SPI

**答案**：
- `@SpringBootApplication`包含`@EnableAutoConfiguration`
- `@EnableAutoConfiguration`导入`AutoConfigurationImportSelector`
- 该类读取`META-INF/spring.factories`（JDK9后用`AutoConfiguration.imports`）中的自动配置类
- 每个自动配置类通过`@Conditional`系列注解判断是否生效
- 满足条件的配置类注册Bean到容器

### Q11: Spring事务传播行为？

**考察点**：事务管理、分布式事务

| 传播行为 | 说明 |
|---------|------|
| REQUIRED | 有事务则加入，没有则新建（默认） |
| REQUIRES_NEW | 总是新建事务，挂起当前事务 |
| SUPPORTS | 有事务则加入，没有则非事务执行 |
| NOT_SUPPORTED | 非事务执行，挂起当前事务 |
| MANDATORY | 必须在事务中，否则抛异常 |
| NEVER | 必须非事务，有事务则抛异常 |
| NESTED | 嵌套事务（保存点） |

## 四、数据库

### Q12: MySQL索引原理？为什么用B+树？

**考察点**：数据结构、性能优化

**答案**：
- **B+树特点**：非叶子节点只存key，叶子节点存data，叶子节点链表连接
- **为什么不用B树**：B树每个节点都存data，单页能存的key少，树更高，IO更多
- **为什么不用红黑树**：红黑树是二叉，树高更高，磁盘IO更多
- **聚簇索引**：叶子节点存整行数据（主键索引）
- **非聚簇索引**：叶子节点存主键值，需要回表
- **覆盖索引**：查询列都在索引中，无需回表

### Q13: 事务隔离级别？

**考察点**：并发控制、MVCC

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不可能 | 可能 | 可能 |
| REPEATABLE READ（默认） | 不可能 | 不可能 | 可能（InnoDB通过MVCC+间隙锁解决） |
| SERIALIZABLE | 不可能 | 不可能 | 不可能 |

**MVCC原理**：每行数据有隐藏列（事务ID、回滚指针），通过undo log版本链+ReadView实现一致性读。

### Q14: 如何优化慢SQL？

**考察点**：性能优化、实战经验

**答案**：
1. EXPLAIN分析执行计划（type、key、rows、Extra）
2. 添加合适索引（避免索引失效：函数、隐式转换、like前缀%、OR）
3. 避免SELECT *，只查需要的列
4. 深分页优化（游标分页/延迟关联）
5. 小表驱动大表（join顺序）
6. 适当反范式设计（冗余字段减少join）
7. 读写分离、分库分表

## 五、分布式

### Q15: 分布式事务方案？

**考察点**：分布式系统、一致性

| 方案 | 一致性 | 性能 | 适用 |
|------|--------|------|------|
| 2PC/XA | 强一致 | 低 | 资金类 |
| TCC | 最终一致 | 中 | 核心业务 |
| SAGA | 最终一致 | 高 | 长事务 |
| 本地消息表 | 最终一致 | 高 | 异步场景 |
| 事务消息 | 最终一致 | 高 | RocketMQ |

### Q16: 分布式锁的实现方式？

**考察点**：分布式协调、并发控制

| 实现 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Redis | SETNX+过期+Lua | 性能高 | 锁不可重入、主从切换可能丢锁 |
| Redisson | Redis+看门狗续期 | 功能完善 | 依赖Redis |
| ZooKeeper | 临时顺序节点 | 强一致、可重入 | 性能较低 |
| 数据库 | 唯一索引/行锁 | 简单 | 性能差、单点 |

### Q17: 什么是CAP理论？

**考察点**：分布式基础

**答案**：
- C（一致性）：所有节点数据一致
- A（可用性）：每个请求都能得到响应
- P（分区容错性）：网络分区时系统仍能工作
- 分布式系统必须保证P，只能在C和A之间权衡
- CP：ZooKeeper、etcd（强一致）
- AP：Eureka、Cassandra（高可用）

## 六、微服务

### Q18: 微服务网关的作用？

**考察点**：微服务架构

**答案**：
- 路由转发：统一入口，路由到后端服务
- 认证鉴权：统一登录验证、权限校验
- 限流熔断：保护后端服务
- 日志监控：统一访问日志、链路追踪
- 协议转换：HTTP→gRPC等
- 缓存：缓存热点数据

### Q19: 服务雪崩？如何解决？

**考察点**：服务治理、高可用

**答案**：
- **雪崩**：一个服务故障导致级联故障，整个系统不可用
- **解决方案**：
  1. 熔断：错误率达阈值时快速失败（Hystrix/Sentinel）
  2. 降级：返回兜底数据
  3. 限流：限制QPS保护服务
  4. 超时设置：避免线程长时间阻塞
  5. 舱壁模式：线程池隔离
  6. 集群部署：避免单点

## 七、算法与设计

### Q20: 设计一个短链接系统？

**考察点**：系统设计、架构能力

**答案要点**：
- **发号器**：雪花算法/号段模式生成唯一ID
- **转码**：ID转62进制（0-9a-zA-Z）
- **存储**：短码→长URL映射，Redis缓存
- **跳转**：302重定向（可缓存）
- **统计**：访问计数、PV/UV
- **自定义短码**：用户自定义短码，冲突检测
